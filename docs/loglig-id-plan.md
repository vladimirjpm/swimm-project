# Loglig ID — план привязки пловцов к loglig.com

Статус: **план, не начато** (2026-07-19). Цель — хранить у `Swimmer` его ID на платформе
loglig (карточка вида `https://loglig.com:2053/Players/Details/{id}?seasonId={sid}`),
чтобы получить надёжный внешний идентификатор (лечит дедуп по имени) и источник
обогащения (год рождения, клуб, результаты/PB по сезонам).

## Разведка (проверено вживую 2026-07-19)

- **Карточка игрока** отдаётся программно: сайт делает redirect сам на себя и ставит
  куку `DetailsPageVisited` — с CookieContainer обычный GET возвращает полный HTML.
  Внутри: `<h1>` имя (иврит), год рождения, пол, клуб, селектор сезонов, таблица
  результатов (дистанция/стиль, длина бассейна 25/50, время, дата, название
  соревнования — совпадают с нашими импортами из isr.org.il).
- **Публичного поиска по имени на loglig нет**: `/Players/Search` есть, но его
  AJAX-эндпоинт `POST /Players/LoadData` стабильно 500 (пробованы все варианты
  DataTables-параметров, в т.ч. из браузера на самой странице). Перепроверить позже —
  если починят, батч-поиск станет тривиальным (JSON с UserId/FullName/ClubName/
  Gender/BirthdayString).
- **Страницы соревнований** (isr.org.il `comp.asp?compID=…` → loglig
  `/LeagueTable/AthleticsDisciplines/{logligCompId}` → результаты/стартлисты/участники)
  содержат имя+год рождения+клуб+время, но **без ссылок на игроков** — playerId там нет.
- **Перебор ID не работает**: ID разреженные (глобальный UserId платформы),
  соседние отдают 500.
- **Google индексирует карточки** — проверено: `site:loglig.com ברנצב סבינה` возвращает
  карточку Сабины первым результатом (в сниппете даже год рождения/клуб). Значит
  Google Programmable Search Engine (CSE) — рабочий генератор кандидатов.

## Схема

`Swimmer`:
- `LogligId int?` — уникален по всем Swimmer (один loglig-профиль = один пловец)
- `LogligIdStatus` — `Suggested` / `Verified` / `Rejected`
- `LogligIdSource string?` — `admin` / `user-claim` / `auto`
- `LogligIdSuggestedByUserId` / `LogligIdSuggestedAt` — аудит + rate-limit
- `LogligIdVerifiedAt timestamptz?`

Привязка — чисто обогащение данных, прав никаких не даёт (правило: внешние привязки
недоверенные, как primary favorite).

## Пайплайн привязки

1. **Кандидаты — Google CSE** (Custom Search JSON API, движок ограничен `loglig.com`):
   запрос `site:loglig.com "<имя на иврите>"`, оба порядка имя/фамилия; фолбэк — только
   фамилия. Берём топ-5 URL с паттерном `Players/Details/{id}`, не «первый результат».
2. **Верификация по данным, не по имени**: тянем карточку каждого кандидата
   (`LogligClient`), сверяем год рождения + клуб + пересечение результатов
   (дата + дистанция/стиль + время) с нашими `Results`. ≥2–3 совпавших заплывов —
   привязка автоматическая; неоднозначно — кандидаты админу на выбор.
3. **Режимы**:
   - MVP «на кнопке»: в админке на карточке пловца кнопка «Find loglig ID»
     (CSE → верификация → сохранить/показать кандидатов) + поле ручной вставки ссылки.
   - Батч: ночной джоб в пределах квоты CSE (100 запросов/день бесплатно, дальше
     $5/1000, максимум 10k/день; на ~2000 пловцов — разово ~$10 или ~3 недели бесплатно).
   - Краудсорс (вариант Влада, асинхронный): если у пловца нет `Verified`-привязки,
     любой залогиненный может **предложить** LogligId (вставить ссылку) → пишется как
     `Suggested` без синхронной проверки. Ночной джоб берёт всех `Suggested`, тянет
     карточку и сверяет **имя + год рождения** (клуб — бонус-сигнал; полная сверка по
     временам — для спорных): совпало → `Verified` (locked: пользователи и джоб больше
     не меняют, снять может только админ), не совпало → `Rejected` (не перепроверять и
     не давать повторно спамить тем же ID; виден админу).
### Безопасность (обязательное)

- **Анти-SSRF:** присланный пользователем URL никогда не фетчим как есть. Из ссылки
  извлекаем только числовой `{id}` (regex по паттерну `Players/Details/(\d+)`), URL
  карточки собираем сами из константного хоста `https://loglig.com:2053`. Джоб и
  LogligClient принимают на вход `int logligId`, не строку-URL.
- Rate-limit на эндпоинт предложения (как у auth) + не принимать ID, уже висящий
  `Rejected` у этого же пловца.
- Парсер карточки — только чтение значений из HTML (имя/год/клуб/строки), никакого
  выполнения/встраивания сырого HTML куда-либо.

4. **Обогащение** (позже): по известному LogligId периодически подтягивать год
   рождения, клуб, свежие результаты/PB.

## Реализация (порядок)

1. Миграция: `LogligId` (unique) + `LogligIdStatus` + `Source` + `SuggestedByUserId/At`
   + `VerifiedAt` (`--context SwimmDbContext`; swimm_ro — Swimmer уже публичная).
2. `LogligClient` (Infrastructure): HttpClient + CookieContainer (handshake с
   `DetailsPageVisited`), парсер карточки → DTO (имя, год, пол, клуб, строки
   результатов). Юнит-тесты на сохранённом HTML карточки 304199.
3. `LogligMatchService`: сверка DTO ↔ наши Results (нормализация времени `MM:SS.ff`,
   дистанция+стиль из ивритских названий: חופשי/גב/חזה/פרפר/מעורב), пороги авто-привязки.
   Юнит-тесты (расчёты/edge — обязательно).
4. CSE-клиент (ключ `apiKey`+`cx` в user-secrets/appsettings, graceful при отсутствии).
5. Admin UI: кнопка + ручная ссылка + экран кандидатов; снятие/смена `Verified` — только здесь.
6. User-claim флоу (предложение `Suggested`) + ночной джоб верификации
   (имя+год рождения → `Verified`/`Rejected`).
7. (позже) CSE-батч по всем непривязанным.

## Что нужно от Влада перед стартом CSE-части

- Ключ Custom Search API в Google Cloud Console + движок на
  programmablesearchengine.google.com с сайтом `loglig.com` → `apiKey`, `cx`.
- Шаги 1–3 (миграция, клиент, матчер) можно делать без ключа.
