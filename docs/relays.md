# Эстафеты (relays) — как устроено и где искать баги

> **При ЛЮБОМ баге, связанном с эстафетами — читай этот файл первым.**
> Симптомы, которые сюда: эстафета видна одному пловцу, но не другим её ногам;
> медиа/реакции на эстафете не показываются участнику; переимпорт соревнования с
> эстафетами падает или плодит дубли; склейка пловцов теряет ноги; очки клуба за
> эстафету не начисляются; парсер не собрал состав эстафеты. Почти каждый такой баг —
> следствие одного правила ниже, которое где-то нарушено.

---

## Золотое правило

**Строка результата эстафеты принадлежит ОДНОМУ пловцу (владельцу строки, обычно первая
нога), но сама эстафета принадлежит ВСЕЙ команде через `RelayMembers`.**

Любой запрос вида «в каких эстафетах участвовал пловец X» обязан идти через
`RelayMembers`, а НЕ через `Result.SwimmerId`. Если код фильтрует эстафеты по
`Result.SwimmerId` — он покажет эстафету только владельцу строки, и это баг.

---

## Модель данных

| Сущность | Что это |
|---|---|
| `ResultRecord.RelayId` (nullable) | Строка результата эстафеты. `RelayId != null` ⇒ это эстафета. Одна эстафета = ОДНА строка результата, у неё один `SwimmerId` — владелец строки (нога-якорь). |
| `Relay` | Команда эстафеты: `TeamName`, `SwimmersName` (состав **текстом**, историческое поле), навигация `Members`. |
| `RelayMember` | Структурная нога: `RelayId`, `SwimmerId`, `LegOrder`, `SplitTime`. Именно это — источник истины о составе. Публичная reference-таблица (грант `swimm_ro`). |

Таблица `RelayMembers` в БД (не `Sys_*` — она публичная). Колонки: `Id, RelayId,
SwimmerId, LegOrder, SplitTime`.

### Почему так (историческая справка)

Изначально (до `cf5d7ec`) эстафетный результат был привязан к одному пловцу — первой
ноге, — а состав жил только текстом в `Relay.SwimmersName`. Из-за этого эстафета
показывалась лишь «владельцу» строки. Классический симптом: **у пловца видна
freestyle-эстафета (где он первая нога), но не medley-эстафета (где он третья нога).**
Коммит `cf5d7ec` ввёл структурную сущность `RelayMember` — «эстафета видна всем ногам».

---

## Как это должно работать в запросах

- **«Заплывы пловца» (My swims, `MySwimsRepository.GetMySwimsAsync`)** — включает эстафеты
  по членству: `r.RelayId != null && RelayMembers.Any(m => m.RelayId == r.RelayId &&
  swimmerIds.Contains(m.SwimmerId))`, а не только по `r.SwimmerId`. Плюс отдаёт
  `member_swimmer_ids` для клиентских чип-фильтров/счётчиков. Сезоны тоже считаются по
  членству.
- **Клиент** (`results-table`, `my-media-project`) — матчит пловца к эстафете по
  `member_swimmer_ids`, не по владельцу строки. Поля строки: `is_relay`,
  `relay_swimmers` / `relay_swimmers_name`, `relay_team_name`.
  **Канон:** матчинг «заплыв ↔ пловец по id» делается ТОЛЬКО через
  `HelperSwimmer.resultBelongsToSwimmer` / `resultBelongsToAny`
  (`client/src/utils/helpers/helper-swimmer.ts`) — новый фильтр/счётчик не должен
  сравнивать `swimmer_id` сам. `/api/results` отдаёт `member_swimmer_ids` на каждой
  эстафетной строке (проекция `Relay.Members` в `ResultMapping`); контракт закреплён
  тестом `GetPaged_RelayRow_CarriesMemberSwimmerIds` (`Swimm.Tests`).
- **Медиа на эстафете** — привязано к строке (одна нога), т.е. к `SwimmerId` владельца.
  Но принадлежит всей команде: `UserMediaRepository.GetForUserAsync(userId, swimmerId)`
  при заданном `swimmerId` включает и медиа на relay-результатах, где `swimmerId` —
  участник по `RelayMembers` (owner-фильтр `UserId` сохраняется). См. раздел «Баг: медиа
  эстафеты…» ниже.

## Импорт и парсинг эстафет

Тонкие места, каждое закрыто отдельным коммитом (см. журнал):

- **Составы из PDF.** Ноги эстафеты лежат в PDF таблицей под строкой команды. PdfPig
  рвёт имена посередине слова — восстановление по X-координатам колонок
  (`ReconstructEnRelaySwimmerNames`, RTL-раскладка для HE). Собралось меньше 4 ног —
  возвращаем `null`, без догадок. (`7e9366b`, `7e0babf`, `c85a1af`, `7e9366b`)
- **Заполнение `RelayMembers` при импорте.** Импорт матчит ноги тем же матчингом, что и
  обычных пловцов, но **скоупом ростера соревнования** (при неоднозначности — по клубу
  эстафеты); линкует только при однозначном совпадении; владелец строки — якорь.
  Upsert/удаление соревнований синхронизируют/чистят членов. (`cf5d7ec`)
- **Коллизия ключа матчинга.** Ноги приходят отдельными строками с `RelayId=NULL`,
  делящими заплыв/дорожку (до 5 строк на ключ). Внутри групп-коллизий сначала пары по
  `SwimmerId`, затем остаток по порядку. `SwimmerId` в сам ключ НЕ добавлен намеренно —
  иначе ломается переход «аноним → именованный пловец» (кейс Маккабиады). Симптом при
  поломке: переимпорт вставляет строки заново вместо обновления. (`e5133c6`)
- **Бэкфилл старых данных.** `dotnet run -- --backfill-relay-members [--apply]` (dry-run по
  умолчанию, идемпотентно) — заполняет `RelayMembers` из текста `Relay.SwimmersName` по
  ростеру соревнования, без переимпорта. Fail-safe: сомнительную ногу пропускаем (никаких
  ложных связей, не создаём/не мёржим пловцов). (`f362f6b`)

## Известные баги и их фиксы

### Маккаби: эстафеты «без категории» — три фикса одной сверки (2026-08-15)

**Симптом:** клубный зачёт Маккаби-2026 «цеирим» (comp 1565) не сходился с официальной
таблицей: обе эстафетные дисциплины (152 команды) вовсе не импортировались, а после
импорта — очки эстафет получал только топ-20 сквозного списка.

1. **Заголовок эстафеты без категории не парсился.** «4X50 חופשי שליחים» (ни пола, ни
   возраста) выставлял только `pendingRelay*` — masters-механика ждала строку «מאסטרס …»,
   которой у Маккаби нет, и команды молча выпадали. **Фикс:** первая же командная строка
   материализует событие (`RelayHeaderNoCategoryRxHE`); в `RelayTeamLineRxHE` добавлены
   статусы DNF/DNS. Регрессия — `IsrOrgCompetitionParserMaccabiRelayTests` на реальной
   фикстуре `Fixtures/Parsing/isr-maccabi-spring-2026-youth-he.pdf`.
2. **Места сквозные, а зачёт организатора — по полосам.** PDF печатает эстафеты одним
   списком по времени (1..79) без пола/возраста. `RelayBandReconstructor` (вызывается из
   `MapHebrewOnly`) разбивает такие дисциплины на полосы «возрастная группа × пол»:
   возраст — по СТАРШЕЙ ноге, пол — из индивидуальных заплывов того же файла (точный матч
   имя+год главнее фолбэка по однозначному имени), места пересчитываются внутри полосы,
   DQ/NS/DNF остаются без места. Всё детерминировано от файла — `Gender` входит в ключ
   upsert, и зависимость от БД плодила бы дубли на переимпорте (И-4). «Всё или ничего»:
   не классифицировалась хоть одна команда — дисциплина остаётся сквозной, как напечатана.
   Решения Р35–Р37 в [data-integrity.md](data-integrity.md).
3. **Полосы склеивались в ложные prelim/final.** `AssignHeatTypes` (проход по составу, Р31)
   считал «участником» эстафеты `клуб+имя команды`, а имя команды у Маккаби равно клубу —
   полосы одной дисциплины из одних и тех же клубов опознавались как prelim/final пары, и
   33 команды теряли очки (prelim — не награда, Р34). **Фикс:** участники эстафеты — ЛЮДИ
   её ног; «клуб+команда» — только фолбэк, когда состав не разобран.

Итог первой итерации: порядок всех 25 клубов совпал, очки ~97.6%. Остаток добит на второй
итерации (2026-08-15, по вопросу Влада «почему у калансуа 15, а не 16»):

4. **Шкала Маккаби — не федеральная.** Live-зачёт loglig (`loglig.com:2053/LeagueTable/
   AthleticsDisciplines/14668`, ссылка нашлась на comp.asp федерации) показывает колонку
   «ניקוד קבוצתי»: 25/22/20/18/**17/16/15/14/13/12/10**/9/…/1 — места 5–10 на +1 выше
   правила 4, 11-е место 10. Заведено правило клубов 5 `maccabi.25pt.20pl.2026` (ManualOnly),
   привязано к 1565.
5. **Полосы эстафет — из регламента** (loglig doc 3185): девочки 9-11 и 12-13, мальчики
   9-10/11-12/13-14. `MaccabiRelayBand` в реконструкторе; возраст вне сетки → дисциплина
   остаётся сквозной (страховка для «ноар-богрим» и чужих форматов).

**Финал: зачёт 1565 = официальная таблица Маккаби, 25/25 клубов, sum|delta| = 0.**
Решения Р35–Р39 в [data-integrity.md](data-integrity.md). Предел PDF-подхода: категория
эстафеты ЗАЯВЛЯЕТСЯ клубом (в live есть команды младших составов, заявленные в старшие
категории) — восстановление «по старшей ноге» может точечно разойтись; на суммах 1565
не сказалось.

### Маккаби «נוער ובוגרים»: вторая сетка полос эстафет (2026-08-18)

**Симптом:** зачёт comp 1576 (OrgCompId 16818, loglig 14669) расходился с официальным
דירוג מועדונים на −1764 очка (16 071 против 17 835). Индивидуальные очки совпадали
1:1 (15 163), весь недобор — эстафеты: 908 против 2672.

**Причина:** `MaccabiRelayBand` знал только сетку «צеирим» (Р39) и на возрастах 15+
отдавал null → страховка «всё или ничего» оставляла обе дисциплины сквозными (40 команд,
места по времени вперемешку по полам). Очки получал только топ-20 сквозного списка —
практически одни взрослые парни, все девочки и младшие в нуле.

**Фикс:** сеток стало ДВЕ, выбор — на весь файл с приоритетом младшей (`PickGrid`): Youth,
если по ней раскладываются все команды всех дисциплин файла, иначе Senior. Сетка Senior
(сверено с событиями live-зачёта 14669): девочки `14-15` и `16-99`, мальчики `15-16` и
`17-99` — две старшие полосы ОТКРЫТЫ сверху. У открытых полос в названии события взрослые
`נשים`/`גברים` вместо `בנות`/`בנים`. Решение Р40, регрессия —
`IsrOrgCompetitionParserMaccabiSeniorRelayTests` на фикстуре
`Fixtures/Parsing/isr-maccabi-spring-2026-senior-he.pdf`.

**Ограничитель:** реконструкция теперь применяется только к протоколам с маркером
«אליפות מכבי» в названии. Сетки полос — из регламента Маккаби, а эстафеты «без категории»
бывают и у ARENA (бугрим 1562, צעירים 1512, מוקדמות 1526), где организатор полос НЕ делает:
до второй сетки их спасал возрастной потолок Youth-сетки, теперь спасает маркер.

**NB:** у полос `16-99`/`17-99` `EventStyleAge` сознательно остаётся ЧИСЛОМ — так работает
`RelayEventAge` (полоса из заголовка побеждает только при верхней границе ≤ 18, иначе
masters-логика прочитала бы «17-99» как NaN). Полоса при этом видна в названии события и в
`EventStyleGender`; на клубные очки, которые считаются от `Position`, это не влияет.

**Итог: порядок всех 22 клубов = официальному, 18 клубов в ноль, сумма 17 801 из 17 835
(99.81%).** Остаток 34 невоспроизводим: в полосе «вольная, בנים 15-16» движок loglig выдал
ДВА первых места по 50 очков (строка נהריה 01:49.45 напечатана в протоколе первой, хотя
медленнее семи других) и сдвинул остальных на ступень вверх — пересчёт по времени так не
делает. Тот же класс артефактов, что у эстафеты 68822 лета-2025. Помечать через
`pointrule.verify` «расходится».

### FK `RelayMember → Swimmer` (Restrict) роняет переимпорт (`93317d8`)

Пловец, оставшийся только ногой эстафеты (без индивидуальных результатов), считался
сиротой и удалялся при чистке, но FK `RelayMember→Swimmer` (Restrict) блокировал DELETE →
откат всего импорта. **Фикс:** фильтр чистки сирот (upsert и `DeleteCompetitionCore`)
исключает пловцов-ног (`RelayMembers.Any(...)`). Урок: пловец-нога — не сирота.

**Рецидив 2026-08-02:** тот же предикат, но вторая его копия — `SwimmerDedupService.OrphanQuery()`
за кнопкой «Удалить всех сирот» в `/Admin/Swimmers` — проверку так и не получила: в списке
сирот висели 102 живых эстафетчика из 109. Спас FK Restrict (удаление одной транзакцией
отбилось бы целиком). Починено; см. [admin-pages/swimmers.md](admin-pages/swimmers.md).

### Склейка пловцов теряла ноги эстафет (`98cc9c1`)

При merge дубля в канонического пловца ноги эстафет (`RelayMember`) не переносились.
**Фикс:** `SwimmerMergeService` переносит `RelayMembers` на канонического.

### Очки клуба за эстафеты (`ff27734`)

Эстафетные результаты не давали очки клубу. **Фикс:** начисление учитывает relay-строки.

### Возраст эстафеты брался от первой ноги → ложные «NEW RECORD» (2026-07-31)

**Симптом (кейс Влада):** в заплыве «4X50 מעורב שליחים - בנות 11-12» (event 13) бейдж
«NEW RECORD» висел на 4-м, 5-м, 10-м и 11-м местах, а победитель заплыва был без бейджа.

**Причина.** `IsrOrgParser.CreateRelayResult` брал `RelaySwimmers.First()` — просто того, кого
протокол напечатал первым, — и писал его возраст в `EventStyleAge`. Строки ОДНОГО заплыва
получали то `11`, то `12`, в зависимости от порядка ног. Клиентский `isRecordTime` сравнивал
«11» с рекордом возраста 11 (02:15.73) вместо возраста 12 (01:58.55) — разрыв 17 секунд,
отсюда поток ложных рекордов. Тот же разнобой дробил один заплыв на два ключа объединённого
зачёта (`CombinedPlaceCalculator.EventKeyOf` включает `EventStyleAge`); соревнований, где
включён Combine All Results и есть эстафеты, — 7.

**Фикс.** Для эстафет `EventStyleAge` = **возрастная полоса из заголовка** («11-12»), которую
парсер и так знал (`IsrOrgCompetitionResult.EventStyleAge`), — хелпер `RelayEventAge`.
Только детские полосы (верхняя граница ≤ 18): у masters возраст обязан остаться числом, иначе
`isResultMasters` прочитает «25-29» как NaN.

Существующие данные починены на месте, без переимпорта: `UPDATE "Results" SET "EventStyleAge"
= "AgeGroup"` для relay-строк с детской полосой — 1708 строк, бэкап в
`tmp_relay_age_backup_20260731`.

**Побочный эффект, который сейчас является желаемым:** ключа «11-12» нет в дереве возрастных
рекордов, поэтому бейдж рекорда на эстафетах больше не показывается вовсе. Это сознательно:
эстафетные возрастные рекорды хранятся полосами **10-11 / 12-13 / 14-15 / 16-17** (одна и та же
запись продублирована на оба возраста), а соревнование делит детей на **11-12 / 13-14** —
полосы не совпадают, и «правильного» возрастного рекорда для заплыва 11-12 не существует.
Пока это не решено, лучше не показывать ничего, чем показывать неверное. Серверный
`CompetitionRecordsDetector` эстафеты и так исключает («вне скоупа v1») — теперь клиент с ним
согласован.

### Баг: медиа эстафеты не видно ноге-не-владельцу (карточка спортсмена)

**Симптом (кейс Влада, 2026-07-24):** у Сабины на карточке видно видео 4×50 freestyle
(где она первая нога = владелец строки), но НЕ видно видео 4×50 medley (где она третья
нога, владелец строки — другой пловец), хотя на самой строке результатов камера горит у
обеих.

**Причина.** Карточка тянет медиа через `useUserMedia(swimmerId)` →
`GET /api/me/media?swimmerId=X`, а `GetForUserAsync` фильтровал строго
`m.SwimmerId == X`. Медиа эстафеты привязано к владельцу строки (у medley это не Сабина),
поэтому в список Сабины не попадало. На строках результатов (`/api/media/results`) и на
My media (`GetMySwimsAsync`, раскладка по `result_id`) баг не проявлялся — там медиа
цепляется по `ResultId`, независимо от пловца.

**Фикс.** `UserMediaRepository.GetForUserAsync` при заданном `swimmerId` расширен: включает
медиа на relay-результатах, где `swimmerId` — участник по `RelayMembers` (owner-фильтр
`UserId` сохранён — чужое медиа не подтягивается). Тест
`UserMediaRepositoryTests.GetForUser_RelayMedia_SurfacesForCoMemberSwimmer`.

## Чек-лист при отладке бага эстафет

1. Пловец вообще есть в `RelayMembers` этой эстафеты? (`SELECT * FROM "RelayMembers" WHERE
   "RelayId" = N`.) Если нет — проблема в импорте/бэкфилле состава, а не в отображении.
2. Запрос, который «теряет» эстафету, идёт через `RelayMembers` или через
   `Result.SwimmerId`? Второе — почти всегда баг.
3. Клиент матчит по `member_swimmer_ids` или по владельцу строки?
4. Медиа/реакции: цепляются по `ResultId` (правильно для показа всем) или по `SwimmerId`
   владельца (сузит до одной ноги)?
5. Переимпорт падает/дублит? → раздел «Импорт», особенно FK-сирота (`93317d8`) и коллизия
   ключа (`e5133c6`).
