## Поток A. Дедуп пловцов — подготовка (делает Fable, применение только после «да» Влада)

Фон: PDF-импорт матчит пловцов по `(LastName, FirstName, BirthYear)` — варианты написания
(`גוסטמלסקי` / `גוסטומלסקי`) плодят дубли. `Swimmer.SwimmerOrgId` есть, но реальным
импортом не заполняется (реальные ID появятся в потоке B). Плюс сироты: удаление
соревнования не чистит Swimmer без результатов.

- A1. **Матчинг-отчёт**: `server/db/dedup-report.sql` (или `dotnet run -- --dedup-report`) —
  кандидаты на склейку по нормализованному имени (trim/регистр/`ё`→`е`-аналоги для иврита —
  напр. совпадение при удалении одной буквы, расстояние Левенштейна ≤1) + одинаковый
  BirthYear + пересечение/близость клубов. Разделить на «уверенные» и «спорные».
  Отдельно — список сирот (0 Results, 0 memberships, 0 favorites). Синтетику
  (`SwimmerOrgId LIKE 'SYNTH-%'`) исключить. Результат — `docs/tasks/dedup-report.md`
  с таблицами: id-пары, имена, годы, клубы, число результатов у каждого.
- A2. **Merge-скрипт с dry-run**: перевесить на канонического пловца Results, Relays,
  Sys_UserFavorites, Sys_HubGroupMembers, Sys_UserMedia, AppUser.SwimmerId (проверить
  полный список FK по схеме!), затем удалить дубль. Вход — таблица пар (canonical_id,
  duplicate_id). Dry-run печатает, что будет сделано, без изменений. Конфликты
  (у обоих один и тот же заплыв) — репортить, не мержить автоматически.
- A3. **Тесты**: юнит на merge-логику (если она в C#-сервисе — предпочтительно, годится
  и для админ-UI 7.2 позже) — перенос всех связей, конфликт → отказ, сирота-чистка.
- A4. **Чистка сирот при удалении соревнования**: в `DeleteCompetitionAsync`
  (JsonImportService) добавить удаление Swimmer, оставшихся без Results/memberships.
- **СТОП-ЛИНИЯ: скрипт к реальной БД НЕ применять.** Отчёт + инструменты + тесты,
  спорные пары — Владу на глаза.

## Поток B. Автозабор isr.org.il (делает Fable, целиком) — роадмап фаза 6

По ROADMAP 6.1–6.4 (см. docs/ROADMAP.md — там детали):
- B1. `ICompetitionDiscoveryProvider` + `IsrOrgDiscoveryProvider`: HTML-список
  соревнований с https://isr.org.il/competitions.asp (даты, названия, PDF-ссылки).
  Typed HttpClient, вежливые интервалы, иврит-кодировки. Живую вёрстку изучить
  браузером/WebFetch ДО кода; снапшот HTML сохранить в тест-фикстуры.
- B2. Админ-«входящие»: страница обнаруженных соревнований (новое/импортировано —
  матчинг по дате+названию), «затянуть» → скачать PDF → существующий пайплайн
  parse→preview→import.
- B3. BackgroundService по расписанию (интервал и вкл/выкл через Settings).
- B4. Устойчивость: снапшоты HTML/PDF на диск, при смене вёрстки — явная ошибка
  в админке, не тихий ноль (урок HeaderRxENinHE).
- B5. **Заполнение SwimmerOrgId**: если протоколы/сайт дают ID пловца — заполнять при
  импорте и матчить сперва по нему, потом по имени (это системное решение дедупа).
  Если ID в PDF нет — зафиксировать этот факт в отчёте A1 и оставить матчинг по имени.
- Приёмка: новое соревнование появляется во «входящих» без человека; импорт в 2 клика.

## Footguns

- Build-lock :5078 (см. CLAUDE.md; осиротевшие dotnet-процессы — netstat → kill).
- Два DbContext: EF-команды с `--context SwimmDbContext`.
- В локальной БД 3М синтетики (`Note='SYNTH'`) — НЕ удалять (Влад велел оставить);
  дедуп-запросы обязаны её исключать, иначе отчёт утонет.
- isr.org.il — чужой прод: интервалы между запросами, не долбить; снапшоты в фикстуры,
  тесты НЕ ходят в сеть.
- Rate-limit на /auth/* при живых проверках.
- Мердж пловцов необратим — всё, что пишет в БД, только dry-run до «да» Влада.

C1 принят после ревью; всё закоммичено по шагам, память обновлена.
