# Фаза 3.2 — контракт paged-режима `/api/results`

Контракт между сервером и клиентом для `ResultsLoadMode = paged`: клиент перестаёт выкачивать
соревнование целиком и запрашивает у сервера уже отфильтрованную страницу. На этот документ
ложатся: серверные доработки (`ResultFilter`/`ResultRepository`/`ResultsController` — Fable)
и клиентская часть (`loadFromApi`-ветка `paged`, filter-section, Redux — Sonnet, отдельное задание).

Статус: **черновик на приёмку**. Решения, требующие подтверждения, помечены «⚠ решение».

---

## 1. Принципы

- **Full-режим не трогаем.** Все изменения аддитивны: существующие query-параметры и форма
  ответа сохраняются, `full` продолжает работать как сейчас. Paged включается админ-настройкой
  или `?loadMode=paged`.
- **Один запрос = одна страница.** Никаких циклов `while hasMore` в paged-ветке.
- **Фильтры — серверные.** Всё, что в full-режиме фильтруется на клиенте, в paged уезжает
  в query-параметры. Исключения перечислены в §5 (и это осознанные исключения, не «забыли»).
- **Сортировка фиксированная** (как сейчас): `CompetitionDate DESC, Position ASC`.
  Под неё есть индекс `(CompetitionId, CompetitionDate DESC, Position)` (фаза 3.3).
  Пользовательской сортировки по колонкам в UI нет — параметр `sort` не вводим, пока не появится.

## 2. Запрос: `GET /api/results?...`

### Уже есть (менять не надо)

| Параметр | Семантика |
|---|---|
| `competitionId` | id одного дня/однодневки, либо `last` |
| `eventId` | все дни многодневного события |
| `competition` | prefix по названию соревнования |
| `name` | prefix по имени/фамилии (RU + EN) |
| `club` | prefix по названию клуба (RU + EN) |
| `styleName`, `distance`, `gender`, `poolType` | точные совпадения |
| `dateFrom`, `dateTo` | диапазон по `CompetitionDate` |
| `page`, `pageSize` | страница (1-based), размер ≤ 500 |

### Добавить на сервере (дыры под клиентские фильтры)

| Параметр | Семантика | Где не хватает |
|---|---|---|
| `birthYearFrom`, `birthYearTo` | клиентский фильтр Age — это **годы рождения** (одиночный год = from=to) | `ResultFilter` + `Where(r => r.Swimmer.BirthYear >=/<=)` |
| `ageGroup` | masters-режим фильтра Age: точное совпадение строки `Results.AgeGroup` («25-29», …) | `ResultFilter` + `Where(r => r.AgeGroup == …)` |
| `position` | `top` → `Position <= 10` **или без места** (DSQ/DNS остаются — зеркало клиентского фильтра), `podium` → `Position <= 3` строго; отсутствует/`all` → без фильтра | `ResultFilter` (enum-строка) |
| `eventDate` | конкретный день события, формат `dd/MM/yyyy`; серверно = `CompetitionDate == дата` | `ResultFilter` (можно переиспользовать DateFrom=DateTo, но отдельный параметр честнее для кэш-ключа) |

Валидация: неизвестные значения `position` → 400; `eventDate` не парсится → 400.
Все новые поля обязаны попасть в `ResultsCacheKey`.

### Ограничение глубины

`page * pageSize > 10 000` → 400 с текстом «narrow the filter». OFFSET в Postgres линейный
(замер 3.3: ~37 мс на глубине 10k, дальше хуже); реальные сценарии глубже не ходят —
пользователь сужает фильтр, а не листает 200 страниц. Keyset-пагинацию не вводим,
пока UI — «номерные» страницы/инфинит-скролл от начала.

## 3. Ответ

```jsonc
{
  "page": 3,
  "pageSize": 100,
  "hasMore": true,
  "total": 4963,        // ← НОВОЕ: общее число строк под текущим фильтром (без пагинации)
  "data": [ /* ResultDto[] — без изменений */ ]
}
```

- `total` нужен клиенту для пейджера/«N results». Считается отдельным `COUNT(*)` по тому же
  фильтру и кэшируется **отдельным ключом без page/pageSize** (тот же TTL 2 мин): смена страницы
  не пересчитывает count. С индексами 3.3 count по competition/event — index-only, дёшево.
- `hasMore` остаётся (full-режим и обратная совместимость); в paged клиент может опираться
  на `total`.
- ⚠ решение: `total` отдаём и в full-режиме (одна форма ответа проще двух) — возражений не жду,
  но фиксирую.

## 4. Клиентская сторона (рамка для задания Sonnet)

- `loadFromApi` в paged-ветке: один fetch текущей страницы с фильтрами из
  `state.filterSelected`, маппинг клиентских фильтров в query-параметры по §2.
- Redux: `dataSourceSelected.results` в paged-режиме содержит **текущую страницу**, плюс
  `resultsPaging: { page, pageSize, total, hasMore }` в state. Компоненты, выводящие «все
  результаты» (счётчики, доступные опции фильтров), в paged-режиме берут опции из
  публичного `GET /api/results/filter-hints?field=&q=&limit=` (field: style | distance |
  club | competition | name) или из `total`, а не из полного массива.
- Смена любого фильтра сбрасывает `page = 1`.
- Debounce на текстовых фильтрах (name/club) — 300 мс, чтобы не бить API каждым символом.

## 5. Что в paged-режиме v1 остаётся клиентским (осознанно)

| Фильтр | Почему | Поведение в paged v1 |
|---|---|---|
| `level_filter` (нормативный уровень) | уровень = функция (время × стиль × дистанция × пол × возраст × бассейн) через `RecordsHelper`; серверный аналог = join с NormativeStandards — реально, но это отдельная работа | ⚠ решение: фильтр уровня в paged v1 **скрыт/disabled** (бейджи уровня на строках остаются — они считаются по загруженной странице). Серверный вариант — кандидат в 3.4 |
| `is_recalculated` (пересчёт мест по лучшему времени) | пересчёт требует полный датасет события; на странице из 100 строк он не имеет смысла | ⚠ решение: тумблер в paged v1 **скрыт/disabled**. Серверный вариант (`ROW_NUMBER()` по событию) — кандидат в 3.4 |
| `activity_type` (training/competition) | тренировки в БД отсутствуют — сервер отдаёт только competition | в paged показываем только competition; тренировочные экраны живут на своих данных как сейчас |
| favorites-подсветка | подсветка построчная, датасет не меняет | без изменений |

Логика: paged-режим нужен для масштаба (глобальный просмотр, большие соревнования). Пока
он opt-in через админку — допустимо, чтобы два клиентских тумблера в нём отсутствовали;
вернём их серверными в 3.4, если режим станет основным.

## 6. Чек-лист серверных доработок (Fable, 3.2-server)

1. `ResultFilter`: + `BirthYearFrom`, `BirthYearTo`, `AgeGroup`, `PositionFilter`, `EventDate`.
2. `ResultRepository.GetPagedAsync`: + 5 предикатов, + `total` (отдельный кэш-ключ),
   расширить `ResultsCacheKey`.
3. `ResultsController.GetResults`: + параметры, валидация, лимит глубины, `total` в ответе.
4. Тесты `ResultRepositoryTests`: новые предикаты, total, глубина.
5. EXPLAIN-прогон новых предикатов на синтетике (`server/db/explain-top-queries.sql` дополнить
   birthYear/position-вариантами).

## 7. Приёмка (пары full vs paged)

На одном и том же соревновании с реальными данными: выдача первой страницы, счётчик total,
каждый фильтр из §2 в отдельности и в комбинации — paged-ответ совпадает с тем, что full-режим
показывает после клиентской фильтрации (кроме исключений §5).
