# Даты израильских мастерских рекордов: источник пишет месяц/день (задание Sonnet)

## Контекст

У израильских мастерских рекордов (`Records`, `RegionCode='ISR'`, `Category='masters'`,
845 строк, источник `isrorg-masters`) даты лежат в двух видах, и оба неверны:

| в базе | строк | что это |
|---|---|---|
| `7/20/2019`, `2/15/2019` (без нулей) | 386 | не разобрались и легли как есть |
| `04/05/2024`, `07/09/2010` (с нулями) | 459 | «разобрались», но, как правило, **развёрнуты неверно** |

Найдено 18.09.2026 на табе Masters страницы `/records`, где рядом стояли `7/20/2019` и
`03/11/2022`.

**Причина установлена (разведка вызывающей сессии, 18.09):**

1. **Источник пишет даты МЕСЯЦ/ДЕНЬ/ГОД.** Проверено по архивным PDF федерации
   (`!records-sources/isrorg-masters-50m__source-2025-04__fetched-2026-09-16.pdf` и
   `…-25m__source-2026-01__…`) через `pdftotext -layout`:

   | файл | дат | вторая часть > 12 (точно М/Д) | первая часть > 12 (точно Д/М) | неоднозначно |
   |---|---|---|---|---|
   | 50 м | 450 | **243** | 1 | 206 |
   | 25 м | 467 | **208** | 4 | 255 |

   Ведущих нулей в PDF нет ни у одной даты. Пять строк Д/М — свежие добавления федерации
   (`18/7/2023`, `13/12/2025`, `14/12/2025`…): файл ведут руками, и новые строки пишут
   по-другому.

2. **Парсер читает дату как ДЕНЬ/МЕСЯЦ.**
   `server/Swimm.Parsing/Parsers/IsrOrgMastersRecords/IsrOrgMastersRecordsParser.cs`,
   `NormalizeDate` (~стр. 636): `parts[0]` → день, `parts[1]` → месяц, `new DateTime(...)`.
   - `7/20/2019` → месяц 20 → исключение → `catch` возвращает строку как есть → те 386 сырых.
   - `3/12/2022` → «3 декабря» → `03/12/2022`, хотя в источнике 12 марта → те 459 «с
     нулями», **молча неверные**. Это хуже, чем сырая строка: выглядит нормально.

## Решения (зафиксированы, не пересматривать)

1. **Чинится в одном месте — в разборе даты парсера `isrorg-masters`.** Данные в БД руками
   НЕ править: исправленный парсер → обычный путь дифф/Apply перепишет строки.
2. **Правило разбора даты `a/b/yyyy` (и `a.b.yyyy`) для этого источника:**
   - `a > 12` → это **день/месяц** (свежие строки федерации);
   - иначе → **месяц/день** (формат файла: 451 против 5);
   - невалидная дата (например `b > 31`) → вернуть строку как есть (как сейчас).
3. **Выход — `ParserConstants.DateFormat` (`dd/MM/yyyy`)**, как у всех остальных источников.
4. **Известная цена, принять и записать:** свежая строка Д/М, у которой обе части ≤ 12,
   прочитается как М/Д. Отличить её нечем — в файле нет ни признака формата, ни порядка
   строк по дате. Видимых Д/М на весь справочник 5 из ~917, так что потерь единицы, а
   альтернатива (читать всё как Д/М) портит сотни.
5. **Разбор даты вынести в отдельный `internal static` метод** (например
   `ParseSourceDate(string raw, char separator)`), чтобы его можно было покрыть тестом без
   PDF. Если в `Swimm.Parsing` нет `InternalsVisibleTo` для `Swimm.Tests` — сделай метод
   `public static` в том же классе, это проще, чем заводить атрибут.
6. **Другие парсеры не трогать**, даже если там похожий код: у `isrorg-age` (возрастные
   рекорды) даты в PDF день-первые, их разбор верен (проверено 17-18.09, И-26).

## Тесты (обязательно)

Новый файл `server/Swimm.Tests/IsrOrgMastersDateTests.cs`, `[Theory]`:

| вход | ожидается | почему |
|---|---|---|
| `7/20/2019` | `20/07/2019` | однозначно М/Д (было: сырая строка) |
| `3/12/2022` | `12/03/2022` | неоднозначно → М/Д (было: неверное `03/12/2022`) |
| `7/9/2010` | `09/07/2010` | неоднозначно → М/Д |
| `18/7/2023` | `18/07/2023` | первая часть > 12 → Д/М |
| `13/12/2025` | `13/12/2025` | первая часть > 12 → Д/М |
| `12/12/2020` | `12/12/2020` | обе равны — формат не важен |
| `7.20.2019` | `20/07/2019` | разделитель-точка по тому же правилу |
| `2/30/2020` | `2/30/2020` | невалидная дата → как есть |

Плюс один тест-инвариант с комментарием про решение 4: `1/5/2025` → `05/01/2025` (так и
задумано, даже если в источнике это было 1 мая).

## Footguns

- **Build-lock**: `MSB3027`/`MSB3021` «locked by .NET Host» — жив прежний `dotnet run`; убей
  через `Get-CimInstance Win32_Process` или собирай с `--configuration Release`.
- **Ты работаешь в изолированном worktree** — там нет запущенного API, и не надо его
  поднимать: всё проверяется CLI `--records-dump` и тестами. Для `--records-dump` нужна
  локальная Postgres (Docker, порт 5445) — она общая и уже запущена; если ругается на 5445,
  значит Docker Desktop выключен — напиши в отчёте, не пытайся запускать.
- `--records-dump` ничего не пишет в БД, только читает источник. Безопасно.
- Порядок источников в боевом `--records-refresh` важен (И-13) — боевой прогон НЕ запускать.

## Вне скоупа (не делать)

- **Не делать Apply и не запускать `--records-refresh` без `--dry-run`.** Заливку решит Влад
  после приёмки: она перепишет даты почти у всех 845 строк.
- Не класть файлы в `!records-sources/` и не трогать `SHA256SUMS.txt`.
- Не трогать парсер `isrorg-age` и другие источники.
- Не править данные в БД SQL-ом.
- Не коммитить.
