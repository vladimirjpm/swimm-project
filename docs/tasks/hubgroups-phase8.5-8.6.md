## Часть A — 8.5: внутренний зачёт группы (исполнитель: Opus/Sonnet)

### Зафиксированные решения

1. **Зачёт = сезонный рейтинг участников по клубным очкам.** Очки за место — по механике
   `ClubPointsRule`/`ClubPointsRuleEntry` (шкала место→очки): правило выбирается по дате
   соревнования (`EffectiveFrom` — последнее вступившее в силу) и scope
   (`Competition.IsMasters` → masters, иначе non-masters; правило "all" подходит обоим).
   `Position` null или `TimeFail` → 0 очков. Эстафеты (`RelayId != null`) не участвуют.
2. **Сезон**: с 1 сентября последнего прошедшего сентября по сегодня (израильский
   плавательный сезон). `season_label` вида `"2025/26"`.
3. **«Ближайшие старты» — НЕ делать.** Будущих соревнований в БД нет (проверено
   2026-07-10: max(Competition.Date) = 07/07/2026, уже в прошлом). Вернуться после
   фазы 6 (автозабор isr.org.il).
4. Считается и для обычной группы, и для виртуальной `favorites` — общий код в
   `HubGroupPublicRepository.FillAggregatesAsync`.

### Сервер

- `HubGroupDetailsDto` + новое поле `standings` (`List<HubGroupStandingDto>`), сортировка
  по `club_points` desc, затем по `swims` desc:
  ```
  HubGroupStandingDto: swimmer_id, name, name_en, role,
    swims (кол-во заплывов за сезон, без эстафет),
    golds, silvers, bronzes (Position 1/2/3 за сезон),
    club_points (сумма по правилам),
    best_fina (max InternationalPoints за сезон, 0 если нет)
  ```
  Плюс поле `season_label` на уровне `HubGroupDetailsDto`. JsonPropertyName — snake_case,
  как у остальных полей файла `HubGroupPublicDtos.cs`.
- Реализация в `HubGroupPublicRepository`: правила грузить одним запросом
  (`ClubPointsRules` + `Entries`) и применять в памяти к выборке сезонных результатов
  участников (поля: SwimmerId, Position, TimeFail, RelayId, InternationalPoints,
  CompetitionDate, Competition.IsMasters). Отдельного кэша не надо — ответ уже под
  HTTP-кэшем (ETag), а favorites не кэшируется намеренно.
- Участники без заплывов за сезон (в т.ч. тренер) — В таблице, с нулями, в конце списка.

### Клиент

- Карточка **Season standings** на странице группы (groups.tsx), между Members и
  Group records: колонки — место (1..N), пловец (+ роль-бейдж как в Members), Swims,
  медали (🥇🥈🥉 числами), Points (club_points, hp-mono акцент), Best FINA.
  `season_label` — в подзаголовке карточки. Пустой сезон → «В этом сезоне заплывов нет».
- Типы — в `client/src/projects/hub-groups-project/types.ts`.

### Приёмка A

- Смоук по образцу фаз 3–4 (см. историю): создать группу с 2–3 пловцами с результатами
  (psql), убедиться, что `/api/hub-groups/{slug}` отдаёт `standings` с ненулевыми очками,

## Часть B — 8.6: самообслуживание (исполнитель: Sonnet)

### Модель ролей (зафиксирована Fable с Владом 2026-07-10 — не смешивать три «coach»!)

В слове «тренер» живут ТРИ разных понятия, у каждого своё хранилище:

1. **Site-роль `Coach`** (`Sys_AppRoles`/`Sys_AppUserRoles`) — привилегия АККАУНТА:
   право СОЗДАВАТЬ группы при `HubGroupCreationPolicy=coach`. Выдаёт только админ
   (пока SQL-запросом, см. ниже; UI-выдача ролей — вне скоупа 8.6). «Главный coach»
   в терминологии Влада = пользователь с этой ролью, владелец своих групп.
2. **`HubGroupMember.Role='coach'`** — бейдж на ПЛОВЦЕ в составе группы (уже есть
   с фазы 1). К аккаунтам сайта отношения не имеет, прав не даёт.
3. **Со-тренер группы** — НОВОЕ: право ПОЛЬЗОВАТЕЛЯ управлять конкретной группой.
   Таблица `Sys_HubGroupManagers` (это права → Sys_-префикс, БЕЗ grant swimm_ro):
   `Id, HubGroupId (FK, cascade), UserId (FK Sys_AppUsers), GrantedByUserId, CreatedAt`,
   unique (HubGroupId, UserId).

**Права** (проверяются в одном месте — хелпере/сервисе, не размазывать по хендлерам):

| Действие | Admin | Владелец (OwnerUserId) | Со-тренер |
|---|---|---|---|
| создать группу (policy=coach/any, лимит MaxPerUser) | ✔ (без лимита) | ✔ | ✖ (только свои) |
| править данные группы, состав, роли-бейджи участников | ✔ | ✔ | ✔ |
| назначать/снимать со-тренеров СВОЕЙ группы | ✔ | ✔ | ✖ |
| удалить группу, сменить владельца | ✔ | удалить ✔ / владельца ✖ | ✖ |

Со-тренерство НЕ каскадирует (со-тренер не назначает других со-тренеров) и НЕ даёт
site-роль Coach — «коачем только в своей группе», эскалации привилегий нет.
Назначение со-тренера: по точному email существующего пользователя (без листинга
пользователей — приватность); нет такого email → понятная ошибка.

### SQL для Влада — выдать site-роль Coach руками (до появления UI):

```sql
INSERT INTO "Sys_AppRoles" ("Name") SELECT 'Coach'
  WHERE NOT EXISTS (SELECT 1 FROM "Sys_AppRoles" WHERE "Name"='Coach');
INSERT INTO "Sys_AppUserRoles" ("UserId","RoleId")
  SELECT u."Id", r."Id" FROM "Sys_AppUsers" u, "Sys_AppRoles" r
  WHERE u."Email"='<email>' AND r."Name"='Coach'
  ON CONFLICT DO NOTHING;
-- ВАЖНО: смена ролей вступает в силу после ребута сессии — бампни SecurityStamp:
UPDATE "Sys_AppUsers" SET "SecurityStamp"=gen_random_uuid()::text WHERE "Email"='<email>';
```
(роль Coach также добавить seed-миграцией, чтобы прод не зависел от ручного SQL)

### Скоуп реализации

1. **Enforcement настроек**: создание не-админом при `HubGroupCreationPolicy=coach`
   (роль Coach) или `any`; лимит `HubGroupMaxPerUser` по `OwnerUserId` (админа не касается).
2. **Пользовательский API** `[Authorize]` (создать/править/удалить свою группу + участники
   + со-тренеры) поверх общей логики с `HubGroupAdminService` (slug-валидация,
   PostgresException-обработка — переиспользовать, не копипастить) + клиентская форма
   на странице групп («Моя группа» / кнопка «Создать группу» видна по правам).
3. **Приватность per-group**: серверное поведение готово (repo фильтрует IsPublic) —
   здесь только галочка в пользовательской форме. НО: владелец/со-тренер должны видеть
   свою скрытую группу — приватный путь через rw-контекст по правам, не через swimm_ro.
4. **Заявки на вступление** — ВНЕ скоупа 8.6 (отдельное решение с Владом).

Открытый вопрос к Владу перед стартом: нужна ли модерация названий/иконок пользовательских
групп (при `any` — рекомендую хотя бы пост-модерацию: админ видит новые группы в /Admin).
