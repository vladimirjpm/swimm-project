## Исходные данные (сняты с живой БД 2026-07-18)

Клубов всего 531, реальных (без `SYNTH%`) — 231. Три класса проблем:

1. **~85 клубов-мусора от парсера**: заметка дисквалификации утекла в название —
   `הפועל דולפין נתניה DNS`, `הפועל דולפין נתניה 4.4 SW /`, `SWIM TLV 8.3 SW /` и т.п.
   Запрос для повторного снятия среза:
   ```sql
   SELECT count(*) FROM "Clubs" WHERE "Name" NOT LIKE 'SYNTH%'
     AND ("Name" ~ 'DNS$|SW /$|NS$' OR "Name" ~ '[0-9]\.[0-9]');
   ```
2. **Кросс-скриптовые дубли**: `Hapoel Dolphine Netanya` (id 1248, из EN-протоколов
   Maccabiah) против `הפועל דולפין נתניה` (id 438). Точным `Name↔NameEn` не ловятся
   (0 совпадений — у ивритских клубов `NameEn` пуст). Ловятся пересечением пловцов.
3. **Псевдоклубы Maccabiah**: `USA`, `Israel`, `Germany`, `Ukraine`, `M25`,
   `Maccabiah MIX` — в протоколе вместо клуба страна/команда. НЕ дубли; решение:
   оставить, но исключить из club-summary (отдельным флагом или списком — решить в B).

Связи `ClubId` (все надо перецеливать при merge): `Results`, `Swimmers`, `HubGroups`
(+ partial unique index на официальные группы!), `HubGroupClubRequests`, `UserFavorites`.
`ClubPointsRule` клубов НЕ трогает. Админ-страницы Clubs пока нет (бэклог 7.2).

## Фаза A — починить парсер (источник мусора). Fable, первым делом

- Найти в `Swimm.Parsing/Parsers/IsrOrg/IsrOrgResultLineParser.cs` (и/или ветках
  `IsrOrgCompetitionParser`), где при разборе DQ/DNS-строки хвост заметки
  («4.4 SW /», «DNS», «NS») прилипает к названию клуба.
  Живой пример строки: `- 2 3 ZELINGER SEAN 2017 Maccabbi Weisgal DQ / SW 7.1 0`.
- Починить так, чтобы club = «Maccabbi Weisgal», а заметка ушла в TimeFailNote.
- Тесты в `Swimm.Tests` на DQ-варианты (`DQ / SW x.y`, `DNS`, `NS`) в обеих ветках
  (HE и EN), включая случай клуба, перенесённого на соседнюю строку.
- Критерий: повторный импорт любого протокола не создаёт клубов с хвостами.

## Фаза B — ClubMergeService + кандидаты. Fable

По образу `SwimmerMergeService`/`SwimmerDedupService` (та же пара интерфейсов в
Application, реализации в Infrastructure, dry-run по умолчанию).

Кандидаты (`IClubDedupService.FindCandidatesAsync`), три эвристики по убыванию уверенности:
1. **Мусорный суффикс** (после фазы A это уже наследие): `Name` = `Name` другого клуба
   + известный хвост (`DNS`, `NS`, регэксп `\d\.\d SW /` и т.п.) → sure, льются пачкой.
2. **Пересечение пловцов**: доля общих `Swimmers.ClubId`/участников результатов между
   двумя клубами выше порога (напр. ≥30% меньшего клуба, минимум 3 пловца) → кандидат;
   именно это ловит кросс-скрипт (`Hapoel Dolphine Netanya` ↔ `הפועל דולפין נתניה`),
   транслитерация не нужна. Свежий merge пловцов усилил сигнал.
3. **Левенштейн ≤ 1** внутри одного скрипта (опечатки, приставки:
   `גרינברג הפועל דולפין נתניה`). Порог консервативный, шум не показывать.

Merge (`IClubMergeService.MergeAsync(pairs, dryRun)`):
- Перецелить: `Results.ClubId`, `Swimmers.ClubId`, `HubGroups.ClubId`,
  `HubGroupClubRequests.ClubId`, `UserFavorites.ClubId`.
- Guard 1: если у ОБОИХ клубов есть официальная hub-группа (partial unique index
  `HubGroups.ClubId WHERE IsOfficial`) — merge пары блокируется с внятной ошибкой.
- Guard 2: дедуп `UserFavorites` (у юзера клуб может оказаться в избранном дважды —
  оставить одну запись).
- Дозаполнить пустые `NameEn`, `CountryId` канонического из дубля; удалить дубль.
- Канон в кросс-скриптовой паре — ивритская запись (латиница → `NameEn`), иначе —
  у кого больше результатов (симметрично пловцам).
- Инвалидация кэша club-summary (фаза 3.4) после merge.
- Синтетика (`SYNTH%`) исключена из кандидатов и защищена от merge.
- Юнит-тесты: каждая эвристика кандидатов, оба guard-а, dry-run ничего не пишет,
  дозаполнение полей, инвалидация кэша.
