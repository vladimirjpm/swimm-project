# /Admin/Competitions — соревнования (справочник БД + входящие isr.org.il)

Файлы: `Pages/Admin/Competitions/Index.cshtml(.cs)`, `Edit.cshtml`. Данные списка —
`ICompetitionAdminRepository.GetUnifiedAsync` (реализация `CompetitionAdminRepository`);
CRUD — тот же репозиторий; каскадное удаление — `IImportService.DeleteCompetition(Event)Async`.
Действия входящих — API `DiscoveryAdminController` (`/api/admin/discovery/*`) + сервисы
`CompetitionDiscoveryService` / `CompetitionDiscoveryBackgroundService`; матч —
`DiscoveryCompetitionMatcher`. DTO — `Dtos/UnifiedCompetitionDtos.cs`, `CompetitionCrudDtos.cs`.

**Объединённый список:** одно соревнование — одна строка со стадией жизненного цикла
(`CompetitionStage`): `OnSite` (на сайте, в БД нет) / `Imported` (есть и там, и там) /
`DbOnly` (только в БД, PDF-импорт без OrgCompId) / `Ignored` (скрыто). Склейка справочника
`Competitions` и входящих `Sys_DiscoveredCompetitions` по `OrgCompId` (+ fallback имя+дата).
Раньше это были две отдельные страницы (Competitions + Discovery) — объединены 2026-07.

**Фильтры:** поиск (имя/подзаголовок), категория (из /Admin/Categories), **тип** (все /
чемпионат Израиля, `?kind=champ`), **сезон**, стадия,
чекбокс «показать синтетику» (SYNTH Meet…, по умолчанию скрыта). Сортировка по дате (убыв.),
пагинация 20/стр. Merge в памяти (admin-масштаб ~1.5k; при росте — вынести в БД-пагинацию).

**Сезон = сен–авг, зовётся годом окончания** (2025 = 24/25) — как `cYear` на isr.org.il
(проверено на списке `cYear=2025`: окт-2024 … авг-2025). `CompetitionAdminRepository.SeasonOf`.
Фильтр списка — параметр `?season=` (раньше был `?year=` с календарным годом); применяется
в памяти одним предикатом по дате строки, поэтому одинаково режет и БД-строки, и строки с
сайта. Список сезонов в селекте — `GetAvailableSeasonsAsync` (справочник + `Sys_DiscoveredCompetitions`),
иначе после забора прошлого сезона его нечем было бы отфильтровать. `GetAvailableYearsAsync`
(календарные годы) остался только у /AssignRules.

**Сезоны сайта.** Рядом с «Проверить сейчас» — селект «Сезон на сайте»: `текущий`
(без `cYear` — как раньше) или прошлый сезон (`cYear=<год окончания>`: 2025 = 24/25).
Уходит в `POST /api/admin/discovery/sync?year=`, дальше `ICompetitionDiscoveryService.SyncAsync(year)`
→ `FetchListAsync(finished, year)`. Прошлые сезоны — только по кнопке; фон
(`CompetitionDiscoveryBackgroundService`) всегда тянет текущий. Строки прошлых сезонов
попадают в те же «входящие» и импортируются обычным «Затянуть»; после забора страница
сама открывается с `?season=<год>`, чтобы новые строки не тонули в общем списке.

## Панель строки (открыть/закрыть)

У каждой строки одна кнопка **«▸ Открыть / ▾ Закрыть»** — снаружи остаётся только она и
«Удалить» (деструктивное не должно жить под раскрытием). Всё остальное внутри панели:

- **действия**: «Изменить» (страница Edit), «Качество», действия входящих (Затянуть, ✓ имп.,
  Синхр. языки, PDF, скрыть/вернуть);
- **дни многодневного события** — раньше они разворачивались кликом по строке; теперь клик по
  строке не делает ничего, дни живут в панели (у каждого — своё «Изменить»/«Удалить»);
- **быстрая правка**: категории, Awards / 🏆 Чемпионат Израиля / Combine, тип бассейна,
  клубные очки, High Point → handler `QuickSave` → `ICompetitionAdminRepository.QuickUpdateAsync`.

**Сохранение применяется КО ВСЕМ дням события** (регламент у события один, а поля лежат у
каждого дня). Внутри `QuickUpdateAsync` идёт через обычный `UpdateAsync` по каждому дню —
бесплатно достаются валидация уникальности, синк категорий, пересчёт объединённых мест при
смене Combine и сброс кэша. Первая ошибка прекращает цикл (лучше сказать, чем применить
половину дней). Имя/дата/подзаголовок/страна/OrgCompId в панели НЕ правятся — они у дней
разные, для них Edit. Открытые панели переживают перезагрузку страницы (`sessionStorage`),
поэтому после «Сохранить» строка остаётся раскрытой. Аудит — `competition.quick-edit`.

**Действия входящих (site-строки):** «Проверить сейчас» (sync списка), «Затянуть»→превью-модал→
импорт (через очередь, см. Import History), «✓ имп.» (пометить вручную), «Синхр. языки»
(дозаполнить EN-имена из EN-протокола без переимпорта), PDF, скрыть/вернуть. Все дёргают
`/api/admin/discovery/*`; после мутаций страница перезагружается. Имена discovery-строк для
JS — через `window.__DISC` (id→name), не onclick (экранирование иврита/кавычек).

**«Чемпионат Израиля» — РУЧНОЙ ФЛАГ** `Competition.IsChampionship` (галка «🏆 Чемпионат
Израиля» на Edit, рядом с Awards; миграция `AddCompetitionIsChampionship`). Он источник
истины для всего: фильтр «Тип», колонка 🏆 в списке, бейдж в ячейке флагов, `is_championship`
в `/api/competitions` → 🏆 и тумблер «Championships» в селекторе на клиенте, кубок в плитке.
У многодневного события флаг = «помечен хотя бы один день».

**Эвристика по названию осталась в двух местах** (`CompetitionAdminRepository.IsChampionship`):
одноразовый бэкфилл в миграции (13 из 21 соревнования на 2026-07-29) и строки «только на
сайте», которых в БД ещё нет — флага там взять негде. Для строк, которые в БД есть, эвристика
НЕ применяется: снятая руками галка не должна возвращаться сама. Правило эвристики:
«אליפות» И «ישראל» в имени (или английские championship + israel). Слова проверяются
ПО ОТДЕЛЬНОСТИ, а не подстрокой: между ними бывает вставлен спонсор — «אליפות "ארנה" ישראל»,
«אליפות arena ישראל» (подстрока дала бы 39 из 42). Клубные/городские «אליפות מכבי»,
«אליפות חדרה» сюда не попадают — в этом и смысл; отборочные «מוקדמות אליפות … ישראל»
попадают (часть того же чемпионата). Отдельного признака в исходных данных нет: у входящих
с сайта, кроме имени и даты, ничего нет, а категории (Kids/Youth/Masters…) — про возраст,
не про ранг. Поэтому и понадобился ручной флаг.

Строка списка несёт готовое `UnifiedCompetitionRowDto.IsChampionship` (колонка 🏆 слева от
названия) — вьюха ничего не пересчитывает. **На клиенте** —
[`competition-source.ts`](../../client/src/utils/helpers/competition-source.ts):
`isChampionshipSource` читает `is_championship` с сервера и падает на `isChampionshipName`
(та же эвристика) только там, где флага в объекте нет.

**Состояние списка живёт в URL.** Любой выбор в фильтрах сразу сабмитит форму (JS на `change`
у `#filters-form`), пустые поля из query выкидываются — так «назад» в браузере возвращает
предыдущую выборку. Ссылки «Изменить»/название несут `back=<url списка с фильтрами и страницей>`;
Edit возвращает по нему из «← К списку» и после сохранения/удаления (`EditModel.BackLink`,
проверка `Url.IsLocalUrl` — открытый редирект отбивается, чужой URL → просто /Admin/Competitions).
`back` протаскивается через все POST-хендлеры формы (`asp-route-back`), иначе после первого
сохранения он бы потерялся.

**CRUD справочника:** «Изменить» (Edit-страница — многодневные события/EventId, PoolType,
IsMasters/IsAward, страна, категории, URL результатов), «Удалить» день/событие (каскад с
подтверждением), «+ Новое соревнование». Эталон CRUD для новых админ-страниц.

## Роль в клубном зачёте (K6)

Селект **«Роль в клубном зачёте»** (`Competition.StandingKindOverride`, nullable) — ручное
переопределение того, каким чемпионатом соревнование считается на **странице клуба**
(грид «сезон × группа», карточка Standings, бейдж ❄/☀ в истории).

**По умолчанию «Авто» — и почти всегда так и надо оставлять.** Роль выводится сама:

```
🏆 Чемпионат + бассейн 25м → ❄ зимний
🏆 Чемпионат + бассейн 50м → ☀ летний
не чемпионат              → в зачёт не идёт (но в истории клуба виден)
```

Правило проверено на всех 23 чемпионатах в БД (2026-08-01): 12 в 25м — январь/февраль,
11 в 50м — июль/август, исключений нет. Подпись у пункта «Авто» показывает, что именно
выведется при текущих флагах. Поле заведено под случаи вне правила — прежде всего
**открытую воду**, где бассейна нет вовсе; значение `none` явно исключает соревнование
из зачёта.

⚠ **Зачёт образуют только категории возрастной лестницы** (`Category.ReservedKeys`).
Кастомные (`result-maccabiah` и будущие) — «соревнование само по себе», зачёта по ним нет.
Старт, висящий в ДВУХ категориях лестницы, даёт два зачёта — по строке на группу.

⚠ **Двух зимних (или двух летних) чемпионатов одной группы за сезон быть не может.**
Уникальным индексом это не выразить (сезон производен от даты, группа лежит в M:N),
поэтому проверка живёт в дашборде: метрика **«Дубль клубного зачёта»**. Ненулевое
значение означает ошибку в `IsChampionship`/`PoolType` конкретного соревнования — чинить
надо там, а не в зачёте. Пропуск (чемпионат отменили) — штатный случай, не ошибка.

Модель целиком — [../plans/club-page-model.md](../plans/club-page-model.md) §2.1.

## Привязка правил очков (Э4)

В форме соревнования — два селекта, **Клубные очки** и **High Point**
(`Competition.PointRuleClubsId` / `PointRuleSwimmersId`, оба nullable). Значение по
умолчанию — «Авто (по дате и типу)»: правило подбирает `CompetitionRuleResolver`, но
только среди правил **без** флага `ManualOnly`. Список правил — /Admin/PointsRules
([pointsrules.md](pointsrules.md)).

- **Правило хранится у каждого дня отдельно**, а регламент у многодневного события один →
  на Edit есть кнопка «Проставить правила всем дням события» (handler `ApplyRulesToEvent`).
  Она сохраняет ТОЛЬКО правила; остальные поля формы при этом не пишутся.
- **Массовая простановка** — отдельная страница `/Admin/Competitions/AssignRules`
  (`AssignRules.cshtml(.cs)`), в стиле MoveResults: фильтры (сезон / masters / только без
  привязки) → отметить строки → выбрать правила → применить. Список — по дням, а не по
  свёрнутым событиям; синтетика (SYNTH…) скрыта.
- У каждого поля выбор из трёх состояний: **не менять** / **Авто** (снять привязку) /
  конкретное правило. `null` — легитимное значение, поэтому «менять или нет» вынесено в
  отдельный флаг `SetClubs`/`SetSwimmers` (`CompetitionRuleAssignmentDto`), а не кодируется
  через null.
- Несуществующий Id правила отбивается валидацией (`ValidateRuleIdsAsync`) — иначе FK
  RESTRICT дал бы 500. После простановки сбрасывается кэш; аудит — `competition.assign-rules`.

## Deep-link фильтры «здоровье данных» (T3b)

`?filter=ignored|discovery-new` — алиасы на `Stage` (как раньше). `?filter=discovery-error|
no-org-comp-id|no-results` — новый доп-параметр `qualityFilter` в
`GetUnifiedAsync` (те же предикаты, что в `DashboardStatusService`): применяется
поверх стадии/поиска/сезона, PageModel кладёт его в `QualityFilter` для шапки списка
(«активный фильтр… сбросить») и пробрасывает во все ссылки пагинации/месяцев.
Для свёрнутого многодневного события «нет OrgCompId»/«нет результатов» проверяются
по любому дню/сумме дней, а не только по «голове» строки.

## Кнопка «Качество» — проверка достоверности результатов

Кнопка **«⚑ Качество»** стоит прямо в строке таблицы рядом с «Открыть» — у каждой строки
с результатами (заголовок многодневного события → скоуп `eventId`, одиночное соревнование →
`competitionId`); открывает модал `#quality-modal`. До 2026-08-01 она жила только внутри
раскрывающейся панели и потому не попадалась на глаза; дубль в панели остался.
⚠ Автозапуска после импорта НЕТ — проверку надо нажимать руками (необязательный план, как
это автоматизировать: `docs/plans/import-quality-autoscan-plan.md`).
API — `SuspectResultsAdminController` (`/api/admin/suspect-results`), сервис
`SuspectResultService`, правила — чистая функция `SuspectResultDetector`, коды причин —
`Swimm.Domain.SuspectReasons`. Поля в `Results`: `SuspectReason` / `SuspectIsManual` /
`SuspectNote` (миграция `AddResultSuspectReason`, частичный индекс по непустым).

**Зачем.** Проверка ищет ошибки САМОГО протокола — то, что не лечится ни парсером, ни
переимпортом. Эталон: Маккабиада 2026, `100m Butterfly - Women` — у Elisa MOSHKOVITCH
напечатано 00:32.59 (её же полтинник 27.27), у Ophir RAKAH 00:53.42 (её двухсотка 2:17.37,
что несовместимо), и организаторы посчитали из этих времён 4702 и 1067 очков. Такие заплывы
«бьют» национальные рекорды в шапке соревнования.

**Что делает пометка.** Строка остаётся в результатах (заплыв был, время в протоколе есть),
но исключается из детекции рекордов — фильтр `SuspectReason == null` в
`ResultRepository.GetOverviewAsync`. Скрытия/удаления нет сознательно.

**Правила** (одна строка получает ОДНУ причину — первая сработавшая):
`time_vs_distance` (быстрее мирового рекорда; пороги в `WorldBestMs` ПО ПОЛУ — женские на
5–8% медленнее, и по мужскому порогу женские ошибки проходили), `relay_time_in_individual`
(время отрезка вместо дистанции), `time_outlier` (выброс против медианы своей дисциплины
**в своей возрастной ступени** — см. ниже),
`gender_mismatch` (пол против остальных заплывов пловца), `duplicate_swim` (повтор
дисциплины в один день с разным временем — разные дни это норма, предварительные/финал).
Эстафеты, DSQ/DNS и строки без времени вне скоупа.

⚠ **`time_outlier` считает медиану ПО ВОЗРАСТНОЙ СТУПЕНИ** (`AgeGroup` в ключе группировки),
а не по дисциплине целиком. На детской лиге в одной дисциплине плывут и восьмилетки, и
семнадцатилетние: медиану задают младшие, и победители старшей ступени становятся «выбросами».
2026-08-02 так пометились 25.25 и 26.03 на 50 вольным при медиане 43.53 по всем 93 строкам —
нормальные результаты 17-летних, а третий призёр (26.47) отличался от второго на 0.44 с и
порог прошёл. Правило от сужения не ослабло: ошибка протокола выбивается и внутри ступени.

**Ручные пометки живут дольше автоматических.** Скан перезаписывает только автоматические;
`SuspectIsManual` не трогает — и переимпорт тоже (`ApplyPayloadUpdate` сбрасывает автопометку,
ручную сохраняет). Кнопка «Снять» ставит `SuspectIsManual=true` с пустой причиной, поэтому
повторный скан строку не вернёт. Прогон пишется в аудит (`result.quality-scan`), ручная
правка — `result.quality-manual`; после обоих сбрасывается кэш (рекорды в шапке).

**Замер на реальных данных (2026-07-28):** 5168 результатов трёх соревнований → 2 пометки,
обе — настоящие ошибки протокола, ложных нет. `Shane GOLLAND 00:57.33` на 100 fly НЕ
помечена и осталась национальным рекордом — правильно: её 50 fly 27.83 даёт нормальное
соотношение 2.06.
