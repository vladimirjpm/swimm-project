# /Admin/Competitions — соревнования (справочник БД + входящие isr.org.il)

Файлы: `Pages/Admin/Competitions/Index.cshtml(.cs)`, правая панель — `_CompChecklist.cshtml` +
`CompChecklistView.cs`, быстрая правка — `_CompQuickEdit.cshtml`, превью — `_CompPreview.cshtml`,
`Edit.cshtml(.cs)` (там же удаление); скрипт списка —
`wwwroot/js/admin/competitions-index.js` (Razor-данные `window.__DISC` — inline перед ним). Данные списка —
`ICompetitionAdminRepository.GetUnifiedAsync` (реализация `CompetitionAdminRepository`);
CRUD — тот же репозиторий; каскадное удаление — `IImportService.DeleteCompetition(Event)Async`.
Действия входящих — API `DiscoveryAdminController` (`/api/admin/discovery/*`) + сервисы
`CompetitionDiscoveryService` / `CompetitionDiscoveryBackgroundService`; матч —
`DiscoveryCompetitionMatcher`. DTO — `Dtos/UnifiedCompetitionDtos.cs`, `CompetitionCrudDtos.cs`.

**Объединённый список:** одно соревнование — одна строка со стадией жизненного цикла
(`CompetitionStage`): `OnSite` (на сайте, в БД нет) / `Imported` (есть и там, и там) /
`DbOnly` (только в БД, PDF-импорт без OrgCompId) / `Ignored` (скрыто). Склейка справочника
`Competitions` и входящих `Sys_DiscoveredCompetitions` по `OrgCompId` (+ fallback имя+дата).
Раньше это были две отдельные страницы (Competitions + Discovery) — объединены 2026-07.

**Фильтры:** поиск (имя/подзаголовок; **число** — ещё и compID федерации или Id соревнования в
базе, у события — любого дня: на `?q=<Id>` ведут находки /Admin/Health, 22.11.2026), категория (из /Admin/Categories), **тип** (все /
чемпионат Израиля, `?kind=champ`), **дисциплина** (`?discipline=`, см. ниже), **сезон**
(полосы над списком, не селект — см. ниже), стадия,
чекбокс «показать синтетику» (SYNTH Meet…, по умолчанию скрыта). Сортировка по дате (убыв.),
пагинация 20/стр. (выбран месяц — весь месяц, см. «Состояния строки и адрес»). Merge в памяти (admin-масштаб ~1.5k; при росте — вынести в БД-пагинацию).

**Дисциплина (`?discipline=`).** Федерация проводит не только плавание: во входящих с
isr.org.il ~6% — артистическое (שחייה אומנותית), где нет ни времён, ни дистанций. Дефолт
фильтра — **только плавание**; `all` показывает всё, `artistic`/`other` — конкретную
дисциплину. Скрытые НЕ удаляются: над списком стоит «Скрыто фильтром дисциплины: N» со
ссылкой «показать все».

Признак **хранится** (`Competition.Discipline`, `Sys_DiscoveredCompetitions.Discipline`), а не
угадывается при каждом показе: иначе правило живёт во вьюхе, новая дисциплина требует ещё
одной подстроки в разметке, а промах распознавания нельзя поправить на одной строке.
Проставляется `Disciplines.GuessFromName` при обнаружении и импорте — и только НОВЫМ строкам:
у известных дисциплину мог поправить админ селектом в строке (`POST /api/admin/discovery/{id}/discipline`),
и автозабор это решение не перетирает.

**Сезон = сен–авг, зовётся годом окончания** (2025 = 24/25) — как `cYear` на isr.org.il
(проверено на списке `cYear=2025`: окт-2024 … авг-2025). `CompetitionAdminRepository.SeasonOf`.
Фильтр списка — параметр `?season=` (раньше был `?year=` с календарным годом); применяется
в памяти одним предикатом по дате строки, поэтому одинаково режет и БД-строки, и строки с
сайта. `GetAvailableYearsAsync` (календарные годы) остался только у /AssignRules.

**Сезон и месяц выбираются ПОЛОСАМИ над списком** (вариант E, этап 2, 23.11.2026; раньше — чипы
`25-26 12+2/14 ✓`) — селекта «Сезон» в форме фильтров нет (в форме остался только hidden `season`,
чтобы «Найти» не сбрасывало выбор). **Полоса сезонов:** ячейка на сезон (свежий слева), в конце —
ячейка «Все» (`season=all`, в макете её нет — вопрос Владу), справа строка-итог выбранного сезона
(«Сезон 26-27 · закрыто 24 из 80 · долг 15 · впереди 41»). **Полоса месяцев:** 12 ячеек в порядке
сезона сентябрь → август (`CompetitionRowStateRules.SeasonMonthOrder`), подписи Сен…Авг. Ячейка
(`StripCell` во вьюхе — одна функция на обе полосы): подпись + число строк, полоска из трёх
сегментов (зелёный — закрыто, оранжевый — долг, голубой — впереди; ширина — доля от числа строк,
инлайн `style="width:N%"`, нулевой сегмент не рисуется), под ней ОДНА пометка по приоритету:
«долг N» → «впереди N» → «закрыт» → «нет стартов». Выбранная ячейка — голубая рамка и лёгкая заливка
(`border-admin-accent bg-admin-accent/10`). Клик по выбранному снимает фильтр (сезон → `season=all`,
месяц → без `month`). Полная расшифровка («затянуто X из Y, тянуть нечего у Z, ждёт затягивания N ·
закрыто · долг (ждёт затягивания / ждём протокол) · впереди (из них идёт)») — в `title` ячейки
(`PullHint` + `StatesHint`). Данные — `SeasonCounts[i].States` и `MonthStates[0..11]`
(индекс 0 = январь); ссылки — через `ListRoute()`, параметры не менялись. Смысл — видеть дыры
импорта не заходя в каждый сезон.

**«Тянуть нечего» — отдельное число, иначе счётчик врёт.** Строка, которой нет в БД, не
всегда долг: у части входящих **пустой протокол** (`EmptySourceAt`) или строка **скрыта**
админом (Ignored — решение принято). Сделать с ними нельзя ничего, а «12 из 14» читалось
как «две недотянуты» (живой случай — февраль 2026: 12 затянуто, у двух нет протокола).
Такие идут плюсом, и когда ждать больше нечего — счётчик зеленеет и получает **✓**: месяц
закрыт, возвращаться не надо. Предикат — `CompetitionAdminRepository.IsNothingToPull`,
разметку собирает одна функция `StripCell` во вьюхе (ячейка сезона и ячейка месяца обязаны
выглядеть одинаково).

⚠ **Отсутствие loglig-id «нечего тянуть» НЕ означает** — соблазн большой, и первая версия
на нём и погорела: у 89 строк сезона 2025/26 его нет просто потому, что **детали ещё не
загружались** (грузятся при первом «Затянуть»). С этим правилом апрель 2026 — три
незатянутых соревнования, ни одного загруженного — показывал «0+3/3 ✓», то есть ровно
наоборот. Правильно там «0/3» без галочки. Ошибка забора (`LastError`) — тем более повод
вернуться, а не закрытый вопрос.

Счётчики приходят из `UnifiedCompetitionList.SeasonCounts` (`SeasonCountDto(Season, Total,
Imported)`) и `MonthCounts`/`MonthImported`. Порядок в `GetUnifiedAsync` важен: сезоны
считаются **до** фильтра по сезону (иначе в полосе остался бы один), месяцы — **после** него,
но до фильтра по месяцу. Список сезонов больше не берётся из `GetAvailableSeasonsAsync`:
ячейки строятся по тем же строкам, что и список, так что «пустых» сезонов на них не бывает.

## Состояния строки и адрес (вариант E, этап 1 — 23.11.2026)

Переделка страницы по хэндоффу «вариант E» идёт шестью этапами; этап 1 — фундамент без смены
вида. **Состояние** вычисляется поверх стадии (стадия в данных прежняя) чистой функцией
`CompetitionRowStateRules.Evaluate` (`Swimm.Application/Mapping/CompetitionRowStateRules.cs`),
у каждой строки — `UnifiedCompetitionRowDto.Status` (`CompetitionRowStatus`). Вход —
`CompetitionRowStateInput`: стадия, первый/последний день, вердикт results-auto, «∅»
(`EmptySourceAt`), «не опубликованы» (`LastError` при пустом `LogligId`), видимая отметка
«результаты неполные» (только у строк базы), «✓ имп.» вручную (`MarkedImported`: статус
imported у строки «Входящих», которой в базе нет). Даты — объединение диапазонов базы и сайта:
многодневку тянут по дням (путь Б в [pull-to-prod](../pull-to-prod.md)), в базе лежат только
затянутые дни, и по ним одним старт «кончался» бы на второй день. «Сегодня» — по Израилю, `CompetitionRowStateRules.IsraelToday(TimeProvider)`; часы
приходят в модель страницы инъекцией (`TimeProvider`, зарегистрирован в `Program.cs`).

| Состояние | Условие | Корзина полос |
|---|---|---|
| впереди (`Ahead`) | на сайте, до первого дня (стартовый протокол не влияет) | впереди |
| идёт (`Running`) | на сайте, с первого по последний день включительно; «день N из M» | впереди |
| ждёт затягивания (`ReadyToPull`) | прошёл; вердикт `would-take`, `blocked` («ждёт тебя») или вердикта нет | долг |
| ждём протокол (`WaitingProtocol`) | прошёл; вердикт `not-finished` («неполный»), `empty` («протокола нет»), `failed` («сбой разбора»); без вердикта — «не опубликованы» | долг |
| закрыто (`Closed`) | в базе; скрыто, «∅» или «✓ имп.» вручную (серое, `NothingToPull`) | закрыто |

Вердикт, если есть, сильнее ошибки забора (он свежее). Исключение из «в базе = закрыто»:
затянутое с видимой отметкой «результаты неполные» (Р114) — после последнего дня (по сайту)
это «ждём протокол · неполный» (долг), пока старт идёт — «идёт». **Решение Влада 23.11.2026:
неполный протокол у затянутого — долг**, а не «закрыто», как было в таблице хэндоффа.
**Решение Влада 23.11.2026 (этап 3):** затянутая по дням многодневка БЕЗ отметки «неполные», у
которой последний день по сайту ещё не прошёл, — «идёт» (`Running`, «день N из M», в полосах —
«впереди»); после последнего дня — закрыто. Только у многодневки (`DayCount > 1`): однодневный,
затянутый в день старта, закрыт сразу. **Решение Влада 23.11.2026 (этап 3): пропавшая с сайта**
(`MissingSince`) после даты старта — долг, как и раньше; если её нет на сайте
`CompetitionRowStateRules.MissingSuggestHideDays` (= 7) дней или дольше (считается от
`MissingSince`, по дню Израиля, а НЕ от даты старта) и строка в долге — у статуса
`SuggestHide` и `MissingDays`, в списке пометка «пропал N дн. — скрыть?» вместо «пропал».
Сама ничего не закрывает: скрывает Влад кнопкой «✕» (на этапе 6 — «Скрыть»).
**Решение Влада 23.11.2026 (этап 3): недотянутая многодневка.** Затянутое (`Imported`) без отметки
«неполные», у которого разных дней в базе МЕНЬШЕ, чем дней в диапазоне сайта
(`Site.DateStart..DateEnd`; `CompetitionRowStateRules.ShortOfSiteDays`), после последнего дня по
сайту — «ждём протокол · неполный» (долг), в шапке панели «Затянуто N из M дней по сайту
федерации» (`CompetitionRowStatus.PulledDays` / `SiteDays`). Ложный долг (диапазон сайта длиннее
реального старта) снимается «Принять как есть» на Edit — **без миграции**: принятие хранится как
`PartialResultsAcceptedAt` у дня при ПУСТОЙ `PartialResults` (`CompetitionListItemDto.MissingDaysAccepted`,
у события — любой день). Все прочие читатели `PartialResultsAcceptedAt` (витрина, «Требует
внимания», частичный индекс) смотрят его только вместе с отметкой — для них ничего не меняется.
`PartialResultsRule.Apply` при полном переимпорте дня такое принятие сохраняет; если день
переимпортируют НЕполным — появится обычная отметка Р114, и принимать нужно её. Блок на Edit
(«⏳ Затянуты не все дни», `#missing-days`) — у дня без отметки, когда `ShortOfSiteDays` или уже
принято; «Вернуть в долг» снимает принятие у всех дней события
(`CompetitionAdminRepository.SetMissingDaysAcceptedAsync`; решение Р115 в [data-integrity.md](../data-integrity.md)). Сайт ищется по OrgCompId дней — у
строки, склеенной с «Входящими» только по имени, блока на Edit не будет (на 23.11 таких нет).
На проде 23.11.2026 под правило попали 5 строк: e62 (Эйлат Open 2026, 2 из 3), e6 (Maccabiah 2026,
3 из 6), e28 (עמק חפר 2025, 1 из 2), c1862 (06–07.06.2025, 1 из 2), c1858 (06–07.12.2024, 1 из 2). Тесты —
`CompetitionRowStateRulesTests`, `CompetitionStateCountersTests`. Строка без читаемой даты получает состояние «ждёт
затягивания», но в счётчики сезонов и месяцев **не входит** — её сезон и месяц не определить
(так было и у прежних чипов); в списке без фильтра сезона она видна внизу.

**Счётчики** — ОДИН источник, состояния строк (`CompetitionStateCounts`: Ahead, Running,
ReadyToPull, WaitingProtocol, Closed и часть закрытого `ClosedNothingToPull`; `Debt` = ждёт +
ждём протокол, `AheadTotal` = впереди + идёт). Прежний счётчик чипа «затянуто+нечего/всего»
собирается из них же (`SeasonCountDto.FromStates`: затянуто = `ClosedInDb`, нечего =
`ClosedNothingToPull`), так что сумма на чипе всегда равна «всего»; отдельного предиката
`IsNothingToPull` больше нет. У сезона — `SeasonCountDto.States`
(без фильтров сезона и месяца), у месяцев — `UnifiedCompetitionList.MonthStates` (с сезоном,
без месяца; индекс 0 = январь), у списка — `ListStates` (со всеми фильтрами, кроме `?state=`).
Инварианты: `States.Total == Total`; сумма `MonthStates` = сезон. С этапа 2 выводятся
полосами (см. выше), расшифровка — в `title`. Строки «ждёт затягивания» по
блокам дней (последний день старта, свежий первым) — `IndexModel.ReadyToPullByDay`.

**Адрес.** Прежние параметры не менялись. Новое:
- **голый адрес** → текущий сезон и месяц (`CompetitionListUrl.ShouldOpenOnCurrentMonth`):
  только если в адресе нет ни одного непустого параметра. `q`, `filter`, `stage`, `cat`, `kind`,
  `season` без `month`, `p`… — выборка явная, месяц не подставляется (ссылки Jobs/Health/дашборда
  ищут по всему сезону или по всем). **Фильтры держат месяц, поиск — всегда по всем сезонам**
  (решения Влада 23.11.2026, этап 3): форма фильтров шлёт сезон и месяц под именами `fseason` /
  `fmonth` (`CompetitionListUrl.FormSeasonKey` / `FormMonthKey`), сервер
  (`CompetitionListUrl.FormRedirect`) переадресует на чистый адрес: при непустом `q` сезон и
  месяц выбрасываются (неважно, подставлены они или выбраны явно, после перезагрузки или быстрой
  правки), иначе становятся `season`/`month` — дисциплина, категория, тип, стадия остаются в
  месяце. Работает без JS. Готовые ссылки с `q` и `season` (Jobs «Что изменилось»:
  `?q=…&season=…&discipline=all`) этих имён не несут и открывают то же, что раньше;
- `season=all` — ячейка «Все» (иначе голый адрес вернул бы текущий месяц). С ним же ведут ссылки
  других экранов, которым нужен ВЕСЬ список (решение Влада 23.11.2026,
  `CompetitionListUrl.AllSeasonsHref`): дашборд «Без правила очков» (`dashboard.js`), Health
  «дубль даты у события» (`InvariantDataChecks`), Jobs «Входящие» (`BackgroundJobsStatusService`).
  Сайдбар, `admin-home.html` и ссылка с Import остаются голыми — текущий месяц;
- `state=waiting|ahead|closed` — фильтр по корзине (`CompetitionStateFilters`), комбинируется
  со `stage`, на счётчики не влияет; с этапа 3 — переключатель «Все / Ждут / Впереди / Закрыто»
  над списком;
- `sel=<ключ строки>` — выбранное соревнование (`CompetitionRowKey`: `e{EventId}` / `c{Id}` /
  `s{DiscoveredId}`; `s…` находит и уже затянутую строку). С этапа 3 по нему открывается панель
  справа; запоминание раскрытых строк в `sessionStorage` убрано;
- **пагинация** (`IndexModel.Unpaged`): выбраны сезон И месяц — весь месяц одной страницей, `p`
  не пишется; месяц без сезона (`season=all&month=`, тот же месяц за все годы) и всё остальное —
  `p` по 20.

Все ссылки, формы и редиректы после POST собираются из одного `IndexModel.ListRoute()` —
раньше копий было шесть, и после быстрой правки терялись `discipline` и `filter`.

**Сезоны сайта.** «Проверить сайт федерации» в шапке — текущий сезон (без `cYear`); «Ещё ▾ → Сезон
на сайте → Забрать» — прошлый сезон (`cYear=<год окончания>`: 2025 = 24/25).
Уходит в `POST /api/admin/discovery/sync?year=`, дальше `ICompetitionDiscoveryService.SyncAsync(year)`
→ `FetchListAsync(finished, year)`. Прошлые сезоны — только по кнопке; фон
(`CompetitionDiscoveryBackgroundService`) всегда тянет текущий. Строки прошлых сезонов
попадают в те же «входящие» и импортируются обычным «Затянуть»; после забора страница
сама открывается с `?season=<год>`, чтобы новые строки не тонули в общем списке.

**Перенос / отмена и журнал запусков (часть В, 19.10.2026).** Синхронизация текущего сезона
(кнопка без сезона, фон, `--discovery-sync`) сама помечает будущие старты: сдвинули дату —
`PreviousDateStart` (перенос), пропал из обоих списков сайта — `MissingSince` (отменён);
правила и предохранитель — `DiscoverySyncRules`, решение Р85 в
[data-integrity.md](../data-integrity.md). Строка `#sync-info` под шапкой после проверки дописывает
«перенесено: N, пропало: M», если не ноль. Успешная проверка текущего сезона кнопкой пишет успех
задачи `discovery` в журнал `Sys_JobRuns` — фоновое расписание (ProdAdmin) после этого не идёт на
сайт повторно до следующего интервала. Проверка прошлого сезона и неудачная проверка расписание не
сдвигают — только строка истории с итогом на [/Admin/Jobs](jobs.md) (её пишет и успешная). Пометки
переноса/отмены видны пометками строки списка («перенесён с 14.11», «пропал») и чипами в шапке
панели (решение Влада 22.11.2026, `DateChangeChipsHtml`): «⇄ перенесён с 14.11» (жёлтый, в подсказке
«было → стало») и «✕ пропал с сайта · 20.11»
(красный, вероятно отменён; снова появится на сайте — пометка снимется сама). Их же видно в
календаре `/competitions`.

## Экран страницы (вариант E — итог этапов 1–6, 23.11.2026)

Переделка по хэндоффу «вариант E, чек-лист» закончена шестым этапом. Таблицы и раскрывающейся
панели строки больше нет. Экран сверху вниз:

```
┌ шапка: Competitions · [поиск] [Фильтры · N ▾] · [Проверить сайт федерации] [Ещё ▾] [+ Новое соревнование]
├ жёлтая плашка «Активный фильтр …  сбросить ✕» (только при ?filter=)
├ полоса сезонов + итог выбранного сезона
├ полоса месяцев (Сен → Авг)
└ две колонки: список слева (360–420 px) │ правая панель выбранного соревнования (липкая, своя прокрутка)
```

### Шапка (`Index.cshtml`, `ViewData["OwnHeader"] = true` — своя шапка вместо `_PageHeader`, как у /Admin/Jobs)

- **Поиск** — «Название, ID федерации или № в базе» (число ищется ещё и как compID и как Id
  соревнования, у события — любого дня). Поиск идёт по всем сезонам (решение Влада 23.11.2026, ниже).
- **«Фильтры»** — кнопка рядом с поиском (решение Влада: одной кнопкой). Внутри прежние поля:
  Стадия, Категория, Тип, Дисциплина, «показать синтетику (SYNTH)»; «Скрыто фильтром дисциплины: N
  показать все ↗»; ссылки «results-auto: ждут тебя · взяла бы сама» (предложение хэндоффа); «Найти» и
  «Сброс». Заданный фильтр виден на кнопке: «Фильтры · N» голубым (N — сколько из пяти задано).
  Скрытое дисциплиной продублировано и рядом с кнопкой («скрыто дисциплиной: 24 ↗»), чтобы
  не прятать его в закрытом меню. Выбор в селекте/чекбоксе сразу отправляет форму (как раньше).
  Поиск и фильтры — одна форма `#filters-form`, поэтому «Найти» не сбрасывает фильтры.
- **«Проверить сайт федерации»** — бывшая «Проверить сейчас»: тот же `POST /api/admin/discovery/sync`
  текущего сезона, те же сообщения в строке `#sync-info` под шапкой, потом перезагрузка.
- **«Ещё ▾»** — «Правила очков» (AssignRules), «Перенос результатов» (MoveResults), «Сезон на сайте»:
  селект прошлого сезона + «Забрать» (`sync?year=`; после забора страница открывается с `?season=`).
- **«+ Новое соревнование»** — второстепенной кнопкой (основной цвет отдан затягиванию).
- Инфо-плашка «Одно соревнование — одна строка со стадией…» убрана.

**Выпадающие «Фильтры» и «Ещё ▾» (шапка и панель) — `<details>`** с классами админки
(`admin-btn`, `admin-card`): готового выпадающего меню в админке нет, новый компонент не заводили.
Клик мимо закрывает (`details.page-pop` / `details.ck-more` в `competitions-index.js`).

**Жёлтая плашка** «Активный фильтр «здоровья данных»: … сбросить ✕» — над полосами, как раньше
(`?filter=discovery-error|no-org-comp-id|no-results|autopull-blocked|autopull-would-take`). Алиасы
`?filter=ignored|discovery-new` — это `stage`, плашки у них нет (так было и раньше).

**Ход затягивания и импорта** (`window.pullFlow` в `competitions-index.js`) — статусами и строками
шагов 5–7 в чек-листе своей строки (у события — в общей части панели `.ck-event-flow`, статусы у всех дней; плавающей панели нет с этапа 4).
Тексты — прежней панели «Затягивание». Сервер кладёт статусы на КАЖДУЮ фазу (`none`, `parsing`,
`parse-failed`, `preview`, `preview-expired`, `importing`, `import-failed`, `nothing`) в `data-phases`;
JS только ставит `data-status`. Подпись шага 5 после разбора — «418 результатов · 1 день в файле»,
шага 6 — «осталось: бассейн и 2 рекорда». «Затянуть» / «Перезатянуть» прячутся на время разбора,
превью и импорта. Признак конца импорта — состояние job'а (`GET /api/admin/import/status/{jobId}`,
раз в 1.5 с, потолок 10 мин). После импорта страница перезагружается, строка уже «закрыто», под
шагом 7 — «Итог затягивания»: создано, сверка с файлом (Д1), «сомнительные», прогон проверок (Д5),
«Промежуточные: доклеиваются сами в фоне» → итог доклейки, когда она кончится (раздел «⏱ Промежуточные»).
Строка не видна при фильтрах — итог над панелями (`#pull-elsewhere`).

**Р116 — «тянуть нечего» спокойно (этап 6).** Если разбор ответил «все строки — неявка»
(`NoStartProtocol.Marker`) или настоящий пустой PDF («No competitions found» / «0 lines extracted»),
это не сбой: фаза `nothing`, шаг 5 — ✓ «тянуть нечего: в протоколе одни неявки (NS)» / «тянуть
нечего: протокол пуст» (без «Не удалось разобрать»), чип шапки — «закрыто · тянуть нечего», в
строке списка — «∅ нет протокола». Сервер в этот момент уже поставил `EmptySourceAt`, поэтому после
F5 строка в «Закрыто», а ход из `sessionStorage` сбрасывается. Текст сервера («почему тянуть нечего»)
виден приглушённой строкой у шага 5. **Подсветка (Влад, 23.11.2026):** в фазе `nothing` кнопка
«Нет протокола» в шапке панели (и копия в шаге 5 — она скрыта `.ck-noproto-step` и показывается только
в этом исходе) светится и медленно мигает (`.ck-noproto-pulse`, ~2 с, цвет warning; при
`prefers-reduced-motion` — статичное свечение). Класс вешает `render()` по `flow.phase`, поэтому
снимается сам: клик перезагружает страницу, другая строка (`cancel`) и новое «Затянуть» меняют ход.
После F5 не восстанавливается — ход `nothing` сбрасывается. B4 и прочие исходы не светят.
**«Нет loglig-iframe» (Влад, 24.11.2026).** Если детали comp.asp прочитаны, а iframe на странице нет,
сервер пишет в `LastError` единый текст `DiscoveryErrors.NoLogligIframe`, а DTO строки отдаёт явный признак
`UnifiedSiteInfo.NoLogligIframe` (нет `LogligId` + именно этот текст; сеть, таймаут и разбор
его не включают). Два шага по давности (федерация иногда выкладывает протокол позже), порог —
`NoLogligIframeRules.FinalAfterDays` = 7, ступень считает сервер (`UnifiedSiteInfo.NoLogligIframeFinal`,
от последнего дня старта; у многодневки — после конца; ровно 7 дней — уже вторая ступень):
- **меньше 7 дней** — «Протокола пока нет» (`.ck-noproto-soon`, спокойный цвет), кнопка «Нет протокола» НЕ мигает;
- **7 и больше** — крупная жирная строка warning «Протокола нет и не будет» (`.ck-noproto-never`),
  «Нет протокола» мигает (`.ck-noproto-pulse` + `data-keep-pulse`, `render()` её не снимает) с самого
  открытия карточки, не только после «Затянуть».

В обоих случаях под основной строкой мелко — техпричина (нет loglig-iframe). **«Парсер не распознал ни одного результата… (B4)» — НЕ спокойный
исход** (ревью PR #267): это поломка разбора, красный сбой с «!» и полным текстом. С 23.11.2026
так же считают и сервер (`DiscoveryPreviewService` не ставит `EmptySourceAt` при B4), и пачка
(🔴 «сбой», не ⚪), и автопроверка (`failed` «сбой разбора», не `empty`): после F5 строка остаётся
в долге. Три «пустых» исхода: настоящий пустой PDF (исключение «No competitions found» / «0 lines
extracted») → ∅; одни неявки (`NoStartProtocol.Marker`) → ∅; B4 (PDF есть, строк нет, а
парсер ничего не собрал) → сбой.

**F5 и переключение строк.** Весь ход — в `sessionStorage.pullFlow` (фаза, строки, ответ превью,
выбор в превью, jobId); итог — `pullDone`. Разбор, оборванный перезагрузкой, запускается заново сам;
превью собирается из сохранённого ответа (на сервере живёт 60 минут по `previewId`); опрос импорта
продолжается. Прежний ключ `pullPending` (до этапа 4) больше не читается. Блок превью один на
страницу, JS переносит его в `.ck-preview-slot` видимой области. Начать затягивание другой строки
во время импорта нельзя (alert); **очереди одиночных затягиваний нет** (решение Влада: для
нескольких — пачка). Без `sel` в адресе «Затянуть» ставит адрес ссылки строки (replaceState).

**Быстрая правка** (шаг 6 у одиночной строки базы; у события — блок в общей части): категории, Awards / 🏆 Чемпионат Израиля / Combine / «Клубный
зачёт не ведётся», тип бассейна, клубные очки, High Point → handler `QuickSave` →
`ICompetitionAdminRepository.QuickUpdateAsync`. **Сохранение применяется КО ВСЕМ дням события**
(надпись «сохранение применится ко всем дням события (N)»; регламент у события один, поля лежат у
каждого дня). Внутри — обычный `UpdateAsync` по каждому дню (валидация, синк категорий, пересчёт
объединённых мест, сброс кэша); первая ошибка прекращает цикл. Имя/дата/подзаголовок/страна/OrgCompId
— только на Edit. Редирект после «Сохранить» несёт ВСЕ параметры списка (`ListRoute`: в том числе
`discipline` и `filter`) и `sel` строки — панель открыта и после перезагрузки. Аудит —
`competition.quick-edit`. Под формой — «Регламент (תקנון)» и «Проверить регламент» (раздел ниже).

### Удаление — только на Edit (этап 6)

Кнопок «Удалить» в списке и в панели нет (ни у строки, ни у события, ни у дня). Удаляют на
странице Edit, блок «Опасная зона»:
- «Удалить безвозвратно» — это соревнование (одиночное или ДЕНЬ события), подтверждение точным
  названием (handler `Delete`);
- у дня события ещё «Удалить всё событие» — все дни и сам `CompetitionEvent`, подтверждение точным
  названием события (handler `DeleteEvent` → `IImportService.DeleteCompetitionEventAsync`; раньше эта
  кнопка была только в списке).
Оба пишут аудит (`competition.delete` / `competition.delete-event`, как прежнее «Удалить» в
списке) и возвращают в список по `back=` с теми же фильтрами; `sel` удалённой строки из адреса
убирается (после удаления дня события `sel=e…` остаётся). Обработчиков удаления у `IndexModel`
больше нет.

## Пачки «за день» и «за месяц» (вариант E, этап 5 — 23.11.2026)

**Кто попадает в пачку — одно правило на сервере**: `BulkPullSelection` (Application/Mapping,
тесты `BulkPullSelectionTests`). По нему `IndexModel` считает `MonthBulk` и `DayBulk`, а
разметка кладёт в кнопку готовые id для обоих положений чекбокса (`data-ids` — без чемпионатов,
`data-ids-all` — с ними). JS только выбирает набор по чекбоксу и отправляет его как есть; по
видимым строкам он ничего не собирает. N на кнопке = длина этого набора = число строк, ушедших в
`BulkPullService.StartAsync`.

- Берутся строки списка (уже под всеми фильтрами страницы: сезон, месяц, дисциплина, поиск…) в
  состоянии **«ждёт затягивания», которых нет в базе**. Никогда: «ждём протокол», «идёт»,
  «впереди», закрытые и недотянутая многодневка Р115 (она «ждёт затягивания», но дни в базе).
  Чемпионаты Израиля (по названию, `CompetitionNameRules.IsChampionship` — то же правило, что
  у сервиса) — только при «включая чемпионаты». Порядок — дата начала от ранней.
- **«Затянуть за месяц (N)»** — только когда выбраны сезон и месяц (`season=Y&month=M`, месяц виден
  целиком). Прочие фильтры (дисциплина, `filter=`, `stage`, `state`) сужают выборку — кнопка берёт
  отфильтрованное подмножество месяца, число на ней честное. Без месяца сезона (поиск — он идёт по
  всем сезонам, весь сезон, `season=all`) кнопки месяца нет; кнопки
  **«за день»** тогда есть, только если весь список на одной странице (иначе блок дня на странице мог
  быть неполным). Кнопки «за сезон» нет (решение Влада).
- Чекбокс «включая чемпионаты» стоит под кнопкой месяца и меняет N у неё и у всех кнопок дней.
  Ноль — кнопки нет; день, где ждёт только чемпионат, — приглушённое «чемпионат — отдельно».
- **Потолок** `BulkPullLimits.MaxBatchSize` = 30 не поднят: в месяце до ~25 строк. Если под кнопку
  попадает больше, кнопка берёт 30 самых ранних и рядом пишет «ещё K — следующим заходом».
  Сервер больше не обрезает молча: больше 30 id — 400 от `bulk-pull` и исключение в `StartAsync`.
- **Сервер перепроверяет каждую присланную строку тем же правилом на момент клика**
  (`BulkPullService.StartAsync` → `ICompetitionAdminRepository.GetUnifiedAsync` без фильтров страницы,
  `state=waiting`, сегодня по Израилю → `BulkPullSelection.IsCandidate`). Вкладка могла простоять час:
  отсекаются скрытые, «✓ имп.», «∅», затянутые (связаны с базой), перенесённые в «впереди», идущие,
  с вердиктом results-auto «не закончено» / «пусто» / «сбой». Они уходят в `skippedNotReady` статуса,
  панель пишет «на кнопке N, в пачке M · K уже не ждут затягивания — пропущены» (имена — в подсказке).
  Новых строк перепроверка не добавляет. Тесты — `Service_RechecksEachRow_WithTheSameRule`.

**Пачка в правой панели** (`#panel-bulk.row-panel` в `#comp-detail`) — вместо чек-листа.
Содержимое прежней карточки: шапка (+ подпись «За день · Пт 20.11 · на кнопке 3, в пачке 3»),
строка хода, таблица с флагами 🟢🟠🟡⚪🔴, «Импортировать отмеченные», «Снять все без регламента»,
«Закрыть». Клик по строке списка возвращает её чек-лист — пачка на сервере идёт дальше; вернуться —
строкой `#bulk-strip` над списком: «Идёт пачка: 3 из 8 → показать», «Пачка: импорт 2 из 5 →
показать», «Пачка готова: 8 → показать». Строки пачки помечены в списке: «в пачке», «пачка:
тяну…», «🟢 в пачке», «импорт…», «✓ импорт».

**F5.** В `sessionStorage`: `admin-bulk-pull-batch` (batchId), `admin-bulk-pull-meta` (что было на
кнопке), `admin-bulk-pull-shown` (пачка была открыта справа). После перезагрузки пачка снова
открыта справа или видна строкой над списком; опрос продолжается. Пачка висит, пока её не
закроют, — в том числе готовая (раньше отработанная сбрасывалась молча). Статус пачки теперь несёт
`queueIds` — id строк пачки, по ним помечается список.

**С одиночным «Затянуть» (`pullFlow`).** Пока пачка тянет или импортирует — одиночное
«Затянуть»/«Перезатянуть» погашено везде с подсказкой, `pullFlow.start` отказывает alert'ом. Пока
готовая пачка открыта — погашено у её строк, которые ещё можно импортировать из неё (иначе один
старт ушёл бы в импорт дважды). Наоборот: пока идёт одиночный разбор, превью или импорт, кнопки
пачек погашены, а клик — alert «Сначала закончи одиночное затягивание…».

**После импорта.** Когда импорт отмеченных доработал, страница перезагружается сама (один раз) —
строки уходят в «закрыто» или «ждём протокол · неполный»; пачка после перезагрузки на месте с
флагом «✓ Импорт завершён». Если в очередь не ушло ничего (`queued = 0`), перезагрузки нет.

**Что переживает F5 и автоперезагрузку** (`sessionStorage.admin-bulk-pull-state`, ревью PR #266):
- галочки, которые трогали руками (и «Снять все без регламента»): снятое не возвращается;
- после первого импорта из пачки оставшиеся строки по умолчанию СНЯТЫ — их сознательно оставили;
- итог «Импортировать отмеченные»: сколько ушло и что не ушло с причиной («длина бассейна не
  определена…», «разбор истёк…») — показывается в панели и после перезагрузки;
- когда строка впервые пришла затянутой: через 60 минут её разбор на сервере истёк — строка
  «⌛ разбор истёк — затяни заново», галочку не поставить, одиночное «Затянуть» для неё не запрещено.

**Замки на время без ответа сервера.** С клика по кнопке пачки до ответа `POST bulk-pull` гаснут ВСЕ
кнопки пачек (и одиночное «Затянуть»); после F5 до ответа `GET bulk-pull/{id}` пачка считается идущей,
строка над списком — «Пачка: проверяю состояние на сервере…». Опрос забывает пачку только на 404
(пачки нет — перезапуск API); обрыв сети или 502 — «Связь с сервером потеряна… пробую ещё», запреты
остаются.

**Решения Влада 23.11.2026 по вопросам PR #266** — все «оставить как сделано»:
1. возврат к пачке — строкой над списком («Идёт пачка: 3 из 7 → показать» / «Пачка готова: 7 → показать»);
2. готовая пачка висит, пока не нажмут «Закрыть» (и после F5, и после импорта);
3. кнопки «за день» без выбранного месяца — только если весь список на одной странице;
4. новая пачка поверх открытой, где есть неимпортированные строки, — через подтверждение. Без `sel` в адресе «Затянуть» ставит адрес ссылки строки
(replaceState): F5 и итог импорта возвращаются к ней, а не к автовыбору.

## Превью, пометки и флаги

**Пометка «∅ нет протокола».** У части соревнований на isr.org.il PDF пустой — страница без
единой строки текста, парсер отдаёт «No competitions found in PDF». Это НЕ сбой, который стоит
повторить, а факт «тянуть нечего», поэтому поле отдельное (`DiscoveredCompetition.EmptySourceAt`),
а не `LastError`. Ставится **автоматически** при разборе, который ничего не нашёл, и **снимается
автоматически**, если протокол потом появился (файл могут выложить позже). Плюс кнопка в панели —
«Нет протокола» / «Протокол есть» (`POST /api/admin/discovery/{id}/empty-source`). Без пометки
строка выглядит обычной «новой», и «Затянуть» жмут по кругу — живой случай: OrgCompId 4561,
«ליגת הפועל נוער ובוגרים 3».

**Протокол из одних неявок — тоже «∅ нет протокола»** (23.11.2026, Р116 в `docs/data-integrity.md`).
Соревнование, которое не провели или по которому не внесли результаты, loglig экспортирует
списком заявок с «NS» у каждого. Разбор при этом «удаётся», и раньше строка висела с бейджем
«превью» в «ждёт затягивания»: живой случай — compID 14676 «ליגה בוגרים 2 -קיץ 2025» (13.06.2025),
273 строки NS, ни одного времени; в таблице дисциплин loglig «סה"כ משתתפים» = 0 у всех 10.
Теперь `DiscoveryPreviewService` после разбора проверяет `NoStartProtocol.AllNoStart` (неявка —
`StartStatus.IsNoStart`: NS/DNS; DQ и DNF — стартовал) и, если стартов нет ни одного, ставит
`EmptySourceAt` («auto») и отвечает ошибкой «…все строки — неявка (NS/DNS)…». Пачка и авто-забор
читают её как `Empty` (`BulkPullClassifier`), авто-забор перепроверяет через 6 ч; хоть одно
время в файле при следующем «Затянуть» снимет пометку само. Скрывать («Скрыть», Ignored) — решение
человека, автоматически не делается.

В чек-листе этот ответ разбора — спокойный исход (раздел «Экран страницы», «Р116 — тянуть нечего спокойно»).

**«Перезатянуть»** (у уже импортированных): то же превью, но галка «перезаписать существующее»
взводится сразу, если превью нашло соревнование в базе (`existingCompetitionId`) — протоколы на
сайте правят, да и наш парсер чинится, старым разбором остаются испорченные строки; «удалять
лишние» не трогаем, это отдельное решение. Соревнование в базе превью ищет тем же правилом, что импорт
(Р118, [data-integrity.md](../data-integrity.md)): «имя + дата + бассейн», при промахе — день того же
compID по дате. До 23.11.2026 превью смотрело только имя+дату+бассейн: у c1973 (compID 16926) бассейн в
базе 50m, а парсер без бассейна в протоколе даёт 25m — превью «не находило» соревнование, перезапись не
взводилась, а импорт находил день по compID и откатывался «Дубль: … уже содержит результаты». Теперь у
уже затянутого `existingCompetitionId` есть, и в `existingCompetitions` по каждому дню файла видно, найден
ли он. Если имя и compID указали на разные соревнования или на дату приходится несколько дней, — строка
«⚠ …» в предупреждениях превью. **Бассейн** обязателен, если в файле есть хоть один НОВЫЙ день (подсказка
«в файле есть новый день — выбери бассейн»): выбранный бассейн получает только новый день, существующие
дни свой сохраняют; файл целиком из существующих дней бассейна не требует. Пачка такие строки отдаёт
«вручную» («соревнование уже в БД — нужно решение о перезаписи»), а не падает «Дублем».

**Свёрнутый протокол (Р119, [data-integrity.md](../data-integrity.md)).** loglig у многодневки
печатает всем строкам ПОСЛЕДНЮЮ дату диапазона (И-60), такие события тянут по дням (путь Б), и потом
«Затянуть» / «Перезатянуть весь протокол события» положили бы те же строки ещё одним днём. Если в файле
одна дата, а у этого compID в базе есть дни с результатами и другими датами, и файл покрывает их строки
(≥ 90%), — превью показывает красный блок «⛔ Протокол свёрнут в одну дату: … уже есть дни … (всего N — те
же результаты)…», **«Импортировать» погашена**, подпись шага 6 — «импорт заблокирован».
Сервер такой импорт откатывает тем же текстом (`JsonImportService`), пачка и results-auto относят строку к
ручной проверке. **Обход (решение Влада 23.11):** в красном блоке галочка «Я проверил — импортировать всё
равно» — для ложного блока (например, «свои» дни события на деле — соседний compID без штампа, окружные
e1/e7/e10/e12). Текст рядом предупреждает: все строки лягут в день с датой файла, а если дни уже
затянуты — дубль. Отмеченная галочка включает «Импортировать» (подпись шага 6 — «⚠ обход Р119 отмечен»; день файла новый —
снова нужен бассейн, подсказка у поля возвращается),
запрос уходит с `allowCollapsedProtocol: true`; сервер принимает его, только если у этого превью блок был.
F5 и новое превью галочку сбрасывают. Обход пишется в аудит (`competition.import-collapsed-override`) и
строкой «⚠ Р119 обход» в журнал импорта. В пачке, results-auto и CLI `--repull` обхода нет (`--repull
--dry-run` предупреждает, что настоящий откажет). Живой случай — e62 «אליפות אילת
הפתוחה 2026» (compID 16891): 1579 строк датой 07/11 = 766 + 813 дней 05.11 и 06.11. Её «Затянуто 2 из 3
дней» — ложный долг (третьего дня не было): «Принять как есть» на Edit дня; «Перезатянуть» остаётся
заблокированным и после этого. Файл на `/Admin/Import` (путь Б) compID не несёт — проверка там не
срабатывает. «Синхр. языки» дозаполняет EN-имена из EN-протокола без
переимпорта. Все действия входящих дёргают `/api/admin/discovery/*`; после мутаций страница
перезагружается. Имена discovery-строк для JS — через `window.__DISC` (id→name), не onclick
(экранирование иврита/кавычек).

**Официальный клубный зачёт в превью.** Затягивая соревнование, сервер попутно спрашивает
loglig, опубликован ли там «דירוג מועדונים», и если да — снимает фактическую шкалу очков и ищет
среди `PointRulesClubs` правило с ровно такой шкалой. В превью появляется блок «Клубные очки»:

- **зелёный** — зачёт есть, шкала опознана, правило подставлено в селект (менять можно);
- **жёлтый** — зачёт есть, а правила под его шкалу нет: завести на `/Admin/PointsRules` ДО
  импорта, иначе соревнование уедет на автоподбор и получит чужие очки;
- **серый** — зачёта нет (лиги, мокдамот, региональные этапы) либо проверить не удалось.

Если шкала новая, под жёлтым блоком появляется **«Завести правило по этой шкале»**: имя версии
предзаполнено по конвенции (`9pt.8pl.2026`), рядом показана сама шкала. Кнопка, а НЕ галочка
«создать автоматически» — шкалу снимает эвристика, и админ должен увидеть, что именно заводит:
у «גביע האביב 2026» регламент вдобавок содержал условие сверх шкалы (в зачёт идут только два
быстрейших от клуба), которого машине не видно. Правило создаётся `ManualOnly` с
`RelayMultiplier = 2` и сразу подставляется в селект. Шкалу сервер берёт из своего кэша превью,
а не из тела запроса (`POST /api/admin/discovery/club-rule` принимает только `previewId` и имя
версии), запись идёт в аудит `pointrule.create`.

Выбранное правило уезжает в импорт (`pointRuleClubsId` в `POST /api/admin/discovery/import`) —
раньше импорт из входящих всегда молча уходил на автоподбор. Результат проверки сохраняется в
`Competition.HasOfficialClubStanding` (true/false/null = не проверяли) — его же ставит фоновый
импорт и разовый прогон `dotnet run -- --probe-club-standings [--force]`. Признак — НЕ наличие
кнопки на loglig (она в шаблоне у всех), а непустая таблица; подробности в
`docs/points-rules-per-competition-plan.md` §10.8.

**«Чемпионат Израиля» — РУЧНОЙ ФЛАГ** `Competition.IsChampionship` (галка «🏆 Чемпионат
Израиля» на Edit, рядом с Awards; миграция `AddCompetitionIsChampionship`). Он источник
истины для всего: фильтр «Тип», кубок в строке списка и в шапке панели, бейдж флагов, `is_championship`
в `/api/competitions` → 🏆 и тумблер «Championships» в селекторе на клиенте, кубок в плитке.
У многодневного события флаг = «помечен хотя бы один день».

**«⏱ Есть промежуточные» — флаг `Competition.HasSplits`** (галка на Edit рядом с 🏆; миграция
`AddCompetitionHasSplits`, 19.09.2026). Ставит **доклейка промежуточных** (ниже) тем дням,
где промежуточные появились; сам он не снимается. Быстрая правка из списка его не трогает —
это факт данных дня, а не регламента события. Сам импорт промежуточные НЕ пишет
(решение Влада 20.09.2026, [../relays.md](../relays.md), «Промежуточные эстафет») — их сразу за
импортом доклеивает отдельный шаг (решение Влада 23.11.2026, раздел ниже).

## «⏱ Промежуточные» — доклейка без переимпорта

### Сама после импорта (решение Влада 23.11.2026)

После импорта, который **что-то записал** (`ImportPostStepRules.Succeeded`: создал или обновил
строки) и знает compID, `ImportBackgroundService` ставит задачу во вторую очередь — «шаги
loglig»: сперва промежуточные (`ISplitAutoAttachService` → тот же `ISplitAttachService`, что у
кнопки, боевым прогоном), потом штамповка loglig-id. Друг от друга шаги не зависят: доклейка
сопоставляет по дисциплине, времени и году рождения, loglig-id пловца ей не нужен; промежуточные
первыми — их видно на сайте и их итог ждёт шаг 9.

- **Тумблер** `SplitAttachOnImport` в `/Admin/Settings` (по умолчанию включён) — по образцу
  `LogligStampOnImport`.
- **За ними, своей очередью, — игрок loglig у строки** (Р122, 24.11.2026): когда доклейки и
  штамповки ВСЕЙ пачки закончены и импортов в очереди нет (шаг игроков одного старта не
  задерживает промежуточные следующего), `LogligRowPlayerService` обходит страницы дисциплин и пишет `Results.LogligPlayerId` строкам,
  совпавшим однозначно по заплыву, дорожке и времени. На странице его итога нет — он в журнале
  (`competition.loglig-row-players`), а находки — в `/Admin/Health`, «Два игрока loglig на одной
  карточке». Тумблер `LogligRowPlayersOnImport` (по умолчанию включён, перечитывается в начале
  шага — выключает и уже поставленные); ~2 с на страницу: старт в 20 дисциплин — ~40 с, чемпионат
  в 150–250 — 5–8,5 мин; читает не дольше 20 мин (прочитанное записывается), потолок 25 мин. Прошлые старты — CLI `--stamp-row-players <compID>`.
- **Последним во второй очереди — пол с карточек loglig** (Р125/Р126, 25.11.2026): пловцам этого импорта, у кого
  пол пуст (плыли только смешанные заплывы), а loglig-id подтверждён, `LogligCardGenderService`
  берёт пол с карточки loglig — при совпавших имени и годе (заплыв как доказательство личности не нужен с Р127, 25.11.2026). Проставленный пол не трогает; случаи с
  серьёзными последствиями (рекорд, место, медаль, очки, топ) не пишет — они уходят в находку
  «Пол с loglig ждёт ручной проверки» (`/Admin/Health`). Запрос на пловца с паузой 1 с, не больше 40
  на импорт (обычно таких пловцов единицы), потолок 5 мин; карточка, открытая за сутки, берётся из
  `Sys_SwimmerLogligClubs` без сети. Итог — в логе задачи («проставлен N; ждут ручной проверки — M»)
  и строками аудита `swimmer.gender-from-loglig`. Тумблер `LogligGenderOnImport` (по умолчанию ВЫКЛЮЧЕН — решение Влада
  25.11.2026: включить после независимого ревью расчёта последствий):
  перечитывается в начале шага и останавливает уже поставленные; включение ПОСЛЕ постановки шага
  его не запустит — остаток и старые находки добираются кнопкой в `/Admin/Health`.
- **Нагрузка.** У второй очереди один читатель: на loglig всегда идёт один старт за раз, запросы
  внутри старта — тоже по одному (дисциплина за дисциплиной). Импорт следующей задачи пачки шагов
  loglig не ждёт — пачка из 30 не удлиняется на время доклейки, а loglig не получает шквала.
  Потолок одной доклейки — 15 минут (`SplitAutoAttachRules.Timeout`), дальше — «не удалось»
  («прервано: … дольше своего потолка»); таймаут ОДНОГО запроса к loglig пишется иначе — «loglig не
  ответил вовремя (таймаут запроса)».
- ⚠ **Очередь шагов loglig — в памяти процесса**, как и сама очередь импорта: после перезапуска API
  не начатые доклейки пачки теряются (импорт уже лёг) — у таких дней шаг 9 без итога, повтор кнопкой.
- **Сбой или таймаут** итог импорта не меняют (задача уже `Completed`): строка в журнале процесса,
  «не удалось — повторите кнопкой» у шага 9 и «!» у его кружка. Сюда же — источник, прочитанный
  не целиком (`SplitSource.Incomplete`: личные промежуточные упали на 504 loglig), если ничего не
  записано: пустой ответ тогда значит «не знаем», а не «промежуточных нет» (пойман вживую 23.11.2026
  на compID 16917 — первый прогон записал «нет», повтор через минуту прочитал 27 дисциплин). Если
  что-то записано, а часть источника не прочиталась (эстафеты легли, личные — 504), исход
  **«частично — … повторите кнопкой»** (`partial`): тоже «!» и красная подпись, у всех дней прогона.
- **Сбой посреди записи не оставляет полдоклейки.** Запись — одна транзакция; если она сорвалась
  (потолок, остановка, ошибка базы), трекер контекста чистится ДО записи аудита
  (`ChangeTracker.Clear()`), иначе `SaveChanges` аудита дописал бы часть ног и `HasSplits`. У доклейки и
  штамповки loglig-id — свои scope и свой `DbContext` (тест `WriteFailure_LeavesDatabaseUntouched…`).
- **Дни — только этого compID** (`ISplitAttachService.AttachAsync(..., onlyDays)`), один прогон на
  событие; LogligId — тоже по этим дням. В окружных чемпионатах дни одного события — разные compID и
  разные турниры loglig: в локальной базе на 23.11 таких событий четыре — e1 (16786/16789), e7
  (16745/16837), e10 (14678/14679), e12 (6598/6599); прогон по всему событию взял бы LogligId соседнего
  дня и записал своему «нового нет». Кнопка по-прежнему идёт по всем дням события.
- **Перезатягивание того же старта во время доклейки.** Upsert импорта пересоздаёт ноги эстафет
  (`ApplyRelayUpdate`: старые `RelayMembers` удаляются, новые вставляются без `SplitTime`). Доклейка,
  идущая параллельно, в удалённые ноги не пишет: запись перечитывает ноги по Id, исчезнувшие просто не
  находятся; если удаление попало между чтением и `SaveChanges`, запись падает (0 строк обновлено) —
  чисто, итог «не удалось». В обоих случаях новые ноги остаются без промежуточных недолго: перезалив
  ставит свою доклейку в ту же очередь ПОСЛЕ текущей, и она их дописывает.
- **Не запускается:** импорт отказал или ничего не записал («Дубль», Р119, пустой JSON, откат на
  ошибках строк) — тогда не выполняется и ни один другой пост-шаг (статус «imported» строке
  входящих, проба клубного зачёта, loglig-id); файл с `/Admin/Import` без compID; тумблер выключен.
- **Аудит.** Каждому дню прогона — строка `competition.attach-splits` (тот же код, что у кнопки),
  актор **`auto:import`**, в `DetailsJson` — `Trigger: "import"`, `Kind`
  (`attached` / `partial` / `none-on-loglig` / `nothing-new` / `failed`), счётчики дня, полный отчёт,
  `Extra.JobId`, `Extra.OrgCompId`. Пишется ВСЕГДА, в том числе «нечего» и «не удалось». Боевой прогон
  кнопки с 23.11.2026 пишет так же — всегда и каждому дню события (`Trigger: "button"`, актор — email
  админа), иначе после ручного повтора у остальных дней застревало бы «не удалось» автозапуска. CLI
  `--attach-splits` аудит не пишет, как и раньше.

**Шаг 9 — откуда итог.** Подпись шага (`SplitAutoAttachRules.Caption`) берётся по порядку:
1. доклейка этого compID ещё идёт — «промежуточные доклеиваются сами после импорта…» (очередь
   импорта в памяти процесса, `ImportJobStatus.Splits`); страница перезагружается по `Completed`
   импорта, когда доклейка за ним ещё качает loglig, поэтому JS (`watchSplits`) опрашивает тот же
   `GET /api/admin/import/status/{jobId}` (поле `splits`) и меняет подпись шага 9 и строку «Итога
   затягивания» (шаг 7) без перезагрузки;
2. последняя строка аудита `competition.attach-splits` дня (`ISplitAttachJournal`) — «промежуточные:
   доклеено: личных 340, ног эстафет 48 · само после импорта 23.11 14:05» / «на loglig промежуточных
   нет» / «нового нет: уже стоят или не сопоставились» / «частично — … повторите кнопкой» и «не удалось —
   повторите кнопкой» (красным, «!»,
   полный отчёт — в подсказке); у ручного прогона — «· вручную»;
3. флаг `HasSplits` — «промежуточные есть»;
4. иначе прежнее «Синхр. языки · Loglig-id · Промежуточные».

Почему аудит, а не флаг или журнал задачи: `HasSplits` знает только «есть», а не «искали — нет» и
«сорвалось»; очередь импорта живёт в памяти и пустеет при перезапуске; новая колонка у дня —
миграция ради одной подписи, а аудит уже хранит кто, когда и что вышло.

### Кнопка

Кнопка «Промежуточные» остаётся — для повтора и стартов, импортированных до 23.11.2026. Она —
шаг 9 чек-листа (у события — у выбранного дня, по его Id), есть только у строк, у которых
в базе уже есть результаты: операция ничего не создаёт и не удаляет, она дописывает два поля
(`RelayMembers.SplitTime`, `Results.TimeSplit`) к СУЩЕСТВУЮЩИМ строкам.

- **первый клик — всегда сухой прогон**, ничего не пишется; «Применить» появляется только
  если есть что писать. Повторный прогон пишет 0 — операция идемпотентна;
- отчёт печатается целиком (команд в источнике / доклеено / без ног / неоднозначно; по личным —
  то же) **с разбивкой по дням события**: прогон идёт по ВСЕМ дням, какой бы день ни открыли.
  Своей «Сверки с файлом» у операции нет, поэтому отчёт — единственный контроль;
- **«loglig id»** рядом с кнопками нужен только стартам без строки «входящих» (склейки из
  окружных, старый импорт из JSON) — остальным номер находится сам;
- ⚠ **идёт минуты**: источник качается по одной дисциплине (у соревнования 1581 это 115
  запросов, ~2.5 минуты). Фонового job'а, как у «Затянуть», здесь нет — вкладку не закрывать.

API — `POST /api/admin/splits/{competitionId}?apply=&loglig=` (`SplitsAdminController`),
внутри тот же `ISplitAttachService`, что и у CLI-флага `--attach-splits`, — правило живёт в
одном месте. Боевой прогон идёт через `ISplitAutoAttachService.AttachByButtonAsync`: аудит
`competition.attach-splits` — всегда и каждому дню события (раздел выше); сухой прогон в аудит не
идёт. Зачем это отдельная операция, а не переимпорт: переимпорт ради промежуточных
задваивает соревнование, когда старые строки импортированы иначе (1581: 3561 лишняя строка) —
[../data-integrity.md](../data-integrity.md), И-28, и
[../plans/splits-attach-without-repull-plan.md](../plans/splits-attach-without-repull-plan.md).

**Эвристика по названию осталась в двух местах** (`CompetitionAdminRepository.IsChampionship`):
одноразовый бэкфилл в миграции (13 из 21 соревнования на 2026-07-29) и строки «только на
сайте», которых в БД ещё нет — флага там взять негде. Для строк, которые в БД есть, эвристика
НЕ применяется: снятая руками галка не должна возвращаться сама. Правило эвристики:
«אליפות» И «ישראל» в имени (или английские championship + israel). Слова проверяются
ПО ОТДЕЛЬНОСТИ, а не подстрокой: между ними бывает вставлен спонсор — «אליפות "ארנה" ישראל»,
«אליפות arena ישראל» (подстрока дала бы 39 из 42). Клубные/городские «אליפות מכבי»,
«אליפות חדרה» сюда не попадают — в этом и смысл; отборочные «מוקדמות אליפות … ישראל»
попадают (часть того же чемпионата). Отдельного признака в исходных данных нет: у входящих
с сайта, кроме имени и даты, ничего нет, а категории (Kids/Youth/Masters…) — про возраст,
не про ранг. Поэтому и понадобился ручной флаг.

Строка списка несёт готовое `UnifiedCompetitionRowDto.IsChampionship` (кубок слева от
названия) — вьюха ничего не пересчитывает. **На клиенте** —
[`competition-source.ts`](../../client/src/utils/helpers/competition-source.ts):
`isChampionshipSource` читает `is_championship` с сервера и падает на `isChampionshipName`
(та же эвристика) только там, где флага в объекте нет.

**Состояние списка живёт в URL.** Любой выбор в фильтрах сразу сабмитит форму (JS на `change`
у `#filters-form`), пустые поля из query выкидываются — так «назад» в браузере возвращает
предыдущую выборку. Ссылки «Изменить» / «Изменить день N» несут `back=<url списка с фильтрами, страницей и sel>`;
Edit возвращает по нему из «← К списку» и после сохранения/удаления (`EditModel.BackLink`; после удаления `sel` удалённой строки снимается,
проверка `Url.IsLocalUrl` — открытый редирект отбивается, чужой URL → просто /Admin/Competitions).
`back` протаскивается через все POST-хендлеры формы (`asp-route-back`), иначе после первого
сохранения он бы потерялся.

**CRUD справочника:** «Изменить» (Edit-страница — многодневные события/EventId, PoolType,
IsMasters/IsAward, страна, категории, URL результатов, «Опасная зона»: удалить день / одиночное и
«Удалить всё событие» — каскад с подтверждением названием), «+ Новое соревнование». Эталон CRUD для новых админ-страниц.

## Роль в клубном зачёте (K6)

Селект **«Роль в клубном зачёте»** (`Competition.StandingKindOverride`, nullable) — ручное
переопределение того, каким чемпионатом соревнование считается на **странице клуба**
(грид «сезон × группа», карточка Standings, бейдж ❄/☀ в истории).

**По умолчанию «Авто» — и почти всегда так и надо оставлять.** Роль выводится сама:

```
🏆 Чемпионат + бассейн 25м → ❄ зимний
🏆 Чемпионат + бассейн 50м → ☀ летний
не чемпионат              → в зачёт не идёт (но в истории клуба виден)
```

Правило проверено на всех 23 чемпионатах в БД (2026-08-01): 12 в 25м — январь/февраль,
11 в 50м — июль/август, исключений нет. Подпись у пункта «Авто» показывает, что именно
выведется при текущих флагах. Поле заведено под случаи вне правила — прежде всего
**открытую воду**, где бассейна нет вовсе; значение `none` явно исключает соревнование
из зачёта.

⚠ **Зачёт образуют только категории возрастной лестницы** (`Category.ReservedKeys`).
Кастомные (`result-maccabiah` и будущие) — «соревнование само по себе», зачёта по ним нет.
Старт, висящий в ДВУХ категориях лестницы, даёт два зачёта — по строке на группу.

⚠ **Двух зимних (или двух летних) чемпионатов одной группы за сезон быть не может.**
Уникальным индексом это не выразить (сезон производен от даты, группа лежит в M:N),
поэтому проверка живёт в дашборде: метрика **«Дубль клубного зачёта»**. Ненулевое
значение означает ошибку в `IsChampionship`/`PoolType` конкретного соревнования — чинить
надо там, а не в зачёте. Пропуск (чемпионат отменили) — штатный случай, не ошибка.

Модель целиком — [../plans/club-page-model.md](../plans/club-page-model.md) §2.1.

## Привязка правил очков (Э4)

В форме соревнования — два селекта, **Клубные очки** и **High Point**
(`Competition.PointRuleClubsId` / `PointRuleSwimmersId`, оба nullable). Значение по
умолчанию — «Авто (по дате и типу)»: правило подбирает `CompetitionRuleResolver`, но
только среди правил **без** флага `ManualOnly`. Список правил — /Admin/PointsRules
([pointsrules.md](pointsrules.md)).

- **Правило хранится у каждого дня отдельно**, а регламент у многодневного события один →
  на Edit есть кнопка «Проставить правила всем дням события» (handler `ApplyRulesToEvent`).
  Она сохраняет ТОЛЬКО правила; остальные поля формы при этом не пишутся.
- **Массовая простановка** — отдельная страница `/Admin/Competitions/AssignRules`
  (`AssignRules.cshtml(.cs)`), в стиле MoveResults: фильтры (сезон / masters / только без
  привязки) → отметить строки → выбрать правила → применить. Список — по дням, а не по
  свёрнутым событиям; синтетика (SYNTH…) скрыта.
- У каждого поля выбор из трёх состояний: **не менять** / **Авто** (снять привязку) /
  конкретное правило. `null` — легитимное значение, поэтому «менять или нет» вынесено в
  отдельный флаг `SetClubs`/`SetSwimmers` (`CompetitionRuleAssignmentDto`), а не кодируется
  через null.
- Несуществующий Id правила отбивается валидацией (`ValidateRuleIdsAsync`) — иначе FK
  RESTRICT дал бы 500. После простановки сбрасывается кэш; аудит — `competition.assign-rules`.

### «Клубный зачёт не ведётся» (решение Р19)

Галочка `Competition.ClubPointsDisabled` — в форме соревнования (блок правил очков) и в
быстрой правке строки списка (там применяется ко всем дням события, как остальные флаги).

Смысл — отличить **«правило не нужно»** от **«правило забыли привязать»**: в БД оба
выглядели как `PointRuleClubsId = null`, и проверка реестра `competitions.no-club-point-rule`
([health.md](health.md)) звала чинить лиги и товарищеские старты наравне с настоящими
пропусками. Помеченные соревнования из находок исчезают.

⚠ Это **пометка, а не выключатель**: на расчёт очков (Top Clubs, таб Clubs, сезонный зачёт)
она сознательно не влияет — это отдельное решение, меняющее цифры на публичных страницах.
Зато она (вместе с `HasOfficialClubStanding = false`) включает на витрине серый чип
**«Unofficial»** везде, где видны клубные очки старта (Overview, Clubs, Swims, страница
клуба): очки остаются, но подписаны как наша оценка
(Р80, [competition-overview-cards.md](../competition-overview-cards.md) → Top clubs).
Если флаг `HasOfficialClubStanding` у соревнования `null` (loglig не проверялся), чип
появится только с этой галочкой. **Привязка правила очков вручную чип снимает** — шкала тогда
из регламента, а не наша оценка (решение 08.10.2026).
У события флаг показывается как «не ведётся», только если помечены ВСЕ его дни.

## Проблемы старта: значок, фильтр «С ошибками», блок «Что не так» (24.11.2026)

Зачем: ошибка Health по старту была видна только в Health и в итоге затягивания — в списке строка
выглядела обычной «закрытой» (живой случай: `results.merged-sessions` по c1895, 24.11.2026).
**Только вид**: проверки, состояния строк, долг сезонов и месяцев не меняются; автообновлений нет.

**Одно правило** — `CompetitionProblemRules` (`Swimm.Application/Mapping`, тесты
`CompetitionProblemRulesTests`, `CompetitionProblemsListTests`). Причины по порядку: открытая
ошибка Health (Severity 2) → предупреждение (1) → сомнительные строки «⚑» → «неполный» (видимая
отметка Р114 или `PulledDays/SiteDays` статуса — Р115) → промежуточные не доклеились
(`SplitAutoAttachRules.NeedsRetry` последней доклейки хоть одного дня). Значок, фильтр и блок
берут условие отсюда, своего не держат.

**Что считает значок** («✕ N» красный — ошибки, «⚠ N» жёлтый — предупреждения; в `title` —
«Название проверки — N» по строке, с пометкой «по записанным находкам»): открытые
(`Resolution IS NULL`) находки `Sys_DataCheckFindings` с Severity Warning/Error. Принятые и Info не
считаются. У события — сумма по дням плюс находки самого события (`CompetitionProblemRules.Merge`).
Названия проверок — из реестра `IDataCheck` (нет — id). Какие `EntityType` относятся к старту
(сверено по `Services/DataChecks/*` 24.11.2026):

| EntityType | Как привязан к строке | Проверки |
|---|---|---|
| `Competition` | EntityId = Id соревнования (дня) | `results.merged-sessions`, `results.official-club-points-mismatch`, `competitions.empty`, `competitions.no-club-point-rule`, `import.reconciliation-mismatch`, `entries.no-show-unmatched`, `series.*` |
| `Result` | Results.Id → CompetitionId (по `PK_Results`) | `results.no-gender`, `results.exact-duplicate`, `results.fk-anomaly`, `results.relay-distance-without-relay`, `results.upsert-key-collision`, `relays.gender-conflict` |
| `Relay` | Relays.Id → строка эстафеты `Results.RelayId` → CompetitionId (по `IX_Results_RelayId`) | `relays.empty` |
| `CompetitionEvent` | EntityId = EventId → строка события | `competitions.duplicate-day` |
| **не считаются:** `Swimmer` | пловец плывёт во многих стартах — одна находка зажгла бы значок у каждого | `swimmers.*`, `results.gender-vs-card` (пишет по пловцу) |
| **не считаются:** `Club`, `Country`, `Check` | не про старт (`Check` — упавшая проверка) | `clubs.*`, `countries.duplicate` |

Новая проверка с новым `EntityType` в значок не попадёт, пока его не добавят в
`CompetitionAdminRepository.OpenHealthRows` и в эту таблицу.

⚠ **Только записанные находки.** Почти каждая проверка пишет не больше 50 находок (`.Take(50)`),
полное число — в `Sys_DataCheckStates.Total`. Старт, чья находка не попала в срез, остаётся без
значка и вне фильтра. Поэтому при `?filter=problems` над списком строка на каждую срезанную
проверку, у которой бывают находки про старт: «проверка «…» усечена: записано N из M — список
может быть неполным» (`LoadTruncatedChecksAsync`, `UnifiedCompetitionList.TruncatedChecks`).
Полное решение — агрегат по CompetitionId без среза прямо в проверке — отдельная задача, не сделано.

**Запрос** — `CompetitionAdminRepository.LoadHealthCountsAsync` поверх `OpenHealthRows`: один на
весь список, без N+1, `UNION ALL` четырёх веток + `GROUP BY (событие?, владелец, CheckId,
Severity)`. План (локальная база, 24.11): каждая ветка входит через частичный индекс
`IX_Sys_DataCheckFindings_Open`, строка `Results` достаётся по `PK_Results` (ветка `Result`) или
`IX_Results_RelayId` (ветка `Relay`) — Nested Loop, одна выборка на находку, `Results` целиком не
читается: цена растёт с числом открытых находок, а не строк результатов (0.9 мс на 42 находках).
Трансляция проверена на Postgres тестом `CompetitionProblemsPgTests`. Тексты находок для блока —
тот же `OpenHealthRows`, суженный до строк страницы (`ANY(@ids)`), до 8 на строку.

**Журнал доклеек** (аудит `competition.attach-splits`) читается ОДИН раз за показ: репозиторий
читает его для строк страницы (при фильтре — для всех) и отдаёт странице (`UnifiedCompetitionList.
SplitNotes`) для подписи шага 9 — второго запроса нет. Берётся только последняя строка на день
(`max(Id)` по EntityId, потом эти строки с JSON) — вся история с `DetailsJson` не тянется
(`SplitAttachJournal.LatestAsync`). **Служебные вызовы** (`BulkPullService` — отбор пачки)
передают `decorate: false`: ни находок, ни журнала, ни срезов.

**Промежуточные — одно правило** `SplitAutoAttachRules.DayNeedsRetry(note, pending)`: последняя
доклейка дня не удалась или частичная, И она не идёт прямо сейчас (compID дня в очереди импорта —
страница передаёт `splitsPendingOrgCompIds` в репозиторий). По нему `Row.SplitsNeedRetry`
(фильтр, значок, блок) и «!» шага 9 — пока доклейка идёт, строки нет ни в фильтре, ни в блоке.

**Фильтр «С ошибками»** = `?filter=problems` — пункт в меню «Фильтры» (решение Влада 23.11:
«фильтры — одной кнопкой»), рядом с ссылками results-auto. Это фильтр «здоровья данных», как
`discovery-error` и прочие: жёлтая плашка «Активный фильтр … сбросить ✕», **по всем сезонам**
(ссылка без `season`/`month`, как поиск), пагинация по 20, комбинируется с «Ждут / Впереди /
Закрыто». Полосы сезонов и месяцев при нём считают только проблемные строки (так у всех `?filter=`).
У строки, попавшей в фильтр без своей пометки, — чип «⏳» (неполный вне «ждём протокол · неполный»,
например Р114 у идущего старта) или «⏱» (промежуточные не доклеились).

**Блок «Что не так»** — в шапке карточки справа, под категориями (`_CompChecklist.cshtml`,
`.ck-problems`): находки Health строками (текст, «в Health ↗» на `/Admin/Health#check-<id
проверки>` — группа раскрывается и прокручивается, `health.js`; «чинить ↗» — `Link` находки, только относительный путь админки: `CompetitionProblemRules.AdminLinkOrNull`),
«и ещё N — в Health ↗», если находок больше 8; «⚑ сомнительных строк: N» + кнопка «Качество»;
«неполный: …» + «Принять как есть ↗» (одинаковый текст Р115 у всех дней — один раз);
«промежуточные: не доклеились — повторите кнопкой «Промежуточные» (шаг 9)» — по
`Row.SplitsNeedRetry`, то же правило, что у фильтра. Нет причин — блока нет. Скриншоты — `docs/design-briefs/admin-competitions/problems-*.png`.

**«Неполный — чего не хватает»** (просьба Влада 24.11.2026: «ждём протокол · неполный — а чего не
хватает?»). Пункт «⏳» блока «Что не так» объясняет без наведения мыши — `IncompleteExplanationRules`
(Application, тесты `IncompleteExplanationRulesTests`):
- **Р115** (затянуты не все дни): «По сайту федерации старт идёт 22–23.12.2023 (2 дня). В базе есть:
  22.12 (1337 строк). Нет: 23.12.» Даты — диапазон сайта (`Site.DateStart..DateEnd`) против дат дней в
  базе со строками. Ниже две подсказки: почему так бывает (день ещё не выложен; федерация держит дни
  разными соревнованиями на loglig, а на странице федерации привязан один; протокол всех дней свёрнут
  в один день — Р119) и что делать («Перезатянуть» — только если на странице федерации появился
  протокол этого дня; дня не будет — «Принять как есть»). Подпись шага 5 дописывает «— нет 23.12».
- **Р114** (в протоколе дисциплины без времён): «В протоколе 2 из 16 дисциплин без результатов (в
  последнем заплыве нет времён):» и список дисциплин с причиной, «и ещё N». Разбирается текст отметки
  (`CompetitionProgressSummary.PendingLines`: заголовок «ждут N из M событий», первые 3, «и ещё K») —
  поимённо известны только первые три. Текст не того вида — показывается как есть. У события — по
  каждому дню, с подписью «День N · дд.мм:».

Живой случай Р115, где «Перезатянуть» бесполезен: **compID 488** («הזדמנות אחרונה 2023», 22–23.12.2023,
на проде). Пятница и суббота на loglig — два разных соревнования: 9816 (пятница) и 9817 (суббота).
К странице федерации привязано только 9816, поэтому перезатягивание снова приносит одну пятницу, а
суббота из протокола федерации не придёт (сведения о 9816/9817 — от Влада, 24.11.2026). В локальной базе 488 не затянут; вживую объяснение проверено на e62 (Р115)
и c1936 (Р114), скриншоты `problems-5-incomplete-explained.png`, `problems-6-partial-protocol.png`.

### «Проверить, чего не хватает» — вердикт по программе loglig и кнопки решения (Р123, 25.11.2026)

Просьба Влада («может добавить кнопку решение? … посмотрел глазами и нажал кнопку, что оба дня
есть»). У пункта Р115 (есть даты, которых нет в базе, и у строки есть discovery) — кнопка
**«Проверить, чего не хватает»**. Сеть только по клику: ни открытие карточки, ни загрузка списка
loglig не трогают.

- **Эндпоинты** — `ProgrammeCheckAdminController`: `POST api/admin/programme-check/{discoveryId}/check`
  и `…/split`, оба `[AutoValidateAntiforgeryToken]` (заголовок `X-XSRF-TOKEN`, как у остальных
  действий страницы). Сервис — `IProgrammeCheckService` → `ProgrammeCheckService` (Infrastructure):
  даты федерации и loglig-id — из строки входящих, дни в базе — `CompetitionIdentity.ResolveDaysAsync`

  «клубный зачёт не ведётся», категории, правило клубных очков (личных — уходит в импорт молча, как

  общее название», по умолчанию `LogligTitleRules.CommonName` (без дня недели, дат и висящих тире, с

  привязанного и соседа заново с loglig (2 запроса) — кандидат по-прежнему годится; под шлюзом —

  сверка, она строже: по строкам, а не по количеству.

- **Пути сбоя (ревью PR #284, 25.11.2026).** Завершение (`CompleteAsync`) не бросает: любой исход —
  строка аудита и текст для человека. Импорт ничего не записал или задача упала — «⚠ Не получилось:
  результаты 07.12 не записаны (…)» (`ImportFailedAsync` снимает и замок «день затягивается»). Новый
  день ищется ДО сбора, и шаги loglig по нему планируются при любом исходе сбора. Сбор упал до записи —

## «Результаты неполные» и «Принять как есть» (Р114, 22.11.2026)

Импорт (любой путь) считает по разобранному протоколу каждого дня, все ли события проплыты, —
тем же правилом, что results-auto «ещё идёт» (`CompetitionProgress`: событие проплыто, если в
последнем заплыве есть время; строки с отметкой судьи DNS/DQ/DNF в этом не участвуют, а секция из одних таких строк проплыта — Р120; «NS» отметкой не считается: так loglig печатает невнесённый результат). Не все → у дня отметка `Competitions.PartialResults` с текстом
«ждут 2 из 16 событий; <событие>: ещё не плыли (0 из 9 со временем)». Полный протокол при
повторном импорте снимает её сам. Решение и тонкости — [data-integrity.md](../data-integrity.md) Р114.

- **Чип в списке** — «⏳ неполные» рядом с названием (у события — «⏳ неполные: N дн.», у дня — ⏳ в строке
  дней панели и «!» у его шага 5); текст в `title`. Виден, пока отметка стоит и не принята.
- **Edit** — блок «⏳ Результаты неполные» над формой (якорь `#partial-results`, туда ведёт строка
  «Требует внимания» с `/Admin/Jobs`): что ждёт, когда найдено, кнопка **«Принять как есть —
  остального не будет»** (своя форма, остальные поля не трогает; аудит `competition.partial-accept`).
  После неё блок серый «✓ Неполные — принято как есть» с кнопкой «Вернуть отметку»
  (`competition.partial-unaccept`). Принятие держится, пока повторный импорт приносит ТОТ ЖЕ
  неполный протокол (тот же текст); другой неполный возвращает отметку, полный снимает всё.
- **На сайте** то же самое — чип «⏳ Partial results» с подсказкой по-английски (шапка
  соревнования, селектор, календарь). Принятие убирает его сразу: сохранение идёт через EF, и
  перехватчик сбрасывает кэш витрины по строке `Competitions` сам.
- Отметку руками не ставят и текст не правят — только импорт.

## results-auto: чип, причина и фильтр (П5, 20.11.2026)

Фоновая задача `results-auto` ([jobs.md](jobs.md), план
[prod-auto-pull-plan.md](../plans/prod-auto-pull-plan.md) «П5 — ход») в режиме `report` смотрит
прошедшие строки «Входящих» и пишет им вердикт — **сама ничего не импортирует**.

- **Чип** у строки «на сайте» (рядом с бейджем SL, `AutoPullChipHtml` в `Index.cshtml`):
  `auto: взяла бы сама · 25m` (зелёный), `auto: ждёт тебя` (жёлтый), `auto: ещё идёт` /
  `auto: протокола нет` (серый), `auto: сбой разбора` (красный). В `title` — когда проверяла и
  причина. У «ждёт тебя» причина ещё и строкой под названием («auto: бассейн не задан: …»).
- **Фильтр** — ссылки «results-auto: ждут тебя · взяла бы сама» над списком и блок дашборда:
  `?filter=autopull-blocked` (не затянуто и вердикт `blocked`) и `?filter=autopull-would-take`
  (вердикт `would-take` при любой стадии — после ручного затягивания строку видно для сверки
  с тем, что взяла бы задача). Константы — `AutoPullFilters`, предикат — `GetUnifiedAsync`.
- Поля — `Sys_DiscoveredCompetitions.AutoPull*` (миграция `AddDiscoveredAutoPullVerdict`),
  в `UnifiedSiteInfo` их кладёт `CompetitionAdminRepository.GetUnifiedAsync`.

## Кнопка «Качество» — проверка достоверности результатов

Кнопка **«Качество»** — шаг 8 чек-листа, у строк с результатами (одиночное → `competitionId`; у
события с этапа 6 — по выбранному дню, тоже `competitionId`); рядом бейдж «⚑ N» / «✓», «⚑ N» ещё и

**С 29.09.2026 скан запускается сам после каждого импорта и переимпорта** (по событию целиком
или по дню без события; итог — строкой «Качество: …» в логе импорта; Р70,
`docs/plans/import-quality-autoscan-plan.md`). Кнопка остаётся для повторного прогона и ручных
пометок. Без автоскана переимпорт сбрасывал автопометки: 1512 после переимпорта 19.09 месяц
показывал «лучшим заплывом» отсечку 50 м вместо финиша на 400 в/с (117 333 очка). Помеченные
строки не участвуют в рекордах, Best swim и High Point (Р69). Для однодневки есть и CLI:
`dotnet run -- --quality-scan <competitionId> --competition`.

### Пометить сомнительным прямо в превью импорта

В превью затягивания у блока «Файл побьёт рекордов: N» **у каждого заплыва — галочка
«пометить заплыв сомнительным»**. Отмеченная строка ложится в БД **сразу с РУЧНОЙ
пометкой** (`SuspectIsManual=true`, `SuspectReason=manual`) и в детекцию рекордов не идёт.

**Как выглядит и как на неё ссылаться (26.11.2026).** Это оранжевая кнопка-тумблер
`label.btn-mark-suspect` (`admin-btn admin-btn-warning btn-mark-suspect`, разметка — в
`renderRecordPreview`, `wwwroot/js/admin/competitions-index.js`; вид — в `Styles/admin.css`).
Отмеченная — залита оранжевым целиком. Внутри остался настоящий чекбокс `.suspect-flag`:
его читают `captureForm` (выбор переживает F5) и «Применить», поэтому `<button>` из неё не
делали. Раньше это был серый текст с галочкой, и под красным вердиктом loglig его не замечали.
Общие типы кнопок админки: `admin-btn` + один из `admin-btn-primary` (голубая заливка),
`admin-btn-ghost` (контур, серый текст), `admin-btn-danger` (красный), `admin-btn-warning`
(оранжевый, появился с этой кнопкой).

**Зачем.** Между импортом и ручным прогоном «Качество» ошибочный заплыв успевает побыть
национальным рекордом на витрине, а автоскан ловит такое не всегда. Живой случай
(OrgCompId 16769, 06.02.2026): 200 баттерфляй за 02:04.41 — на 5 с быстрее рекорда
взрослых, при том что у той же пловчихи в том же протоколе 200 комплекс 2:47.91.
`time_vs_distance` молчит (мировой рекорд 2:01.81 быстрее), `personal_outlier` тоже —
ему нужно 3 её старта в окне ±120 дней, а есть два. То есть автоматика тут бессильна
по построению, и единственный шанс — человек, который уже смотрит на этот экран.

**Как адресуется строка.** У неё ещё нет Id в БД, поэтому адрес — порядковый номер в
разобранном файле (`ImportRecordPreviewRow.RowIndex`, он же `RecordCandidateRow.ResultId`
в превью). Сопоставлять по имени и времени было бы гаданием: бывают тёзки и одинаковые
времена. Выбор уезжает в `POST /api/admin/discovery/import` (`suspectFlags`), оттуда
`ImportPayloadSuspectFlags.Apply` проставляет строкам payload'а поле `suspect_note` — и
дальше обычный импорт. Очередь и фоновый обработчик об этом ничего не знают.

**Заметка пишется сама** («02:04.41 быстрее Open record 02:09.69 קרן זיבנר») — пометка без
причины через полгода неотличима от случайного клика. Один заплыв, бьющий два рекорда
(open + возрастной), — это две строки превью с одним `RowIndex`: галочка у них общая,
помечается заплыв, а не «рекорд». Итог виден в панели затягивания строкой «Помечено
сомнительными: N», и `ImportResult.SuspectFlagged` его же несёт.

**Штатный ложный случай — под списком висит подсказка.** Когда тянем протокол ТОГО САМОГО
старта, на котором рекорд и был установлен, заплыв «бьёт» запись справочника, потому что это
она и есть (время равное или на сотые лучше — федерация округляет). Сверить имя и время в
скобках, галочку не жать. Без подсказки это читается как ошибка разбора.

⚠ При **переимпорте** галочка перекрывает прежнее состояние строки: это новое решение
человека, принятое сейчас. Отсутствие галочки чужую ручную пометку НЕ снимает — снять
можно только кнопкой «Снять» в модале «Качество».

**Бейдж состояния в строке.** Рядом с кнопкой «⚑ Качество» — три состояния, и «не
проверялось» это отдельное состояние, а не «всё чисто»: <span>⚑ N</span> оранжевым, если
есть помеченные строки; ✓ зелёным с датой прогона, если проверка была и не нашла ничего;
пусто, если не проверяли — иначе список создавал бы ложное успокоение. Отметка о прогоне
живёт в `Competition.QualityScannedAt` (ставит `ScanAsync` по всему скоупу). У шапки
многодневного события ✓ появляется, только когда проверены ВСЕ дни, и показывает самый
старый прогон.

**Ручная пометка (поиск в модале).** Автоматика ловит только нарушения порогов, а ошибка
протокола бывает внутри них: 200 вольным за 1:53.09 у пловца со стольником 1:05.05 рекорда
не бьёт, ни одно правило не срабатывает — так не плавают, и видит это только человек.
Поэтому в модале есть поиск по имени/клубу/времени/дистанции (`GET /api/admin/suspect-results/search`)
и кнопка «Пометить» с обязательной заметкой: пометка без причины через полгода неотличима
от случайного клика. До 2026-08-03 такого входа не было вовсе — модал показывал только уже
помеченные строки, и пометить «тихую» ошибку было нечем.
API — `SuspectResultsAdminController` (`/api/admin/suspect-results`), сервис
`SuspectResultService`, правила — чистая функция `SuspectResultDetector`, коды причин —
`Swimm.Domain.SuspectReasons`. Поля в `Results`: `SuspectReason` / `SuspectIsManual` /
`SuspectNote` (миграция `AddResultSuspectReason`, частичный индекс по непустым).

**Зачем.** Проверка ищет ошибки САМОГО протокола — то, что не лечится ни парсером, ни
переимпортом. Эталон: Маккабиада 2026, `100m Butterfly - Women` — у Elisa MOSHKOVITCH
напечатано 00:32.59 (её же полтинник 27.27), у Ophir RAKAH 00:53.42 (её двухсотка 2:17.37,
что несовместимо), и организаторы посчитали из этих времён 4702 и 1067 очков. Такие заплывы
«бьют» национальные рекорды в шапке соревнования.

**Что делает пометка.** Строка остаётся в результатах (заплыв был, время в протоколе есть),
но исключается из детекции рекордов — фильтр `SuspectReason == null` в
`ResultRepository.GetOverviewAsync`. Скрытия/удаления нет сознательно.

**Правила** (одна строка получает ОДНУ причину — первая сработавшая):
`time_vs_distance` (быстрее мирового рекорда; пороги в `WorldBestMs` ПО ПОЛУ — женские на
5–8% медленнее, и по мужскому порогу женские ошибки проходили), `relay_time_in_individual`
(время отрезка вместо дистанции), `time_outlier` (выброс против медианы своей дисциплины
**в своей возрастной ступени** — см. ниже),
`gender_mismatch` (пол против карточки пловца; при незаполненной карточке — против остальных его заплывов этого соревнования), `duplicate_swim` (повтор
дисциплины в один день с разным временем — разные дни это норма, предварительные/финал),
`seed_time_jump` (минимум две дорожки одного заплыва на 13%+ быстрее заявочного времени при
сиде от 250 очков FINA — сбой хронометража заплыва, И-55/Р87 в `docs/data-integrity.md`),
`personal_outlier` (вдвое больше очков FINA, чем личный лучший за ±120 дней — см. ниже).
Эстафеты, DSQ/DNS и строки без времени вне скоупа.

⚠ **`seed_time_jump` видит заявки только после сшивки** (`CompetitionEntries.ResultId`). На
импорте сшивка идёт перед сканом сама; если стартовый протокол затянули ПОСЛЕ протокола
(`--stitch-start-list`), нажмите «Проверить качество» ещё раз.

⚠ **`personal_outlier` — единственное правило, которому нужна история пловца** за пределами
соревнования: её подаёт `SuspectResultService` отдельным запросом, детектор остаётся чистой
функцией. Ловит то, что внутри порогов остальных правил: 200 вольным за 1:53.09 у пловца со
стольником 1:05.05 рекорда не бьёт и от медианы ступени недалеко, но так не плавают.
Порог 2.0 против ЛУЧШЕГО личного (не медианы) в окне ±120 дней при минимум 3 своих стартах —
калибровка и цифры в `docs/data-integrity.md` §12: по медиане с порогом 1.4 правило дало бы
1528 находок, принятый вариант даёт 5 на всю базу.

⚠ **`time_outlier` считает медиану ПО ВОЗРАСТНОЙ СТУПЕНИ** (`AgeGroup` в ключе группировки),
а не по дисциплине целиком. На детской лиге в одной дисциплине плывут и восьмилетки, и
семнадцатилетние: медиану задают младшие, и победители старшей ступени становятся «выбросами».
2026-08-02 так пометились 25.25 и 26.03 на 50 вольным при медиане 43.53 по всем 93 строкам —
нормальные результаты 17-летних, а третий призёр (26.47) отличался от второго на 0.44 с и
порог прошёл. Правило от сужения не ослабло: ошибка протокола выбивается и внутри ступени.

⚠ **Оба «временных» правила требуют ОТРЫВА, а не просто отличия от статистики** (калибровка
2026-08-23, решения Р40/Р41 в `docs/data-integrity.md` §9):

- `time_outlier` — кроме медианы ступени (0.6) время должно быть быстрее 0.55 от **ближайшего
  результата** ступени. В детских лигах разброс двукратный (9-10 лет, 50 вольным: 46.89 …
  1:41.14 при медиане 1:18.31), поэтому лидер ступени всегда ниже 60% медианы — просто потому,
  что умеет плавать. По одной медиане правило дало 11 пометок на всю базу, настоящая ошибка
  среди них одна, и ту ловит `time_vs_distance`; в одном заплыве метились ЧЕТЫРЕ девочки.
- `personal_outlier` — не ставится, если время **подтверждено собственным заплывом**: не
  медленнее 0.9 от лучшего соседа по `Heat` (при ≥3 соседях). Специализацию правило принимало
  за ошибку: мастерс 1977 г.р. проплыл 50 вольным 31.95 (256 очков) при своих 50 баттерфляем
  41.06 (82) и 100 вольным 1:17.46 (74) — и выиграл свой заплыв у соседей 32.84 / 34.47 / 35.17.

Общее у обеих поправок: опора проверки — заплыв, то, что видели судьи. Настоящая ошибка
протокола изолирована и в нём (01:53.09 на 200 вольным при ближайшем соседе 02:28.82).

**Ручные пометки живут дольше автоматических.** Скан перезаписывает только автоматические;
`SuspectIsManual` не трогает — и переимпорт тоже (`ApplyPayloadUpdate` сбрасывает автопометку,
ручную сохраняет). Кнопка «Снять» ставит `SuspectIsManual=true` с пустой причиной, поэтому
повторный скан строку не вернёт. Прогон пишется в аудит (`result.quality-scan`), ручная
правка — `result.quality-manual`; после обоих сбрасывается кэш (рекорды в шапке).

**Замер на реальных данных (2026-07-28):** 5168 результатов трёх соревнований → 2 пометки,
обе — настоящие ошибки протокола, ложных нет. `Shane GOLLAND 00:57.33` на 100 fly НЕ
помечена и осталась национальным рекордом — правильно: её 50 fly 27.83 даёт нормальное
соотношение 2.06.

## Регламент соревнования (תקנון) — галочки по PDF (2026-08-22)

В шаге 6 чек-листа, под быстрой правкой, — поле «Регламент (PDF)» и кнопка
«Проверить регламент». Файл **никуда не сохраняется**: сервер читает его
(`POST /api/admin/competitions/analyze-regulation`, `RegulationAnalyzer` в `Swimm.Parsing`)
и возвращает находки, по которым панель сама проставляет галочки:

| нашли в регламенте | что делаем |
|---|---|
| медали (`מדליות`, `מדלית`…) | ставим **Awards** |
| командный зачёт (`ניקוד קבוצתי`, `דירוג הקבוצות`…) | снимаем **«Клубный зачёт не ведётся»** |
| `אליפות ישראל` | ставим **🏆 Чемпионат Израиля** |

Сохраняет по-прежнему кнопка «Сохранить» — анализатор ничего не пишет в БД сам. Рядом с
галочками показываются **цитаты** из регламента, по которым принято решение: регламент чужой
документ произвольной формы, и админ должен видеть основание.

**Две ловушки, ради которых это написано именно так:**

- Иврит в PDF федерации извлекается **задом наперёд**, поэтому каждое слово ищется в обоих
  направлениях, а цитата перед показом разворачивается.
- Клубный зачёт в регламентах называется **командным** (`ניקוד קבוצתי`), а не «клубным»
  (`דירוג מועדונים`), как на loglig — искать формулировку loglig бесполезно. Слова идут с
  артиклями («הניקוד הקבוצתי»), поэтому маркеры — регулярки, а не подстроки. Плюс извлечение
  рвёт слова пробелами («מדליו ת»), это тоже учтено.

**Где лежит регламент (уточнено 2026-08-23).** На сайте федерации его действительно нет —
ни на `comp.asp`, ни в `documents.asp` (там только уставные документы). Но он есть **на
loglig**: на странице соревнования `LeagueTable/AthleticsDisciplines/{logligId}` стоит ссылка
`<a href="/LeagueTable/ShowLeagueDoc/{docId}">תקנון</a>` — рядом с кнопкой `דירוג מועדונים`,
отдаёт `application/pdf` (проверено на docId 2502). Ссылка есть не у всех стартов.

**Автозабор (2026-08-23).** Ссылку вынимает `LogligClient.GetRegulationAsync` — регуляркой
по разметке той же страницы, что уже читается ради клубного зачёта, — и скачивает PDF;
разбирает его существующий `IRegulationAnalyzer`. Связывает их `IRegulationFetchService`;
своего парсера регламента там НЕТ, и заводить его не надо. Цена — один дополнительный GET
страницы соревнования (клубный зачёт и регламент запрашиваются независимо, каждый в своём
потоке); шесть строк ради экономии одного запроса того не стоили.

Кнопка «Проверить регламент» теперь работает **без файла**: если поле пустое, панель зовёт
`POST /api/admin/discovery/regulation` (`{orgCompId}` или `{discoveredId}`) и тянет регламент
сама, а рядом с находками показывает ссылку на найденный PDF. Файл остаётся запасным входом
(`AnalyzeRegulation([FromForm] IFormFile)`) — для стартов без ссылки и тех, кого нет во
«входящих» (PDF-импорт: loglig-id взять неоткуда).

Тесты — `RegulationAnalyzerTests` (на реальных строках регламентов Маккаби-2026 и
чемпионата Израиля 2026, в перевёрнутом виде) + живой прогон по настоящим PDF под
`SWIMM_LOCAL_PDF=1`.


## Пакетное затягивание (2026-08-23)

Одна кнопка вместо двадцати нажатий «Затянуть». План и решения — в
[`../plans/bulk-pull-plan.md`](../plans/bulk-pull-plan.md); здесь — что где лежит.

**Где.** С 23.11.2026 (вариант E, этап 5) — кнопки «за день» / «за месяц» и пачка в правой панели,
раздел выше; абзац ниже — как было до этого. В строке итога под чипами месяцев (`Всего: 20 · месяц: Nov`) — чекбокс
**«включая чемпионаты»** (по умолчанию ВЫКЛ) и кнопка **«⏬ Затянуть все незатянутые (N)»**.
Кандидаты берутся из строк ТЕКУЩЕЙ СТРАНИЦЫ списка в состоянии **«ждёт затягивания»**
(с 23.11.2026; раньше — все не в БД, не скрытые и без «∅», включая будущие): месяц теперь
показывается целиком, и впереди / идёт / ждём протокол в пачку не идут. Число на кнопке — ровно
то, что уйдёт: без чемпионатов, пока не отмечено «включая чемпионаты» (чекбокс переключает
готовые списки `data-ids-no-champ` / `data-ids-all` и число), и не больше
`BulkPullLimits.MaxBatchSize` (30, тот же предел у `BulkPullService`), от ранней даты. Результат — раскрывающаяся панель под той же строкой (не модал:
забор идёт минутами, из него надо уметь уйти и вернуться).

**Как.** `POST /api/admin/discovery/bulk-pull` `{ids, includeChampionships}` → `batchId`;
панель поллит `GET …/bulk-pull/{batchId}` раз в 2 секунды; `batchId` лежит в `sessionStorage`,
поэтому перезагрузка страницы пачку не теряет. Строки обрабатываются **последовательно** —
параллелить значит долбить loglig; за раз берётся не больше `BulkPullService.MaxBatchSize`
(30). Состояние пачки живёт в памяти процесса: перезапуск приложения её теряет.

**Затягивание одной строки — общий код с одиночной кнопкой.** Логика переехала из контроллера
в `IDiscoveryPreviewService` (`DiscoveryPreviewService`), и обе кнопки зовут его. Там же
живут отложенные разборы: TTL поднят с 15 до **60 минут** — в пачке первый разбор не должен
протухнуть, пока тянется последний.

**Вердикт строки** считает `BulkPullClassifier` — чистая функция, ни сети, ни БД
(тесты `BulkPullClassifierTests`, по кейсу на правило):

| Признак | Флаг | В автоимпорт |
|---|---|---|
| Забор/разбор упал | 🔴 ошибка | нет |
| Протокол пуст (`No competitions found`) | ⚪ нечего тянуть | нет |
| Бьёт **хоть один** рекорд | 🟡 нужна проверка | нет |
| Уже есть в БД | 🟡 нужна проверка (перезапись) | нет |
| В файле > 1 дня | 🟡 нужна проверка (событие) | нет |
| Зачёт есть, правила под шкалу нет | 🟡 нужна проверка | нет |
| Есть `warnings` парсера | 🟡 нужна проверка | нет |
| Регламент не найден | 🟠 без регламента | **да**, отмечена — можно снять |
| Ничего из перечисленного | 🟢 беспроблемная | да |

Правила, которые легко потерять при правках:

- **Рекорд — всегда руками, порога нет.** Настоящий рекорд редок; пачка не тот режим, где
  его стоит проглядеть.
- **Клубный зачёт — два источника, они не взаимозаменяемы.** Галочку «зачёт ведётся» даёт
  регламент, а правило очков — только фактическая шкала с loglig
  (`IOfficialClubStandingService.ProbeAsync`). Не совпала ни с одним правилом → строка
  проблемная: иначе соревнование уедет на автоподбор по дате и получит чужую шкалу.
- **Если в одиночном превью появится новый вопрос к админу, его надо добавить и в
  классификатор** — иначе пачка молча ответит за человека.

**Импорт.** `POST …/bulk-import` `{batchId, ids}` — по отмеченным строкам тот же
`IImportJobQueue.Enqueue`, что и у одиночного пути; дальше всё видно в /Admin/ImportHistory.
Жёстко: категория всем одна — **`results-8-99`**; `OverwriteExisting` и `DeleteMissing`
**никогда** не ставятся (массового удаления результатов одной кнопкой не даём, «Перезатянуть»
остаётся одиночным). Медали из регламента доносятся до импорта через `is_award` в payload
(`ImportPayloadAwardFlag`) — тем же приёмом, каким туда попадают пометки «сомнительный».
Кнопка «Снять все без регламента» снимает разом все 🟠.

**После импорта.** Строка, ушедшая в очередь, получает в статусе пачки `queued = true`
(`BatchState.QueuedJobs`: строка → задача очереди) и больше не предлагается к импорту: её разбор
уже отдан очереди и удалён, повторно импортировать нечем. При загрузке страницы пачка из
`sessionStorage` показывается снова, только если из неё ещё есть что импортировать или импорт
ещё идёт; отработанная сбрасывается молча (до 23.11.2026; с этапа 5 пачка висит, пока её не закроют, —
отмеченные строки после импорта уже погашены, «свежей» она не выглядит). Раньше она всплывала после каждой перезагрузки с
отмеченными строками и выглядела предложением затянуть уже импортированное (06.10.2026).

**Ход импорта и флаг окончания (08.10.2026).** «Импортировать отмеченные» только ставит строки
в фоновую очередь, а сам импорт идёт по одному. Статус пачки на каждый опрос спрашивает у
очереди состояние задачи каждой отправленной строки: `importState` = `queued` / `running` /
`completed` / `failed`, плюс `importCreated` (сколько строк создано) и `importError`;
`importsPending` — какая-то задача ещё не доработала. Панель опрашивает, пока тянется пачка
**или** `importsPending`. Строки показывают колесико «в очереди импорта» / «импортирую…», затем
«✓ импортировано (N строк)» или «✗ импорт упал» с причиной. Строка хода заканчивается флагом
«✓ Импорт завершён: N из M» (или «…, ошибок K»). Кнопки «Затянуть все незатянутые» и
«Импортировать отмеченные» на время своей работы «заняты» (`adminBusy`, колесико на кнопке).
Если очередь задачу не помнит (перезапуск API), строка остаётся «✓ отправлено в импорт» и не
ждётся. Тесты — `BulkPullServiceTests` (`Import_StatusFollowsTheQueue_…`, `Import_QueueForgotTheJob_…`).

⚠ **Очередь импорта стала неограниченной** (`ImportJobQueue`). Канал был на 20 задач, а
`Enqueue` писал `TryWrite` без проверки: при отметке больше 20 строк (пачка — до 30) лишние
молча не попадали в очередь и навсегда оставались «Queued», а их разборы уже были удалены.
Тест — `ImportJobQueueTests`.

**Регламент в пачке решает сам.** Одиночная панель показывает находки и ждёт человека; в
пачке ждать некому, поэтому находки применяются автоматически, а **цитаты сохраняются**: они
видны в строке панели и уезжают в аудит `competition.bulk-import` вместе со ссылкой на PDF.
Это осознанное ослабление правила «анализатор ничего не решает сам».

**Чемпионаты** определяются по двум источникам — имя (`CompetitionAdminRepository.IsChampionship`)
и регламент (`IsChampionship`); при выключенном чекбоксе они не тянутся вовсе, а панель
пишет «исключено: N» со списком.

Аудит: `competition.bulk-pull` (сколько строк, исключённые чемпионаты) и
`competition.bulk-import` (что ушло в очередь, вердикты, цитаты регламента, ссылка на PDF).
Тесты — `BulkPullClassifierTests`, `BulkPullServiceTests`.


## Рекорды в превью: сверка по loglig (2026-08-23)

Карточка «Файл побьёт рекордов: N» показывает подозрительные заплывы и галочку «пометить
заплыв сомнительным». Под каждым заплывом теперь стоит **вердикт по карточке пловца на
loglig** — рекомендация, жать галочку или нет.

**Почему это работает.** Протокол мы качаем С LOGLIG, значит его время обязано быть и в
карточке пловца. Совпало — рекорд настоящий; в карточке время заметно ХУЖЕ — почти наверняка
разбор поехал (эталон: 00:32.59 на 100 баттерфляем у Маккабиады).

| Вердикт | Что значит |
|---|---|
| `Confirms` ✓ | на loglig то же время (или быстрее) — помечать не нужно |
| `Contradicts` ⚠ | на loglig время хуже на N секунд — рекомендуем пометить |
| `NoData` | карточка есть, но этой дистанции в ней нет — сверить не с чем |
| `NotChecked` | пловца нет в базе / не привязан к loglig / карточка недоступна |

**Ссылка ведёт в нужный сезон.** `…/Players/Details/{id}?seasonId={сезон соревнования}&tab=results`.
Сезон берётся СО СТРАНИЦЫ соревнования (`LogligClient.GetCompetitionSeasonIdAsync`, тот же
`ParseSeasonId`, что у клубного зачёта), а не из конфига `Loglig:SeasonId`: с чужим сезоном
карточка показывает другой год, и «посмотреть глазами» ведёт не туда.

**Если пловец не привязан** — прямо в строке поле `id с loglig` + «привязать», а рядом кнопки
`♂`/`♀`, когда пол в базе не заполнен. Оба действия идут ШТАТНЫМИ эндпоинтами:
`POST /api/admin/loglig/set` (он сам тянет карточку, сверяет год и клуб, пишет аудит) и
`POST /api/admin/swimmers/{id}/gender` (та же логика, что у кнопок на /Admin/Health:
`IDataCheckRunner.SetSwimmerGenderAsync` — пол уходит пловцу и в его строки БЕЗ пола).
После ввода id проверка НЕ перезапускается: сверять уже не надо, человек смотрит карточку сам.

**loglig-id берётся из САМОГО протокола.** На странице заплыва без `isModal` —
`LeagueTable/AthleticsDisciplineResults/{eventId}?showCategories=True` — каждое имя напечатано
ссылкой `<a href="/Players/Details/{id}?seasonId=…">`. В модальной (печатной) версии, которую
читает `LogligEventResultsParser`, ссылок НЕТ — поэтому участников тянет отдельный метод
`LogligClient.GetCompetitionParticipantsAsync`, и он ходит именно за немодальной страницей.

Это и есть ответ на «а если пловца у нас в базе нет»: id известен ДО импорта, поэтому время
сверяется даже для новичка — привязать его просто некому (появится при импорте). А тем, кто
в базе есть и не привязан, панель показывает кнопку **«привязать #109926»** с готовым
номером; поле ручного ввода остаётся только там, где протокол id не дал.

Обход платный (страница на заплыв, у чемпионата их под сотню), поэтому: ищем **только**
имена подозрительных строк, останавливаемся, как только нашли всех (`wanted`), берём максимум
`maxEvents` заплывов и держим результат в кэше 30 минут — record-check зовут повторно.

**Три исхода сопоставления с базой** (`PreviewSwimmerMatch`) — и они разные не для красоты:

- `One` — ровно один пловец с этим именем и годом: с ним и работаем;
- `None` — пловца ещё нет (соревнование не импортировано): время сверяем по id из протокола,
  привязывать некому;
- `Many` — **тёзки**; время сверяем, но привязку не предлагаем (id уедет не тому) — отправляем
  в /Admin/Swimmers/Loglig.

Сопоставление — нормализованный НАБОР токенов имени + год рождения: в протоколе «имя
фамилия», у нас поля раздельные и порядок другой. Нормализация общая с дедупом
(`SwimmerDedupService.Normalize`: финальные ивритские буквы, гереш) — своей копии нет.

**Проверка ленивая.** Отдельный запрос `POST /api/admin/discovery/preview/{previewId}/record-check`
после того, как превью отрисовано: карточка тянется по одной на пловца, и держать на них
разбор (тем более пакетный забор на 30 строк) нельзя. Поэтому отложенный разбор в кэше несёт
и превью рекордов (`DiscoveryPreviewEntry.Records`) — иначе детектор пришлось бы гонять заново.

**Штамповка loglig-id на импорте (2026-08-23).** Раз id известен из протокола, после каждого
импорта он проставляется пловцам этого соревнования: `ILogligStampService` →
`LogligStampService`, вызывается из `ImportBackgroundService` **после** импорта и пробы
клубного зачёта, за тумблером `LogligStampOnImport` (по умолчанию включён). Сбой ничего не
ломает — привязки просто не появятся. С 23.11.2026 штамповка идёт во второй очереди службы
(«шаги loglig», один читатель) после доклейки промежуточных, и только за импортом, который что-то
записал: после «Дубля» / Р119 / отката её нет (раздел «⏱ Промежуточные»).

**Игрок loglig у строки (2026-11-24, Р122).** Штамповка ставит id КАРТОЧКЕ и опознаёт её по имени.
Отдельный шаг за ней — `ILogligRowPlayerService` → `LogligRowPlayerService` — ставит id игрока
каждой личной СТРОКЕ (`Results.LogligPlayerId`), опознавая её по заплыву, дорожке и времени, без
имени. Это данные для проверки Health `swimmers.two-loglig-players`: два разных игрока у одной
карточки в одном соревновании — слиты два человека (И-69). `Swimmers.LogligId` шаг не трогает и
штамповке id не подсказывает — это отдельная тема.

Три правила, которые важнее покрытия:

- **уже привязанного не трогаем** — связь в базе поставил человек;
- **тёзок пропускаем** (одно имя + один год у нескольких пловцов): привязать не тому хуже,
  чем не привязать;
- **занятый id не отбираем** у другого пловца — это симптом дубля, разбирается дедупом.

Статус ставится `Verified`, источник — **`protocol`** (отличается от `admin` / `user-claim` /
`auto`): по нему такие привязки потом находят и, если понадобится, снимают пачкой.

Для уже импортированных стартов — кнопка **«Loglig-id»** — шаг 9 чек-листа
(`POST /api/admin/discovery/stamp-loglig`, аудит `swimmer.stamp-loglig`).

**Сопоставление имён — общий хелпер `TokenNameMatcher`** (Application/Validation): точное
совпадение набора нормализованных токенов + год, а если его нет — единственный кандидат, чьё
имя ПОЛНЕЕ или короче нашего. Живой случай: на loglig «אליה מאשה גדול», у нас «אליה גדול» —
двойное имя печатают не везде. Двое подходящих значит «не знаем» и привязки не будет.

⚠ Ловушка, стоившая одного промаха: ячейки таблицы схлопывают пробелы, а имя внутри ссылки —
нет («אליה  מאשה גדול» с двойным пробелом). Пока имя не нормализовали так же, оно «не
находилось» в собственной строке и год рождения терялся вместе с сопоставлением.

Код: `IPreviewRecordCheckService` → `PreviewRecordCheckService` (загрузка и сопоставление),
`RecordCheckComparer` (чистое сравнение времён, допуск 30 мс — федерация печатает сотые,
loglig хранит тысячные). Тесты — `RecordCheckComparerTests`, `PreviewRecordCheckServiceTests`,
`LogligParticipantsParseTests` (на снапшоте живой страницы заплыва).


## Флаги соревнования прямо в превью (2026-08-23)

В карточке превью, над категориями, — блок **«Флаги соревнования»**: `Awards (медали)`,
`🏆 Чемпионат Израиля`, `Masters`, `клубный зачёт не ведётся` и селект **длины бассейна**.
Раньше это ставили РУКАМИ после импорта, в панели строки, и про половину забывали.

Галочки проставляются сами, но каждая подписана **основанием** — под блоком идут строки вида
«Awards: регламент: «…цитата…»», «🏆: в названии «אליפות … ישראל»» и ссылка на сам регламент:

| флаг | откуда предлагается |
|---|---|
| Awards | регламент (`מדליות`) — забирается с loglig автоматически |
| 🏆 Чемпионат | название (`אליפות` + `ישראל`, тот же предикат, что у фильтра списка) **или** регламент |
| Masters | разобранный файл (в нём есть мастерс-заплывы) |
| клубный зачёт не ведётся | проба loglig сказала «зачёта нет». Если проба вернула «не проверяли» (нет loglig-id, сайт лёг) — галочка НЕ ставится: это разные вещи |
| бассейн | **регламент** — фраза «25/50 מטר, N מסלולים» (`RegulationAnalyzer`, флаг `pool`). С 25.11.2026 все варианты записи собраны в одном классе `PoolLengthFinder` (`Swimm.Parsing/Parsers/Regulation`, тесты `PoolLengthFinderTests`): с дорожками, «בריכת N» вплотную и фраза о месте проведения, где «бассейн» и «N метров» разнесены (перевёрнутый текст PdfPig; живой случай — чемпионат на 5 км, compID 486, loglig doc 1541). Новый способ записи в регламенте — новая строка правил и кейс в тестах там же. С 24.11.2026 — ещё и «בריכת 25/50 מ'» без числа дорожек (слово «бассейн» вплотную перед числом; живой случай — «ההזדמנות האחרונה» 2023, loglig 9816). Протокол loglig бассейна НЕ пишет, а `25m` в строках парсера — умолчание; до 22.09 превью выдавало его за «распознано парсером», и летний чемпионат טריילז лёг 25-метровым (И-30). Регламент молчит — селект пуст, и **новое** соревнование без выбора 25/50 кнопка «Импорт» не пропускает (у существующего пустой селект ничего не меняет) |

Предложение считает `DiscoveryPreviewService.SuggestFlagsAsync` → `CompetitionFlagSuggestion`;
решение принимает человек — в импорт уезжает то, что он видел на экране.

**Как флаги доезжают до БД.** Через `ImportEventOptions` (`IsAward`, `IsChampionship`,
`IsMasters`, `ClubPointsDisabled`, `PoolType`) — все nullable, `null` = «не трогать».
`JsonImportService` применяет их и к НОВОМУ соревнованию, и к существующему
(`ApplyCompetitionFlags`) — при перезатягивании свежее решение админа должно побеждать.

⚠ **Бассейн подменяется ДО построения ключа соревнования.** Ключ дедупа —
`Name|Date|PoolType`; поменять длину бассейна «потом» значит завести второй Competition с тем
же именем и датой. Поэтому `eventOptions.PoolType` перекрывает распознанное парсером до
`ImportCompetitionMatcher.Key`.

**Пакетное затягивание и бассейн (22.09.2026).** Бассейн строки — из регламента; нет там —
у не-чемпионата честное умолчание `25m` (лиги), у чемпионата `null`: классификатор ставит
«нужно решение» (`BulkPullClassifier`), а «Импорт пачки» такую строку пропускает с причиной.

**Один путь вместо двух.** Пакетное затягивание раньше доносило медали, дописывая `is_award`
в payload (`ImportPayloadAwardFlag`); теперь и оно шлёт флаги теми же опциями, а хак удалён —
два механизма для одного и того же расходятся первыми.


## Категории подбираются по названию (2026-08-23)

Чек-лист категорий в превью больше не пустой: отмечается то, что удалось вывести из
названия соревнования. Правило Влада — «есть в названии слово из /Admin/Categories —
применяй; если там не только эти возраста — добавляй 8-99»:

| в названии | подбор |
|---|---|
| слово категории (`נוער ובוגרים`) | Juniors + Adults |
| возраст цифрами (`לגילאי 8-11`) | Kids — по полосам `MinAge`/`MaxAge` из /Admin/Categories |
| `17+` | Adults (полоса открыта сверху) |
| про возраст ничего (`ליגה מס 1 הפועל ירושלים`) | Age 8-99 |
| диапазон шире лестницы (`8-99`) | Age 8-99, а не «все полосы разом» |

Слова берутся из самой таблицы категорий (`Name` + `NameHe`), полосы — из её же колонок:
завёл категорию — она сразу участвует, переименовал — код не расходится. Ивритские
приставки не мешают (`לצעירים`, `ובוגרים`). `Age 8-99` по своему имени не подбирается —
оно ставится правилом, иначе причина в подписи была бы непонятной. Masters добавляется ещё
и по файлу, когда в названии слова нет (`ליגת ותיקים`).

Считает `CategoryNameMatcher` (чистая функция, тесты — `CategoryNameMatcherTests` на живых
названиях). Проверено на разметке, которую Влад делал руками: `לגילאי 9-11` → Kids
(9 таких соревнований в базе), `לגילאים צעירים` → Young, `נוער ובוגרים` → Juniors + Adults.

## Кнопка «⇄ Источники» — из каких compID собран стартовый протокол

«⇄ Источники» — шаг 2 чек-листа у строк базы, модал
`#sources-modal`, API — `/api/admin/competition-sources`.

**Зачем.** Одному нашему соревнованию может соответствовать НЕСКОЛЬКО compID федерации.
Эталон: «אליפות ישראל ארנה 8-11 חורף 2026» — у нас один старт из трёх дней, а на isr.org.il
это четыре окружных протокола (север 16789, центр 16787 и 16788 в один день, юг 16786).
Скалярный `Competition.OrgCompId` выражает только один из них, поэтому привязки живут в
отдельной публичной таблице `CompetitionSources` (см. `Swimm.Domain/Entities/CompetitionSource.cs`),
а таб «Start list» на клиенте рисует по одному подтабу на источник — подпись «дата · #N»
(имена протоколов на иврите, в подпись их не пускаем; полное имя — в тултипе).

**Что в модале.** Сверху «Привязано» (compID, дата, имя у федерации, число затянутых заявок,
«Отвязать»), ниже «Кандидаты из «Входящих»» — строки, чья дата попадает в диапазон дней
соревнования ±сутки, с селектом «привязать к дню». Кандидат, уже привязанный к ДРУГОМУ
соревнованию, помечен «занят» — не фильтруется, потому что такую ошибку надо видеть.

**Порядок работы.** Привязка ничего не тянет: после неё нажимают «Стартовый протокол» на
строке этого compID во «Входящих». «Отвязать» не удаляет заявки — они принадлежат compID,
а не привязке, поэтому ошибочную привязку можно переставить, ничего не перезабирая.

**Автоматика.** Импорт привязывает свой compID сам (`JsonImportService`, рядом со штампом
`OrgCompId`), так что у обычных однодневных стартов таб появляется без похода сюда. Руками
собирают только составные — окружные чемпионаты.

## Кнопка «Стартовый протокол» (С5, docs/plans/start-list-plan.md)

Кнопка живёт в `SiteActions` рядом с «Затянуть»/«Loglig-id» — рисуется у **любой не скрытой**
(`Status != "ignored"`) строки, включая будущие старты (у них ещё нет результатов, поэтому
обычные кнопки затягивания не рисуются вовсе — эта первая, что появляется). У прошедших тоже
рисуется — удобно проверять забор на архивных данных.

**Что делает.** `POST /api/admin/discovery/{id}/start-list` (`id` — `Sys_DiscoveredCompetitions.Id`,
как у соседей) резолвит `OrgCompId` и зовёт `IStartListPullService.PullAsync` напрямую —
без превью и без очереди: заявки идут сразу в `CompetitionEntries`, справочник `Competitions`
не трогается. Долгий запрос (у чемпионата — под две сотни обращений к loglig с паузой,
минуты), поэтому кнопка на время запроса гасится, а отчёт идёт в **модал** `#startlist-modal`
(2026-08-28; до этого писался в общий `info`-блок в шапке страницы — со списка, прокрученного
вниз, его не было видно, и кнопка выглядела мёртвой). Модал не закрывается сам: в нём лежат
код ответа `HTTP N`, тело ответа и кнопка «Скопировать отчёт» — это и есть диагностика,
которую присылают на разбор.

**Статусы отчёта** (`StartListPullReport.Status`):
- `ok` — стартовый протокол прочитан полностью, заявки обновлены.
- `partial` — часть заплывов не прочиталась (`EventsFetched < Events`); заявки из
  прочитанных обновлены, повторное нажатие дочитает остальное.
- `empty` — ожидаемое состояние источника, не ошибка: либо у соревнования ещё нет
  `LogligId` (жми сперва «Проверить сайт федерации» / дождись фонового `RefreshUpcomingDetailsAsync`),
  либо посев стартового протокола на loglig ещё не сделан (до старта это норма). Человекочитаемый
  текст уже в `Error` — показывается спокойно, без ⚠.
- `error` — неожиданный сбой (сеть, разбор); текст — в `Error`.

Повторное нажатие идемпотентно: `Добавлено 0, снялись 0`, если протокол на сайте не менялся.

**Куда смотреть при пустом результате.** Если `LogligId` у соревнования нет — либо оно
ещё не подгружено кнопкой «Проверить сайт федерации»/`RefreshDetailsAsync`, либо iframe loglig на
`comp.asp` появляется не сразу (бывает и после старта), см. §1.6 плана. Фон `start-list`
дочитывает такие строки сам: будущие в окне `StartListDaysAhead` и прошедшие за 30 дней со
статусом `new` (с 16.11.2026).
Если `LogligId` есть, а всё равно `empty` — посев на loglig ещё не сделан, ждать.

**Колонки «заявок N» нет — вместо неё бейдж (ниже).** Считать `CompetitionEntries` по каждой
строке дорого; число заявок берётся из журнала заборов `Sys_StartListPulls`.

## Бейдж стартового протокола (решение Влада 18.10.2026)

С этапа 6 варианта E бейджа как такового нет: то же правило (`StartListBadgeRules`) даёт подпись шага 2
чек-листа («забран 18.10 · заявок 214», «забран частично…», «забирали… — пусто», «забор… сорвался»,
хвост «· обновить») и журнал заборов в подсказке; «обновить» — ещё и пометкой строки списка у
впереди/идущих. Ни разу не тянули — «не забирали». Прежний вид бейджа:

| Последний забор | Бейдж | Цвет |
|---|---|---|
| `ok`, заявки есть | `SL 214 · 18.10 14:30` | зелёный |
| `partial` | `SL частично · …` | жёлтый |
| `empty` (или `ok` без заявок) | `SL пусто · …` | серый |
| `error` / незнакомый статус | `SL ошибка · …` | красный |

**«Пора обновить»:** до старта 3 дня или меньше (`StartListBadgeRules.StaleWindowDays`), а
последнему забору больше суток (`StaleAfter`) — бейдж жёлтый с хвостом «· обновить» (ошибка
остаётся красной). Стартовый протокол меняется до последнего дня — это и ловим. Прошедшим
стартам пометки нет. В `title` — последние 5 заборов: время, статус, заявок, `+добавились
−снялись пересев N`.

**Устройство.** Отдельной галки «затянуто» сознательно нет: факт уже в журнале, второй экземпляр
разошёлся бы с ним. Правило — чистая функция `Swimm.Application/Mapping/StartListBadgeRules.cs`
(тесты `StartListBadgeRulesTests`); данные — `CompetitionAdminRepository.AttachStartListBadgesAsync`:
**только строкам текущей страницы и одним запросом на страницу** (журнал по их `OrgCompId`),
результат — `UnifiedSiteInfo.StartList`; разметка — `StartListBadgeHtml` в `Index.cshtml`.
Ключ — `OrgCompId` строки входящих, поэтому у многодневки бейдж показывает забор того
compID, который висит на строке. После нажатия «Стартовый протокол» страница не
перезагружается — новый бейдж видно после F5.

## Кнопка «Разминка» — справка о старте (Т1, docs/plans/start-list-ticket-plan.md)

Стоит рядом со «Стартовым протоколом», по тому же условию (любая не скрытая строка).
Открывает модал `#meetinfo-modal` с двумя вещами, из которых таб Start list считает
**«во сколько приезжать»**: время начала разминки по дням и тип старта.

**Данные** — публичные таблицы `CompetitionMeetInfos` (ключ `OrgCompId`, без FK на
`Competitions`: у будущего старта справочной строки ещё нет) и `CompetitionWarmUps`
(ключ «соревнование + день»). API — `GET/POST /api/admin/discovery/{id}/meet-info`
(`id` — `Sys_DiscoveredCompetitions.Id`, как у соседей), сервис `IMeetInfoAdminService`.

**Разминка вводится РУКАМИ** (решение Влада 29.08.2026) — регламент под неё не разбираем:
формулировки федерации разношёрстные, и лишний автоматический источник кривых данных решено
не заводить. Админ читает תקנון и вбивает время. Поле — местное израильское «HH:mm»; в базе
лежит момент UTC (перевод — `IsraelTime`, тот же, что у времени заплывов). **Пустое поле
стирает** время этого дня.

**Дни берутся из заявок**, а если их ещё нет — из диапазона дат «Входящих»: разминку вводят
ДО забора протокола, читая регламент. Рядом с каждым днём — сколько заявок затянуто, чтобы
день не оказался опечаткой в датах.

⚠ **Флаг «чемпионат» — только для чтения; правится ОТДЕЛЬНЫМ полем.** Сам флаг ставит забор
стартового протокола по регламенту (`RegulationAnalyzer.IsChampionship`, вместе с его вето
на «готовимся к чемпионату»), и забор идемпотентен — его жмут до последнего дня. Пиши админ
в то же поле, его решение жило бы до следующего прогона; поэтому в модале селект
«Переопределить» пишет `IsChampionshipOverride`, а витрина видит `Override ?? IsChampionship`
(строка «Витрина видит: …» в модале). Тот же приём, что `Competition.StandingKindOverride`.
Регламент забор перечитывает не чаще раза в неделю (`RegulationRecheckAfter`).

**Куда это уходит.** `GET /api/start-list/{orgCompId}` отдаёт `is_championship` (действующее
значение) и `warm_up_at` в каждом дне. Блок ARRIVE BY на витрине рисуется только при трёх
условиях сразу: чемпионат ∧ юзер залогинен ∧ отмечена галочка «I'm coming». Разминки нет →
блока нет, и это штатное состояние большинства стартов.
