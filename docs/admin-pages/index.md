# /Admin — Dashboard

Файлы: `Pages/Admin/Index.cshtml(.cs)`, скрипт `wwwroot/js/admin/dashboard.js`; API: `AdminController` (`/api/admin/*`,
включая `GET /api/admin/dashboard/status`), `DashboardStatusService` (DTO —
`Swimm.Application/Dtos/DashboardStatusDtos.cs`).

## Здоровье данных — вариант 1c (master–detail)

Один запрос `GET /api/admin/dashboard/status` (кэш 2 мин) → 8 переставляемых
блоков-строк слева + системная строка внизу (вне reorder) + sticky-панель
деталей выбранного блока справа (540px, top 24px). Блоки (дефолтный порядок):

0. **Проверки данных** → [`/Admin/Health`](health.md) — сводка реестра
   (docs/data-integrity.md, Д3): последний прогон (когда + триггер),
   открытые ошибки/предупреждения/инфо, в панели деталей разбивка по
   проверкам. ⚠ Прогонов не было — блок так и говорит; нули там читались
   бы как «всё чисто».
1. Пловцы → `/Admin/Swimmers`
2. Клубы → `/Admin/Clubs`
3. Соревнования → `/Admin/Competitions`
3.5. **Клубные очки** → [`/Admin/PointsRules`](pointsrules.md) — итоги ручной
   сверки зачёта с официальным. Метрики: расхождения, из них **без
   пояснения** (бейдж «★ расхождение» на витрине без объяснения = утверждение
   без доказательства), соревнования без правила очков, не сверявшиеся.
   В панели деталей — блок **«Где спорим с федерацией»**: каждое соревнование
   с расхождением поимённо, с нашими и официальными очками и числом
   разошедшихся строк. Считается по СОБЫТИЯМ, а не дням: отметка стоит на
   каждом дне многодневки, и один чемпионат выглядел бы четырьмя
   расхождениями. ⚠ Официальных очков может не быть (`—`): построчный эталон
   приезжает только из пособытийного источника loglig, а у PDF-импортов
   величину расхождения знает лишь пояснение.
4. Результаты → `/Admin/Results`
5. Рекорды → `/Admin/Records` (карточка на каждый `recordSets[]`; **мир и Израиль —
   отдельными карточками, все прочие страны свёрнуты в одну «Другие страны ·
   стран: N»**: после Фазы 11 в `Records` лежат рекорды более двухсот стран, и карточка на
   каждую превратила бы блок в простыню. Сворачивает сервер —
   `BuildRecordSetsAsync` отдаёт синтетический набор с `regionType =
   countries-other` и счётчиком `countries`). Кнопка **«Проверить апдейты»** —
   по очереди Fetch (dry-run дифф) каждого из пяти источников; каждый Fetch пишет
   строку журнала `Sys_RecordSourceChecks`. Строки источников видны и ДО нажатия —
   **свежесть из журнала** (`GET /api/admin/records/freshness`): «проверено N дн.
   назад», упавшая последняя попытка, «ждёт Apply +a / ~c»; «!» жёлтым — пора
   проверить (старше 7 дней, ни разу или сбой). Пилюли **«Источники: пора
   проверить»** и **«Изменения ждут Apply»** появляются, только когда есть что
   показать (plans/records-freshness-plan.md §9). Там же **качество справочника**
   (`recordQuality`, см. `RecordQualityService`; сверка и её сводка считаются
   только по `world` + `ISR` — рекорд чужой федерации сверять не с чем, наши
   протоколы израильские): метрики «Спорные записи»,
   «Подтверждены протоколом», «Время совпало, дата другая», «Не найдены в
   протоколах» + кнопка «Сверить с протоколами»
   (`POST /api/admin/records/verify`) и список открытых претензий в панели
   деталей. ⚠ «Не найдено» — НЕ ошибка справочника: протоколы загружены не за
   все годы; формулировку не «улучшать»
   (docs/plans/records-quality-plan.md). Метрика **«Кандидаты в спорные»** и их
   список появляются, только когда сторож импорта нашёл неправдоподобное время
   (статус `candidate`, И-20): на сайте они не видны до перевода в `open`, так что
   дашборд — место, где их замечают (records.md, «Кандидаты сторожа импорта»)
6. Медиа → `/Admin/Media`. Метрика **«Жалобы»** (29.09.2026) → [`/Admin/MediaReports`](mediareports.md):
   сколько МЕДИА ждут решения по жалобам «Report» (не жалоб — тем же
   `IMediaReportService.CountOpenAsync`, что вкладка «Ждут решения», чтобы числа не разошлись),
   в подписи — сколько из них уже набрали порог и спрятаны (`ModerationState = under_review`).
   ⚠ Сводка кэшируется 2 минуты: свежая жалоба появится не сразу.
7. Пользователи и группы → `/Admin/Users`
8. **Кэш** → [`/Admin/Cache`](cache.md) (15.09.2026) — сколько записей в серверном кэше и
   сколько они весят (байты JSON), под строкой — когда был последний общий сброс. Метрика «Без
   меток данных» (должно быть ✓ 0: такую запись сбросит только общий сброс, сторож К5). В панели
   деталей — разбивка «ответы API / записи данных», память процесса, последний общий сброс с
   причиной, **кнопки сброса** (весь кэш — с подтверждением, все клубы — сразу; общий скрипт
   `Shared/_CacheReset.cshtml`) и последние 5 сбросов. ⚠ Данные — НЕ из
   `dashboard/status` (он кэширован на 2 мин), а своим живым запросом
   `GET /api/admin/cache/summary`: после кнопки сброса блок перечитывается сразу. Сбой этого
   запроса роняет только блок кэша. Производительность: запрос читает списки кэша без блокировок;
   размер записей данных меряется при первом взгляде админки и запоминается — путь посетителя за
   это не платит ([cache.md](cache.md), «Размер»).
9. **Jobs** → [`/Admin/Jobs`](jobs.md) (20.10.2026) — фоновые службы процесса. Главная цифра —
   служб с проблемой (последний запуск расписания упал, расписание просрочено, база не отвечает,
   мост кэша не слушает, локальная база отстаёт от прода), при нуле — зелёная ✓; подпись — «все в
   порядке / служб с проблемой · N служб, работают M · ошибок за 24 ч». Метрики: расписания с
   ошибкой, просроченные, ошибок за 24 ч. В панели деталей — список проблемных служб со ссылкой на
   их карточку (или ближайший запуск, если проблем нет). Данные — своим живым запросом
   `GET /api/admin/jobs/summary` (`JobsAdminController` → `IBackgroundJobsStatus.GetSummaryAsync`),
   это та же сводка, что плитки вверху `/Admin/Jobs` (`JobsOverviewBuilder`), здесь не
   пересчитывается. Без истории прогонов: запрос дешёвый — состояние журнала и один счётчик
   прогонов за неделю. Сбой запроса роняет только этот блок.

Блок может нести `rowNote` — короткий текст в строке после пилюль метрик (у «Кэша» — дата
последнего общего сброса): метрики-пилюли умеют только числа.

Клик по строке блока выбирает его и открывает детали справа. Ручка «⠿» —
drag-reorder (HTML5 draggable); блок, ставший первым, автоматически
выбирается. Порядок сохраняется в `localStorage`, ключ
`admin:dashboard:block-order` (массив ключей блоков). Нулевые метрики
сворачиваются в чипы «✓ Название · 0» (флаг `COLLAPSE_ZERO` в скрипте
страницы). Рекорд считается «устаревшим» (серым), если `lastUpdatedAt`
старше `RECORDS_STALE_MONTHS` (по умолчанию 3) месяцев.

**Часть метрик берётся из реестра проверок, а не считается здесь.** Уверенные
дубли пловцов/клубов, сироты, пустые клубы, FK-аномалии, эстафеты без состава
приходят из `Sys_DataCheckStates` (полное число последнего прогона, без среза
в 50). Если проверка ещё не гонялась или упала — метрика считается вживую, как
раньше. Смысл: два места не должны считать одно и то же разным кодом. Цена:
это картина последнего прогона, поэтому его дата видна в блоке «Проверки
данных». Подробности и список соответствий — `docs/data-integrity.md`,
врезка «Дашборд на реестре».

Каждая метрика — ссылка на целевую админ-страницу с query-параметром
`filter` (карта ссылок — в
`!design_handoff/design_handoff_data_health_dashboard/README.md`, раздел
«Контракт ссылок»; целевые страницы должны сами читать параметр — задача T3).

Ниже строк — пунктирный плейсхолдер «＋ Кастом-карточка» (без функционала,
задел под конфигурируемые SQL-счётчики) и системная строка (почта/последний
импорт/проверка медиа-ссылок/discovery-скан/действия аудита за 7 дней).

**Почта** (14.10.2026) — первый пункт системной строки, куда уходят письма этого процесса:
`SMTP · smtp.resend.com`, `в консоль (dev)` или жёлтое `⚠ не отправляются`; ссылка на карточку
`/Admin/Settings#email` с тестовым письмом. Берётся не из `/api/admin/dashboard/status`, а из
конфига процесса: Razor кладёт её в `data-email-*` у `#dash-system` (`IndexModel` →
`IEmailSender.Transport`). Подробно — [settings.md](settings.md#почта-блок-статуса-и-тестовое-письмо-2026-10-14).

Ниже дашборда — вкладка **Users**: список пользователей с фильтрами
(поиск/роль/статус), панель деталей, смена ролей — без изменений.

## Блок «Рекорды» → «Ось возраста ступеней» (2026-08-22)

Под кнопкой «Сверить с протоколами» показывается разбивка: по какой оси возраста ступень
каждой записи справочника сходится с найденным пловцом — календарной (год заплыва, ось
федерации) или сезонной (наш возраст в сезоне). Строка «Различают ось» — единственная
информативная: заплывы января–августа попадают в «обе оси» и об источнике не говорят
ничего.

Там же — «Не сходится с текущей осью»: сколько записей при нынешней настройке
`RecordAgeAxis` наша сверка отправит не в ту строку справочника. Что считается и почему
часть записей не проверяется — `docs/data-integrity.md` §13.
