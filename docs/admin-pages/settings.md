# /Admin/Settings — параметры приложения

Файлы: `Pages/Admin/Settings.cshtml`; API `/api/admin/settings`
(`AdminSettingsService` — in-memory, перечитываются фоновыми джобами каждый тик).

Ключевые ключи: DiscoveryEnabled/DiscoveryIntervalHours,
LogligVerifyEnabled/LogligVerifyIntervalHours (дефолт вкл/24ч),
LogligBatchEnabled/LogligBatchPerRun/LogligBatchIntervalHours (дефолт ВЫКЛ/50/24ч),
**RecordAgeAxis** (дефолт `calendar`, значения `calendar`/`season`).
Scope: admin / livesite / both.

## RecordAgeAxis — ось возраста для сверки с рекордами (2026-08-22)

`calendar` — возраст = год заплыва минус год рождения, как ведёт свои ступени федерация
(дефолт). `season` — возраст в сезоне, как считаем возраст у себя. Оси расходятся **только
с сентября по декабрь**; с января по август значение настройки ни на что не влияет.

Действует в `CompetitionRecordsDetector` — то есть на предупреждение «файл побьёт рекордов»
в /Admin/Import и на карточку «New records» страницы соревнования. Возраст ПЛОВЦА (ростер,
зачёт, категории, season best) настройка НЕ трогает: он всегда сезонный, `SeasonMath`.
Разбор, зачем это разные вещи, и статистика по справочнику — `docs/data-integrity.md` §13.

⚠ Как и все настройки здесь, значение живёт в памяти процесса: после рестарта API
возвращается `calendar`. Для этой настройки так и задумано — дефолт совпадает с рабочим
режимом, а `season` включают, чтобы посмотреть, как бы считалось по-нашему.

Кнопка «Пересчитать / сбросить кэш» (фаза 7.3 op#3) → `POST /api/admin/cache/invalidate`
(`ICacheService.InvalidateAllAsync` + аудит `cache.invalidate`). Агрегаты (club-summary,
клубные очки, результаты) не персистятся — считаются на чтение и кэшируются в памяти с
TTL, поэтому «пересчёт» = сброс кэша: свежие данные соберутся при следующем публичном
запросе. Полезно после ручных правок результатов / переноса.

## Debug details — двухуровневый выключатель подробностей (2026-08-22)

Секция внизу страницы. Показывает опции из таблицы **`Sys_DebugOptions`**, над которыми стоит
общий тумблер — настройка **`DebugDetails`** (bool, дефолт `false`) в таблице выше.

**Опция действует, только когда включены ОБА уровня.** Поле `effective` считает сервер, и
админка так и подписывает строку: «действует» либо «включена, но DebugDetails выключен».
Смысл двух уровней — гасить всё одним движением, не снимая галочки по одной.

Почему опции в БД, а не в настройках: настройки живут в памяти процесса и сбрасываются при
рестарте (`AdminSettingsService`), а состояние опций должно переживать деплой. Побочный
эффект удобен: **`DebugDetails` после рестарта сам возвращается в `false`**, то есть
подробности не остаются включёнными на боевом сайте по забывчивости, а галочки при этом
сохраняются.

Ключи опций перечислены в коде (`DebugOptionKeys.All`) и досеиваются в таблицу при первом
обращении — новая подробность не требует своей миграции.

API: `GET /api/admin/debug-options`, `PUT /api/admin/debug-options/{key}` (тело `{enabled}`),
пишется в аудит как `debug-option.update`. Действующие опции уезжают на сайт через
`GET /api/client-config` → `debug`.

### ShowAgeRecordsDetails

Под датой рекорда на карточке «ISR Age Records» — год рождения держателя и его возраст в год
рекорда: `born 2011 · age 10 ?`.

Ради чего: видно, почему запись стоит в ступени 10, хотя пловчихе того же года рождения в
сезоне уже 11 (разбор — `docs/data-integrity.md` §13).

⚠ **Год рождения — это наша реконструкция, а не данные справочника.** В справочнике федерации
года рождения нет, мы ищем держателя среди своих пловцов по имени (в обеих перестановках слов:
справочник пишет «טלר מרק», мы — «מרק טלר»); тёзки с разными годами отбрасываются. Отсюда
знак «?» в подписи. Покрытие на 2026-08-22 — 278 записей из 781, у остальных подписи нет.

Сверку «рекорды ↔ протоколы» (`Sys_RecordVerifications`) для этого сознательно НЕ используем,
хотя она надёжнее: публичный read-путь ходит под ролью `swimm_ro`, у которой нет прав на
`Sys_*` (`server/db/setup-roles.sql`). Открывать ей системные таблицы ради отладочной подписи
не стоит.
