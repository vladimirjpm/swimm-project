# /Admin/AppInsights — телеметрия прод-сайта

Файлы: `Pages/Admin/AppInsights.cshtml` (каркас страницы) + `.cshtml.cs` (`AppInsightsModel`, пустой
`OnGet`), скрипт `wwwroot/js/admin/appinsights.js`. Пункт сайдбара «App Insights» в разделе «System»,
сразу после «Jobs». Источник — Azure Application Insights (план:
[application-insights-plan.md](../plans/application-insights-plan.md)); админка только читает.

Страница открывается сразу с каркасом и «Загрузка…», **сервер в `OnGet` в Azure не ходит** — цифры
доезжают скриптом одним запросом (1–2 с, первый после старта API — до 5 с, при сбое Azure — до 15 с).
Автообновления нет: кнопка «Обновить» шлёт `refresh=true` (мимо серверного кэша на 2 минуты).

Админка бывает только локально у Влада (Development и ProdAdmin, решение В17) — на проде страницы нет.

## Что показывает

Сверху — шапка-панель: карточка состояния подключения, «этот процесс шлёт / не шлёт телеметрию как
`roleName`», «последняя запись с прода», сегментные переключатели **периода** (1 ч / 24 ч / 7 дней)
и **роли** (Сайт / ProdAdmin), «Обновить», «данные на HH:MM (кэш 2 мин)» и ссылки в портал Azure
(Failures, Performance, Live metrics, Logs, Overview — берутся из ответа API, только если задан
`ResourceId`). Период и роль лежат в query `?range=&role=`, ссылка открывается так же.

Ниже, если есть причины жёлтого/красного, — баннер «почему» (`reasons`), затем восемь плиток (запросов,
ошибки 5xx, p95 ответа, исключения, p95 Postgres, медленные операции, принято сегодня, последняя
телеметрия; клик — якорь к таблице) и четыре таблицы:

| Таблица (якорь) | Что в ней |
|---|---|
| Частые исключения `#exceptions` | тип, сообщение, сколько, последний раз, операция (пусто — «фон») |
| Самые медленные операции `#slow` | операция, сколько, p50, p95 (выше 1000 мс — жёлтым), 5xx |
| Ошибки по маршруту и коду `#errors` | ответы 400+, 5xx красным и первыми, 4xx приглушены |
| Сбои фоновых служб `#background` | исключения и логи Error+ вне запроса (пустой `OperationId`) |

Длинные сообщения обрезаются (`truncate`), полный текст — в `title`. На 375 px таблицы скроллятся
внутри карточки, страница — нет. Таблица без строк — «Пусто — хорошо».

## Три состояния без данных

`connection.state` ≠ `ok` — вместо плиток и таблиц одна большая карточка (тон нейтральный, не красный):

| state | Карточка | Что делать |
|---|---|---|
| `not-configured` | «Не настроено», серая; в `hint` две команды `az` | подставить значения в gitignored `appsettings.Local.json` (Development) или `appsettings.ProdAdmin.Local.json`, перезапустить API |
| `no-login` | «Нет входа az», серая; `hint` = `az login` | выполнить `az login`, обновить страницу |
| `failed` | «Не удалось прочитать», жёлтая рамка; `text` — причина | по тексту; чаще таймаут/права |

`hint` показан в `<pre>` с кнопкой «Скопировать». Отдельно — сбой самого запроса (сеть, 500):
карточка «Не удалось загрузить» с кнопкой «Повторить».

## API

Оба эндпоинта — `[Authorize(Roles="Admin")]`, только GET, всегда 200 с карточкой `connection`, если
Azure недоступен (400 — только на неверный параметр). Серверная часть: `AppInsightsAdminController`,
`IAppInsightsReader`, сборка тонов — `AppInsightsOverviewBuilder`.

- `GET /api/admin/appinsights/overview?range=1h|24h|7d&role=web|prodadmin&refresh=true` — страница.
  Умолчания `24h` / `web`; кэш 2 минуты по паре (range, role).
- `GET /api/admin/appinsights/summary` — блок дашборда ([index.md](index.md), п. 10): сайт за 24 ч.

## Чьи запросы в цифрах (решение Влада 19.11.2026)

Сайт метит каждый запрос (`Swimm.API/Telemetry`), страница считает по меткам:

| Метка в `AppRequests.Properties` | Что | Где учитывается |
|---|---|---|
| `swimm.source` = `visitor` / `bot` / `warmup` / `uptime` | кто прислал: человек, робот по User-Agent, наш прогрев после старта (заголовок + loopback), внешний мониторинг | плитка «Запросов» — разбивка; p50/p95 и «Медленные операции» — только `visitor` + `bot` |
| `swimm.cold` = `true` | первые 10 минут после старта процесса (пустой кэш, нет соединений) | в p50/p95 и «Медленные операции» не входит; плитка p95 пишет «без N холодных (стартов: M)» |
| `swimm.db.query_count`, `swimm.db.query_ms` | сколько SQL сделал запрос и сколько они шли (все, включая быстрые) | на странице пока нет — KQL по `Properties`; 0 = ответ из кэша |
| `AppVersion` (колонка) | короткий хэш коммита сборки | KQL: что сделала конкретная выкатка |

Строки до 19.11.2026 меток не имеют — считаются посетителями и тёплыми. SQL быстрее 400 мс в Azure
не уходят (`Telemetry:SqlSpanMinMs`), поэтому «Postgres p95» — по медленным и упавшим командам.

## Откуда тоны и пороги

Тоны (`ok | warning | danger | info | neutral`) приходят с сервера готовыми, **клиент пороги не считает**.
Пороги — в `Swimm.Application/Mapping/AppInsightsThresholds.cs`: красный — сайт молчит > 30 мин или 5xx
> 5 % запросов; жёлтый — есть 5xx, исключения, сбои фона или ProdAdmin, приём ≥ 80 % дневного лимита,
тишина > 15 мин; серый — нет данных. Согласованы с оповещениями на почту (А4): страница загорается
раньше письма, не позже.

## Грабли

- **Ни одного идентификатора Azure в разметке, JS и MD** — репозиторий публичный. Ссылки в портал
  приходят из ответа API (`links`), он собирает их из локального конфига; в каталоге
  `/Admin/Services` — только общие ссылки.
- Текст из ответа (сообщения исключений и логов) — недоверенный текст с прода: в HTML и в `title`
  только через `esc()`.
- Log Analytics сам кэширует ответ на одинаковый запрос минуту-другую — «Обновить» сразу после загрузки
  может вернуть те же цифры. Это не баг, на клиенте не «чинить».
- **Запросы уходят по одному и параллельно (`/query`), не пакетом (`$batch`)** — разбор 19.11.2026.
  Симптом: карточка App Insights на `/Admin` «—», справа «Не удалось прочитать — Log Analytics вернул
  ответ, который не удалось разобрать (повтор тоже не помог) … (InvalidOperationException)». Причина —
  не KQL и не маппер (живой ответ итогов — 18 колонок, сходится с `AppInsightsRowMapper`, тест
  `Prod_shaped_totals_row_19_11_fills_dashboard_card`), а сам `$batch`: Log Analytics иногда отдаёт
  элемент пакета с `body` **строкой** вместо объекта, и SDK падает в
  `LogsBatchQueryResult.DeserializeLogsBatchQueryResult` («requires an element of type 'Object', but
  the target element has type 'String'»). Окна: 17.11 ~12:51–12:53 и 19.11 07:50–07:51 UTC (3 сбоя
  подряд), потом проходит само; сырым REST не воспроизводится. Повтор не помогал — по всей видимости,
  потому что Log Analytics кэширует ответ на одинаковый текст запроса: второй вызов через 40 мс
  получал тот же битый ответ. Сделано
  (`AzureLogsQueryRunner`): `QueryWorkspaceAsync` на каждый запрос, параллельно; первый сбой отменяет
  остальные. У одиночного запроса ошибка Azure приходит HTTP-ответом с кодом → `RequestFailedException`,
  и карточка пишет причину; в журнал — статус и код (`HTTP 504, …`), без текста ответа. Где смотреть
  такие сбои: телеметрия самой ProdAdmin — `AppExceptions`/`AppTraces` с `AppRoleName ==
  'swimhub-prodadmin'` (стек исключения там целиком). ⚠ Предупреждение повтора пишется с исключением,
  поэтому попадает в «ошибки ProdAdmin» на карточке — 19.11 это были 3 из 11.
- У роли ProdAdmin тишина — норма (её запускают руками): плитка «Последняя телеметрия» серая.
- Переключатели шлют только `1h|24h|7d` и `web|prodadmin`; `range=30d`, `role=dev` → 400.
- Правки Tailwind-классов в `appinsights.js` — `npm run css:build` и коммит `wwwroot/css/admin.min.css`
  (классы из `wwwroot/js/admin/**` собирает `@source` в `Styles/admin.css`).
- Только чтение: оповещения и настройки Azure отсюда не меняются.
