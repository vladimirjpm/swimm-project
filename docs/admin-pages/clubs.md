# /Admin/Clubs — дубли клубов

Файлы: `Pages/Admin/Clubs/Index.cshtml`, скрипт `wwwroot/js/admin/clubs.js`; API `ClubsAdminController`
(`/api/admin/clubs`): dedup-candidates (+`/loglig`, `/loglig/check` — Р112), merge, dedup-ignore(+remove/список),
{id}/status. Сервисы: `ClubDedupService`, `ClubMergeService`, `ClubPairLogligService`.

Аналог страницы Swimmers для клубов: кандидаты на склейку, dry-run → apply,
скрытие «не дублей». Плюс переключение статуса клуба (псевдо-клубы `IsPseudo`).

## Мягкая склейка (K2) и публичная страница клуба

Merge **не удаляет** клуб: строка остаётся, у неё проставляется `Club.MergedIntoId`.
Так ссылки на старый Id не гниют — `/clubs/{старый id}` показывает клуб-приёмника
(редиректа нет, решение Влада 2026-08-01). Склеенные исключены из дедуп-кандидатов,
выпадашки клубов hub-групп, подсказок фильтра, «дыр данных», счётчиков дашборда и — что
важнее всего — из кэша клубов в импорте: иначе следующий импорт нашёл бы дубль по имени
и повесил новые результаты на клуб, которого уже нет. Название надгробия импорт при этом
узнаёт и ведёт строку в канон (ниже, «Вид склейки»).

Повторная склейка уже склеенного блокируется (склеивать в надгробие нельзя, а надгробие
повторно — незачем).

## Вид склейки: «Дубль» и «Переименование» (с 18.11.2026, Р96)

У каждой пары в таблице — выпадашка **Вид** (в API — поле `kind` пары: `duplicate` по
умолчанию или `rename`). Решает человек: по данным дубль и переименование неотличимы.

- **Дубль** — один клуб записан двумя названиями (мусор парсера, другое написание). Всё как
  было: связи переезжают, пустой `NameEn` канона дозаполняется из дубля.
- **Переименование** — клуб сменил название: дубль = старое название, канон = новое.
  Дополнительно: строка `ClubNames` (старые `Name`/`NameEn`, `Kind=former`, `UsedFrom`/`UsedTo` —
  первый и последний старт дубля, посчитанные ДО переноса, `MergedClubId` = дубль);
  перенесённым строкам ставится `Results.ClubNameId` (строка, уже помнящая более старое
  название, остаётся при своём); английское название дубля канону НЕ передаётся — это старое
  название. На витрине: «Formerly: …» в шапке и SEO клуба, поиск по старому названию,
  «then: …» в окне истории клубов пловца, а протокол и карточки старого соревнования пишут
  клуб как напечатано, с подсказкой «now: …» (Р97).

Переименование среди кандидатов обычно не всплывает (названия разные) — для него под
таблицей строка **«Пара руками»**: Id канона, Id дубля, вид → «Добавить пару». Имена
клубов такой пары показывает dry-run первой строкой отчёта (««дубль» #id → «канон» #id —
переименование»). Ручные пары живут до перезагрузки страницы. Если пара уже есть среди
кандидатов (Hapoel/Aluma всплывает как «Общие пловцы (92)»), вторая строка не заводится:
у существующей выставляется вид и ставится галочка.

**Цепочек нет.** Склейка перевешивает на канон и клубы, склеенные в дубль раньше
(`Clubs.MergedIntoId: N склеенных в дубль → canonical`), и прежние названия дубля. Старые
цепочки (до 18.11.2026 склейка их не трогала: на проде `1329 → 605 → 1372`,
`1361/1408 → 447 → 1372`) догоняет консоль:

```bash
dotnet run --project server/Swimm.API -- --flatten-club-merges --dry-run   # план
dotnet run --project server/Swimm.API -- --flatten-club-merges             # записать
```

`/clubs/{id}` на всякий случай идёт по цепочке до конца (`ClubPublicRepository.ResolveClubIdAsync`).

**Импорт** находит клуб и по старым названиям: после промаха по живым клубам — прежнее
название (`ClubNames`) или название надгробия → итоговый канон (`ClubAliasIndex`). Живой
клуб-тёзка важнее старого названия. До 18.11.2026 название надгробия заводило клуб заново. На Edit склеенного клуба висит плашка со ссылкой на приёмника;
у любого клуба в шапке — ссылка на его публичную страницу `/clubs/{id}`.

После merge пересчитывается материализованный клубный зачёт (`ClubCompetitionStandings`),
причём ДВУМЯ проходами: по зачётам, где стоял сам дубль (собираются ДО переноса
результатов), и по соревнованиям канона. Ручной прогон, если что-то разошлось:
`dotnet run --project server/Swimm.API -- --rebuild-club-standings`.

## Эвристики поиска дублей

Шесть, в порядке убывания уверенности: **`same-name`** (одно и то же имя у разных Id —
самый частый случай: следы второго импорта, у канона имя на иврите без `NameEn`, у дубля
то же имя и заполненный `NameEn`), **`name-en`** (латинское `Name` клуба = `NameEn`
ивритского), `suffix` (мусорный хвост парсера), **`word-order`** (те же слова в другом
порядке), `swimmers` (пересечение пловцов), `levenshtein` (опечатка).
«Уверенные» — `same-name`, `name-en` и `suffix`; `word-order`, `swimmers`, `levenshtein` — «спорные».
`--merge-same-name-clubs` льёт только `same-name`; `name-en` склеивается со страницы.

- `name-en` (с 19.11.2026, Р108): у дубля в `Name` латиница, и после Normalize она равна
  `NameEn` клуба с ивритским `Name`. Пример: `Bnei Herzeliya` (1262) → `בני הרצליה` (439,
  `NameEn` = `Bnei Herzeliya`) — `same-name` сравнивал `Name` с `Name` и эту пару не видел,
  её склеили руками 18.11. Канон — ивритская запись. Если тот же `NameEn` у двух ивритских
  клубов — пара не предлагается (неясно, к кому).

- `same-name` группирует по `SwimmerDedupService.Normalize(Name)`, а не по точному имени
  (с 18.11.2026): Normalize сводит гереш `׳` (U+05F3) и апостроф `'`, финальные буквы,
  регистр и пробелы. Пример: `הפועל ג׳מים אילת` = `הפועל ג'מים אילת`.
- `word-order` (с 18.11.2026): отсортированный набор слов после Normalize совпадает, а
  запись разная — `SWIM TLV` / `TLV SWIM`, `Swimming Eilat` / `Eilat Swimming`. Минимум два
  слова. Спорная, а не уверенная: порядок слов в названии клуба иногда несёт смысл, а
  склейка необратима. Канон — у кого больше результатов. Клуб, уже ставший дублем
  `same-name`, канона не берёт, а канон другой пары дублем не становится (нет цепочек).

## Колонка «loglig» у пар «Общие пловцы» (с 19.11.2026, Р112)

Эвристика `swimmers` ловит и переходы: дети ушли из клуба в клуб, карточка ещё в старом
(смена ждёт loglig, Р98), строки протоколов — уже в новом, и два настоящих клуба выглядят
дублем (`הפועל ירושלים` 509 / `הפועל ירושלים אומנותית` 1455, 23 общих). Поэтому у таких пар —
колонка **loglig**: в каком клубе федерация видит общих пловцов.

- **Сводка** — `канон N · дубль N · оба N · другой N · архив N · без ID N · не проверено N`
  (нули не печатаются). Канон и дубль одновременно → красная строка «loglig видит оба клуба —
  похоже на два клуба»: склеивать нельзя, скорее скрыть пару «не дубли». «Оба» — название loglig
  подходит обоим клубам (у нас одинаковые названия). «Без ID» — нет `Verified` loglig-id, «не
  проверено» — loglig-id есть, ответа нет (или он снят под другим id / карточка без клуба).
- **Клик по сводке** — список общих пловцов: имя (иврит) → `/Admin/Swimmers?club={id}`
  (панель клуба пловца), клуб в карточке, клуб на loglig с датой ответа, «профиль #id» →
  `https://loglig.com:2053/Players/Details/{LogligId}?seasonId=…` (сезон — как у
  `LogligClient`, `Loglig:SeasonId`).
- **«Проверить в loglig»** — `POST /api/admin/clubs/dedup-candidates/loglig/check` `{idA, idB}`
  (antiforgery). Открывает карточки общих пловцов, чей ответ старше суток (или его нет, или под
  другим loglig-id), **последовательно, ~1 в секунду**, не больше 120 за нажатие (остаток —
  «осталось N — нажми ещё раз»). 23 пловца ≈ 25 секунд, кнопка всё это время «Проверяю…».
  Данных клуба и пловцов не меняет — пишет только ответ loglig.
- Открытие страницы и раскрытие списка (`GET …/dedup-candidates/loglig?a=&b=`) **в сеть не
  ходят** — только сохранённые ответы.

Ответ хранится в `Sys_SwimmerLogligClubs` (пловец → loglig-id, клуб на карточке, время) — общее
место с суточной сверкой кандидатов смены клуба (`swimmer-club-check`, Р98): что открыла кнопка,
сверка второй раз за сутки не открывает, и наоборот. Название сравнивается тем же
`ClubNameMatcher` (Normalize, прежние названия `ClubNames`, надгробия → канон). Правило —
`ClubPairLogligRule`, сервис — `ClubPairLogligService`; тесты `ClubPairLogligRuleTests`,
`ClubPairLogligServiceTests`.

⚠ `levenshtein` совпадающие (после Normalize) имена **пропускает** (`na == nb → continue`) —
их ловит `same-name`. До появления `same-name` (2026-08-01) такие дубли находились только
случайно, через общих пловцов. Тогда их было 65 групп / 68 клубов / 7793 результата, все
склеены.

## Правка клуба (фаза 7.3 op#2)

`Pages/Admin/Clubs/Edit.cshtml(.cs)`; репозиторий `IClubAdminRepository`
(`ClubAdminRepository`). Переименование (Name/NameEn) + флаг IsPseudo. Имя клуба
нигде не денормализовано (результаты ссылаются по ClubId), поэтому «каскад» — это
инвалидация кэша агрегатов после сохранения. Мутация пишется в аудит (`club.update`
со снимком before/after). Вход: поле «Клуб по Id» на тулбаре Index + клик по имени
клуба в таблице кандидатов (открывается в новой вкладке). Дедуп — через merge, удаление —
только для пустых клубов (ниже).

## Deep-link фильтры «здоровье данных» (T3b)

`?filter=dedup-sure|dedup-unsure` — как раньше. `?filter=no-swimmers|no-country` —
новая сворачиваемая секция «Качество данных» под кнопками merge, грузится лениво
через `GET /api/admin/clubs/quality?filter=…` (`IDataQualityService`, топ-200 + total),
предикаты те же, что в `DashboardStatusService`. Строка линкует на Edit.

## Удаление пустого клуба

В списке `no-swimmers` (и только в нём) у строки есть «✕» — `DELETE /api/admin/clubs/{id}`
→ `IClubAdminRepository.DeleteEmptyAsync`, подтверждение + запись в аудит (`club.delete`
со снимком имени: строки в БД после удаления уже не будет).

Это мусор парсера: имена вида «фамилия + клуб» («גרינברג הפועל דולפין נתניה»), у которых
0 пловцов и 0 результатов. Merge им не помогает — склеивать нечего, останется надгробие.

Сервер **перепроверяет предикат сам**, не доверяя списку на странице (между отрисовкой
и кликом импорт мог повесить на клуб результаты). Отказ с внятным текстом, если клуб:
склеен (надгробие держит старые ссылки `/clubs/{id}`), сам приёмник склейки, псевдо-клуб,
имеет пловцов/результаты, лежит у кого-то в избранном или на него есть заявка на статус
клуба — последние три в БД защищены FK `ON DELETE RESTRICT`, без проверки был бы 500.
Плюс клуб из журнала смен клуба пловцов (`Sys_SwimmerClubChanges` / `Sys_SwimmerClubCandidates`,
Р101): FK там нет, удаление молча оборвало бы историю «было → стало» и откат. Такой клуб и в
список `no-swimmers` / проверку `clubs.empty` не попадает.
После удаления сбрасывается кэш агрегатов.

Рядом с фильтрами — **«Удалить все пустые (N)»** (`POST /api/admin/clubs/delete-empty` →
`DeleteAllEmptyAsync`, подтверждение со вводом слова «удалить», аудит `club.delete-empty-all`
со списком имён). Чистит **весь** список, а не видимые топ-200; каждый клуб проходит ту же
полную проверку, непрошедшие возвращаются в `skipped` и показываются с причиной. Удаление —
одной транзакцией (`SaveChanges` после всего цикла).

⚠ Приёмник склейки без своих результатов формально пуст и в список фильтра попадает —
удалиться он не может (в него склеены дубли) и будет висеть в `skipped` постоянно.
Пока таких нет; появятся — фильтр `no-swimmers` стоит сузить, а не проверку ослаблять.
