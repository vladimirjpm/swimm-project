# /Admin/Health — здоровье данных

Файлы: `Pages/Admin/Health.cshtml(.cs)`; API `DataChecksAdminController`
(`/api/admin/data-checks`): GET (находки + история), `run`, `{id}/accept`, `{id}/reopen`.
Сервис `DataCheckRunner`, проверки — `Services/DataChecks/*` (реализации `IDataCheck`).
Консоль: `dotnet run --project server/Swimm.API -- --check-data`.

Единое место всех проверок целостности (фаза Д3 в [../data-integrity.md](../data-integrity.md)).
До неё проверки жили в семи сервисах: у каждого свой UI, свой запуск, никакой истории и
severity — 20 битых строк и 3 клуба без страны выглядели одинаково.

## Как устроено

Проверка = класс с `Id`, `Title`, `Description`, `Severity` и методом `RunAsync`. Существующие
сервисы (`DataQualityService`, дедупы) НЕ переписаны — поверх них тонкие адаптеры, логика
выборок остаётся в одном месте. **Добавить проверку = класс + строка в `DependencyInjection`.**

Проверка обязана быть ЧИТАЮЩЕЙ: ставит диагноз, лечение (переимпорт, склейка, удаление) —
отдельное осознанное действие на своей странице.

Упавшая проверка не роняет прогон: она сама становится находкой с текстом ошибки. Иначе один
битый запрос лишал бы админа всей картины.

## Находка живёт до устранения

Ключевое решение фазы. Таблица `Sys_DataCheckFindings` **не привязана к прогону**, ключ
находки — `(CheckId, EntityType, EntityId)`:

- находка вернулась → обновляются текст и `LastSeenAt`, статус сохраняется;
- находки больше нет → `Resolution = fixed`, счётчик «закрыто» в прогоне;
- неустранимую можно **принять как есть** (`accepted`) — переживает следующие прогоны.

Почему так: часть находок неустранима (ошибка в протоколе федерации, особенность данных).
Если чистить находки каждым прогоном, решение придётся принимать заново каждый раз — ровно
та боль, ради которой в качестве результатов сделан `SuspectIsManual`. «Принято» пишется
в аудит (`datacheck.accept` / `datacheck.reopen`).

`Sys_DataCheckRuns` хранит историю прогонов со счётчиками по severity — по ней видно, стало
лучше или хуже.

## Калибровка: проверка не должна кричать волком

Первая версия `results.upsert-key-collision` ловила совпадение ключа upsert как такового —
и дала **8071 группу** на живой базе. Причина: заплывы нумеруются ВНУТРИ возрастной ступени,
поэтому «100 комплекс, заплыв 1, дорожка 4» законно повторяется в ступенях 8, 9-10, 11-12
у разных пловцов. Матчер не зря берёт вторым дискриминатором `SwimmerId` — проверка теперь
смотрит на ключ вместе с пловцом и находит 10 групп, где есть на что посмотреть.

Урок в реестр: **новую проверку обязательно прогонять на живой базе до коммита**. Проверка,
которая кричит полсотни раз на здоровых данных, обесценивает все остальные.

`competitions.no-club-point-rule` калибруется тем же способом: проверяется только правило
**клубов**, только у соревнований с результатами и только без пометки «клубный зачёт не
ведётся» (`Competition.ClubPointsDisabled`, галочка в форме соревнования и в быстрой правке
списка — решение Р19). Без пометки проверка звала чинить 20 соревнований, из которых часть
чинить не надо: «зачёт не нужен» и «правило забыли» выглядели в БД одинаково. Правило пловцов нарочно не проверяется —
«не привязано → legacy-расчёт по FINA» это легитимный режим (masters и Маккабиада живут так
намеренно), и находка по каждому такому соревнованию была бы ложной тревогой. Пустые
соревнования тоже пропускаются: считать там нечего, а про пустоту кричит `competitions.empty`.

⚠ И побочное: `Id` проверки — часть ключа находки. Переименование (`relays.gender-from-leg`
→ `relays.gender-conflict`) закрывает старые находки как «починенные» и заводит новые.
Видно в истории: прогон #6 показал «закрыто 92» ровно по этой причине.

## Что уже принято как есть

`relays.gender-conflict` по Маккабиаде-мастерс (42 строки) — **принято, не чиним** (решение
Р16 в [../data-integrity.md](../data-integrity.md)). Там смешанные команды помечены женским
полом, потому что мастерс-полосы сумм возрастов разбираются неверно (инцидент И-10). Сегмент
узкий, личные результаты не затронуты. Если проверка снова покажет эти строки как открытые —
значит их кто-то переоткрыл или данные переимпортировали.

## Кто запускает прогоны

В истории у прогона виден триггер:

- `manual` — кнопка на этой странице;
- `cli` — `dotnet run --project server/Swimm.API -- --check-data`;
- `import` — автозапуск в конце импорта (Д5, решение Р13). Гонится всё сразу, после коммита
  и в `try/catch`; итог показывается прямо в панели хода затягивания на `/Admin/Competitions`
  со ссылкой сюда. Значит, после каждого «Затянуть» история пополняется — это норма.

## Ссылка «на сайте ↗»

У находки две ссылки: `Link` — куда идти **чинить** (страница админки) и `PublicLink` —
куда идти **смотреть глазами** (публичная страница). В БД лежит только относительный путь
(`/competitions/1484`), базу подставляет страница при отрисовке: иначе dev-адрес
`localhost:5173` осел бы в данных и уехал в прод.

База — настройка `PublicSite:BaseUrl`. Пусто = тот же origin (прод, где клиент и админка
живут вместе); в Development по умолчанию `http://localhost:5173`, потому что Vite крутится
на своём порту. Другой порт — пропиши настройку.

Пути строятся `PublicRoutes` — это **четвёртое зеркало** контракта чистых URL
(`client/src/utils/routes.ts` — истина, плюс rewrite в `vite.config.js` и `Program.cs`).
Меняешь путь — правь все четыре. В путь идёт только идентичность ресурса; `tab`/`swim`
и прочий вид туда не добавляем — правило контракта.

## Имя субъекта и точечное исправление

У находки два дополнительных поля: `SubjectName` — имя субъекта ОТДЕЛЬНО от текста (в
`Message` оно вплавлено вместе с дисциплиной, и выделять его мышью — мучение), и пара
`FixKind`/`FixEntityId` — якорь для кнопки-исправления прямо из списка.

На странице имя показывается моноширинным чипом с кнопкой «копировать» — его несут в поиск,
чтобы найти пловца в интернете. Пока заведено одно исправление: `swimmer-gender` у находок
`results.no-gender` — кнопки ♂/♀ (`POST /api/admin/data-checks/{id}/fix-gender`).

⚠ Эндпоинт правит НЕ только пловца, но и его строки результата **без пола**. Проверка смотрит
на `Results.Gender`, а он заполняется на импорте из пловца: поставь пол только пловцу — и
находка провисит до переимпорта, то есть кнопка будет выглядеть сломанной. Строки с полом
ИЗ ПРОТОКОЛА не трогаются: источник мы не перезаписываем.

Кнопки пола цветные — ♂ синяя, ♀ розовая: их жмут по одной на находку, и цвет читается
быстрее подписи.

Рядом — поле **loglig id** с кнопкой «привязать». Смысл в маршруте человека: он всё равно
идёт на loglig искать пол, а id видит там же — глупо заставлять его потом идти на
/Admin/Swimmers/Loglig ради одного числа. Дёргается **штатный** эндпоинт привязки
`POST /api/admin/loglig/set`: он тянет карточку, сверяет год и клуб и пишет свой аудит.
Заводить вторую привязку внутри реестра значило бы держать две расходящиеся реализации.

**Проставленное видно сразу.** Активный пол — залитая кнопка с галочкой; привязанный loglig —
зелёный чип со ссылкой на карточку вместо поля ввода. Без этого после нажатия непонятно, что
уже сделано, и человек жмёт по второму разу.

Оба значения **живые**: `SubjectGender` и `SubjectLogligId` читаются из `Swimmers` в момент
выдачи списка, а не хранятся в находке. Находку обновляет только прогон — сохранённое
значение врало бы ровно там, где оно нужнее всего: сразу после нажатия кнопки.

Реестр при этом остаётся читающим: сам он не чинит, а показывает кнопку, и лечит отдельный
эндпоинт со своим аудитом (`datacheck.fix-gender`).

## Полное число vs список находок

Проверка кладёт в находки не больше 50 строк, но полное число хранится — в
`Sys_DataCheckStates` (строка на проверку: `Total`, `Shown`, `Failed`, когда и в каком
прогоне). Отсюда «показано 50 из 8071» в шапке группы и отсюда же дашборд `/Admin` берёт свои
счётчики, чтобы не считать то же самое вторым кодом. Считать полное число по таблице находок
нельзя — его там физически нет.
