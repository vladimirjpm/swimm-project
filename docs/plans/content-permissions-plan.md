# План — права на медиа отдельно от входа

**Статус:** ☐ не начато (поставлено 16.10.2026, решение Влада). **Оценка:** ~1 день.
Соседний план — [sign-in-rules-plan.md](sign-in-rules-plan.md) (правила входа и регистрации): тот же
принцип «отдельное включаемое правило в одном месте», но про вход, а не про контент.

## Зачем

16.10.2026 убрана галочка 13+ ([important.md](../important.md), «Аккаунт — без возрастного порога»):
войти теперь может кто угодно, в том числе ребёнок с разрешением родителя (Google Family Link).
Сейчас вход = всё сразу: любой вошедший может добавить ссылку на видео и попросить публикацию в клуб или
группу. Нужно развести «вошёл» и «может добавлять / публиковать».

**Примеры, ради которых это делается:**
- **Ребёнок 10 лет:** смотрит результаты, ведёт избранное, ставит «болею» — но не добавляет медиа (или
  добавляет только себе, без публикации).
- **Новый незнакомый пользователь:** добавить медиа себе может, публиковать на всех — после того, как
  админ поставит «можно публиковать».
- **Нарушитель:** админ снимает «можно публиковать» в `/Admin/Users` — аккаунт и избранное остаются.

## Как сейчас (сверено с кодом 16.10.2026)

- Медиа — **только ссылки** (YouTube и т. п.), файлов нет. `Sys_UserMedia.MediaType` различает фото и видео,
  `Visibility` — `private` (по умолчанию) / `public`.
- Публикация уже отделена от добавления: своё медиа приватно, публикация в клуб/группу — запрос с
  одобрением (`UserMediaPublicationService`, `MediaPublicationAudience`).
- **Комментариев нет**; реакции — «нравится» к медиа и «болею» к результату (`ReactionsController`).
- Роли: `User`, `Admin`, `Coach`. Персональное исключение уже есть по образцу — `AppUser.HubGroupLimit` +
  правило `Swimm.Application/Mapping/HubGroupCreationRules.cs` + переключатель в `/Admin/Users`.

**Точки записи контента (где ставить проверку):**

| Действие | Эндпоинт |
|---|---|
| добавить своё медиа | `POST /api/me/media` (`MediaController`) |
| попросить публикацию в клуб/группу | `POST /api/me/media/{id}/publications` |
| медиа в группу | `POST /api/hub-groups/{id}/media` (`HubGroupsController`) |
| медиа к тренировке | `POST /api/hub-groups/{id}/sessions/{sessionId}/media` (`HubGroupTrainingSessionsController`) |
| реакции | `POST /api/media/{id}/like`, `POST /api/results/{id}/cheer` (`ReactionsController`) |

## Устройство

**Права — свойства пользователя, решение — одно правило.**

1. `AppUser`: три поля-исключения `bool?` — `CanAddPhotos`, `CanAddVideos`, `CanPublish` (null = как
   решает политика по умолчанию). Реакции отдельным правом НЕ делаем, пока нет злоупотреблений.
2. Политика по умолчанию — настройки в `Sys_AdminSettings` (реестр `AdminSettingsService`):
   `ContentDefaultCanAddPhotos`, `ContentDefaultCanAddVideos`, `ContentDefaultCanPublish` — по
   умолчанию `true`, то есть поведение до плана не меняется. Прод видит правку через мост кэша.
3. Правило `Swimm.Application/Mapping/ContentPermissionRules.cs` (по образцу `HubGroupCreationRules`):
   `Decide(ContentAction action, string mediaType, bool? personalOverride, bool policyDefault, bool isAdmin)`
   → `Allowed` / `Denied(reason)`. Админу — всегда да. Чистая функция → юнит-тесты на каждую ветку.
4. Сервис `IContentPermissionService` (Infrastructure) читает пользователя и настройки и зовёт правило;
   эндпоинты из таблицы выше спрашивают его первым делом → `403 { error }` с понятной причиной.
5. `GET /auth/me` отдаёт `permissions: { addPhotos, addVideos, publish }` — клиент прячет кнопки «Add video»,
   «Publish», а не показывает их, чтобы потом отказать.
6. `/Admin/Users`: три переключателя на пользователя (вкл / выкл / по умолчанию) + аудит, как у лимита групп.

## Шаги

| # | Что | Готово, когда |
|---|---|---|
| P0 | миграция: три `bool?` в `Sys_AppUsers` | `--migrate` локально, `*PgTests` не падают |
| P1 | `ContentPermissionRules` + юнит-тесты | все ветки: админ, исключение да/нет, политика да/нет, фото/видео |
| P2 | настройки политики в реестре `AdminSettingsService` | видны на `/Admin/Settings`, дефолт `true` |
| P3 | `IContentPermissionService` + проверки в 4 эндпоинтах | интеграционный тест: запрещённому — 403, разрешённому — как раньше |
| P4 | `/auth/me` → `permissions`; клиент прячет кнопки | при запрете кнопок «Add video»/«Publish» нет нигде (медиа, результаты, группа, тренировка) |
| P5 | `/Admin/Users`: переключатели + аудит | смена права видна сразу (мост кэша), запись в `Sys_AdminAudit` |
| P6 | доки: `docs/media-page.md`, `docs/admin-pages/users.md`, `/privacy` (если меняется смысл) | — |

**Поэтапно и безопасно:** до P5 включительно дефолты `true` — сайт ведёт себя как раньше. Ограничивать
(например «новым — без публикации») — отдельным решением после P5, сменой настройки.

## Открытые решения (за Владом)

1. Дефолт для **новых** пользователей после запуска: всё можно (как сейчас) или «публиковать — только после
   одобрения админом»?
2. Нужны ли права на **реакции** (лайк, «болею»)?
3. Что делать с уже опубликованным медиа, если у автора сняли «можно публиковать»: скрывать или оставлять?

## Можно ли отдать Sonnet

P1 и P2 — да: чистая функция и строки реестра, образец есть (`HubGroupCreationRules`, `AdminSettingsService`).
P3–P5 — лучше Opus: четыре контроллера, клиент и админка, легко пропустить точку записи.
