## 0. Порядок этапов

```
K0 сезонный шов (общий со страницей спортсмена)
 ├─► K1 маршрут /clubs/{id}          ──┐
 ├─► K2 club_id + мягкий merge       ──┤
 └─► K3 ClubCompetitionStanding      ──┴─► K4 API ──► K5 клиент ──► K6 админка/качество
```
K1, K2, K3 независимы между собой и могут идти параллельно. K4 требует всех трёх.

**Гейт K0.** Сезонный агрегат (1 сен – 31 авг) нужен и спортсмену, и клубу; считать его дважды
по-разному нельзя. Если ветка спортсмена стартует раньше — K0 делается там, здесь переиспользуется.

## 1. Кто делает

Принцип разделения:

- **Влад/Opus (я):** всё, где цена ошибки — молча неверные цифры или деградация горячего пути.
  Это очки, медали, ранги, эстафеты (`RelayMultiplier`), merge клубов, `ResultDto`.
  Такие баги не падают тестами — они просто показывают неправду.
- **Делегируем Сонету** (`/delegate` → `sonnet-implementer`): работы с **механической приёмкой** —
  есть образец в репозитории, есть чёткий критерий «готово», нет доступа к расчёту очков.

| Этап | Кто | Почему |
|---|---|---|
| K0 сезонный шов | **я** | общий примитив двух страниц, границы сезона + PB-детекция |
| K1 маршрут `/clubs/{id}` | **Сонет** | есть точный образец `swimmer.html`; приёмка проверяемая |
| K2 `club_id` + мягкий merge | **я** | горячий путь `ResultDto` + правка `IClubMergeService` |
| K3 `ClubCompetitionStanding` | **я** | ядро: очки, медали, эстафеты, многодневность |
| K4.1 API overview | **я** | форма ответа и кэш определяют всю страницу |
| K4.2 API roster/records | **Сонет** | ростер тривиален; ось рекордов копируется с hub-групп (8.3) |
| K5.1 каркас страницы + тема + фильтры | **я** | глобальный scope-стейт — шов всех карточек |
| K5.2 карточки по одной | **Сонет** | каждая карточка = отдельный таск с макетом и контрактом |
| K6 админка + чек качества | **Сонет** | есть образцы страниц и чеков `IDataQualityService` |

⚠ Сонету **не отдаём**: `ClubCompetitionStanding`-расчёт, `ResultDto`, merge клубов, правила
очков. Даже как «мелкую правку рядом» — таск-документ должен это явно запрещать.

## 2. Этапы

### K0. Сезонный шов ✅ — я (2026-08-01)

- `Swimm.Domain/SeasonMath.cs` — календарь сезона: `StartYearOf`, `Label`, `RangeOf`,
  `IsInSeason`, `CurrentStartYear`.
- `Swimm.Application/Mapping/SeasonAggregator.cs` — `SeasonSwimRow` (проекция заплыва),
  `IsCountable`, `DisciplineKey`, `SeasonBests`, `PersonalBests`, `SeasonsPresent`.
- Существующие места переведены на шов: `MySwimsRepository`, `HubGroupPublicRepository`,
  `CompetitionAdminRepository`.

⚠ **Находка при реализации: в проекте жили ДВЕ нумерации сезона.**
`MySwims`/`HubGroup` считали по году **начала** (2025/26 → `2025`), а
`CompetitionAdminRepository` — по году **окончания** (`cYear` на isr.org.il → `2026`).
Обе законны и обе нужны, но раньше это нигде не было записано — идеальный шанс на молчаливый
сдвиг ровно на год. Теперь обе в `SeasonMath` (`StartYearOf` / `FederationYearOf`) с явным
предупреждением, а `CompetitionAdminRepository.SeasonOf` делегирует туда же.

**Приёмка выполнена:** 21 новый юнит-тест (границы 31 авг / 1 сен, исключение DSQ и
`SuspectReason`, 25m ≠ 50m, PB в первом заплыве, повтор времени ≠ PB, обе нумерации);
**вся сюита 828/828 зелёная**.

### K2. `club_id` в результатах + мягкий merge ✅ — я (2026-08-01, коммит `89c57c0`)

1. `club_id` в `ResultDto` (горячий путь — замерить до/после).
2. `Club.MergedIntoId` (int?, self-FK) + миграция.
3. `IClubMergeService` перестаёт удалять клуб: проставляет `MergedIntoId`, убирает из публичных
   выборок (справочник, фильтры, зачёты). **301 не делаем** (решение Влада) — `/clubs/{старый id}`
   просто отдаёт актуальный клуб.
4. `ClubCompetitionStanding` при merge пересчитывается (иначе останутся места исчезнувшего клуба).

**Приёмка выполнена.** `club_id` отдаётся (замер на 500 строках: 15-24 мс прогретым, лишнего
JOIN нет — читается из готового FK). Merge покрыт тестами: строка не удалена, `MergedIntoId`
проставлен, повторный merge отбит, зачёт канона пересчитан, склеенный исчез из дедупа.
Тесты 847/847.

⚠ **Найдено попутно:** склеенный клуб надо было исключить не только из витрин, но и из
**кэша клубов в `JsonImportService`** — иначе следующий импорт нашёл бы дубль по имени и
повесил новые результаты на клуб, которого уже нет, молча откатив merge. Также исключены:
дедуп-кандидаты, выпадашка клубов hub-групп, подсказки фильтра, «дыры данных», счётчики
дашборда.

### K3. `ClubCompetitionStanding` ✅ — я (2026-08-01, коммит `0757864`)

1. Сущность + миграция + грант `swimm_ro` (публичная таблица).
2. Расчёт: клуб × зачётная единица → ранг, очки, медали, стартовало/доплыло/заплывов.
   - зачётная единица = **событие** (`EventId`), а не день; одиночное соревнование — само собой;
   - очки по `PointRuleClubs` соревнования, эстафеты с `RelayMultiplier`;
   - `EventCategory` в клубном зачёте **не** учитывается (сознательно).
3. Подключить к `ICompetitionRecalculationService` (импорт, пересчёт, смена правила, merge).
4. Вывод роли зачёта: `IsChampionship` + `PoolType` (25m→winter, 50m→summer) + категория
   возрастной лестницы; поле `StandingKindOverride` — ручное исключение.

**Приёмка выполнена.** 15 тестов + живая сверка на реальной БД: `--rebuild-club-standings`
построил 573 строки на 15 зачётных единиц; для события 1 (Kids зима 2026) таблица
**совпала с `/api/club-summary?eventId=1` до единицы** (61 клуб, топ: 2793/17/6/15/62/138,
2719, 2454, 2430, 1811), то же на соревновании 64 и событии 8.

⚠ **Решение, найденное при сверке: зачёт считается по ПРОТОКОЛЬНЫМ местам.**
У соревнований с `ShowCombineAllResults` есть два законных набора цифр: по протоколу
(у Дольфина на событии 1 — 2430 очков и 12 золотых) и по объединённым местам (1743 и 7).
Оба воспроизводятся расчётом точно; выбран протокольный, потому что тоггл «Combine All
Results» на клиенте по умолчанию **выключен** (`store.filterSelected.is_recalculated = false`),
и витрина Top clubs по умолчанию показывает именно его. Иначе страница клуба молча
противоречила бы странице соревнования. Если Влад решит, что официальный зачёт —
объединённый, меняется одна строка в `ClubStandingService` (и бэкфилл перезапускается).

### K4. API ☐

**K4.1 `GET /api/clubs/{id}/overview?season=&group=` ✅ — я (коммит `7ac6039`)**
Hero + сезоны + грид + standings + timeline + top swimmers + **первые N** ростера и рекордов.
`IsPseudo` → 404. Кэш + ETag, инвалидация на шве K3.
⚠ При `Season=All` грид отдаёт `gridSeasons` (default 3, максимум 20) сезонов, **никогда не все**.

Отклонение от модели §4.5: ростер и рекорды в `overview` **не вкладываются** — они уже есть
отдельными пагинируемыми эндпоинтами (K4.2), дублировать первые N значило бы держать два
источника одной правды.

⚠ **Поймано при живой сверке: двухкатегорийные старты удваивали KPI.** Старт, висящий и в
Kids, и в Young (Хадера-2026, Лига-3), даёт две строки грида — это правильно. Но KPI и
история складывали обе, и у Дольфина выходило 20236 очков вместо 16057 и 13 записей истории
вместо 11. Теперь для KPI и истории строки схлопываются по `CompetitionId`, фан-аут по
группам остаётся только гриду и плиткам. Покрыто тестом.

⚠ **Известное упрощение:** `ClubCompetitionStandings` хранит ОДНУ таблицу на соревнование,
даже если оно висит в двух группах лестницы. Модель (§2.1) предполагает два раздельных зачёта
(таблица Kids и таблица Young отдельно) — это потребует ключа по категории в таблице зачёта.
Сегодня ни один ЧЕМПИОНАТ не двухкатегорийный, поэтому грид не врёт; вернуться, если такой
появится.

## 5. Как разошлись коммиты (закрыто)

K3 готов и проверен, но **коммит требует решения Влада**. В рабочей копии лежит его
незакоммиченная работа (лестница категорий, версии правил очков, админ-страницы), и она
живёт **в тех же файлах**, что правки K3:

| Файл | Мои хунки | Чужие хунки |
|---|---|---|
| `SwimmDbContext.cs` | 2 (DbSet + конфиг сущности) | seed категорий, версии `PointRuleClubs` |
| `ResultRepository.cs` | 3 (вынос расчёта в калькулятор) | 5-6 хунков чужой работы |
| `SwimmDbContextModelSnapshot.cs` | новая таблица | категории + правила, хунки вперемешку |

Разделять снапшот EF по хункам опаснее, чем закоммитить вместе, поэтому по решению Влада
K3 (`0757864`) уехал одним коммитом вместе с его правками в этих трёх файлах — это
отмечено в теле коммита. K0, K1 и K2 закоммичены чисто.
