## Как устроено (в двух словах)

- **Чтение.** `GetOrCreateAsync` (одна сборка на ключ) → пока ответ строится, перехватчик SQL
  (`CacheDependencyInterceptor`) ставит метки сам: `table:T`; в блоке `CacheRows` — `row:R:id` +
  `anyrow:T`; на названные в SQL служебные колонки — `col:T.C` (кроме корня в своём блоке).
- **Запись.** После коммита `CacheInvalidationInterceptor` сбрасывает `table:T`, `row:` (своя строка
  корня и FK на корни — старое и новое значение), `anyrow:T` (каскад, >500 строк, строка не из
  запроса), `col:T.C` вместо `table:T` для правки только служебных колонок
  (`CacheServiceColumns`). Мимо EF — `InvalidateTableCacheAsync<T>()` /
  `InvalidateColumnsCacheAsync<T>(…)`. Весь кэш — только импорт, смена настройки, кнопка.
- **Сторож (К5).** Собранная запись без меток данных и без `CacheTags.NotFromDb` — в Development
  исключение, на проде предупреждение в лог (одно на вид). Режим задаёт регистрация в DI; кэш из
  тестов собирается без режима и молчит, как до К5.
- **Руками (#36).** Ответы клуба несут `page:clubs` и `page:club:{id}` (`CacheTags.ClubPageTags`);
  кнопки «Refresh this club» (таб Admin клуба) и «Сбросить кэш всех клубов» (`/Admin/Cache`) — для
  правки мимо этого процесса API (psql, `dotnet run -- --флаг`, другой экземпляр).
- **Смотреть:** `/Admin/Cache` — записи с метками, журнал сбросов (кто что выкинул), сверка на
  попадании.

## Что дальше

Кэшу больше нечего делать до прода: оба оставшихся этапа ждут внешнего события.

1. **К6 — Redis — отложен до фазы масштабирования** (решение Влада 15.09.2026, §5
   [cache-tags-plan.md](cache-tags-plan.md)). До второго экземпляра API пользы не даёт, а второй
   экземпляр требует ещё выбора лидера для фоновых сервисов, настроек не в памяти и состояния
   превью не в `IMemoryCache` — делать одной фазой. Что учесть в самом Redis — §7 плана К4б: TTL
   ключей версий (версия не должна начинаться заново), `MGET` на попадании, потолок меток строк (200).
2. **К4б.7 — страница пловца**, только если журнал сбросов на ПРОДЕ покажет, что `http:swimmer:*`
   часто выкидывает не импорт и не общий сброс. Там же — уточнить реестр служебных колонок и
   решить про общую метку корня (`row:Clubs:438` роняет и состав, и группы клуба, §6 плана К4б).
   Первым делом на проде — заглянуть в блок «Без меток данных» на `/Admin/Cache` и в лог
   (предупреждения сторожа К5): на проде сторож не бросает, только пишет.

## Как проверять вживую

- API Влада на :5078 не глушить. `dotnet build server/Swimm.API -c Release` → превью
  `swimm-api-5079` (админ через DevAdminBypass), клиент — `client-5181-api5079`.
- «Failed to connect to 127.0.0.1:5445» — не запущен Docker Desktop: запустить его, дождаться
  `docker info`, потом `docker compose -f server/docker-compose.yml up -d`.
- Метки записей — `/Admin/Cache`, блок «Все записи»; журнал сбросов — там же. Прогревать
  эндпоинты с `max-age` через `fetch(url, { cache: 'no-store' })`, иначе ответ даст кэш браузера.
- Правка данных для приёмки — только обратимая: снимок до (psql через Bash — PowerShell съедает
  кавычки идентификаторов), возврат после. Кнопки и смена настроек пишут строки аудита.

## Грабли

- PG-тесты молча зеленеют без базы — проверить, что `swimm-postgres` жив; новое ключевое
  утверждение — мутацией (сломать → красно → вернуть).
- Новое место кэша, которое в Development падает «собрана без меток данных», — не глушить
  `NotFromDb`, пока не ясно, откуда данные: почти всегда они прочитаны до фабрики (так было у
  `/api/categories/{key}`). Грабли и приёмы — конец [../admin-pages/cache.md](../admin-pages/cache.md).
- Правка файлов скриптом: не терять BOM у файлов, которые им начинаются (`club-project.tsx`,
  `ClubsPublicController.cs`), иначе дифф шумит.
- Стопку PR сливать обычным merge-коммитом (не squash) и перед каждым слиянием переводить
  следующий PR на `master` (`gh pr edit N --base master`): ветки при слиянии тут не удаляются, и
  GitHub сам не перенацеливает.
- Репозиторий ПУБЛИЧНЫЙ — уязвимости в доках, коммитах и описаниях PR не расписывать.
