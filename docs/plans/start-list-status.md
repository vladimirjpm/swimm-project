## 1. Что это делает

Перед соревнованием тянем с loglig стартовый протокол — кто, в каком заплыве, на какой
дорожке и во сколько плывёт, — и показываем это родителю по ссылке, без логина.

Три уровня одного экрана: программа дня → заплыв с дорожками → карточка пловца
(«первый старт ≈11:24, приезжать к 10:39»). Плюс срез клуба и «ближайшие старты» избранных.

## 2. Как этим пользоваться

### Затянуть

| Способ | Где |
|---|---|
| **Кнопка** (основной) | `http://localhost:5078/Admin/Competitions` → «Стартовый протокол» в строке соревнования |
| По расписанию | `/Admin/Settings` → `StartListEnabled = true`, окно — `StartListDaysAhead` (по умолчанию 14 дней). **Выключено по умолчанию** |
| Из консоли | `dotnet run --project server/Swimm.API -- --pull-start-list <orgCompId>` |

Повтор **идемпотентен** — жать можно сколько угодно; это штатный режим, посев меняется до
последнего дня. У чемпионата забор занимает минуты: под две сотни запросов с паузой 2 с.

Ответ `empty` — не ошибка, а «тянуть пока нечего»: либо посев ещё не сделан, либо у
соревнования нет `logligId` (тогда сперва «Обновить» на той же строке).

Сшивка с результатами идёт **сама** в конце импорта протокола. Вручную:
`dotnet run --project server/Swimm.API -- --stitch-start-list <orgCompId>`.

### Посмотреть

Клиент живёт на **:5173** (`cd client && npm run dev`), сервер — на :5078. Не путать:
`:5078` это `/Admin/*`, `/api/*` и `admin-home.html`; всё публичное — на :5173.

| Что | Адрес |
|---|---|
| Предстоящие в общем списке | `http://localhost:5173/competitions` — секция **Upcoming** сверху |
| Программа дня | `http://localhost:5173/competitions/upcoming/{orgCompId}` |
| Карточка пловца (ссылка родителю) | `…/competitions/upcoming/{orgCompId}?swimmer={swimmerId}` |
| Конкретный заплыв | `…?heat={orgDisciplineId}` |
| У импортированного соревнования | `http://localhost:5173/competitions/{id}?tab=startlist` |
| Конкретный источник составного старта | `…?tab=startlist&src={orgCompId}` |

⚠ `{orgCompId}` — это **compID сайта федерации**, а не наш `Competitions.Id`. Разные
пространства чисел; отдельный сегмент `upcoming` их и разводит.

### API (публичный, анонимный, snake_case)

```
GET /api/start-list/competitions?days=60          предстоящие соревнования
GET /api/start-list/{orgCompId}                   программа дня
GET /api/start-list/{orgCompId}/events/{id}       заплыв с дорожками
GET /api/start-list/{orgCompId}/swimmers/{id}     карточка пловца
GET /api/start-list/{orgCompId}/clubs/{id}        срез клуба
GET /api/start-list/upcoming?swimmerId=1&days=21  ближайшие старты (favorites)
GET /api/start-list/search?orgCompId=1&q=ivan       поиск пловца по имени (все источники)
GET /api/start-list/swimmers/{id}?orgCompId=1&orgCompId=2  карточка по всем источникам
```

**Поиск и избранные в табе** (28.08.2026). Над зумами — панель «найти своего»: поле поиска
по имени и чипы избранных для залогиненного (цвета — токены `--theme-personal-*`, те же, что
у полосы FAVORITES в шапке соревнования). Поиск идёт по ВСЕМ источникам соревнования сразу
и в выдаче показывает ДНИ: у составного старта «в какой день» — половина ответа. Ищем и по
английскому имени, и по ивритскому: у пловцов, заведённых стартовым протоколом, английского
имени ещё нет, а ищут их именно те, кто читает иврит.

**ПРАВИЛО (Влад, 28.08.2026): имена пловцов и названия клубов — на ИВРИТЕ по умолчанию, всегда.**
Английское имя — только фоллбек, когда ивритского нет, либо по явному запросу языка.
Порядок в коде: `FirstName/LastName` → `FirstNameEn/LastNameEn`, не наоборот (носители —
`StartListPublicRepository.SwimmerName`, `UserFavoriteRepository`). Правилу «UI только
English» это не противоречит: то — про строки интерфейса, а имя человека — данные.

**РЕШЕНИЕ: строки стартового протокола — НЕ `SwimRow`** (проверено на живом экране
28.08.2026). Общая строка заплыва собрана под РЕЗУЛЬТАТ: место/медаль, очки, дуга уровня,
крупное время справа. В стартовом протоколе результата ещё нет, и такая строка врёт видом —
посевное время читается как проплытое, а половина ячеек пустует прочерками. Главное число
здесь — ВРЕМЯ СТАРТА, дальше heat и дорожка.

Общим остаётся то, что и должно быть общим: плитку дисциплины рисует `UI_SwimmStyleIcon`,
время — `UI_SwimTime`, имя с эмблемой клуба — `UI_SwimmerNameCell`. Ловушка на будущее:
`quality` у `SwimRow`/`UI_SwimTime` означает СПОРНОЕ время (протокол/рекорд), а не класс
посева, — передавать туда `"seed"` нельзя.

## 4. Решения, которые нельзя переизобрести

1. **Заявки — своя таблица, не `Results`.** Тот же довод, что у `Sys_TrainingResults`: времена
   другого происхождения не должны попадать в таблицу, из которой считаются рекорды, зачёт
   и медали. Полный разбор развилки — план §2.
2. **`Competitions` до старта НЕ трогаем.** У заявки нет FK на соревнование, идентичность —
   `OrgCompId` (И7), `CompetitionId` заполняется бэкфиллом после импорта. Иначе `BulkPullService`
   (фильтр `MatchedCompetitionId is null`) навсегда теряет соревнование из автозабора, а
   «последнее соревнование» на главной уезжает в будущее.
3. **Заявки не стираем.** Заявка без результата = неявка дня старта, единственный ответ на
   «почему в протоколе меньше, чем заявлено».
4. **Пловец матчится по `LogligId`**, имя — фоллбек: в стартовом протоколе имена только
   на иврите. Новичок заводится сразу (решение В5) и один раз на забор.
5. **Клубы НЕ заводятся.** Матчинг-по-имени с созданием — то, что плодило клубы-дубли
   (инцидент И-13). Не нашёлся → «No club» + счётчик в отчёте.
6. **Посевное время — третий класс качества** (`quality: "seed"`). Это личный рекорд
   с ДРУГОГО старта; показывать его как результат нельзя (И11).
7. **У одного соревнования бывает НЕСКОЛЬКО источников.** Скалярный `Competition.OrgCompId`
   — штамп «этот день импортирован из такого-то compID», и он один (AK уникален). А стартовый
   протокол нашего старта может состоять из нескольких протоколов федерации: «אליפות ישראל
   ארנה 8-11 חורף 2026» — у нас один старт из трёх дней, у федерации четыре окружных compID
   (север 16789, центр 16787 и 16788 в один день, юг 16786). Поэтому привязки живут в
   публичной таблице `CompetitionSources`, а не в поле. Овервью отдаёт `start_list_sources[]`;
   при пустом списке он синтезируется из `org_comp_id` — соревнования, заведённые до таблицы,
   работают как раньше. Единица подтаба — ИСТОЧНИК, а не день: в один день бывает два compID.
8. **Предстоящие строятся по заявкам**, а не по «Входящим»: `Sys_DiscoveredCompetitions`
   приватна (нет гранта `swimm_ro`), и публичный путь её не видит.

## 5. Footguns

- **Полночь в источнике = «время не назначено»** (`שעת הזנקה:00:00`), не 00:00. Как и
  `00:00.00` в графе норматива.
- **Вложенная таблица-подсказка** в ячейке норматива рвёт наивный `<tr>(.*?)</tr>` — так
  терялось 8 заплывов из 177 и целый день. Отсюда `TopLevelRows`/`CellsOf` в парсере.
- **Эстафета — 4 строки с одинаковыми heat и lane.** Это одна команда, а не четыре дорожки.
- **Дистанция эстафеты — `4X50`**, «m» к ней не приписывать. Всё форматирование дистанции
  идёт через `swimLabel` в `start-list-helpers.ts` — не заводи шестую копию.
- **`CompDate` лежит в `timestamp without time zone`.** Сравнивать с `DateTime.UtcNow`
  (Kind=Utc) нельзя — Npgsql падает 500. In-memory провайдер в тестах это НЕ воспроизводит.
- **`CachedJson` сериализует дефолтными настройками**, мимо политики MVC: без
  `[property: JsonPropertyName]` наружу поедет PascalCase вместо snake_case.
- **Build-lock:** процесс называется `dotnet.exe`, не `Swimm.API.exe`. И Visual Studio держит
  сборку, пока приложение запущено.
