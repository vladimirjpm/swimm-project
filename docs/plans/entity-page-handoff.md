кто угодно. Отсюда «одна реализация, разные варианты» во всём — от страницы до публикаций.

## 4. Фильтр статусов на `/my-media` — СДЕЛАНО 09.09.2026

Запрос был «сделай фильтр на статусы». Оказалось — фильтр уже написан
(`all · private · pending · published · rejected`, статус выводит `derivedCardStatus` в
`components/status-styles.ts`), но спрятан тремя условиями: карточка рендерилась только при
`seg === 'with'`, применялся он тоже только там, а при уходе с сегмента сбрасывался в `all`.
Поэтому его считали несуществующим.

**Привязка снята** (коммит «/my-media: фильтр статусов отвязан…»):

- карточка «Publication status» в шторке фильтров видна ВСЕГДА;
- убрана внутренняя резка по `media_type === 'video'`: «private» (нет ни одной публикации) для
  фото значит ровно то же, что для видео;
- фильтр действует на ВСЕ ТРИ списка страницы (`mediaVisible` в `my-media.tsx`) — как давно
  делает «Shared with». Иначе выбранный «pending» сужал бы заплывы и молча оставлял
  нетронутыми карточки соревнований и Unlinked media.

Проверено вживую 09.09.2026 (после починки `DevAdminBypass`, §6): страница открывается под
Владом, чипы статусов на месте.

**Плюс карточка-сводка в шапке панели** (запрос Влада «подвинь баннер вправо, левее — сколько
чего»): слева всегда видно `N videos (+ M photos)` и четыре чипа с числами по статусам, справа —
прежний баннер модерации, прижатый `lg:ml-auto`. Считает `mediaStats` в `my-media.tsx` по ВСЕМУ
медиа страницы (заплывы + карточки соревнований + Unlinked, дедуп по id ради ног эстафеты), а не
по видимому: сводка не должна прыгать от выбранного фильтра. Половины ряда про разное — слева
моё медиа, справа чужие заявки, где я модератор.

Чипы сводки — **тот же фильтр**, что карточка «Publication status» в панели: одно состояние
`statusFilter` на оба места, второго списка нет, и выбор в панели подсвечивает чип наверху.
Повторный клик по выбранному снимает фильтр; чип с нулём не кликается (увёл бы страницу в
«Nothing matches the filters» без причины). Выбранный помечен КОЛЬЦОМ, а не заливкой: заливка у
этих чипов уже занята самим статусом.

Что осталось из идей по фильтрам (не делалось): поднять статусы из шторки наверх, рядом с
рядом чипов «Shared with»; и добавить в «Shared with» КЛУБ — после работы по клубам у
публикации есть `target_type`, а чипы показывают только группы.

## 6. Footguns этой сессии — сэкономят час

1. **`DevAdminBypass` — ПОЧИНЕН 09.09.2026** (`server/Swimm.API/Security/DevAdminBypass.cs`).
   Теперь неаутентифицированный запрос идёт от **реального** пользователя из БД: по умолчанию
   первый активный админ, кем именно — `DevAdminBypassEmail` в `appsettings.Development.json`
   (файл не коммитится, ключ придётся добавить у себя). `/auth/me` отвечает как залогиненный,
   таб `Admin` появляется, `/my-media` открывается под своим медиа, решения по заявкам не
   падают на FK.
   Что осталось знать: на **пустой БД** (пользователя нет) обход падает в старый фоллбек —
   синтетический админ `NameIdentifier = "0"`, у которого ровно прежние болячки (нет email-claim,
   FK на `Sys_AppUsers`); защиты от него в `ResolveOwnerIdAsync`/`ResolveAdminUserIdAsync`
   поэтому оставлены. Личность **кэшируется до рестарта API** — сменил `DevAdminBypassEmail`
   или роли, перезапусти процесс.
2. **Кэш витрин 60 секунд** (`Cache-Control: public, max-age=60`), и браузер держит ответ даже
   после сброса серверного кэша. Правишь настройки руками — либо жди минуту, либо читай API
   с `cache: 'no-store'`.
3. **HMR оставляет две копии модуля контекста** при правке нескольких файлов подряд: страница
   падает с `useLoginModal must be used within <LoginModalProvider>`, хотя провайдер на месте.
   Лечится перезапуском dev-сервера. Консоль браузера при этом держит старые записи и после
   перезагрузки — проверять надо по DOM.
4. **Build-lock**: `dotnet build` падает на MSB3027, пока жив запущенный API. Останови процесс,
   потом собирай (правило из корневого CLAUDE.md, ловилось трижды за сессию).
5. **Нативный `<select>` в тёмной теме — белое на белом** (починено 09.09.2026). Раскрытый
   список рисует браузер: цвет текста берёт наш, а подложку — системную. Лечится только
   `color-scheme` (правило в `deep-theme.css`, действует на весь `.theme-deep`), стилизовать
   `<option>` ненадёжно. Заводя тёмный контрол, проверяй его В РАСКРЫТОМ виде — в скриншот
   попапа не видно.
