[спортсмен](../design-handoff-athlete-page.md) · [клуб](../design-handoff-club-page.md).

## 1. Зачем одной фазой

Обеим страницам нужен один и тот же серверный примитив — **сезонный агрегат** и «лучшее в
сезоне». Считать его дважды по-разному нельзя: разойдутся цифры на страницах спортсмена и
клуба, и это будет неотлаживаемо. Поэтому 10.1 — общий шов, а дальше ветки независимы.

```
10.1 сезонный агрегат (общий шов)
 ├─► 10.2 API спортсмена ──► 10.3 страница спортсмена
 └─► 10.4 маршрут клуба ──► 10.5 club_id ──► 10.6 API клуба ──► 10.7 страница клуба
```

## 2. Стартовая асимметрия (главное, что надо помнить)

| | Спортсмен | Клуб |
|---|---|---|
| Чистый URL | ✅ `/swimmers/{id}` | ❌ `club` в query как **фильтр** |
| Профильный API | ✅ `GET /api/swimmers/{id}` | ❌ нет |
| Агрегат | ✅ `/api/athletes/career` (по **имени**!) | ◐ `/api/club-summary` — по соревнованию, не по клубу |
| ID в результатах | ✅ `swimmer_id` | ❌ только строки `club` / `club_en` |
| Медиа | ✅ `/api/swimmers/{id}/media` | ❌ нет (есть у hub-групп) |

Страница спортсмена — **достройка** существующего. Страница клуба — **стройка с нуля**.

## 3. Этапы

### 10.1 Сезонный агрегат — общий шов ☐

Один хелпер «результаты → сезоны», которым пользуются обе ветки.

- Границы сезона: **1 сентября — 31 августа**, метка по году начала (`2025` → `2025/26`).
  Уже так в `HubGroupPublicRepository` и `IMySwimsRepository` — **брать оттуда, не изобретать**.
- Из best/PB исключать `TimeFail` (DSQ/DNS/DNF) и `SuspectReason` (помеченные ошибки протокола).
- Ключ дисциплины: стиль × дистанция × **бассейн** (25m/50m несравнимы). Для спортсмена
  дополнительно `EventCategory` (open/para/mix/возрастная) — иначе три золота Маккабиады
  в одной дисциплине сольются.
- PB-детекция: «улучшил личник» = время лучше всех предыдущих в том же ключе дисциплины.
- **Приёмка:** юнит-тесты на границы сезона (31 авг / 1 сен), на исключение DSQ и
  `SuspectReason`, на 25m/50m как разные ключи, на PB в первом же заплыве.

### 10.2 Спортсмен: `GET /api/athletes/{id}/timeline` ☐

```jsonc
{
  "seasons": [
    { "season": 2025, "label": "2025/26",
      "competitions": 6, "races": 31, "points": 12840, "bestPoints": 512,
      "gold": 3, "silver": 1, "bronze": 2, "podiums": 6,
      "personalBests": 9, "levelPeak": "KMS",
      "clubName": "…",          // клуб В ЭТОМ сезоне — он меняется
      "ageGroup": "14" }
  ],
  "byEvent": [
    { "stroke": "freestyle", "distance": "50", "pool": "25m",
      "careerBest": { "time": "26.41", "timeMs": 26410, "date": "…", "competition": "…", "points": 512 },
      "seasonBests": [
        { "season": 2025, "time": "26.41", "timeMs": 26410, "points": 512, "date": "…",
          "competition": "…", "improvementMs": -640, "isPersonalBest": true }
      ] }
  ]
}
```

Попутный долг: **`/api/athletes/career` ищет по полному имени, а не по id**. Решить здесь —
перевести на id (имя оставить как алиас для попапа), иначе две страницы будут искать
спортсмена по-разному. Плюс известный остаток фазы 3.5: скан по имени без индекса, холодный
запрос ~5 с.

- **Приёмка:** сумма по сезонам сходится с `/api/athletes/career`; кэш+ETag как у соседей.

### 10.3 Страница спортсмена ☐

Довести `/swimmers/{id}` до уровня попапа и выше. Блоки — §3 хендоффа: hero (фото или
монограмма + RTL-имя + клуб-чип + флаг + бейджи 🏆/loglig/local + ❤/⭐), KPI-полоса,
season switcher, график по сезонам, матрица season-bests, best times by event, история
заплывов с фильтрами, медали с раскрытием «за что», рекорды, медиа-галерея, группы.

- Переиспользовать существующее: `UI_NormativeLevelIcon` (дуга уровня), `UI_MedalIcon`,
  `UI_SwimmerTimeCell`, `UI_SwimmerGallery`, `UI_RecordCount`, строки результатов из попапа.
- Обязательно: RTL, light/dark по правилу парных токенов, UI на English, пустые состояния
  (нет фото / нет карьеры / нет уровня).
- **Приёмка:** прокликано вживую, `tsc` чистый, попап не сломан.

### 10.4 Клуб: идентичность ☐

Новый ресурс `/clubs/{id}` (+ опционально `/clubs/{id}/results`).

- Новая html-точка входа (по образцу `swimmer.html`) в `rollupOptions.input`.
- **Три зеркала контракта — правятся вместе:** `client/src/utils/routes.ts`,
  `cleanUrlRewrite` в `client/vite.config.js` (dev), rewrite-middleware в
  `server/Swimm.API/Program.cs` (прод, строки ~410–461).
- В путь — только идентичность; сезон/фильтры остаются в query.
- **Приёмка:** `/clubs/42` открывается и в dev, и в прод-сборке; `parseRoute()` возвращает clubId.

### 10.5 Клуб: `club_id` в результатах ☐

- Добавить `club_id` в `ResultDto` (горячий путь — мерить) **или** сервер резолвит
  `id → набор имён`. Рекомендация: `club_id`, потому что имя не уникально и следы дублей живут.
- **Пережить merge:** после склейки старые id исчезают. Нужен редирект `merged_into`
  (иначе внешние ссылки гниют после каждой чистки — клубов было 231, стало 128).
- **Приёмка:** страница старого id ведёт на актуальный клуб; агрегаты совпадают с
  `/api/club-summary` (который клеит по имени) на контрольном соревновании.

### 10.6 Клуб: API ☐

- `GET /api/clubs/{id}` — профиль: имена HE/EN, страна, `isPseudo`, счётчики пловцов
  (всего / активных в сезоне), первый и последний сезон, ссылка на официальную hub-группу
  (`HubGroup.ClubId` + `IsOfficial`).
- `GET /api/clubs/{id}/timeline` — сезоны: соревнования, пловцы, заплывы, очки, медали,
  лучшее место клуба в зачёте, число личников, новые рекорды.
- `GET /api/clubs/{id}/roster` — состав (пагинация, сортировки), основа `Swimmer.ClubId`.
- `GET /api/clubs/{id}/records` — клубные рекорды по оси стиль × дистанция × бассейн × пол,
  без эстафет и DSQ. **Ось уже реализована для hub-групп (фаза 8.3) — переиспользовать.**
- `GET /api/clubs/{id}/competitions` — история участия: соревнование, дата, очки, медали,
  место клуба.
- **Приёмка:** кэш+ETag; псевдоклуб (`IsPseudo`) отдаёт 404 или явный маркер, а не обычный профиль.

### 10.7 Страница клуба ☐

Блоки — §3 хендоффа: hero (круглый логотип или инициалы + RTL-имя + флаг + бейдж official),
KPI, season switcher, график по сезонам, top swimmers, ростер, клубные рекорды (25m/50m
раздельно), история соревнований, карточка официальной группы.

- Переиспользовать: **`UI_ClubDetails`** (уже богатая карточка клуба в `filter-club`),
  `UI_ClubLogo` (круг + фолбэк на инициалы), `UI_FlagEmoji`.
- **Приёмка:** прокликано вживую, включая клуб без логотипа, клуб без пловцов и псевдоклуб.

## 4. Решения, которые нужны до 10.6

1. **Складывать ли очки клуба за сезон?** Очки начислены по правилу **конкретного
   соревнования** (`PointRuleClubs` с привязкой) — сумма за сезон это сумма несравнимых
   величин. Варианты: (а) сумма со сноской, (б) показывать **место в зачёте** каждого
   соревнования вместо суммы. *Рекомендация: (б) как основной визуал, (а) — второстепенной
   цифрой со сноской.*
2. **Логотип клуба.** Сейчас файл по **имени** (`images/club-icon/{name}.png`) →
   переименование в админке ломает картинку. Заводить ли поле в БД? *Рекомендация: да, поле
   `LogoUrl`, файл по имени — фолбэк.*
3. **Псевдоклубы** (`IsPseudo` — «USA», «Israel», «M25»): страницы нет / есть, но иная.
   *Рекомендация: 404 + пояснение, это не клуб.*

## 5. Риски

- **Горячий путь `/api/results`** при добавлении `club_id` (10.5) — мерить, не «на глаз».
  Прецеденты в проекте: фильтр по `Style.Name` через JOIN давал p95 14 с (фикс — резолв в Id).
- **Расхождение цифр** между новой страницей и существующими витринами (Top clubs,
  `club-summary`, попап спортсмена). Единственная защита — 10.1 как единственный источник
  сезонной арифметики + сверка на контрольном соревновании.
- **Merge клубов/пловцов** ломает диплинки, если не сделать редирект (10.5).
- **RTL + смешанные строки** (иврит + латиница + цифры времени) — типовой источник косметических багов.

## 6. Как вернуться к работе

2. Проверить, не изменились ли: `routes.ts` (контракт маршрутов), `ResultDto` (появился ли

3. Начинать с 10.1 — без него остальное разъедется.
