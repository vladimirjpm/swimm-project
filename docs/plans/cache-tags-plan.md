# Кэш: сброс по меткам и готовность к Redis

**Статус:** К1–К4 СДЕЛАНЫ. К1 — метки в `ICacheService` и склейка промахов; К2 — два
нарушения правил Redis исправлены, сторож-тест; К3 — метки таблиц ставятся САМИ, все записи

(решение Влада 15.09.2026, §5). Точность до строки — **решено делать** (Влад, 14.09.2026, §7-2): отдельный план
[cache-row-precision-plan.md](cache-row-precision-plan.md), этапы К4б.0–К4б.7; К4б.0–К4б.6 сделаны
и в master (PR #29–#34; сужение группы и клуба и точность по служебным колонкам включены по
умолчанию; К4б.7 — по замеру на проде).
Продолжение фазы 3 (ROADMAP, пункт 3.6).

**Решение Влада (11.09.2026):** Redis сейчас не нужен, но когда-нибудь понадобится. Всё, что
делаем с кэшем, делаем так, чтобы переезд на Redis был заменой одной регистрации в DI, а не

---

## 1. Как сейчас

- Кэш приложения — `ICacheService` → `MemoryCacheService`, в памяти процесса. Около 30 видов
  ответов, живут от 5 минут до суток (season-best).
- Сбросить умеет только ВСЁ сразу: `InvalidateAllAsync` (отмена одного общего токена),
  вызывается руками примерно в 65 местах записи. `RemoveAsync(key)` есть, но им никто не пользуется.
- Кэш браузера: витрины отдаются с `max-age`; страницы, которые правят из их же таба Admin
  (группа, клуб), — с `no-cache` + ETag (11.09.2026, после «расписание не сохраняется»).

## 2. Почему это станет критично

1. **Сбрасываем слишком много.** Мелкая правка (расписание одной группы) выкидывает и тяжёлые
   витрины — season-best, рекорды, все клубы. Когда группы начнут вести десятки тренеров, общий
   сброс пойдёт каждые несколько минут и кэш перестанет работать. (Наплыв после сброса — N
   одновременных запросов N раз строили один и тот же тяжёлый ответ — закрыт в К1 склейкой
   промахов; сам лишний сброс остаётся до К3–К4.)
2. **Сброс можно забыть.** Он ручной; забыли в новом месте записи — витрина врёт до конца TTL
   (у season-best это сутки).
3. **Несколько экземпляров сервера.** Сброс в памяти одного процесса не виден другим: при двух
   и больше экземплярах на Azure запись сбросит кэш только у того, кто её обработал.

## 3. Решение

### 3.1 Метки

- Ответ, когда кладётся в кэш, перечисляет **метки — из каких данных он собран**. Метка — это
  таблица (`results`, `records`, `competitions`, `clubs`, `hub-groups`…) или таблица с id
  (`hub-group:24`, `club:438`, `swimmer:123`).
- Все метки — константы и фабрики в ОДНОМ классе `CacheTags` (Application). Строки-литералы
  по месту запрещены — иначе метка записи и метка сброса разойдутся опечаткой.
- Каждая запись неявно несёт метку `all`: `InvalidateAllAsync` = сброс `all`. Большой молоток
  остаётся для импорта и аварийных случаев.

**Почему метки объявляет ответ, а не список «таблица → какие кэши сбрасывать».** В списке
знание о зависимостях лежит далеко от запроса: завёл новую витрину — надо помнить, в списки
каких таблиц её дописать, и забывают именно это. Метку пишут рядом с запросом, где видно, что
он читает. (Вопрос §7-1 снят К3: метки берутся из SQL сами.)

**Метки таблиц ставятся САМИ, руками — только точность до id.** Пока строится ответ (внутри
`CachedJson`/загрузки кэша открыт контекст сборки, `AsyncLocal`), каждый SQL-запрос отмечает
таблицы, которые он трогал; ответ кладётся в кэш с этими метками. Так страница клуба получает
метку `records` потому, что стена рекордов читает `Records`, — автор страницы про это не думает.

- Реализация — `DbCommandInterceptor` (`ReaderExecuting`): в тексте SQL ищем закавыченные имена
  таблиц из модели EF (`"Records"`, `"NormativeStandards"`). ⚠ НЕ `IQueryExpressionInterceptor`:
  он срабатывает на КОМПИЛЯЦИИ запроса, а скомпилированный запрос EF кэширует — на втором
  выполнении он молчит, и метка потеряется.
- ⚠ Вложенный кэш: ответ собирается из другого кэшированного ответа (обзор клуба зовёт стену
  рекордов). На ПОПАДАНИИ во внутренний кэш SQL не выполняется, и внешний не узнал бы про
  `records`. Поэтому запись кэша хранит свои метки рядом со значением, и попадание добавляет их
  в текущий контекст сборки. Работает одинаково в памяти и в Redis.
- Лишняя метка (колонка случайно зовётся как таблица) = лишний сброс, не ошибка.
- **Сделано в К3:** `CacheBuildScope` (контекст сборки в `AsyncLocal`) + `CacheDependencyInterceptor`
  (`ReaderExecuting`/`ScalarExecuting`, оба `DbContext` через DI). Запись хранит метки с
  токенами на момент касания; попадание во вложенную запись и ожидание чужой сборки передают
  её метки наружу. Проверено на живой базе: у season-best — `Competitions`, `Results`, `Styles`,
  `Swimmers` (без `HubGroups`); у страницы группы — `HubGroups`, её состав и медиа.

**Пример: изменились рекорды или нормативы** (по коду на 11.09.2026). Таблицу `Records` читают:
справочник `/api/records`, страница клуба (стена рекордов и KPI «Records» в шапке), страница
пловца (его рекорды и колонка «Δ Israel»), обзор соревнования (новые рекорды). Все они получат
метку `records` сами, и правка рекорда сбросит ровно их. `NormativeStandards` на сервере читает
один ответ — `/api/normative-standards`; дуги уровня считает браузер из него.

### 3.2 Кто сбрасывает

- **Автоматически** — `SaveChangesInterceptor`: после успешного сохранения собирает изменённые
  сущности → метки (таблица + id) → `InvalidateTagsAsync`. Карта «сущность → метки» одна, в
  `CacheTags`. «Забыл вызвать сброс» исчезает как класс.
- **Явно** — массовые операции мимо трекера EF (`ExecuteUpdate`/`ExecuteDelete`, сырой SQL,
  импорт). Импорт сбрасывает `results` (+ `competitions`, `clubs`, `swimmers`).
- ⚠ **Сброс — после коммита транзакции, не внутри.** Если сбросить до коммита, соседний запрос
  успеет прочитать ещё старые данные и снова положить их в кэш — до конца TTL. При открытой
  транзакции метки копятся и сбрасываются на `TransactionCommitted`.
- **Сделано в К4 (перехватчик):** `CacheInvalidationInterceptor` (`ISaveChangesInterceptor` +
  `IDbTransactionInterceptor`, синглтон, только на `SwimmDbContext`). Метки — `table:X` каждой
  изменённой таблицы (имя из модели EF), состояние — по экземпляру контекста. Без транзакции
  сброс сразу после сохранения (свою внутреннюю транзакцию EF коммитит ДО события «сохранено»);
  в открытой — на коммите; откат выбрасывает, брошенная транзакция (Dispose без коммита, события
  нет) выбрасывается следующим стартом; сбой коммита — сбрасывает (исход неизвестен, лишний
  сброс безопасен); упавшее сохранение внутри транзакции выбрасывает только свои метки.
  Удаление добавляет таблицы, куда оно каскадит в базе (`Cascade`/`SetNull` из модели, по цепочке).
  Явный сброс массовых операций — `db.InvalidateTableCacheAsync<TEntity>()` (до К4б.2 —
  `InvalidateCacheTagsAsync(TableTag<T>())`; теперь метки `table:T` + `anyrow:T`,
  [cache-row-precision-plan.md](cache-row-precision-plan.md) §2.2 п. 6): имя из модели, не
  литерал, и тоже ждёт коммита открытой транзакции.
- ⚠ **Почему НЕ перехват записей по тексту SQL** (казалось бы, он поймал бы и массовые
  операции): отметка «был онлайн» — массовый `UPDATE "Sys_AppUsers"` на запросах пользователя, а
  страница группы собрана и из `Sys_AppUsers` (живой снимок 14.09.2026). Общий перехват выбивал бы
  страницы групп постоянно. Массовые операции сбрасывают явно — там, где это нужно.

### 3.2а Разбор мест записи при снятии ручных сбросов (К4, 14.09.2026)

- **~50 из ~58 мест писали только через `SaveChanges`** — ручной сброс снят без замены.
- **Единственная массовая запись на этих путях** — стирание объединённых мест в пересчёте
  (`CompetitionRecalculationService.ClearCombinedAsync`, `ExecuteUpdate` по `Results`). Её зовут
  правка соревнования, привязка и правка правил очков, правка результата, ремонт эстафетных
  полос. Сброс теперь внутри неё, и только если строки реально стёрты.
- **Пять мест сбрасывали ДО пересчёта** (`AssignRulesAsync`, пересадка/создание/правка/удаление
  правила очков) — пересчитанное ложилось поверх уже сброшенного кэша. С перехватчиком порядок
  неважен: каждое сохранение сбрасывает своё.
- **Каскад в базе** у пяти удалений (клуб, группа, рекорд, правило очков, медиа пользователя):
  зависимые строки удаляет база, трекер их не видит — отсюда таблицы каскада в перехватчике.
- **Команды `dotnet run -- --флаг`** — отдельный процесс со своим кэшем в памяти: их сброс до
  веб-сервера никогда не дотягивался (с Redis дотянется сам).
- **Общий сброс оставлен:** импорт (`JsonImportService`, 4 места — массовые удаления и сброс
  нумерации), кнопка на `/Admin/Cache`, смена настроек.
- **Точечный ручной сброс клубов (15.09.2026):** для правки мимо этого процесса API (в базе
  руками, `dotnet run -- --флаг`, другой экземпляр) общий сброс избыточен. Ответы клуба несут явные
  метки страницы `page:clubs` и `page:club:{id}` (`CacheTags.ClubPageTags`); кнопки «Сбросить кэш
  всех клубов» на `/Admin/Cache` и «Refresh this club» в табе Admin клуба сбрасывают их
  (`ClubsAdminController`). Данные эти метки не описывают — это ручка, а не зависимость.

### 3.2б Что метки НЕ решают

- **Кэш браузера.** `/api/records` и `/api/normative-standards` отдаются с `max-age=300`:
  посетитель увидит правку через 5 минут, как бы быстро ни сбросился сервер. Если это важно —
  `no-cache` + ETag, как у страниц группы и клуба.
- **Производные данные в базе — это не кэш.** Мировые рекорды — порог для пометки «время под
  вопросом» (`Results.SuspectReason`, `SuspectResultService`). Сменился рекорд — старые пометки
  сами не пересчитаются: нужно не СБРОСИТЬ, а ПЕРЕСЧИТАТЬ. Для этого как раз годится список
  «таблица → какой пересчёт запустить» (идея Влада): пересчёт — действие, его нельзя вывести из
  чтения. Кандидаты: `Records` → проверка качества; правило очков → `ClubCompetitionStandings`
  (эта пара уже сделана руками — `PointRulesRecalcOnEditTests`: раньше правка шкалы сбрасывала
  только кэш, и витрина оставалась на старых очках — ровно тот класс ошибки).

### 3.3 Точность: «везде» или «одна страница»

Получается из меток само:

- Импорт пишет в `Results` → сброс `results` → падает всё, что собрано из результатов
  (season-best, рекорды-сверки, клубы, группы, пловцы). Это правильно: новые результаты
  меняют все эти витрины.
- Правка расписания группы 24 → `hub-group:24` → падает страница одной этой группы.
  Устройство (метки `row:`/`anyrow:`, правило сужения, страницы) —
  [cache-row-precision-plan.md](cache-row-precision-plan.md).
- Точность по колонкам НЕ делаем: «таблица + id» хватает, дальше — сложность без выгоды.
  **Узкое исключение (решение Влада 14.09.2026):** реестр «служебных» колонок — часто пишут, мало
  кто читает (`Swimmers.LogligId*`, `Competitions.QualityScannedAt`…); их правка сбрасывает
  `col:T.C`, а не `table:T`, читатель получает `col:` сам по тексту SQL. §2.6 плана строки;
  сделано в К4б.6 (реестр `CacheServiceColumns`, выключатель `CacheColumnPrecision`).

## 4. Правила, готовые к Redis (действуют уже сейчас)

1. **Только через `ICacheService`.** Никаких `static Dictionary` и прямого `IMemoryCache` в обход:
   второй экземпляр о таком кэше не узнает и не сбросит его. Сторож (К5) — тест
   `DirectMemoryCacheTests`: закрытый список мест с причиной (реализация кэша, состояние сценариев
   «превью → применить», внешний источник, сводки админки); смотрит исходники, поэтому видит и
   `Swimm.API`, который тесты не собирают.
2. **В кэше — только DTO/record со свойствами, которые переживают JSON-круг.** Нельзя: сущности
   EF, кортежи, публичные поля, делегаты, `IQueryable`, `object`. Правило — код
   (`CacheValueRules`), проверяется при КАЖДОЙ записи в `MemoryCacheService` и тестом
   `CacheValueRulesTests.EveryCachedValueType_SurvivesRedis`, который находит все вызовы кэша
   по IL. Два нарушения исправлены в К2:
   - `ResultRepository.GetPagedAsync` клал кортеж `(List<ResultDto>, bool, int)` — System.Text.Json
     сериализует `ValueTuple` в `{}`, в Redis страница молча стала бы пустой → `CachedResultsPage`;
   - `ResultRepository.GetIsraelRecordsAsync` клал сущности `Record` → `CachedRecordAxis`.
3. **Значение из кэша не мутировать.** В памяти правка объекта из `GetAsync` меняет ответ всем
   последующим читателям, в Redis — нет (там копия): поведение молча разъедется.
4. **Ключи и метки — из фабрик**, префикс окружения (`swimm:{env}:`) добавляет реализация.
5. **Сброс — по метке, не перебором ключей:** у Redis нет дешёвого «найди ключи по шаблону».
6. HTTP-уровень от экземпляра не зависит уже сейчас: ETag = хэш содержимого, одинаков на любом
   сервере.
7. **Запись в кэш — только `GetOrCreateAsync`**, не пара `GetAsync` + `SetAsync`: у записи своя
   сборка, и метки своих таблиц она получает сама, от кого бы её ни позвали. Ручной `SetAsync`
   вне чужой сборки кладёт запись без меток таблиц. Сторож — тест
   `CacheValueRulesTests.NoManualSetAsync_OutsideTheCacheItself` (IL всех вызовов). Приём в коде:
   публичный метод = `GetOrCreateAsync(key, () => LoadXxxAsync(...))`, тело — в `LoadXxxAsync`;
   «не найдено» — фабрика возвращает null (T nullable), в кэш он не ложится.
8. **У записи — метки данных или объявление «не из базы»** (К5). Метка данных — `table:`, `row:`,
   `anyrow:`, `col:` (`CacheTags.IsData`); метки страниц `page:*` не в счёт — запись в базу их не
   сбрасывает. Запись, в сборке которой не было ни одного запроса к базе и ни одной вложенной
   записи с метками, почти наверняка собрана из данных, прочитанных ДО `GetOrCreateAsync` (попали
   в замыкание), и врёт до конца TTL. Сторож — в `MemoryCacheService` (`UntaggedEntryPolicy`): в
   Development — исключение, запись не ложится; на проде — предупреждение в лог, одно на вид
   записи. Собранная правда не из базы (настройки, внешний сайт) объявляет `CacheTags.NotFromDb`;
   константный ответ (пустой по аргументам) в кэш не кладут вовсе — отдают до `CachedJson`.
9. **Диагностика кэша — не на пути посетителя** (решение Влада 15.09.2026). Размер записи (байты
   JSON — столько она заняла бы в Redis) меряется при первом взгляде админки и запоминается, а
   не при записи; ответ API знает свою длину сам (`ICacheSizedValue`). В Redis размер значения
   отдаётся даром. Полный сброс — только с подтверждением: после него сайт «холодный».
   → [admin-pages/cache.md](../admin-pages/cache.md), «Размер».

## 5. Как это ляжет на Redis

- Интерфейс: `SetAsync(key, value, ttl, params string[] tags)`,
  `InvalidateTagsAsync(params string[] tags)`, `InvalidateAllAsync()` = метка `all`.
- **Память (сейчас):** на каждую метку свой `CancellationTokenSource`; запись подписана на токены
  своих меток — как сейчас на один общий.
- **Redis (потом):** у метки — номер версии (`INCR swimm:tag:{name}`). Запись хранит версии своих
  меток на момент записи; чтение сравнивает их с текущими одним `MGET` — не совпало = промах.
  Сброс = один `INCR`, виден всем экземплярам сразу, без рассылок и перебора ключей; старые
  записи уходят по TTL.
- Локальный слой в памяти поверх Redis (если понадобится по замеру) потребует рассылки сброса
  через Redis pub/sub. Без замера не делать.
- Переезд = `RedisCacheService` + регистрация в `DependencyInjection.cs` + строка подключения.
- **Одного Redis для нескольких экземпляров мало** (решение Влада 15.09.2026: К6 — часть фазы
  масштабирования, не отдельная работа). Второй экземпляр ломает ещё три вещи, и чинить их вместе:
  фоновые сервисы задублируют записи в базу — нужен выбор лидера
  ([azure-deploy-plan.md](azure-deploy-plan.md) §8.1, там же «ровно один инстанс»); настройки
  живут в памяти (`AdminSettingsService`) и разъедутся по экземплярам; состояние сценариев
  «превью → применить» (импорт PDF, Discovery, дифф рекордов) лежит в прямом `IMemoryCache` —
  список в `DirectMemoryCacheTests.Allowed` — и на соседнем экземпляре не найдётся (липкая сессия
  или общее хранилище). До второго экземпляра Redis пользы не даёт.

## 6. Этапы

| # | Что | Приёмка |
