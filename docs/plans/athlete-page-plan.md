## 2. Решения, принятые до кода (не переоткрывать)

1. **Сезон — календарный** (`SeasonMath`, метка по году начала: «2025/26»). Сезон федерации
   идёт **октябрь — август**; граница 1 сентября в коде — безопасная условность, сентябрьских
   стартов в базе нет вовсе. Подробности и данные — [season-boundary-rule.md](../season-boundary-rule.md).
2. **Витринный сезон ≠ календарный.** Пока не проплыли зимние чемпионаты текущего сезона,
   карусель по умолчанию стоит на **прошлом** сезоне (решение Влада 2026-08-13). Новый сезон
   в карусели присутствует и выбирается руками. Это касается только умолчания — заплывы
   разложены по сезонам календарно.
3. **Возраст — только `SeasonMath.AgeInSeason`** (год окончания сезона), один на все старты
   сезона. Поле `ageAtSwim` из `DATA.md` переименовать в `ageInSeason`: возраст на день заплыва
   разводит осенние и весенние старты одного пловца по двум ступеням — этот баг уже ловили на
   странице клуба.
4. **Ключ дисциплины** — `SeasonAggregator.DisciplineKey(includeEventCategory: true)`.
   На странице спортсмена `EventCategory` входит в ключ, иначе три золота Маккабиады в одной
   дисциплине сливаются в одно.
5. **Из best/PB исключаются** `TimeFail`, `SuspectReason` и эстафеты — это `IsCountable`,
   отдельной логики не заводить.
6. **Время — только `UI_SwimTime`**, носитель спорной строки — `swimFlaggedRowProps`.
   DTO, несущий время, несёт и признак качества (инвариант И11, [data-integrity.md](../data-integrity.md)).
7. **Открытая вода — не третий `PoolType`.** В контракте `poolType: "25m" | "50m"` **плюс**
   `waterKind: "pool" | "open"`, а не `course: "open_water"` как в `DATA.md`
   ([open-water-course-plan.md](open-water-course-plan.md)). Пока `Competition.WaterKind` не
   заведён — поле отдаём как `"pool"` и чип 🌊 не рисуем.
8. **Страна — alpha-3** (`"ISR"`), alpha-2 только флагу. В `DATA.md` пример с `"IL"` — ошибка.
9. **Места — протокольные** (`Position` / `PositionAgeGroup`), не `CombinedPlace`
   ([competition-overview-cards.md](../competition-overview-cards.md)).
10. **🏆 у соревнования — только `Competition.IsChampionship`**; клиент не определяет чемпионат
    по названию.
11. **График Progress рисуем руками SVG.** Библиотеки графиков в проекте нет, тянуть её ради
    одного блока не будем — образец подхода `UI_NormativeLevelIcon`.

## 3. Контракт API (исправленный `DATA.md`)

Пять эндпоинтов, по одному на блок-группу, чтобы табы грузились лениво. Кэш + ETag —
как у страницы клуба (`CachedJson` в `ClubsPublicController`).

### `GET /api/swimmers/{id}` — hero + список сезонов *(расширяем существующий)*

К нынешнему `SwimmerProfileDto` добавляются:

```jsonc
{
  "ageInSeason": 12,                       // SeasonMath.AgeInSeason(текущий витринный сезон)
  "ageGroup": { "code": "Y", "label": "Y 11-14" },
  "programs": ["pool"],                    // "open" добавится с WaterKind
  "recordsHeld": 2,                        // 0 → бейдж не рендерится; см. решение №2 в §6
  "isFavorite": true, "isMe": false,       // вместо isFollowed/isOwner — см. решение №5 в §6
  "seasons": [{ "code": "2025", "label": "2025/26", "isCurrent": true, "isDisplayDefault": true }]
}
```

`isCurrent` — календарно текущий сезон; `isDisplayDefault` — тот, на котором стоит карусель
(решение §2.2). Ровно один сезон помечен `isDisplayDefault`.

### `GET /api/swimmers/{id}/summary?season=2025|all` — KPI и шапка панели

`points`, `medals {gold,silver,bronze}`, `level {code,progress}`, `swims`, `events` +
для таба Season: `standings[]` (❄/☀ карточки: место в группе, очки, заплывы, медали),
`competitions[]` сезона. При `season=all` — карьера, и этим же ответом живёт таб **History**
(отдельного эндпоинта не заводим).

### `GET /api/swimmers/{id}/best-times?season=` — таб Results

Одна дистанция — одна строка, лучшее за сезон. Отличия от `DATA.md`: `poolType` + `waterKind`
вместо `course`; `ageInSeason` вместо `ageAtSwim`; `quality` вместо пары `isFlagged`/`flagReason`
(единая форма, которую понимает `UI_SwimTime`):

```jsonc
{ "quality": { "kind": "protocol", "reason": "…" } | null }
```

Помеченная строка: `points: null`, дуга уровня пустая, чипа `BEST` нет.

### `GET /api/swimmers/{id}/personal-bests?poolType=25m` — таб Records & PB

Плюс к `DATA.md`: дельты приходят **в миллисекундах и уже посчитанными на сервере**
(`deltaToClubBestMs`, `deltaToNationalAgeRecordMs`, оба nullable — `null` значит «не с чем
сравнивать»), `holdsClubBest` / `holdsNationalAgeRecord`. Ось рекорда Израиля:
`Record(RegionType=country, RegionCode=ISR, Category=age, AgeKey=возраст в сезоне, Gender,
PoolType, Style, Distance)`.

### `GET /api/swimmers/{id}/progress?eventId=&poolType=` — таб Progress

История всех заплывов связки стиль+дистанция по возрастанию даты: `timeMs`, `points`, `place`,
`isPb`, `quality`, соревнование. Спорные точки в линию не входят.

## 4. Этапы

### A1. Шов: заплывы пловца одной выборкой ☐

- `ISwimmerPageRepository` (Application/Abstractions) + `SwimmerPageRepository` (Infrastructure),
  по образцу `ClubOverviewRepository`.
- Расширить `SeasonSwimRow` полями строки результата: `Position`, `PositionAgeGroup`,
  `InternationalPoints`, `TimeSplit`, `CompetitionName`, `IsChampionship`.
  ⚠ Поля добавляем к существующей записи, **не** заводя вторую проекцию — иначе через полгода
  будет два способа считать сезон.
- Долг из [entity-pages-plan.md](entity-pages-plan.md) §10.2: `/api/athletes/career` ищет
  **по имени**. Перевести на id, имя оставить алиасом для попапа.
- ⚠ Перф: выбирать по `SwimmerId` + дате, фильтры резолвить в `Id` (правило из
  [perf-unscoped-3m-cliff]: фильтр по `.Name` через JOIN убивает индексы), top-N по дате —
  двухшаговым fetch (LIMIT-ловушка).

**Приёмка:** юнит-тесты на расширенную проекцию; сумма по сезонам сходится с
`/api/athletes/career` на контрольном пловце; замер холодного и прогретого запроса.

### A2. API: профиль + summary ☐

Расширенный `GET /api/swimmers/{id}` (§3) и `GET /api/swimmers/{id}/summary`.
Здесь же — вычисление витринного сезона (`isDisplayDefault`) по дате последнего зимнего
чемпионата; понятие именованное и отдельное от `SeasonMath` (см. правило).

**Приёмка:** сезоны в ответе совпадают с `SeasonAggregator.SeasonsPresent`; `season=all`
сходится с суммой по сезонам; ETag → 304; неизвестный пловец → 404; пловец без результатов
отдаёт пустые сезоны, а не 404.

### A3. API: best-times + personal-bests ☐

**Приёмка:** на контрольном пловце число строк = числу дистанций, а не заплывов; помеченная
`SuspectReason` строка не становится best; 25m и 50m не смешиваются; дельта до рекорда Израиля
считается по возрасту **в сезоне**, а не по году заплыва.

### A4. API: progress ☐

**Приёмка:** порядок по дате возрастающий; PB отмечены через `SeasonAggregator.PersonalBests`
(первый зачётный заплыв — уже PB, повтор времени — нет); спорные точки помечены и исключены
из линии.

### A5. Клиент: каркас ☐

Тема из `theme.css` хендоффа парными токенами `--theme-*`, hero, KPI-плитки, **карусель
сезонов** и **плитки-табы** (берутся 1:1 из `design_handoff_club_page_tabs/SEASON-CAROUSEL.md`
и `TABS.md`), панель-«папка», выбранный сезон в URL как query (`?season=`, не в путь —
правило `routes.ts`).

**Приёмка:** сезон переживает перезагрузку страницы; все табы читают один сезон; `tsc` чистый;
обе темы и 390px.

### A6. Клиент: панели по одной ☐

Порядок: Results → Season → Records & PB → Progress → History → Media.
Каждая панель — отдельная задача с §BLOCKS и контрактом.

**Приёмка каждой:** совпадает с макетом в обеих темах и на 390px; пустое состояние осмысленно
(«нет заплывов в этом сезоне», карусель и табы остаются); строка кликается в
`results_main.html?competitionId=…&tab=swims&swimmerId=…&resultId=…`; спорное время выглядит
как в `record-flag.css`; UI на английском.

## 5. Кто делает

Принцип тот же, что на клубной странице: **мне** — всё, где цена ошибки это молча неверные
цифры; **Сонету** (`/delegate`) — работа с механической приёмкой и образцом в репозитории.

| Этап | Кто | Почему |
|---|---|---|
| A1 шов + career по id | **я** | горячий путь и единственный источник сезонной арифметики |
| A2 профиль + summary | **я** | витринный сезон и KPI — форма ответа определяет всю страницу |
| A3 best-times + PB | **я** (PB) / **Сонет** (best-times) | дельты до рекордов — расчёт; best-times копирует готовый агрегат |
| A4 progress | **Сонет** | выборка тривиальна, PB-детекция уже есть |
| A5 каркас | **я** | общий season-стейт — шов всех панелей |
| A6 панели | **Сонет**, по одной | у каждой есть макет, контракт и проверяемая приёмка |

⚠ Сонету **не отдаём**: расчёт дельт до рекордов, витринный сезон, правку `SeasonAggregator`.

## 6. Решения, которые нужны до A3 (рекомендации мои)

1. **Связь Records ↔ Swimmer.** У `Record` нет `SwimmerId`: держатель — строка `HolderName`
   (иврит), клуб — строка `Club`. От этого зависят и бейдж «🏆 N records», и колонка Δ.
   *Рекомендация:* в первой версии матчить по имени с той же оговоркой, что у Record wall
   клуба; `SwimmerId` в `Records` — в фазу 11.
2. **`Record.Time` — строка, не миллисекунды** («21.08», «01:43.45»). Для дельты надо парсить.
   Это уже открытое решение №3 в [records-all-countries-plan.md](records-all-countries-plan.md).
   *Рекомендация:* завести колонку `TimeMs` там, здесь ею воспользоваться; временно — парсинг
   на сервере в одном месте.
3. **Что такое «Δ club rec».** Клубных рекордов как сущности нет: на клубной странице Record
   wall связан с клубом **по названию**. Альтернатива — считать лучшее время среди пловцов
   клуба по нашей базе. *Рекомендация:* считать по базе (`deltaToClubBestMs`) с подписью
   «among N meets in our database», как у Season best клуба — честнее и целиком в наших данных.
   Отсюда и имя поля: `holdsClubBest`, а не `holdsClubRecord`.
   **УТОЧНЕНИЕ 2026-08-27 (решение Влада):** клубный эталон считается СРЕДИ ПЛОВЦОВ
   СВОЕГО ВОЗРАСТА, а не по всему клубу. До этого двенадцатилетка сравнивалась с лучшим
   временем клуба за всю историю, то есть со взрослыми (на 800 вольным разница выходила
   в сотни секунд), и две дельты карточки меряли разное, выглядя одинаково. Ступень у
   обеих теперь одна и та же — возраст в витринном сезоне (`SeasonMath.AgeInSeason`).
   ⚠ Возраст ЧУЖИХ заплывов считается по СЕЗОНУ ЗАПЛЫВА, и формула в SQL обязана
   совпадать с `SeasonMath.AgeInSeason` — сторож в `SwimmerPageRepositoryTests`.
4. **«Владелец» страницы.** Таблица доступа в `README.md` хендоффа требует `isOwner`
   (редактирование профиля, загрузка фото, «My links»). Владельца у пловца в модели **нет**,
   а «Me» — это primary favorite, логическая привязка, которая прав не даёт (правило проекта).
   *Рекомендация:* колонку владельца из первой версии убрать; таб Media показывает публичную
   галерею (`/api/swimmers/{id}/media` уже режет видимость по зрителю) плюс ссылку
   «Manage in My media →». Привязка аккаунт↔пловец — соседняя тема (родитель–пловец).
5. **Эстафеты.** В best/PB их нет по `IsCountable`. Показывать ли отдельным списком?
   *Рекомендация:* в первой версии нет; позже — блоком в History.
6. **`recordsHeld` при спорных рекордах.** Есть реестр `Sys_RecordIssues`
   ([records-quality-plan.md](records-quality-plan.md)). Считать спорный рекорд в бейдж?
   *Рекомендация:* считать, но помечать качеством `record` через `UI_SwimTime` — не прятать.

## 7. Риски

- **Расхождение с попапом.** Попап считает карьеру **по имени**, страница будет по **id** —
  у пловцов-дублей (`SwimmerOrgId`-дедуп, пловцы-тени из ног эстафет) цифры разойдутся, и это
  будет выглядеть как баг страницы. Сверять на контрольном пловце **до** A6.
- **Пять запросов на страницу.** Кэш + ETag обязательны с первого эндпоинта, не «потом».
- **RTL и смешанные строки** (иврит + латиница + цифры) — типовой источник косметики;
  `dir="auto"`, `min-width:0`, `ellipsis` заложены в `BLOCKS.md`.
- **Пустые состояния — норма, а не край:** нет фото, нет заплывов в сезоне, нет уровня,
  нет медиа. Проверять на реальном пловце без результатов.

| A5 | каркас страницы: тема, hero+KPI, карусель, плитки-табы, панель; сезон и таб в query | диплинк `?tab=pb&season=2024` восстанавливает и таб, и центр карусели, и KPI; мобайл 375 без горизонтального скролла; light/dark |
| A6 | шесть панелей: Season, Results, Records & PB, Progress, Media, History | прокликаны вживую на пловце 7796 |

Общие компоненты вынесены в `client/src/projects/components/deep/` (тема, карусель, плитки-табы)
и теперь используются обеими страницами — хендофф требовал их «1:1 со страницы клуба», а копия
разъехалась бы на первой правке стыка плитки с панелью.

### Контракт разошёлся с `DATA.md` (это правки плана, а не отклонения)

- **`disciplineKey` вместо `eventId`** у прогресса: «событий-дисциплин» в модели нет, ключ —
  связка стиль × дистанция × бассейн × пол, её же отдаёт `/best-times`.
- **`time` строкой И `timeMs`**: `UI_SwimTime` принимает уже отформатированную строку
  протокола, а миллисекунды нужны дельтам и графику.
- **`level` не в ответе**: разряд считает клиент из `NormativeStandard`; вторая реализация
  на сервере разъехалась бы с первой.
- **`isFavorite`/`isMe` не в ответе**: они у каждого зрителя свои, а ответ кэшируется;
  клиент знает их из `useFavoritesContext`.
- **`summary.events` считается БЕЗ категории заплыва** — тем же ключом, что строки Results,
  иначе плитка «12 events» не сходилась бы с «12 best times».

### Попутно исправлено

- **`ShowcaseSeason` был реализован по старой формулировке правила** — «сезон обрывается
  зимним чемпионатом», и витрина клуба показывала окно «с 27/02/2026», теряя декабрь–февраль.
  Теперь витринный сезон — это ЦЕЛЫЙ сезон, который переключается после последнего зимнего
  чемпионата; `showcase_season_from` (дата) стал `showcase_season` (метка «2025/26»).
  У клуба 456 season bests стало 26 за весь сезон.
- **Карьера считала медали без учёта `IsAward`**: первое место на лиге (медалей там не
  вручают, и таблица результатов медаль не рисует) шло в золото карточки. У пловца 7796 было
  3/2/4, стало 2/1/4 — **цифры попапа изменились**, это ожидаемо.

### Осталось / известные дыры

- **Открытая вода** до появления `Competition.WaterKind` попадает в список 25m: у заплыва
  «אליפות ישראל — מים פתוחים» бассейн соревнования 25м. Поле `waterKind` в контракте уже есть
  и отдаётся как `"pool"` — когда заведут колонку, меняется одна строка билдера.
- **Мусорные стили из импорта видны пользователю**: у пловца 7796 в PB и Progress есть строка
  `3000 מטר_חופשי` (стиль id 9). Это данные, а не код: в `Styles` живут `מטר_חופשי` и
  `חופשי_נוקאוט`, их нужно склеить с каноническими.
- **Решения §6 приняты по рекомендациям**: рекорды матчатся по имени держателя (1),
  `Record.Time` парсится на лету (2), «Δ club» считается по нашей базе с подписью (3),
  колонки владельца нет (4), эстафеты отдельным списком не показываются (5), спорные рекорды
  помечаются качеством `record` (6). Если Влад решит иначе — менять здесь.
- **Не прокликано**: пловец-мастерс (нормативы masters), пловец с эстафетами в History,
  спорное время в строке (`SuspectReason`) вживую на этой странице.

## 11. Четыре таба и фильтры внутри Results (2026-08-25)

Шесть плиток верхнего уровня не помещались в мобайл, а по смыслу «Records & PB» и «Progress»
отвечали на тот же вопрос, что и Results, — «как я плыву», отличаясь только точкой отсчёта.
Плитки остались четыре (**Season · Results · Media · History**), а внутри Results появилась
полоса чипов:

| Фильтр | Что показывает | Откуда данные |
|---|---|---|
| ⏱ Best time | лучшее за сезон по каждой дистанции (было содержимым таба Results) | `/best-times?season=` |
| ☀ Season best | **место среди сверстников** — новое | `/season-ranks?season=` + строки `/best-times` |
| 🏅 Records & PB / Personal bests | личники карьеры + дельты; при наличии рекордов — они отдельной секцией сверху | `/personal-bests?poolType=` + `records` из профиля |

**Третий чип меняет ИМЯ по наличию рекордов** (решение Влада 2026-08-25):

- держит хотя бы один рекорд → «**Records & PB**» + бейдж с их числом, а в панели официальные
  рекорды идут **отдельной секцией НАД** таблицей личников;
- рекордов нет → просто «**Personal bests**», без бейджа и без секции.

Слово «Records» у пловца без рекордов обещало бы то, чего нет; прятать фильтр целиком тоже
нельзя — за ним личники карьеры с дельтами до клуба и до рекорда Израиля, а они есть у каждого.
Промежуточный вариант «прятать чип совсем» был реализован и отменён в тот же день ровно
поэтому.

### Откуда берутся сами рекорды

`CountRecordsHeldAsync` заменён на **`GetRecordsHeldAsync`** — счётчик и список считаются
ОДНИМ запросом и едут в профиле (`recordsHeld` + `records`): собранные порознь, они рано или
поздно разошлись бы, и бейдж «4 records» стоял бы над секцией с тремя строками. Список едет
всегда, потому что у подавляющего большинства он пуст и не стоит ничего.

- ⚠ Связь держателя — **только по имени** (у `Record` нет `SwimmerId`, решение §6.1): тёзка
  заберёт чужой рекорд, и подпись под секцией это признаёт.
- Качество записи (`Sys_RecordIssues` → `kind: record`) едет вместе со временем — инвариант И11.
  Претензии тянутся целиком: таблица штучная, а сузить запросом нельзя — рекорды пловца
  разбросаны по регионам, категориям и ступеням.
- Дистанция нормализуется: справочник пишет «200m», протокол — «200», а плита события одна
  на оба источника.
- ⚠ Дата рекорда показывается **как напечатана в справочнике** (`7/27/2024` рядом с
  `04/06/2024` — федерация не выдерживает ведущие нули). Не чиним, как и остальные ошибки
  справочника; если решим приводить к одному виду — это правка импорта, а не витрины.
| 📈 Progress | все попытки одной дисциплины (был таб Progress) | `/progress?disciplineKey=` |

Фильтр живёт в query как `?view=`; умолчание `best` в адрес не пишется. **Старые диплинки
`?tab=pb` и `?tab=progress` приземляются на Results с нужным фильтром** — ссылки на них уже
разошлись, и молча открывать «Best time» вместо запрошенного вида значит тихо соврать.

### `GET /api/swimmers/{id}/season-ranks?season=` — фильтр Season best

Не «моё лучшее время сезона» (это Best time), а **где я стою среди сверстников**: пловцов
того же года рождения и того же пола, по их лучшим временам того же сезона. Правило Влада
(2026-08-25): «первая в брассе среди девочек 9 лет, а в фристайле десятая среди них же».

Решения, которые легко потерять:

- **Строк результатов в ответе НЕТ** — только `{disciplineKey, rank, peerCount, timeMs,
  leaderTimeMs, gapToLeaderMs}`. Клиент клеит их со строками `/best-times` того же сезона.
  Второй набор тех же строк означал бы два места, где «лучшее время сезона» определяется
  заново, — ровно та ошибка, ради которой заведён `SwimmerPageBuilder`.
- **Когорта = год рождения, без фильтра по полу**: пол уже внутри `DisciplineKey`, и второй
  фильтр был бы вторым способом задать то же самое.
- **Ранжир спортивный**: равные времена делят место (двое по 41.23 — оба вторые, следующий
  четвёртый). Поэтому место считается «сколько строго быстрее + 1», а не позицией в списке.
- **Отбор строк тот же, что у `/best-times`** (`SeasonAggregator.IsCountable`): DSQ,
  помеченные времена и эстафеты места не получают.
- **`?season=all` мест не даёт**: сравнение живёт внутри одного сезона, и клиент за карьеру
  запрос не шлёт.
- **Своей строки нет в когорте → дисциплина пропускается**, а не объявляется первой (год
  рождения в справочнике мог разъехаться).

### Бейдж SB и порог «первый среди одного»

Первое место в группе носится как рекорд: строка получает золотой чип **SB**, замещающий
BEST (два чипа на строке — и «первый в группе» потерялся бы среди BEST у всех строк).

**Порог `MIN_PEERS_FOR_SB = 2`** (`swimmer-panels.tsx`): у мастерса 1958 г.р. на 200 на спине
в сезоне вообще нет соперников, и «#1 of 1» читалось бы достижением, не будучи им. Место
сервер отдаёт как есть — прятать данные нельзя, — а панель пишет в колонке группы `alone` и
чип не рисует. Предикат `holdsSeasonBest` ОДИН на оба вида, иначе строка носила бы SB, а
таблица мест её не подсвечивала.

### Плита события — один блок на всю страницу

Событие рисуется ОДНИМ компонентом `EventPlate`
([components/event-plate.tsx](../../client/src/projects/swimmer-project/components/event-plate.tsx)):
`UI_SwimmStyleIcon` (иконка стиля) + дистанция + `UI_PoolIcon` («--25m--»/«-----50m-----»).
Его показывают все три места, где встречается событие: строка результата (Best time, Progress)
и колонка Event обеих таблиц (Season best, Records).

Отдельным модулем, а не внутри `swimmer-panels`: панели импортируют строку результата, и
держать плиту в панелях означало бы круговой импорт.

В строке результата вместе с плитой **убрана подпись «50m pool»** под названием старта:
бассейн теперь внутри плиты, и вторая надпись о том же была бы шумом.

Подпись стиля словом под плитой была добавлена и **убрана по решению Влада** (2026-08-25):
плита остаётся компактной — иконка, дистанция, бассейн. Стиль читается по иконке, а полностью
(«200 backstroke · 50m») — из `title` плиты, при наведении и для скринридера.

⚠ Отсюда следствие, о котором стоит помнить: в таблицах соседние строки одной дистанции и
бассейна («200 · 25m» вольным и «200 · 25m» комплексом) различаются ТОЛЬКО иконкой. Это
сознательный размен в пользу компактности, а не недосмотр.

- Готовый `icon-len` не подошёл: у него дистанция красная по прозрачному фону, а PNG иконок
  нарисованы под светлый фон — в тёмной теме и то и другое пропадает. Поэтому `icon-notext`
  внутри белой плиты `deep-stroke-plate` (она уже была у строки результата) плюс свой
  `__dist` с тенью. Дефисы бассейна берутся у `UI_PoolIcon`, а не переписываются.
- Плита картиночная, поэтому у неё обязателен `title` с читаемой подписью — иначе в колонке
  не остаётся текста вовсе.
- **Мобайл**: плита ужимается с 86 до 62px. При 86px в таблице Records на время оставалось
  22px (замерено) — а время в ней главное.

### Ссылка на будущую страницу `/season-best`

Каждая строка таблицы Season best — ссылка на список этой связки. Адрес строится ТОЛЬКО через
`routes.seasonBest()` ([client/src/utils/routes.ts](../../client/src/utils/routes.ts)):

```
/season-best?season=2025&age=9&gender=female&stroke=breaststroke&distance=50&pool=25m&swimmer=6066
```

| Параметр | Значение | Зачем |
|---|---|---|
| `season` | год НАЧАЛА сезона (2025 = «2025/26») | обязательный; сравнение живёт внутри сезона |
| `age` | возраст В СЕЗОНЕ (`SeasonMath.AgeInSeason`) | ось «по возрасту» |
| `gender` | male / female | группа сверстников — одного пола |
| `stroke` | ключ стиля (`freestyle`, `individual_medley`…) | ось «по стилям» |
| `distance` | без «m»: `50`, `100` | |
| `pool` | `25m` / `50m` | 25 и 50 несравнимы — это часть адреса, а не фильтр по умолчанию |
| `swimmer` | кого подсветить | на выбор списка не влияет |

Пустые параметры не пишутся: `/season-best?season=2025` — законный адрес «весь сезон».

**Страница-заготовка заведена** (`client/season-best.html` → `src/pages/season-best-page.tsx` →
`projects/season-best-project/`): маршрут, разбор адреса и шапка работают, самих списков нет.
Раньше содержимого — сознательно: ссылки на неё уже стоят в таблице, а без страницы они молча
уводили бы на домашнюю (dev-фоллбек Vite отдаёт `index.html` на любой нераспознанный чистый
путь, то есть 200 с чужим экраном).

Маршрут прописан во ВСЕХ зеркалах (правило трёх зеркал из `client/CLAUDE.md`):
`rollupOptions.input` и `cleanUrlRewrite` в [client/vite.config.js](../../client/vite.config.js),
`ResolveCleanUrl` в `server/Swimm.API/Program.cs`. Прод-rewrite проверен на собранном html:
`/season-best?…` → 200 «Season best», нераспознанный путь по-прежнему 404.

Адрес читается ТОЛЬКО через `parseSeasonBestQuery()` — парсер лежит рядом с генератором в
`routes.ts` намеренно: писать и читать один адрес в разных местах значит завести два
контракта, которые разъедутся на первом переименовании параметра.

Данные у списка уже есть: `GetAgeCohortSeasonBestsAsync` возвращает всю когорту, а не только
запрошенного пловца, — списку нужна ровно она, отфильтрованная по `disciplineKey`. Осталось
завести эндпоинт-обёртку и вёрстку списка.

**Подпись сезона сведена к одному формату «2025/26»** (решение Влада 2026-08-25). Клиентский
`seasonLabel` писал «25-26», серверный `SeasonMath.Label` — «2025/26», и на стыке экранов один
и тот же сезон читался как разные. Правка в одном месте — `client/src/utils/helpers/season-helper.ts`;
заодно на общий хелпер переведены две самодельные формулы (заголовок сезона в History и подпись
плитки Season, которая показывала голый «2025» — календарный год вместо сезона).

Затронуты все экраны с подписью сезона: соревнования, селектор источника, My media, зачёт
клуба, карточка Season best нормативов, History и Season страницы пловца, эта страница.
Проверено в браузере: строк старого формата не осталось, ничего не обрезается.

⚠ **Исключение ровно одно и оно осознанное** — колесо сезонов (`deep/season-carousel`)
по-прежнему рисует «25/26»: это циферблат, слот 52px (макет 4c §4), полная запись туда не
влезает. Читаемая подпись у него полная — в `aria-label` («Season 2025/26»). Чтобы и там
была полная запись, надо расширять слот и пересобирать геометрию ленты, общей со страницей клуба.

### Пустые состояния Season best (баг, найден вживую)

Панель висела на «Loading…» навсегда, если в карусели выбрано **∞ (All seasons)**: запрос там
сознательно не шлётся (места считаются внутри одного сезона), а панель не отличала «не
запрашивали» от «грузится» и ждала данных, которых никто не просил.

Лечится не в хуке, а в панели: она получает `season`, `loading` и `error` и решает сама.
Режим All проверяется ПЕРВЫМ, до всякой загрузки:

| Состояние | Что показываем |
|---|---|
| `season == null` (сезонов нет вовсе) | «No seasons to compare yet.» |
| `error` | «Could not load places for this season.» |
| нет данных, `loading` | «Loading…» |
| нет данных, НЕ `loading` | «No places for this season.» — запрос не состоялся, «Loading…» тут соврал бы |

**Та же правка сделана во ВСЕХ панелях страницы** (по просьбе Влада, тем же заходом). Каждая
получает `state` — прямо результат `useJson` (`state={bestTimes}`), а не разобранный на булевы,
и три состояния разводит общий `noDataText(loading, whenIdle)`:

| Панель | При ошибке |
|---|---|
| Season | «Could not load this season.» |
| Results (Best time) | «Could not load best times.» |
| Season best | «Could not load places for this season.» |
| Records & PB | «Could not load personal bests.» |
| Progress | «Could not load the list of events.» / «Could not load this event.» |
| History | «Could not load the career history.» |

У Progress состояния ДВА (`state` + `progressState`): список дистанций и история выбранной
дистанции едут разными запросами, и падение второго не должно стирать первый.

Попутно там же нашлась вторая ложь: пока список дистанций грузился, Progress уверял, что
заплывов нет вовсе («No swims to build progress from yet» стоял на любой пустой список).

Проверено вживую подменой `window.fetch` на 500 для каждого эндпоинта по очереди — все шесть
надписей появляются вместо вечного «Loading…».

### Режим ∞ (All seasons) — места за витринный сезон

Мест «за карьеру» не бывает: сравнение со сверстниками считается внутри одного сезона.
Первым решением был тупик-подсказка «выбери сезон»; заменено (Влад, 2026-08-25) на **показ
мест за витринный сезон** с обязательной оговоркой прямо над таблицей: «The carousel is on
all seasons, but places only exist inside one season — showing 2025/26.» Без неё адрес
`?season=all` и сезонные цифры молча противоречили бы друг другу.

Две ловушки, которые тут легко не заметить:

1. **Строки тоже сезонные.** В режиме ∞ таб Results держит КАРЬЕРНЫЕ лучшие, а места —
   сезонные. Поставить карьерное время рядом с сезонным местом значит показать место за один
   заплыв, а время — за другой. Поэтому панель тянет `best-times?season={витринный}` отдельным
   запросом (`fallbackBest`), а не переиспользует строки таба.
2. **Бейджей SB в режиме ∞ нет.** Список Best time там карьерный, и SB на карьерной строке
   утверждал бы то, чего никто не считал. `sbKeys` пустеет при `activeSeason == null`.

Проверено на пловце 5757 (два сезона): при `?season=all` уходят `season-ranks?season=2025` и
`best-times?season=2025`, оговорка на месте, в табе Best time 16 карьерных строк и **ноль**
бейджей SB; при `?season=2025` оговорки нет, бейдж есть.

### Разряд в шапке: по карьере и по СВОЕЙ таблице (баг 7424)

У 45-летней мастерс-пловчихи плитка LEVEL показывала почти пустую дугу — «первый взрослый».
Две независимые причины, обе исправлены 2026-08-25:

1. **Разряд считался за выбранный сезон.** Теперь — по лучшему заплыву **за всю карьеру**
   (правило Влада): разряд однажды выполнен и сезоном не отменяется, иначе ветеран в
   межсезонье выглядел бы новичком. Карусель на эту плитку больше не влияет; проверено на
   пловце 5757 — при смене сезона строки меняются (6 ↔ 15), плитка стоит.
   Для этого `allBest` (`best-times?season=all`) грузится всегда, а не только на виде Progress.
2. **Мастерс мерялся юношеской шкалой.** `getNormativeLevelInfo` умеет `isMaster` +
   возрастные полосы, но страница спортсмена их не передавала. Цифры на живых данных:

   | Время 00:31.47, 50 на спине, 50м | Результат |
   |---|---|

   | мастерс 45-49 | быстрее МСМК 31.66 → **МСМК** |

   Флаг берётся с самого заплыва: в `SwimmerBestTimeDto` и `SwimmerProgressPointDto` добавлено

Плитка стала «MSMK», строки — MSMK/MS. У немастерса (6066) разряд не изменился («1y»).

**Плюс полоса возраста под дугой.** `UI_NormativeLevelIcon` умеет подписывать полосу

### Перф-аудит страницы (2026-08-25) и что по нему сделано

Замеры на живой связке, не по коду. Найдено шесть вещей, две закрыты сразу.

**Сделано — сжатие ответов API.** `AddResponseCompression` не был подключён нигде в решении, и
справочники, которые тянет КАЖДАЯ страница (`records` + `normative-standards`), уходили
несжатыми: **1 930 КБ → 119 КБ, −94 %**. Цена — 6 мс на самом большом (971 КБ) справочнике.

- Жмём **только `application/json`**, и это не экономия ради экономии: HTML админки отдаётся с
  antiforgery-токеном, а сжатый ответ с секретом плюс подконтрольный ввод — это BREACH.
  Публичный JSON секретов не несёт, поэтому его жмём и по HTTPS.
- Уровень **Optimal, а не Fastest**: у brotli Fastest это quality 1, он на справочниках
  проигрывает даже gzip (83 КБ против 60 КБ у Optimal).
- Смягчающее: `max-age=300` + ETag делают повторные визиты бесплатными (304, 0 байт тела).
  То есть 2 МБ платил только первый визит — но на мобильном это были секунды.

**Сделано — кэш и склейка запросов в `useJson`.** Было три разных потери:

| | Было | Стало |
|---|---|---|
| `best-times?season=all` в режиме ∞ | 4 запроса (2 хука × StrictMode) | 1 |
| Возврат на таб Progress / History | запрос каждый раз | 0, и «Loading…» не мигает |
| Запросов на загрузку страницы | 17 | 13 |
| Самый долгий запрос | 43 мс | 10 мс |

Кэш **модульный, а не в сторе, сознательно**: переходы между пловцами — обычные ссылки
(сборка multi-page, SPA-роутера нет), поэтому стор умирал бы на навигации ровно так же, а
запись в единый `rootSlice` перерисовывала бы всех подписчиков — то есть била бы по тому
самому, ради чего затевалось. Радиус правки — один файл, `useJson` наружу не экспортируется.

**Оставлено осознанно, записано на будущее:**

1. **Когортный запрос — seq scan**, линеен по размеру базы: 16 мс на 81 тыс. строк, ~0.5 с на
   3 млн. Индекс не поможет — 73 % строк попадают в фильтр по дате. Лечится предпосчитанной
   таблицей когортных лучших, но не раньше, чем база вырастет.
2. **`IMemoryCache` без `SizeLimit`** — память ограничена только TTL в 5 минут. Обход
   краулером по многим пловцам удержит все их списки заплывов.
3. **Первый запрос после рестарта ~730 мс** — разовый прогрев EF (у следующего пловца
   профиль уже 43 мс). Для Azure с холодным стартом: compiled models либо пинг при старте.
4. **`/api/swimmers/{id}` всё ещё удваивается в dev** — профиль грузится своим хуком мимо
   `useJson`, и его дублирует StrictMode. В проде это один запрос, чинить нечего.

⚠ **StrictMode удваивает запросы только в dev.** Увидев парные вызовы в консоли, не надо
искать баг — в проде их нет.

### Перф

Замер на живой базе (81 463 результата, 5 551 пловец, когорта 2017 г.р. — 326 человек):
запрос когорты **16 мс**, всё из shared cache. Группировка идёт в SQL — наружу выходит
2 314 строк «сверстник × дисциплина», а не 60 тысяч заплывов.

Ключ кэша — **когорта, а не пловец**: `age-cohort-season-bests:{сезон}:{год рождения}`,
TTL 5 минут. Все сверстники делят одну запись, то есть это один запрос на когорту в 5 минут,
а не на просмотр страницы.

Планировщик берёт seq scan по `Results` (73 % строк принадлежат сезону — индекс по
`CompetitionDate` не выигрывает), поэтому стоимость линейна по размеру базы: на 3 млн строк
это будет ~0.5 с холодным. **Лечится не индексом, а предпосчитанной таблицей когортных
лучших** — заводить её раньше, чем база вырастет, незачем.

### Приёмка

- Пловец 6066 (девочка 2017): брасс 25m и 50m — `#1` с SB, 50 вольным — `#10 of 110`.
  Сверено независимым SQL: та же когорта 110, то же место 10.
- Мастерс 7311 (1958): бейдж «4» на чипе Records, `alone` без SB на двух дисциплинах.
- Мобайл 375: чипы переносятся на вторую строку, горизонтального скролла нет
  (`scrollWidth == clientWidth == 375`); таблица мест ужимается до 4 колонок, «из скольких»
  остаётся, «behind leader» уходит; ни время, ни подпись бассейна не обрезаются (замерено
  `scrollWidth > clientWidth` по каждой ячейке).
- Контраст замерен в браузере с учётом прозрачностей: SB 6.34 (light) / 8.6 (dark) — первая
  версия чипа (золото по золоту) давала 3.19 при 10px bold и была переделана в заливное
  золото с тёмным текстом, как медальные кружки.
- `tsc` чистый, тесты 1442/1442, 7 новых на `SeasonRanks`.
