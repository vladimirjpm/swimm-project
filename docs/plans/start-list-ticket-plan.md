## 0. Что меняется по сути

Сейчас таб — три зума на одном экране и **один** «primary favorite».
Дизайн заменяет вход: **мульти-выбор (несколько пловцов + клуб целиком) → одна карточка
плана-«билета»**. Подтабы источников больше не переключают смысл экрана — внутри карточки
за «когда» отвечают дни-чипы.

Существующий публичный API (С6) закрывает большую часть данных. Не хватает четырёх вещей,
и все они серверные:

| Чего нет | Зачем | Где решается |
|---|---|---|
| Время разминки по дням | ARRIVE BY = разминка − 30 мин | Т1 |
| Флаг «чемпионат» у **будущего** старта | одно из трёх условий ARRIVE BY | Т1 |
| Список клубов соревнования | секция FOLLOW A WHOLE CLUB | Т2 |
| Персистенс состава плана + «I'm coming» | per-соревнование, гость и залогиненный | Т3 |

⚠ **Главный архитектурный узел (Т1).** Времени разминки в проекте нет вообще, а «чемпионат»
живёт там, куда публичный read-путь не смотрит: `Sys_DiscoveredCompetitions` приватна (нет
гранта `swimm_ro`), а строки в `Competitions` у предстоящего старта ещё нет и по решению
§3.1 исходного плана до импорта не будет. Значит, нужна **своя публичная проекция на
`OrgCompId`** — по той же логике, по которой денормализованы `CompDate`/`CompName` в
`CompetitionEntries`.

кнопка «Разминка» на `/Admin/Competitions` (модал + `GET/POST /api/admin/discovery/{id}/meet-info`,

Подробности для админа — `docs/admin-pages/competitions.md`, раздел «Кнопка "Разминка"».
Не прокликано вживую в браузере: модал требует входа админом.

**Решение Влада (29.08.2026): разминка вводится РУКАМИ в админке.** Регламент таканона не
разбираем — `RegulationAnalyzer` не трогаем вовсе. Админ читает регламент сам и вбивает
время; это дешевле, честнее (формулировки регламентов разношёрстные) и не создаёт ещё один
источник кривых данных. Автоизвлечение можно добавить потом как подсказку — схема Т1 к
этому готова полем `Source`.

**Новая таблица `CompetitionMeetInfo`** (публичная, грант `swimm_ro` в `02-grants.sql`):

| Поле | Смысл |
|---|---|
| `OrgCompId` (PK) | идентичность старта, как у `CompetitionEntries` — без FK на `Competitions` |
| `IsChampionship` | что определил забор по регламенту (см. ниже) |
| `IsChampionshipOverride` (nullable bool) | ручная правка админа; null — «как определил забор» |
| `RegulationUrl` | основание, видимое человеку (уже есть у забора) |
| `WarmUpTimes` (jsonb: `[{date, warm_up_local}]`) | по дням: у многодневки разминка своя; только руками |
| `UpdatedAt` | |

**Флаг «чемпионат» ставится АВТОМАТИЧЕСКИ (решение Влада, 29.08.2026).** Заводить ничего не
нужно: забор стартового протокола уже читает регламент через `IRegulationFetchService`, а
`RegulationAnalyzer` уже отдаёт `IsChampionship` — вместе с вето на «готовимся К чемпионату»
(живой случай «מילניום 2025») и цитатой-основанием. Забор просто записывает результат сюда.

⚠ Ручную правку **нельзя хранить в том же поле**: перезабор идемпотентен и вызывается сколько
угодно раз, он затёр бы её на следующем же прогоне. Отсюда отдельный
`IsChampionshipOverride` — тот же приём, что `StandingKindOverride` у `Competition`.
Действующее значение = `Override ?? IsChampionship`.

**Экран в админке**: блок «Start list / Meet info» на странице соревнования
(`/Admin/Competitions`) — по строке на день программы с полем времени разминки (единственное,
что вводится руками) плюс флаг чемпионата **только для чтения** с цитатой из регламента и
кнопкой «переопределить». Дни берём из уже затянутых заявок (`CompetitionEntries`), чтобы
админ не вводил даты руками. Не забыть MD в `docs/admin-pages/` — часть definition of done.

**Отдача наружу**: `StartListProgrammeDto` получает `is_championship`, а `StartListDayDto` —
`warm_up_at` (карточка плана и так грузит программу, отдельного запроса не нужно).

**Тесты** (`Swimm.Tests`): сохранение/чтение `CompetitionMeetInfo`, попадание `warm_up_at`
в нужный день программы у многодневки, публичная выдача при пустой справке и — главное —
**перезабор не затирает `IsChampionshipOverride` и введённую разминку**.

> Никто ничего не ввёл → `warm_up_at` = null → блок ARRIVE BY просто не рисуется. Это
> штатный путь, а не ошибка: у большинства стартов справки не будет.

### Т10. Share link — ✅ СДЕЛАН 30.08.2026

Что получилось: кнопка «Share link ↗» в шапке карточки, формат адреса `?tab=startlist&plan=s10,c506`,
чистые `serializePlanParam` / `parsePlanParam` в `plan-model.ts`.

Решения, которые нельзя переизобрести:

- **Свой формат, а не JSON в query**: ссылку пересылают в родительский чат, она должна
  читаться глазами и переживать копирование из мессенджера.
- **Галочки в ссылку НЕ едут.** «I'm coming» и «Notify me» — про отправителя, а не про того,
  кто ссылку открыл.
- **Открытая ссылка НЕ перезаписывает план получателя.** Состав из адреса показывается с
  пометкой «SHARED PLAN» и подсказкой «Tap Edit to make it yours»; своим он становится
  только после первой правки — тогда же `?plan=` уходит из адреса, иначе после перезагрузки
  вернулся бы чужой состав.
- **Мусор в параметре отбрасывается молча**: ссылка живёт дольше состава (пловца могли снять).
- На телефоне жмётся системное «Поделиться» (`navigator.share`) — это и есть сценарий
  «кинуть в чат»; на десктопе ссылка кладётся в буфер, кнопка отвечает «Link copied».

Проверено вживую: `?plan=c506,c503` открывает чужой состав, `localStorage` при этом пуст;
после первого клика в пикере план сохранился (506, 503 + добавленный 482), а `?plan=` из
адреса исчез.
