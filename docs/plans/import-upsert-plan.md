# Импорт: переимпорт как update-in-place (upsert)

Статус: **реализовано и проверено вживую** (2026-07-20, Fable; не закоммичено).
Шаг 6 пройден на Маккабиаде: 915 строк восстановлены he-переимпортом с overwrite,
медиа (тестовые UserMedia+HubGroupMedia) пережили переимпорт на тех же ResultId.
Дополнительно реализовано сверх плана: предупреждение о массовом удалении в
превью (existingResultCount) и матчинг превью по SubName для дней, привязанных
к событию. Найдено и исправлено попутно: he-ветка парсера никогда не парсила
международные эстафеты (IsrOrgCompetitionParser, регрессионный тест на реальном
PDF). Известное поведение: строки, «переехавшие» между днями из-за другой
раскладки парсера, считаются deleted+inserted (день входит в ключ матчинга). Мотивация — сегодняшний кейс
Маккабиады: фикс парсера (восстановление ног эстафет) требует переимпорта, а
текущий путь — «удалить соревнование и залить заново» — теряет ID результатов и
упирается в Restrict-FK от пользовательского медиа.

**Инцидент и пересмотр Р3 (2026-07-20, тот же день):** OverwriteExisting в исходной
реализации был жёстко сцеплен с удалением — переимпорт PARTIAL-файла (например,
только один зал/группа вместо всего соревнования) молча удалял все результаты,
отсутствующие в файле. На проде это снесло 661 из 915 строк одного соревнования
(915 → 254) при повторном he-переимпорте частичного протокола с включённым
чекбоксом «Обновить существующее соревнование». Причина: чекбокс одновременно
означал «UPDATE/INSERT сматченного» И «DELETE несматченного», хотя админ обычно
хочет только первое. По итогам инцидента удаление вынесено в отдельный опт-ин
флаг `DeleteMissing` (см. ниже) — OverwriteExisting сам по себе теперь **никогда
не удаляет**.

## Что хотим

`ImportAsync` при повторном импорте того же соревнования **обновляет** его на
месте вместо отказа «Дубль … удалите через историю импорта». Сохраняются:
`Competition.Id`, `ResultRecord.Id` для сматченных результатов, и всё, что на
них навешано (UserMedia, HubGroupMedia, CategoryCompetition, избранное через
пловцов). Переимпорт после фикса парсера становится рутинной кнопкой, а не
операцией со сносом данных.

## Разведанные факты (2026-07-20, проверено по коду)

- **Повторный импорт сейчас НЕ создаёт дубль** — он отбивается. Ключ
  соревнования `Name|Date|PoolType` (unique index, SwimmDbContext:89; кэш
  импорта JsonImportService:139-141). Если соревнование по этому ключу уже
  имеет результаты — жёсткий rollback с ошибкой «Дубль» (:304-316). Дубль
  возможен только при отличающемся имени/дате/типе бассейна (например, парсер
  стал выдавать чуть другой заголовок).
- **`OrgCompId` импорт никогда не заполняет** (комментарий
  CompetitionDiscoveryService:13: «имя+дата единственный шов»; при создании
  Competition в JsonImportService:261-273 поле не присваивается). Уникальный
  констрейнт AK_Competitions_OrgCompId есть, но на импортированных строках
  поле всегда null.
- **Результаты — чистый insert.** Ни лукапа существующей строки, ни
  уникального ключа на Results нет (все индексы non-unique,
  ResultRecord.cs:16-22). Relay, Gallery/GalleryItem, ImportHistory — тоже
  pure insert. Лукап-перед-вставкой есть только у Competition, Club, Swimmer,
  Style, Country.
- **Весь импорт — одна транзакция** (execution strategy + BeginTransaction,
  JsonImportService:181-605), выполняется в фоновом воркере
  (ImportBackgroundService, single reader из in-memory очереди). Это
  сохраняем.
- **Что висит на ID снаружи импорта:**
  - `UserMedia.ResultId` и `UserMedia.CompetitionId` — **Restrict** (блокируют
    удаление; главный выгодоприобретатель upsert'а);
  - `HubGroupMedia.ResultId` — **Cascade** (при delete-and-recreate тихо
    исчезает — разметка видео группы теряется молча!);
  - `CategoryCompetition` — **Cascade** (ручная категоризация админа теряется);
  - `ImportHistory` — Cascade; `CompetitionResultUrls` — по OrgCompId, Cascade;
  - Records, UserFavorites, TrainingResults — FK на Results/Competitions не
    имеют, не затронуты.
- **ImportHistory не умеет «этот файл уже заливали»** — хранит только имя
  файла + дату, без хэша содержимого.
- Двухфазный поток превью→импорт живёт в IMemoryCache 15 минут; воркер получает
  готовый ResultsJson, ничего не перепарсивает.

## Решения (ключевые, требуют подтверждения при ревью плана)

### Р1. Идентичность соревнования — оставить `Name|Date|PoolType`

`OrgCompId` был бы честнее, но импорт его не заполняет, и протаскивать его из
Discovery через превью в JSON — отдельная работа с миграцией поведения. Не
сейчас. Ключ `Name|Date|PoolType` уже уникален в БД и уже используется кэшем
импорта — upsert просто меняет реакцию с «отказать» на «обновить».
Побочный кейс «парсер стал выдавать другой заголовок» upsert'ом не решается —
это и сегодня создаёт новое соревнование; фиксируем как известное ограничение.

### Р2. Ключ матчинга результата

Уникального ключа в БД нет, значит матчим в памяти внутри транзакции. Ключ:

```
CompetitionId | StyleId | Distance | Gender | Heat | Lane | IsRelay(RelayId!=null)
```

Обоснование: заплыв+дорожка — физическая идентичность попытки, они не меняются
при перевыпуске протокола; время/место/дисквалификация — меняются, это payload,
а не идентичность. `SwimmerId` в ключ НЕ входит: у эстафет пловцы анонимные
(после фикса дедупа 2026-07-20 каждый — новая строка), а у обычных заплывов
пловец на дорожке однозначен и матч по дорожке его и так найдёт; к тому же
исправление опечатки в имени пловца не должно рвать матч результата.

Коллизии ключа (два результата на одной дорожке одного заплыва — в реальных
протоколах не встречается, но формат не запрещает): матчить по порядку
следования, при расхождении количества — излишки как unmatched.

### Р3. Судьба сматченных/новых/исчезнувших результатов (пересмотрено после инцидента 2026-07-20)

- **Сматчен** → UPDATE payload-полей существующей строки (время, позиция,
  TimeFail, сплиты, очки, AgeGroup, Note...). `Id` сохраняется — UserMedia и
  HubGroupMedia живут. Происходит всегда при OverwriteExisting=true, независимо
  от DeleteMissing.
- **Новый** (есть в файле, нет в БД) → INSERT как сейчас. Тоже не зависит от
  DeleteMissing.
- **Исчезнувший** (есть в БД, нет в файле) → удаление теперь **опт-ин**,
  отдельным флагом `DeleteMissing` (default false), значимым только при
  OverwriteExisting=true:
  - `DeleteMissing=false` (новый безопасный дефолт) — исчезнувшие строки
    остаются нетронутыми: не удаляются, Relay/Gallery/пловцы-заглушки по ним
    не подчищаются (никакого удаления — значит и подчищать нечего). Именно это
    предотвращает повтор инцидента с partial-файлом.
  - `DeleteMissing=true` — **DELETE, но с защитой**: если на строке висит
    UserMedia (Restrict и так не даст) ИЛИ HubGroupMedia (Cascade — удалилось
    бы молча!) — не удалять, а пометить в отчёте импорта как «осиротевший
    результат с медиа, разберитесь руками». Молчаливый Cascade HubGroupMedia —
    главная ловушка всего плана.
- Отчёт импорта дополняется счётчиками: updated / inserted / deleted /
  skipped-with-media. Deleted и skippedWithMedia остаются 0, если
  DeleteMissing=false — так отчёт честно показывает, что удаления не было.

### Р4. Relay и Gallery при апдейте результата

Сейчас создаются через навигацию как приватные 1:1-довески результата
(FK SetNull). При апдейте: если у результата уже есть RelayId — обновить поля
существующей Relay-строки (в т.ч. новый RelaySwimmersName — ради этого всё и
затевалось), иначе создать и привязать. С Gallery аналогично: обновить состав
GalleryItems (проще: очистить и перезаписать items внутри той же Gallery,
Gallery.Id сохраняется). Осиротевшие Relay/Gallery от удалённых результатов —
подчистить как в DeleteCompetitionCoreAsync.

### Р5. Пловцы при переимпорте

Матчинг пловцов не трогаем — он уже upsert по духу (дедуп-ключ + enrich).
Но добавляется новый эффект: переимпорт Маккабиады превратит анонимные ноги в
именованных пловцов → у старого результата сменится SwimmerId (анонимная
заглушка → реальный пловец). Это правильно и желаемо. Осиротевшие анонимные
заглушки после апдейта подчистить тем же фильтром сиротства, что в
DeleteCompetitionCoreAsync:908-922.

### Р6. Явность режима

Upsert НЕ включается молча. В `ImportEventOptions` добавляется флаг
`OverwriteExisting` (default false). Без флага поведение прежнее — отказ
«Дубль». UI: в Admin/Import и в Discovery-превью — чекбокс «Обновить
существующее соревнование», показывать только когда бэкенд превью сообщает,
что соревнование по ключу уже существует. Так админ всегда знает, что делает
перезалив.

Удаление — отдельный опт-ин поверх этого чекбокса (см. пересмотр Р3 выше):
второй чекбокс «Удалять результаты, которых нет в файле» (`DeleteMissing`),
видимый/активный только когда включён «Обновить существующее соревнование»,
по умолчанию выключен. Предупреждение о массовом удалении (до N−M результатов)
показывается только когда оба чекбокса включены — при простом overwrite без
DeleteMissing оно неприменимо, ничего не удаляется.

## Порядок реализации

1. **Матчер результатов**: чистая функция «старые строки + новые строки →
   (matched, insert, delete)» по ключу Р2 + тесты на неё (включая коллизии
   ключа и relay-кейс). Без интеграции.
2. **Ветка upsert в ImportAsync** за флагом `OverwriteExisting`: UPDATE/INSERT/
   DELETE-с-защитой по Р3, Relay/Gallery по Р4, чистка сирот по Р5, счётчики в
   результат импорта. Существующий create-путь не трогается.
3. **Прокладка флага**: ImportEventOptions → AdminController.ImportJson /
   ImportParsed → DiscoveryImportRequest → очередь. Превью дополняется полем
   «existingCompetitionId» (лукап по Name|Date|PoolType), чтобы UI знал, когда
   показывать чекбокс.
4. **UI**: чекбокс в Admin/Import и в Discovery-превью + вывод счётчиков
   updated/deleted/skipped в статусе джобы.
5. **Тесты интеграционные** (InMemory, по образцу SwimmerImportMatchingTests):
   переимпорт того же файла = 0 insert / N update / 0 delete; файл с
   исправленным временем; исчезнувший результат с HubGroupMedia не удаляется;
   анонимная эстафета → именованная (Маккабиада-кейс); повторный импорт без
   флага по-прежнему отбивается «Дубль».
6. **Живая проверка на Маккабиаде**: переимпорт с флагом, eventId=6 показывает
   составы эстафет, медиа на месте.

## Footguns

- **HubGroupMedia.ResultId — Cascade**: любое удаление результата молча уносит
  групповую разметку. Все DELETE в upsert-ветке — только через проверку Р3.
- Многодневные соревнования: один файл = несколько Competition (дни события).
  Матчер работает per-Competition; проверить пересчёт дат CompetitionEvent
  (JsonImportService:542-562) в upsert-ветке.
- Интеримные SaveChanges внутри транзакции: upsert-ветка обязана жить внутри
  той же execution strategy + транзакции, никаких SaveChanges вне неё.
- `CompetitionDate` — `timestamp without time zone`; при сравнении ключей не
  напороться на Kind/таймзону.
- Отчёт «skipped-with-media» должен доходить до UI, а не только в лог — иначе
  админ не узнает, что часть строк не обновилась.
- Перед сборкой — сервер на :5078/:5079 держит dll (netstat -ano | findstr).
- Не трогать чужие незакоммиченные правки (my-media, HubGroups/MediaController).

## Вне скоупа (сознательно)

- Переход идентичности соревнования на OrgCompId (отдельный план, если
  «парсер сменил заголовок» станет реальной болью).
- Хэш содержимого в ImportHistory («этот файл уже заливали»).
- Чистка исторической склейки анонимных пловцов (swimmer_id 8243) — отдельная
  разовая задача по данным.
