## 3. Пять технических фактов, определяющих объём

1. **Качается NR ровно одной страны.** GUID страны — в конфиге
   `RecordsImport:WorldAquaticsNationalCountryId` (дефолт Израиль
   `962f77d6-…`). В проекте справочника «GUID worldaquatics ↔ alpha-3» нет, **но его отдаёт
   сам API** — см. §3а.
2. **`User-Agent` обязателен** — без него api.worldaquatics.com не отвечает вовсе (висит до
   таймаута). Выстрадано на приёмке 2.6.
3. **`RegionCode` берётся не из запроса**, а из кода страны спортсмена в строке XLSX
   (NR/CR → код страны). *Уточнено 2026-09-15 (§3а):* в NR-файлах этот код совпадает с
   запрошенной страной, а мусорные `USA`/`JAM` — это повторённые мировые рекорды `=WR`.
4. **`Record.Time` — СТРОКА** («21.08», «01:43.45»). Рейтинг сортирует по времени →
   строковая сортировка не годится, нужен парсинг в миллисекунды.
5. **`RecordDate` — строка со смешанными форматами** (обычно `dd/MM/yyyy`, в легаси
   встречается `M/d/yyyy`). Для показа и сортировки по дате нужна нормализация.

Плюс: `/api/records` **требует** `region` (400 без него) — рейтинг «поверх всех стран» через
него не сделать. Легаси-дерево `window.normative_*` / `records-helper.ts` с ключом `ISR→NR`
рассчитано на одну страну — новые страницы ходят в API напрямую, минуя дерево.

## 3а. Разведка источника (2026-09-15)

Скачано вживую: список стран, WR SCM/LCM и NR SCM/LCM трёх стран — `USA` (большая), `JAM`
(средняя), `AGU` (Ангилья, крошечная).

**Список стран отдаёт сам API.** `GET https://api.worldaquatics.com/fina/countries` (тоже с
`User-Agent`) — один запрос, 246 записей: `Id` (тот самый GUID для `countryId`), `Code`
(alpha-3, дублей нет), `Name`, `RegionName` (континент). GUID Израиля совпадает с конфигом.
У 11 записей `RegionName` пуст — это не страны: `AIN`, `CLB`, `EOR`, `FINA`, `IOA`, `IOC`,
`IOP`, `NAA`, `NAB`, `NAC`, `SMF` (нейтральные атлеты, сборная беженцев, «Club», сама FINA…).
**Реальных стран 235** → 470 NR-файлов + 2 WR на полный прогон.

**Колонки отчёта:** `Event, Pool, Record Description, Record, Time, Athlete, NF Code, Gender,
Competition, Country, City, Date, Splits, Tags, Status`.
- `NF Code` — федерация спортсмена. Во всех NR-файлах выборки (6 файлов, 181 строка) он равен
  запрошенной стране.
- ⚠ **`Country` — страна МЕСТА соревнования**, полным названием («Great Britain»), а не страна
  спортсмена. Парсер берёт её запасным вариантом, когда `NF Code` пуст
  (`WorldRecordsParser`, строка `string country = …`) — на массиве стран это прямая дорога к
  регионам вида `Great Britain`. В режиме «все страны» этот фоллбек использовать нельзя.
- `Record` бывает составным: `NR, WR`, `NR, AM`, `NR, CR`, `=WR`… Парсер понимает ровно `WR`,
  всё прочее считает национальным.
- `Date` — настоящая дата Excel (не строка), `Status` во всей выборке — `Approved`.

**Откуда `USA`/`JAM` — найдено.** В WR SCM три строки с типом `=WR` (повторённый мировой
рекорд): 100 на спине ж (USA, 54.02) и 100 брасс ж (JAM, 1:02.36, две строки).
`NormalizeRecordType` ждёт ровно `WR` → строка считается национальной, регион берётся из
`NF Code` → она уезжает в `country/USA/open` и `country/JAM/open`. Это баг **сегодняшнего**
импорта, а не только Фазы 11: соавтор мирового рекорда теряется из `world`.
**Починен 2026-09-15** (шаг 0, `docs/data-integrity.md` И-19).

**Мусор бывает и в самом источнике (И-20).** Пробный `--records-refresh --dry-run` 15.09
показал в отчёте WR LCM «мировой рекорд» 40.11 на 100 вольным ж (`Status = Approved`, но
`Record Description = Meet Record`). Импорт правдоподобие не проверяет — на 235 странах
такого будет больше. Отсюда п. 4 в 11.1.3.

**Скорость API.** 8 XLSX: от 2 до 53 с на файл (WR SCM — 52.7 с, NR USA SCM — 30.0 с,
остальные 2–16 с). У `WorldRecordsSourceProvider` таймаут 30 с — **2 файла из 8 в него не
уложились бы**. Если это не разовая медлительность, падает и нынешняя кнопка Fetch (контроллер
ловит `HttpRequestException`, а таймаут — `TaskCanceledException`, будет 500). Полный прогон
470 файлов с паузой 2 с — **от часа до двух**.

**Объём.** NR на страну, оба бассейна: USA 91, JAM 72, AGU 18 строк (до отсева микст-эстафет).
Оценка по всем странам — **≈10–15k строк**, меньше июльских 20k.

## 4. Этап 11.1 — импорт рекордов всех стран

### 11.1.1 Перечисление стран ☐ (исследование ✅)
Исследование сделано: список отдаёт сам API (§3а). **Решение по хранению (предложение):**
тянуть список живым в начале каждого прогона (один запрос) и отсекать записи без
`RegionName`. Миграция не нужна, GUID в БД не храним — он нужен только импорту. Таблицу
`Countries` (100 строк) импорт не трогает; названия стран для витрины — вопрос этапа 11.2.
Разбор списка — тестом на зафиксированном фрагменте JSON (по образцу
`IsrOrgRecordsPageResolverTests`) + живой тест под `SWIMM_NET_TESTS=1`.
**Приёмка:** «список стран» отдаёт 235 пар GUID ↔ alpha-3 без псевдо-сборных; тест на фрагменте.

### 11.1.2 Батч-фетч (только NR, `open`) ☐
- 235 стран × 2 бассейна = **470 NR-файлов**; WR SCM/LCM — **один раз на прогон**, не на страну.
- Не request-scoped фетч, а **фоновая задача** по образцу `ImportJobQueue` +
  `ImportBackgroundService` (очередь в памяти, статус по опросу): пауза 2 с между файлами,
  **таймаут на файл 120 с** (замер — до 53 с, §3а), 2 повтора, прогресс «страна N из 235»,
  список упавших стран и кнопка «повторить только их».
- Итог прогона — дифф, который живёт **до Apply**, а не 10 минут (прогон идёт час и больше;
  TTL в памяти ~12 ч). Рестарт API теряет прогон — допустимо, запускается заново.
- Сохранить контракт: превью-дифф → Apply в транзакции (по выбранным странам) → сброс кэша.
- «Нет в источнике» считать **только по странам прогона**: сейчас счётчик берёт все регионы
  категории `open`, и при прогоне одной страны остальные выглядели бы «пропавшими».
- **ИНВАРИАНТ 1 — age/masters.** Сейчас держится сам собой: Apply только upsert, дифф берёт
  категорию из строк источника (`open`). **Не добавлять удаление «нет в источнике»:** у малых
  федераций наборы неполные, а у `country/ISR/open` есть строки федерации, которых World
  Aquatics не отдаёт, — удаление стирало бы чужие данные.
- **ИНВАРИАНТ 2 — Израиль (добавлен 2026-09-15, в июльском плане его не было).** На
  `country/ISR/open` пишут два источника с одним ключом, выигрывает применённый последним.
  Порядок зафиксирован решением Влада 2026-08-24: сперва World Aquatics, потом федерация
  (И-13, CLI `--records-refresh`). Если батч «всех стран» захватит Израиль, World Aquatics
  **молча откатит 19 более свежих рекордов федерации** (у WA местами отставание на 10 лет).
  **Рекомендация: батч пропускает `ISR`**, Израиль обновляется только `--records-refresh`.
  Альтернатива — батч после себя сам запускает `isrorg-age`; сложнее и дублирует CLI.
**Приёмка:** прогон на 3–5 странах (включая крошечную, вроде `AGU`) → дифф только `open` этих
стран; `count(*)` ISR age/masters/open до и после совпадает; `ISR` в списке прогона нет.

### 11.1.3 Качество кодов регионов ◐ (п. 1 ✅ 2026-09-15)
Разведка (§3а) сузила задачу — отдельный экран карантина, скорее всего, не нужен:
1. ✅ **Баг `=WR` — сделан 2026-09-15 отдельно от фазы** (И-19): парсер, тесты
   `WorldRecordsEqualledRecordTests`, миграция `DropEqualledWorldRecordStrays`. Как было задумано: тип рекорда нормализовать с учётом
   `=` (повторённый рекорд) и составных значений; в WR-файле любая строка — `world`. После
   фикса `DeduplicateByAxes` склеит держателей равных времён: у 100 брасс ж 25 м к `LTU`
   (2013) добавится `JAM` (2014, 2016); у 100 на спине ж обе строки `USA` (2024 и 2025) —
   если это один человек, имя не изменится. Ожидаемо «изменится 1–2» в диффе. Затем удалить артефакты
   `country/USA/open` и `country/JAM/open`. Тест — фрагмент WR-отчёта с `=WR` (по образцу
   `WorldRecordsMedleyStyleTests`).
2. **`RegionCode` — из запроса.** В режиме по странам код региона берётся из запрошенной
   страны (alpha-3 из списка), а не из строки. Строки, где `NF Code` пуст или ≠ запрошенной,
   **не пишутся**, а попадают в отчёт прогона (страна, дисциплина, что пришло). Фоллбек на
   колонку `Country` (место соревнования) в этом режиме запрещён.
3. Если отчёт покажет заметный объём несовпадений — тогда разбор в админке. По выборке их ноль.
4. **Сторож правдоподобия времени (добавлен 2026-09-15, И-20).** Источник сам отдаёт мусор
   («мировой» 40.11 на 100 в/с ж). Минимум: национальный рекорд не может быть быстрее мирового
   той же дисциплины; новый рекорд, улучшающий прежний больше чем на N %, в Apply не идёт, а
   показывается отдельно. Как именно (блок или пометка через реестр спорных рекордов,
   `records-quality-plan.md`) — решает Влад. Нужен и нынешнему `--records-refresh`, не только
   фазе.
**Приёмка:** в БД нет одиночек `USA`/`JAM`; повторённые WR лежат в `world` с двумя держателями;
несовпадения видны в отчёте прогона; невозможное время в Apply не проходит.

## 5. Этап 11.2 — страница рейтинга рекордов

### 11.2.1 API ☐
Новый `GET /api/records/ranking` (через `/api/records` нельзя — он требует `region`).
Фильтры: дисциплина (стиль × дистанция), бассейн 25m/50m, пол, регион(ы), сортировка по
времени, пагинация. **Категория фиксирована `open`** — в фильтрах её нет.
Требует решения по факту №4 (§3): парсинг `Time` в мс — на лету при выборке или
денормализованная колонка `TimeMs` (миграция). *Рекомендация: колонка `TimeMs` — сортировка
по строке иначе не выразима в SQL, а сортировка в памяти по 10–15k строк на каждый запрос
не нужна.*
**Приёмка:** сортировка корректна на смеси форматов («59.99» vs «01:00.01»); кэш по составу
фильтра; EXPLAIN на ranking-запросе в бюджете.

### 11.2.2 Страница `/records` ☐
Таблица «дисциплина → страны по времени», фильтры, флаги стран, **дельта к мировому рекорду**
(секунды и %), подсветка домашнего региона (`HOME_REGION`). Мобильные варианты компонентов.
Маршрут — по правилу трёх зеркал (`routes.ts` + `vite.config.js` + `Program.cs`).
**Приёмка:** прокликано, RTL и обе темы, пустой фильтр не ломает страницу.

### 11.2.3 Клиентский шов ☐
Новая страница ходит в API напрямую, **минуя** легаси-дерево `window.normative_*`
(ключ `ISR→NR` — под одну страну). Существующие попапы/карточки не ломать.
**Приёмка:** попап нормативов и age/masters-карточки работают как раньше.

## 6. Этап 11.3 — head-to-head

### 11.3.1 API ☐
`GET /api/records/compare?a=ISR&b=USA[&pool=&gender=]` — выравнивание по общей оси дисциплин:
время A, время B, дельта, кто быстрее, «нет данных». Только `open`.
**Приёмка:** «нет данных» — отдельное состояние в ответе, не 0 и не null-как-медленнее.

### 11.3.2 Страница `/records/compare` ☐
Выбор двух стран, сводный счёт (сколько дисциплин за кем), таблица по дисциплинам с дельтами,
разрезы по полу и бассейну. Диплинк с обеими странами (в пути или query — по правилу routes.ts).
**Приёмка:** обмен странами местами даёт зеркальный результат; ссылка воспроизводит состояние.

### 11.3.3 Честность сравнения ☐ — требование, не косметика
- Даже внутри `open` у стран **разный набор дисциплин** и **разные даты** рекордов, где-то
  рекорда нет вовсе. **«Нет данных» ≠ «медленнее»** — иначе страница врёт в пользу той страны,
  по которой данных больше.
- Показывать `RecordDate` рядом со временем — иначе сравниваются величины разных эпох
  (нормализация формата — факт №5 в §3).
- В сводном счёте не засчитывать дисциплины, где у одной из стран данных нет.
**Приёмка:** страна с половинным покрытием не «выигрывает» пустотами.

   дёшево. Вопрос в мусоре: у многих федераций наборы неполные или кривые.
   *Рекомендация (уточнена 2026-09-15): тянуть все 235 реальных стран — псевдо-сборные
   отсекаются сами (§3а); порог покрытия — вопрос витрины 11.2, не импорта.*
2. **Что делать с расхождением кода страны** (11.1.3). *Рекомендация изменилась 2026-09-15:*
   июльская — «карантин + разбор в админке»; теперь — `RegionCode` из запроса, несовпадения
   в отчёт прогона, без отдельного экрана (по выборке несовпадений ноль).
3. **`TimeMs`** — колонка миграцией или парсинг на лету (§11.2.1). *Рекомендация: колонка.*
4. **Израиль в батче** (11.1.2, инвариант 2) — новый. Пропускать `ISR` (Израиль только через
   `--records-refresh`) или гнать федерацию после батча. *Рекомендация: пропускать.*
