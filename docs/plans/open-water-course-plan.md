## 1. Рекомендация: площадка — отдельное поле, а не третье значение `PoolType`

**Заводим `Competitions.WaterKind` (`pool` | `openwater`). `PoolType` остаётся строго длиной
бассейна (`25m` / `50m`), при открытой воде — пустая строка, и это держит CHECK-констрейнт.
Наружу (API, UI) едет ОДИН самоописывающий токен курса: `25m` | `50m` | `openwater`.**

Почему не третье значение `PoolType`, хотя оно выглядит дешевле:

- **`PoolType` — это ось справочника.** Колонка с таким именем есть в пяти таблицах, и в четырёх
  (`Records`, `NormativeStandards`, `Sys_RecordIssues`, `Sys_TrainingSessions`) она значит «в каком
  бассейне» и входит в уникальные индексы. Четыре захардкоженные проверки «25m или 50m»
  (`RecordAdminRepository.cs:161,174`, `ClubsPublicController.cs:103,122`) сегодня **верны**. Третье
  значение превращает каждую в «бассейн И не открытая вода» — правило, которое надо не забыть в
  четырёх местах, и любое забытое молча открывает справочник рекордов для моря.
- **Через год.** Два реалистичных расширения — «33 м» (длина) и «река/озеро» (площадка). При
  отдельном поле каждое приземляется в своё поле. При третьем значении «река» превращает
  перечисление длин в скрытую ось площадки и рассыпает по коду `v is OpenWater or River`.
- **Миграция и откат.** `AddColumn` + `Sql`-бэкфилл — готовый шаблон
  (`Migrations/20260810160016_AddCompetitionDiscipline.cs`), `Down` = `DropColumn`. Третье значение
  требует `AlterColumn varchar(5) → varchar(20)` на колонке под уникальным индексом; **`AlterColumn`
  не использован ни разу за 69 миграций**, а сгенерированный EF `Down` сузит тип раньше очистки
  длинных значений и упадёт с 22001.
- **Убирается вторая точка правды.** Сейчас открытую воду можно пометить только
  `StandingKindOverride='openwater'` (`Competition.cs:107-118` — там прямо написано, что поле
  заведено «прежде всего под открытую воду»). После правки роль выводится из данных, а override
  возвращается к роли механизма исключений.

Почему **не** nullable `PoolType`: NULL значит «нет данных», а нам нужно утверждение «бассейна
нет». Он инвертирует уже написанное правило `StandingKinds.cs:49` («бассейн не задан — роль вывести
не из чего»), требует `NULLS NOT DISTINCT` (нигде в проекте не используется) и закрывает состояние,
которое у реальности **уже есть**: `IsrOrgParser.cs:17-18` честно пишет, что длину бассейна протокол
не указывает и парсер ставит `25m` условно — то есть 43 строки из 58 это допущение, а не измерение.

### Что взято из проигравших вариантов

1. **Один токен на проводе.** В БД два поля, наружу — по-прежнему одно `pool_type` со значениями
   `25m|50m|openwater`. Не нужно тащить `water_kind` через шесть DTO; забытая проекция даёт пустую
   строку, а не «50 м».
2. **Слово `openwater`** — как в `StandingKinds.OpenWater`. Не `open` (на клиенте занято открытой
   КАТЕГОРИЕЙ рекордов, `records-helper.ts:148,152`), не `none` (`StandingKinds.None`).
3. **Клиентские места перечисляет компилятор:** расширяем возвращаемый тип `resolvePoolType` так,
   чтобы `getNormativeLevelInfo` его не принимал — `tsc` сам выдаст все вхождения.
4. **Явные ранние выходы** в детекторе рекордов, в бонусе High Point и в превью Б2 — вместо надежды
   на то, что ключ не совпадёт.
5. Из nullable-варианта: CHECK-констрейнт, правило «импорт не подставляет умолчание молча»,
   порядок «код раньше данных», приёмочный SQL на дубли.

## 2. Схема и константы

```
Competitions.WaterKind  character varying(20) NOT NULL DEFAULT 'pool'
```

Форма — как у соседних категориальных полей (`Discipline`, `StandingKindOverride`). Имя `WaterKind`
в репозитории свободно; `Venue` брать нельзя — занято под место проведения
(`DiscoveredCompetition.cs:41-42`, у 16809 = «אילת»).

`Competitions.PoolType` не трогаем: `varchar(5) NOT NULL`, меняется только xml-док. Уникальный
индекс `IX_Competitions_Name_Date_PoolType` не трогаем. `Records`, `NormativeStandards`,
`Sys_RecordIssues`, `Sys_TrainingSessions` не затрагиваются — это и есть письменная фиксация правила
«справочник рекордов и нормативов остаётся бассейновым».

### Инвариант WK1 и CHECK

```sql
CONSTRAINT "CK_Competitions_WaterKind_PoolType" CHECK (
  ("WaterKind" = 'openwater' AND "PoolType" = '')
  OR ("WaterKind" = 'pool'   AND "PoolType" <> '')
)
```

Все 58 существующих строк ему удовлетворяют. CHECK-констрейнтов на `PoolType` сегодня нет ни одного
ни в одной из пяти таблиц.

⚠ **CHECK не ловит мусор вроде `openm`** (правка критика): он проверяет только пустоту/непустоту, а
не вхождение в белый список. За опечатки и остатки старой нормализации отвечает проверка реестра
`competitions.pool-type-unknown` (**Error**), см. §4.

⚠ **CHECK не покрывается тестами**: они идут на EF InMemory, констрейнты там не применяются.
Проверять — на живой БД после `database update`.

### Константы

Новый `server/Swimm.Application/Constants/WaterKinds.cs` по образцу `Disciplines.cs`:

```csharp
public const string Pool = "pool";
public const string OpenWater = "openwater";           // == StandingKinds.OpenWater
public static readonly IReadOnlyList<string> All = [Pool, OpenWater];
public static bool IsValid(string? v);
public static bool IsOpenWater(string? v);

/// Единственная эвристика: «מים פתוחים» (ловит и «במים פתוחים») + английское «open water».
public static bool IsOpenWaterName(string? name);

/// ЕДИНСТВЕННОЕ место, где два поля склеиваются в токен курса: ключ идентичности,
/// значение фильтра и то, что уезжает наружу в pool_type.
public static string Course(string? waterKind, string? poolType)
    => IsOpenWater(waterKind) ? OpenWater : (poolType ?? "");

public static string Label(string? waterKind, string? poolType);   // «Open water» / «25m pool»
```

Две миграции: `AddCompetitionWaterKind` (колонка + CHECK) и `BackfillOpenWater` (одна строка `Sql`
по признаку названия).

## 5. Честная оценка сложности

**Дёшево:** две миграции по шаблону, константы, ветка в `Resolve`, селект в админке, бэкфилл одной
строкой, Ф0 (одна строка SQL — чинит живой баг сегодня).

**Средне и нудно:** ~12 серверных чтений на провод, ~16 клиентских точек. Механика; риск
забывчивости прикрыт тем, что пустая строка на клиенте больше не превращается в «50 м».

**Грабли:**

1. **Калитка превью** `JsonImportService.cs:1268` — самая незаметная строка плана. Симптом пропуска
   не дубликат, а отказ импорта с советом удалить 238 результатов.
2. **Курс в ключе идентичности** → догадка считается от заголовка дня, а не имени события.
3. **Ручная простановка площадки** соревнованию без ключевой фразы в названии: переимпорт
   промахнётся. Сторожа — двусторонняя Info-проверка и Д2 по `OrgCompId`.
4. **`QuickUpdateAsync`** теряет поля, которых не знает.
5. **Двенадцать литералов `PoolType: "25m"`** в парсере остаются: он «немой», площадка считается на
   импорте. Любой будущий источник мимо `JsonImportService` снова привезёт бассейн.

**Чего работа НЕ даст:** клетка «открытая вода» в гриде клуба не зажжётся (#1547 в категории
`results-8-99`, которой нет в `Category.ReservedKeys`, а категорий `ow-*` в БД не существует);
плитки Hero не изменятся; страница #1547 останется неполной без дистанций 1600–10000 в фильтре.

## 6. Точка расширения: справочники рекордов и нормативов

Вопрос Влада (2026-08-12): «у бассейна на длинные дистанции, например 1600, нормативов и
рекордов пока нет, но если появятся — они должны грузиться отдельно». Разбор показал, что
разделение, которого он хочет, **уже существует, но не там, где кажется** — не в категориях
соревнования, а в осях самих справочников:

```
Records:            регион | категория | возраст | пол | PoolType | стиль | Distance   (UNIQUE)
NormativeStandards: вид | страна | пол | PoolType | стиль | Distance | возраст | уровень (UNIQUE)
```

**Дистанция — уже ось.** Отсюда три следствия, которые надо знать заранее.

**1. Длинные бассейновые дистанции подгружаются сами, без единой строки кода.** Рекорд
«1600 вольный, 25 м, 15 лет» — это обычная новая строка справочника. С 1500 не перепутается
(другая дистанция), с морскими 1600 не перепутается (другой бассейн). Категория соревнования
здесь ни при чём: справочники про категории соревнований не знают вообще.

**2. Сегодня длинная вода защищена СЛУЧАЙНО, а не по правилу.** В справочниках максимум 1500
(рекорды: 50/100/200/400/800/1500 + эстафеты; нормативы: те же без эстафет), а в Эйлате плыли
1600/3000/5000/10000 — сравнивать не с чем, поэтому ни ложного рекорда, ни ложного уровня нет.
Это везение, а не защита: **один заплыв на 1500 м в море ломает его** — 1500 в справочниках есть.
Ранние выходы из §3 (Ф2) как раз превращают везение в правило.

**3. Рекорды открытой воды — запланированный upgrade оси, а не «потом придумаем».** Сегодня
`Records.PoolType` — `NOT NULL` и часть уникального ключа: морскому рекорду туда нечего положить.
Когда федерация опубликует рекорды 5K/10K, порядок такой:

- добавить `openwater` третьим значением **в ось справочника** (`Records.PoolType`, при желании
  `NormativeStandards.PoolType`) — миграция без изменения структуры, значение просто становится
  допустимым;
- снять два гейта «только 25m/50m»: `RecordAdminRepository.cs:161,174` и
  `ClubsPublicController.cs:103,122` (первый — вход в справочник, второй — витрина клуба);
- заменить ранний выход детектора (Ф2) на нормальный матч по морской оси: `WaterKinds.Course(...)`
  уже отдаёт `openwater`, то есть ключ соберётся сам;
- дистанции 1600/3000/5000/10000 добавить в статический список фильтра (`filter-data.js:12`).

⚠ Именно поэтому поле у соревнования нужно **в любом случае**: оно отвечает на вопрос «с какой
полкой справочника сверять этот заплыв». Сегодня система сверяет море с бассейновой полкой —
просто полка пока пустая на этих дистанциях.

⚠ И поэтому же категория соревнования эту задачу не решает в принципе: рекорд не привязан ни к
какому соревнованию, у него нет и не может быть категории соревнования. Различать «1600 в
бассейне» и «1600 в море» может только ось воды в самом справочнике.
