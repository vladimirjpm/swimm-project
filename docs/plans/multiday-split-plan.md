# Двухдневный старт, схлопнутый в один день: разделить по дням (план, 07.10.2026)

Статус: **план принят 07.10.2026, начат М1.** Заведён после доклейки промежуточных 6595
([data-health-handoff.md](data-health-handoff.md) §5, п. 3). Решения по данным — в
[`../data-integrity.md`](../data-integrity.md) (Д2: «многодневка = соревнование на день»).

## 1. Проблема

Два зимних мастерс-чемпионата лежат в базе ОДНИМ днём, хотя плыли два:

| Наш comp | OrgCompId / loglig | У нас | По сетке loglig |
|---|---|---|---|
| **#1645** мастерс-зима 2025 | 6595 / 11586 (discovery #177) | 1423 строки, все 04/01/2025 | 22 дисциплины 03/01, 18 — 04/01; строки делятся **737 / 686** без остатка |
| **#64** мастерс-зима 2026 | 16714 / 13805 (discovery #55) | 1389 строк, все 10/01/2026 | 21 дисциплина 09/01, 19 — 10/01 |

У обоих `EventId = null` — события (`CompetitionEvent`) нет.

**Почему так.** В PDF дат по дисциплинам НЕТ: в шапке каждой страницы диапазон
«03/01/2025 - 04/01/2025». Парсер берёт дату из строки под шапкой дисциплины, а не нашёл —
липкую последнюю (`dat_relay`, `IsrOrgCompetitionParser.cs` ~1063, 1522–1540): вышло 04/01 у всех.
Дата дисциплины есть только в сетке loglig (`FetchDisciplineGridAsync` → `StartAtLocal`), и
для результатов её не читает никто (только стартовый протокол — `StartListPullService`).
Стартового протокола у 6595 нет.

**Что врёт из-за этого.** Дата заплыва на странице пловца, в PB/SB и протоколе; сверка
рекордов по ТОЧНОЙ дате (`RecordQualityService`) — у рекордов, проплытых в первый день;
окно ±1 день у `RecordMeetMatcher` / `RelayLeadOffMatcher` ошибку сейчас прячет. Сезон и
возраст мастерса (31.12 года старта) не страдают: оба дня в одном году.

## 2. Почему не «починить даты и перезалить»

`--repull` с правильными датами сделал бы хуже (разбор агентом 07.10, `JsonImportService`):

- строки 03/01 не нашли бы своего дня → **новое отдельное соревнование** без `EventId`,
  без `DayNumber`, без `OrgCompId` (6595 уже занят #1645, индекс уникален);
- в #1645 те же заплывы 03/01 остались бы (без `--delete-missing`) — **дубль**, или удалились бы
  и вставились заново (с ним) — а вместе с ними пропали бы ручные правки, которые на этих строках
  уже есть: 3 ручные пометки Р77 (м 4X50 комплекс — день 03/01), этап ויקטור בלכסן, промежуточные;
- `--repull` не передаёт опции события — день к событию не привяжется;
- у #64 к строкам привязаны 11 медиа пользователей (`Sys_UserMedia.ResultId`).

Вывод: существующие строки **переносим** (UPDATE, `Id` строк не меняется — медиа, реакции,
пометки, этапы, промежуточные едут с ними), а импорт чиним отдельно, чтобы следующий перезалив
не схлопнул дни обратно.

## 3. Этапы

### М1. Даты дисциплин из сетки loglig — один шов

Чистая функция `LogligDisciplineDates` (Swimm.Application/Mapping или Swimm.Parsing):
сетка → словарь «стиль × дистанция × пол → дата». Ключ в словаре наших строк — тот же, что
у сборщика эстафет (`ParserStyleOf`, `RelayGender` — переиспользовать, не копировать).
Ключ на ДВЕ даты (утренние отборы и вечерний финал в разные дни) — **неоднозначно**:
функция не угадывает, а возвращает список таких ключей (Р-сп-3).

Тесты: фикстуры сеток 11586 и 13805 (страницы `AthleticsDisciplines` в Fixtures/loglig);
737 / 686 для 6595 — на синтетике из ключей.

**СДЕЛАНО 07.10.2026.** `DisciplineDates` / `DisciplineDayPlanner` (Application/Mapping),
`IDisciplineDateSource` → `LogligDisciplineDateSource` (Parsing/Discovery, DI в
`Swimm.Parsing/DependencyInjection.cs`); строка без пола («none») получает день, только если у
всех полов дисциплины он один. Тесты — `DisciplineDatesTests` (5). Живая проверка (код М1 по
сетке loglig и строкам базы, без записи): **#1645 — 737 + 686, #64 — 714 + 675, без остатка
и без неоднозначных** — план М2 применим к обоим.

### М2. `--split-days <competitionId> [--apply]` — разделить уже импортированное

Dry-run по умолчанию; отчёт: сколько строк в какой день, неоднозначные и ненайденные ключи.
**Всё или ничего:** хоть одна строка без даты или с неоднозначной — ничего не пишем.

Что делает `--apply` (одна транзакция, через EF — сброс кэша K4 идёт интерцептором сам):

1. `CompetitionEvent` с `Name` = имя соревнования, `OrgCompId` = его OrgCompId (Д2: штамп
   поднимается на событие), `StartDate`/`EndDate` — по дням.
2. Существующее соревнование становится своим днём: `EventId`, `DayNumber`, `SubName`
   (Р-сп-1). `OrgCompId` **остаётся на нём** (Р-сп-2) — на него смотрят discovery, FK
   `CompetitionResultUrls`, `CompetitionSources`.
3. Новый день: копия полей — `Name`, `CountryId`, `PoolType`, `IsMasters`, `IsAward`,
   `IsChampionship`, `HasSplits`, `ShowCombineAllResults`, `Discipline`, `PointRuleClubsId`,
   `PointRuleSwimmersId`, `StandingKindOverride`, `ClubPointsDisabled`, `HasOfficialClubStanding`;
   `Date` — своя; `OrgCompId` — null. Отметки «очки сверены» (`*VerifiedAt/By/Kind`) **не
   копируются**: сверка была по одному дню-сумме — после деления её делать заново.
   Членство в категориях (`CategoryCompetitions`) — то же, что у исходного.
4. Перенос строк: `Results.CompetitionId` и `Results.CompetitionDate` у строк другого дня;
   у их `Sys_UserMedia` — `CompetitionId` вслед за строкой.
5. Пересчёт: `RecalculateCompetitionAsync` обоих дней (клубный зачёт, объединённые места — у
   события они считаются по всему событию, `EventId ?? -Id`); `ClubCompetitionStandings`
   разложатся по дням сами.
6. Аудит `competition.split-days` с числами; затем `--check-data`.

Не трогаем: `Sys_ImportHistory` / `Sys_ImportReconciliation` (история — как была),
`CompetitionNotes`, `CompetitionEntries` (у обоих пусто).

Тесты: InMemory на сервис + **`*PgTests`** (новый путь записи: частичный уникальный
`OrgCompId`, уникальный `(Name, Date, PoolType)`, FK медиа — память
«InMemory не видит CK Postgres»).

### М3. Импорт: перезалив не должен схлопнуть дни обратно

После М2 `--repull` 6595 при датах «всё 04/01» сопоставит ВСЕ строки дню 04/01 (идентичность
по OrgCompId → событие → дни, матчинг по дате) — в нём заведутся дубли заплывов 03/01.
Поэтому до М3 **6595 и 64 не перезаливать** (строка в передаче).

1. В шаге «эстафеты из loglig» (`LogligRelaySplitProvider`, едет вместе с импортом
   чемпионатов) — переписать `date` строк JSON по М1, если в шапке PDF диапазон дат. Тот же
   шов для превью/«Затянуть» и `--repull`.
2. `--repull`: если идентичность нашла событие — передавать его `EventId` в опции импорта,
   чтобы новый день (если появится) привязался к событию, а не встал отдельным.
3. Тест: перезалив поверх разделённого соревнования не меняет число строк по дням
   (1423 = 737 + 686) и не трогает ручные пометки.

### М4. Остальные: кто ещё схлопнут

CLI-обзор `--collapsed-days` (только чтение, ходит в loglig с паузой): по всем discovery с
`LogligId`, у которых в базе один день, — сколько дат у сетки. Ожидание: мастерсы и часть
чемпионатов. Список — в этот план, решение по каждому — Влада. В Health как проверку не
кладём: реестр читает только БД, а здесь нужна сеть (тот же довод, что Р13).

## 4. Порядок и объём

М1 → М2 → прогон на #1645 (бэкап, dry-run, apply, `--check-data`, глазами /competitions) →
#64 → М3 → М4. Минимум для двух известных стартов — М1 + М2 (+ строка «не перезаливать» до
М3). Оценка: М1 — малый, М2 — средний (сервис + CLI + два вида тестов), М3 — малый-средний,
М4 — малый.

## 5. Риски

- **Клубный зачёт.** Официальная таблица у организатора одна на событие; у нас после деления —
  по дню и сумма события. Сверить, что сумма двух дней = прежним 2356 (эстафеты) и общему
  зачёту; прецедент — юношеская зима 2025, событие 26 (дни 1623–1627), там это работает.
- **Правило очков по дням** (`admin-pages/import.md`: правило ставится на день) — копируется
  в М2 п. 3; проверить карточку правил после деления.
- **Кэш.** Только через EF (интерцептор K4); сырой SQL в М2 не использовать.
- **`InvariantDataChecks`** сверяет `Results.CompetitionDate` с днём — после переноса обе
  даты обязаны совпасть (М2 п. 4 пишет обе).

## 6. Решения Влада — ПРИНЯТЫ 07.10.2026 по рекомендациям

- **Р-сп-1. Имена дней.** По прецеденту события 26: `Name` дня = имя события, `SubName` —
  исходное название. Рекомендую так же; `SubName` = «Day 1» / «Day 2» не нужен.
- **Р-сп-2. Где штамп OrgCompId.** Рекомендую оставить на существующем соревновании (у 6595
  это день 2, 04/01) + `CompetitionEvent.OrgCompId`. Переносить на день 1 — лишние правки
  FK и discovery без выгоды.
- **Р-сп-3. Неоднозначный ключ** (одна дисциплина в оба дня — отборы утром, финал завтра).
  У 6595 и 64 таких нет. Рекомендую: отказ целиком с отчётом, а не догадка по `Round`.
- **Р-сп-4. #64 тоже делим?** Рекомендую да, той же командой после #1645; у него 11 медиа на
  строках — едут вместе со строками (М2 п. 4).
