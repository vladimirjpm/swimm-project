## 0. Коротко

- **Сейчас** (после К4) запись сбрасывает метку своей таблицы: правка расписания группы 24
  роняет страницы ВСЕХ групп и обзоры ВСЕХ клубов (обзор клуба читает `HubGroups`).
- **Будет:** запись дополнительно сбрасывает метки строк (`row:HubGroups:24`), а страница одной

- **Плюс служебные колонки** (§2.6): правка, задевшая только колонку из короткого реестра

  которых эта колонка есть. Loglig-задания и проверка качества перестают ронять season-best и
  витрины «по всей стране».
- **Главный риск — недосброс**: страница решила, что читает «только свои строки», а прочла
  чужую. Страховка — одно узкое правило сужения (§2.3), тесты на каждое место сужения, журнал

- **Где выгода:** группы (частые правки владельцев), обзор и состав клуба, всё, что задевают
  loglig и проверка качества. **Где мала:** сужение страницы пловца — делаем только по замеру
  журнала на проде (§3.3).
- **Самая дешёвая выгода — вообще без строк** (К4б.0): страница группы тянет `Sys_AppUsers` ради

## 2. Схема

### 2.1 Метки

| Метка | Смысл | Кто сбрасывает | Кто от неё зависит |
|---|---|---|---|
| `table:T` (есть) | изменилась какая-то строка `T` | любая запись в `T`, кроме служебной (§2.6) | записи кэша, читавшие `T` целиком (списки, рейтинги, season-best) |
| `row:R:id` (с К4б.2 сбрасывает запись; зависеть начнут с К4б.3) | изменилась строка корня `R` с этим id **или её прямой потомок** | запись, которой id известен: своя строка корня, FK на корень | записи, сузившие чтение до этих id |
| `anyrow:T` (новая) | изменились строки `T`, но какие — неизвестно | массовая запись, каскад в базе, сжатие больших сохранений | записи, сузившие чтение `T` (вместе с `row:`) |
| `col:T.C` (новая, §2.6) | в `T` изменилась служебная колонка `C` | правка, задевшая только служебные колонки | записи, в SQL которых есть `"T"` и `"C"` |

Суженная запись кэша теряет `table:T` и получает `row:R:id` + `anyrow:T`. Отсюда весь выигрыш:
обычное сохранение чужой строки сбрасывает `table:T` и `row:R:{чужой id}` — суженную запись не
задевает ни то, ни другое.

**Корни сужения** — короткий реестр в одном месте (рядом с `CacheTags`): `HubGroups`, `Clubs`,
`Swimmers`, `Sys_UserMedia`, `Relays`. Метки строк рождаются только для корней: остальные (свой id
у `Results` никто не сужает) лишь раздували бы каждое сохранение. Сужение по корню вне реестра —
исключение, а не метка, которую никто никогда не сбросит.

### 2.2 Запись: перехватчик сохранения (`CacheInvalidationInterceptor`)

Для каждой изменённой строки таблицы `T`, кроме `table:T` (как сейчас):

1. `T` — корень → `row:T:{PK}`.
2. Каждый FK строки на корень `P` → `row:P:{значение}`. У изменённой строки — **и старое, и новое**
   значение (участник ушёл из группы 24 в 17 → обе; результат переписали на другого пловца →
   оба). У удалённой — старое. `null` пропускается.
3. **Временные значения пропускаются.** Ключ, который выдаст база (новая группа и её участники в
   одном сохранении), принадлежит строке, которой ещё нет, — от неё не может зависеть ни одна
   запись кэша. Поэтому всё считается в `SavingChanges`, как сейчас; перечитывать ключи после
   сохранения не нужно.
4. **Сжатие:** одно сохранение меняет больше N строк одной таблицы (N ≈ 500) → вместо их меток
   строк `anyrow:T`. Слияние клубов (≈1,5 тыс. результатов), пересчёт объединённых мест, перенос
   результатов — редкие админские операции; метки на тысячи строк им ни к чему, а в Redis каждая
   метка — `INCR`.
5. **Каскад в базе** (удаление с `Cascade`/`SetNull`): таблица потомка `C` уже даёт `table:C` (К4),
   теперь ещё `anyrow:C` — какие строки задел каскад и к каким корням они относятся, трекер не
   знает. Удалённая строка корня свою `row:` даёт сама (п. 1), и её прямых потомков, суженных по
   этому корню, это закрывает. `anyrow:C` нужен для потомков, суженных по ДРУГОМУ корню: удалили
   медиа — ушли его публикации, а страница группы сужена по группе.
6. **Явный сброс массовой записи** (`ExecuteUpdate`/`ExecuteDelete`, сырой SQL) — `table:T` +
   `anyrow:T` одним методом (`db.InvalidateTableCacheAsync<T>()`). Старый вызов
   `InvalidateCacheTagsAsync(db.TableTag<T>())` дал бы одну `table:T` и прошёл бы мимо суженных
   записей — это недосброс, поэтому старый вызов убрать. Мест три: стирание объединённых мест в
   пересчёте, перестановка избранного, чистка истории входов. (Сделано в К4б.2: старого метода
   больше нет.)
7. **Строка не из запроса — строки неизвестны** (найдено при К4б.2). Старое значение FK верно,
   только если строку загрузил запрос: тогда исходные значения трекера — из базы. Заглушка
   (`Remove(new HubGroupMember { Id = 100 })`), `Update(объект с формы)`, повторное подключение
   после `ChangeTracker.Clear()` несут исходные значения, которые дал код: у заглушки
   `HubGroupId = 0`, и `row:HubGroups:24` потерялась бы — недосброс. Поэтому контекст с рождения
   следит, какие строки подключены не запросом (событие `ChangeTracker.Tracked` с
   `FromQuery = false`, кроме добавления; `CacheInvalidationInterceptor.Watch` из конструктора
   `SwimmDbContext`), и изменённая или удалённая такая строка с FK на корень даёт `anyrow:T`
   вместо меток строк. Своя метка корня от этого не зависит: ключ у заглушки настоящий. В коде
   таких записей сейчас нет (проверено 14.09.2026: ни `Attach`, ни `Update`, ни заглушек) — это
   страховка на будущее, и она в безопасную сторону: контекст, который не следит, не верит
   никому.

Отметка «был онлайн» (`LastSeenAt`, массовый UPDATE) по-прежнему ничего не сбрасывает (§3.2
cache-tags-plan).

### 2.3 Чтение: сужение

Сужает репозиторий (Infrastructure — там и запросы, и модель); контроллеры меняются только там,
где надо передать id:

```csharp
// Запросы внутри блока читают из этих таблиц ТОЛЬКО строки группы groupId.
using (_read.CacheRows<HubGroup>(groupId, typeof(HubGroupMember), typeof(HubGroupMedia)))
{
    ...
}
```

Внутри блока перехватчик команд (`CacheDependencyInterceptor`) касается не `table:T`, а
`row:HubGroups:{id}` + `anyrow:T` — для перечисленных таблиц и самого корня; остальные таблицы в
том же SQL — как раньше, `table:X`. Вне сборки записи кэша блок ничего не делает (тот же метод
зовут и некэшированные пути).

**Правило — единственное, на чём держится корректность.** Таблицу в блоке можно перечислить,
только если КАЖДЫЙ запрос блока, который её читает, фильтрует её строки по FK на корень
(`m.HubGroupId == id`) или по id корня — и никакой другой экземпляр этой таблицы в том же SQL
чужие строки не читает. Почему этого хватает: раз фильтр содержит `FK = id`, любая строка, которая
была в выборке или может в неё войти, имеет это значение FK до записи или после — а перехватчик
сбрасывает оба (п. 2 §2.2). Приёмы:

- **JOIN не сужают — делят запрос.** Публикации группы вместе с медиа одним SQL — две таблицы разной
  природы. Сначала публикации по группе (сужено), потом медиа по списку id (корень
  `Sys_UserMedia`), потом подписи результатов (таблицей).
- **Id корня — ДО запроса.** Метка снимается в момент касания (как у таблиц, `CacheBuildScope`), а
  касание — до чтения. Поиск по slug внутри блока сузить нельзя: id ещё неизвестен. Страница группы
  уже знает id из проверки доступа (`HubGroupsController` ~116) — загрузка переходит на id.
- **Потомок — только прямой.** `row:HubGroups:24` сбрасывают строки с FK на группы. Внук без своего
  `HubGroupId` сужается по родителю, если тот в реестре корней, или не сужается вовсе.
- **Вложенная сборка сужение НЕ наследует.** Блок живёт в `AsyncLocal` и без явного сброса утёк бы
  во вложенную `GetOrCreateAsync`: общая запись (скажем, «все стили»), собранная внутри блока
  группы 24, легла бы в кэш с меткой группы 24 и потом врала бы всем. `BuildAsync` открывает
  сборку с чистым сужением. Метки вложенной записи наружу наследуются, как раньше, — `row:` тоже.
- **Потолок:** больше M id в одном блоке (M ≈ 200) — блок работает как таблица. Сотня меток у
  страницы группы нормальна; тысяча — уже не выгода, а нагрузка (особенно для Redis, §7).
- **Проверка по модели:** у каждой перечисленной таблицы должен быть FK на корень (или она сама
  корень), иначе исключение — в тестах всплывёт сразу.
- **Почему не `TagWith`:** пометить сам запрос строкой с id соблазнительно, но аргумент `TagWith` —
  константа для EF (`[NotParameterized]`): на каждый id свой скомпилированный запрос, кэш
  запросов EF забивается.

### 2.4 Почему не будет недосброса

Суженная запись страницы группы 24 зависит от `row:HubGroups:24` и `anyrow:` своих таблиц.

| Запись | Её метки | Страница 24 |
|---|---|---|
| правка группы 24 | `table:HubGroups`, `row:HubGroups:24` | падает ✓ |
| правка группы 17 | `table:HubGroups`, `row:HubGroups:17` | живёт ✓ |
| новый участник в 24 | `table:HubGroupMembers`, `row:HubGroups:24` (FK) | падает ✓ |
| участник переехал 24 → 17 | `row:HubGroups:24`, `row:HubGroups:17` | падает ✓ |
| новая группа | `table:HubGroups` (временный id пропущен) | живёт ✓ — от несуществующей строки никто не зависит |
| служебный `UpdatedAt` группы 17 | `col:HubGroups.UpdatedAt`, `row:HubGroups:17` | живёт ✓ |
| массовая запись в `HubGroupMembers` | `table:…`, `anyrow:HubGroupMembers` | падает ✓ |
| удаление пловца (каскад в участников) | `table:…`, `anyrow:HubGroupMembers` | падает ✓ |
| импорт, настройки, кнопка | `all` | падает ✓ |

Недосброс возможен ровно в одном случае — нарушено правило §2.3 (или, для колонок, SQL прочёл
колонку, не назвав её, — §2.6). Против этого — §4.

### 2.5 Выключатели (решено: да)

Две настройки на `/Admin/Settings`, каждая включается после приёмки своего этапа:

- **`cache.rowPrecision`** — выключено: блоки сужения ничего не делают, записи зависят от таблиц.
- **`cache.columnPrecision`** — выключено: служебная правка даёт `table:T`, как обычная.

Два, а не один: всплыл недосброс — выключаешь по одному и сразу видишь, чей он. Смена настроек уже
сбрасывает весь кэш, смеси старого и нового не будет. Это аварийный рычаг: выключить за секунду и
чинить спокойно, без отката релиза. Метки строк запись сбрасывает при любом положении — лишний
сброс никому не мешает.

### 2.6 Служебные колонки (решено: да, отдельным этапом К4б.6)

Узкое отступление от «по колонкам не дробим» (§3.3 cache-tags-plan): не колонки вообще, а
короткий **реестр колонок, которые часто пишут и мало кто читает**.

- **Реестр** — рядом с корнями, свойства сущностей, имена колонок берутся из модели. Стартовый
  список: `Swimmers.LogligId`, `LogligIdStatus`, `LogligIdSource`, `LogligIdSuggestedByUserId`,
  `LogligIdSuggestedAt`, `LogligIdVerifiedAt`; `Competitions.QualityScannedAt`;
  `Results.CombinedPlace`, `IsBestResult`, `BestTimeMs`; `HubGroups.UpdatedAt`;
  `Sys_AppUsers.UpdatedAt`. Окончательный — по журналу К4б.1: в реестр идёт колонка, чья запись
  часто выкидывает записи, которые её не читают. Свойство вне модели — исключение.
- **Запись.** Изменённая строка, у которой ВСЕ изменённые свойства из реестра, даёт `col:T.C` на
  каждую изменённую колонку и метки строк по §2.2, но **не** `table:T`. Всё прочее — как обычно:
  есть хоть одна не-служебная колонка, добавление, удаление, `Update()` (помечает изменёнными все
  свойства). Массовая запись только служебных колонок — явным методом с перечнем колонок →
  `col:` + `anyrow:T` (стирание объединённых мест в пересчёте — как раз такое).
- **Чтение.** Перехватчик команд касается `col:T.C`, если в тексте SQL есть и таблица `"T"`, и
  колонка `"C"` — так же, как метки таблиц в К3. Совпадение не по делу (такая же колонка у другой
  таблицы запроса) даёт лишний сброс, а не ошибку. Внутри блока сужения суженным таблицам `col:`
  не нужен: их закрывают `row:`/`anyrow:`.
- **Почему безопасно.** EF всегда перечисляет колонки по именам — в SELECT, WHERE и ORDER BY.
  Если запрос колонку не назвал, он её не читал, и правка одной этой колонки его ответ не меняет.
  Представлений и чтения сырым SQL в модели нет (проверено 14.09.2026). На будущее перехватчик
  считает `SELECT *` и `"x".*` чтением всех служебных колонок упомянутых таблиц.
- ⚠ **Выгода только у проекций.** Сущность, загруженная целиком (материализация без `Select`,
  `Include`), называет в SQL все свои колонки и получит `col:` — это правильно (она их прочла), но
  падать будет по-прежнему.
- **Что даёт.** Loglig-подсказка, суточные loglig-задания и прогон проверки качества перестают
  ронять season-best, ровесников, обзоры клубов и страницы групп: эти записи служебных колонок не
  читают. Пересчёт объединённых мест роняет только тех, кто показывает места. Вход через Google
  не роняет ничего, если меняется только `UpdatedAt`.

### 3.2 Клуб

Четыре записи (`ClubsPublicController`): обзор, состав, season-best, стена рекордов. Id клуба
известен до сборки (`ResolveClubIdAsync` снаружи, склеенный клуб резолвится в канонический).

- **Обзор** — сужаем ровно одно место: официальная группа клуба (`ClubOverviewRepository`
  ~116-119, `HubGroups WHERE ClubId = rid AND IsOfficial`) — блок `Club`(rid) по `HubGroups`. Это
  единственная таблица клуба с частыми записями: сейчас любая правка любой группы роняет обзоры
  всех клубов; будет — только своего клуба, а у большинства пользовательских групп `ClubId` пуст,
  то есть ничьего. Остальное в обзоре — таблицей: рейтинг по всем клубам соревнования (O9),
  season-best по всей стране (O8), стена рекордов по именам (O7); сужать нечего, пишут импорт и
  админ (а шум loglig и проверки качества снимают служебные колонки, §2.6).
- **Состав** — сужается целиком: `Swimmers WHERE ClubId` и `Results WHERE ClubId AND SwimmerId IN
  (…)` — блок `Club`(rid) по `Swimmers`, `Results`. Правка пловца клуба X роняет состав только X;
  переход пловца в другой клуб — старый и новый `ClubId` (п. 2).
- **Season-best клуба** — не сужается: лидер ступени выбирается по всей стране, фильтр по клубу
  идёт в памяти уже после (`ClubPublicRepository` ~328).
- **Стена рекордов** — `Clubs` сузился бы (строка клуба и склеенные дубли: `MergedIntoId` — тоже FK
  на `Clubs`, п. 2 поймает склейку), но `Records` и `Sys_RecordIssues` читаются целиком, а
  `Clubs` пишет только админ. Выгоды нет, не трогаем.

### 3.3 Пловец — по замеру (решено)

Выгода мала: в таблицы, из которых собраны записи пловца, пишут импорт (сбрасывает всё), админ и
фон, а самый частый шум — loglig — снимут служебные колонки (§2.6). **Решение: сужение пловца
делаем, только если журнал сбросов на ПРОДЕ покажет, что записи `http:swimmer:*` часто
выкидывает что-то, кроме импорта и общего сброса.** Локальная база для такого замера не годится —
на ней нет живого трафика; смотреть после деплоя (docs/plans/azure-deploy-plan.md).

Что сузилось бы (разбор на 14.09.2026, чтобы не повторять):

- `swimmer-swims:{id}` — личные `Results` и `RelayMembers WHERE SwimmerId` (корень `Swimmers`) и
  ⚠ эстафетные `Results WHERE RelayId IN (…)`: это строки первого этапа, обычно чужие, по
  `SwimmerId` их сужать НЕЛЬЗЯ. Корень `Relays` по списку эстафет пловца (п. 2 даёт
  `row:Relays:{RelayId}` из `Results`, `RelayMembers` и `Relays`).
- `swimmer-profile:{id}` — строка пловца (клуб и страну — таблицей).
- `athlete-career-id:{id}`; предстоящие старты (`CompetitionEntries WHERE SwimmerId IN`).
- HTTP-записи профиля, summary, best-times, progress собраны из них, плюс `Competitions`,
  `Styles`, категории и рекорды — таблицей.

Не сужаются: personal-bests, season-ranks, compare. Они вкладывают записи клуба (`club-best-ms`)
и ровесников (`age-cohort-season-bests`), которые читают `Results` и `Swimmers` целиком.

Попутно, независимо от замера: в compare профиль соперника читается ДО сборки
(`SwimmersPublicController` ~298), его метки в запись не попадают — перенести внутрь фабрики
(в К4б.0).

## 4. Чем страхуемся от недосброса

1. **Тесты записи** (InMemory с настоящей моделью `SwimmDbContext`: перехватчику сохранения SQL не
   нужен): своя и чужая строка, FK старое+новое, `null`, временный id, каскад → `anyrow`, сжатие,
   только корни из реестра, массовый метод даёт `anyrow`, строка не из запроса (заглушка,
   `Update`, повторное подключение) → `anyrow`, а `Update()` строки из запроса — точно (§2.2 п. 7);
   служебная правка → `col:` без `table:`, смешанная → как обычно. Сделано для строк в К4б.2
   (`CacheRowTagsTests`); временные id выдаёт только реляционный провайдер — их тест идёт на
   Npgsql без соединения (`CacheInvalidationInterceptor.PreviewTags`).
2. **Тесты чтения** (живой Postgres, только чтение — как `CacheDependencyInterceptorPgTests`):
   настоящая страница группы/клуба собирается в кэш, проверяем метки: есть `row:HubGroups:{id}`,
   нет `table:HubGroups`, нет `table:Sys_AppUsers`; вложенная сборка внутри блока не получает
   `row:`; проекция без колонки не получает `col:`, с колонкой — получает.
3. **Сценарные тесты** стыкуют 1 и 2: метки InMemory-сохранения сбрасываем в кэше, где лежат
   настоящие страницы из PG. «Правка группы B не роняет A», «правка A роняет A», «новый участник
   A», «публикация в A», «медиа добавлено без публикации — A живёт», «группу одобрили официальной
   для клуба, на который подписана A, — A падает», «массовая запись — падает», «loglig-правка
   пловца — season-best живёт». Живую базу тесты не пишут.
4. **Страж мест сужения** (как `NoManualSetAsync`): IL-скан вызовов `CacheRows<…>`, каждое место
   обязано стоять в списке сценарного теста. Новое сужение без сценария роняет тесты.
5. **Журнал сбросов** на `/Admin/Cache` (К4б.1): последние ~200 сбросов — время, источник (какие
   таблицы и колонки поменяло сохранение), метки, сколько и какие записи выкинуты. Им меряем
   «до/после», выбираем служебные колонки и принимаем вживую.
6. **Сверка на попадании — обязательна в Development (решено).** Попали в запись с метками
   `row:` или `col:` — с вероятностью p (настройка, в Development по умолчанию ощутимая, на проде
   выключена) ответ строится заново **целиком мимо кэша**, включая вложенные записи, в
   изолированной сборке, и JSON сравнивается (у `CachedJson` достаточно ETag). Не совпало —
   строка «подозрение на недосброс» в журнале (ключ, метки, первое расхождение) и сброс записи.
   Ловит то, чего не предусмотрели тесты, при обычном прокликивании на :5079. Сверяем только
   записи с `row:`/`col:` — табличные доказаны К4, а шум «от времени» (относительные даты) в
   остальных нам не нужен.
7. **Выключатели** (§2.5).

## 6. Чего план не лечит

- **Удаление медиа** роняет страницы всех групп: каскад в публикации (§2.2-5). Удаляют реже, чем
  добавляют; если журнал покажет иное — `UserMediaRepository.RemoveAsync` предзагружает
  публикации и сбрасывает метки их групп явно.
- **Не-служебные правки общих таблиц** (`Swimmers`, `Clubs`, `Results` админом, новая страна от
  владельца группы) роняют всех табличных читателей, как сейчас. Это редкие записи.
- **Команды `dotnet run -- --флаг`** — отдельный процесс со своим кэшем, до веб-сервера их сброс не
  доходит (как и сейчас). Лечит Redis (К6).
- **Кэш браузера**: у страниц пловца `max-age=60` — правку увидят через минуту, как бы точно ни
  сбросился сервер.

## 7. Redis (К6) и память — что добавить

- У записи может быть сотня меток строк → чтение сверяет их версии одним `MGET`; потолок M (§2.3)
  держит его коротким. Меток `col:` — единицы (реестр).
- Меток строк много, ключам их версий нужен TTL. ⚠ Версия не должна начинаться заново: протух
  ключ, создался снова с «1» — и старая запись с версией «1» совпала бы. Версия — уникальное
  значение (не счётчик с нуля), либо TTL ключа версии заведомо больше самого долгого TTL записи
  (сутки).
- Память сейчас: словарь `_tags` в `MemoryCacheService` копит источники меток строк до общего
  сброса. Подметание: при превышении порога ОТМЕНИТЬ и выбросить источники, на которые не ссылается
  ни одна живая запись. Отмена безопасна (лишний сброс сборки в полёте); выброс без отмены — нет:
  сборка с этим токеном потом не узнала бы о сбросе.
- Сверка на попадании (§4-6) и журнал (§4-5) — диагностика одного экземпляра; с Redis остаются
  такими же, у каждого экземпляра свои.

### С чего начать К4б.3 — сужение при чтении (§2.3)

- **Ветка:** если цепочка #28 → #29 → PR К4б.2 уже в master — от `master`; иначе от

- **Что меняется** (приёмка — §5; сама страница группы переходит на блоки только в К4б.4):
  - `CacheBuildScope` получает сужение: корень (таблица), список id, суженные таблицы. Метод

  - `MemoryCacheService.BuildAsync` (~137, `CacheBuildScope.Begin`): вложенная сборка открывается с

### Грабли этой сессии

- **Репозиторий ПУБЛИЧНЫЙ.** Уязвимости в доках, коммитах и описаниях PR не расписывать — только
  нейтрально («ленты зрителя получили свою проекцию»). Коммит плана из-за этого переписывали.
- **PG-тесты молча пропускаются**, если базы нет (`if (db == null) return;`). Новое ключевое
  утверждение проверять мутацией: перевернуть → убедиться, что падает → вернуть.
- **Помощник `api()` на админ-страницах**: для PUT/POST с JSON нужен
  `headers: { 'Content-Type': 'application/json' }`, иначе 415. Пустой ответ 200 он принимает за
  ошибку JSON («Unexpected end of JSON input») — запрос при этом прошёл.
- **Правка данных для приёмки** — только обратимая и на тестовой группе 24: снимок до
  (`docker exec swimm-postgres psql … -At -c 'SELECT "TrainingSchedule"::text …'`), после — сверка
  `= '<снимок>'::jsonb`. Запись через :5079 не сбрасывает кэш API Влада на :5078 (другой процесс).
  Правка группы 24 для приёмки: `PUT /api/me/hub-groups/24/training-schedule` (тело —
  `{ place, slots: [{ day, start, end }] }`) через `api()` со страницы `/Admin/Cache`; возврат тем
  же запросом с прежним телом даёт пустой сброс (записи уже выкинуты первой правкой).
- **psql из PowerShell:** кавычки идентификаторов (`"HubGroups"`) PowerShell съедает по дороге в
  `docker exec` — SQL с такими именами гонять через Bash.
- **Трекер EF:** `ChangeTracker.Clear()` событий не шлёт; InMemory выдаёт постоянные id уже при
  `Add` (временных у него нет) — тесты временных ключей только на Npgsql.
