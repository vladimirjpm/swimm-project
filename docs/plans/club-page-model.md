# Страница клуба — модель данных

Сведение дизайн-макета (`!design_handoff/design_handoff_club_page/`, вариант «1b Deep») с тем,
что реально есть в БД. Парные документы: бриф [design-handoff-club-page.md](../design-handoff-club-page.md)
(что есть сейчас), план фазы [entity-pages-plan.md](entity-pages-plan.md) (этапы 10.4–10.7).

Дата: 2026-08-01. Ветка: `feature/point-rules-schema`.

---

## 0. Главный вывод

Макет держится на понятии **зачёт** — `сезон × зачётная группа × ❄winter/☀summer`, внутри
которого клубы стоят по местам. Сегодня клубный ранг существует только **внутри одного
соревнования** (`/api/club-summary`, `CompetitionOverviewDto.top_clubs`), места за сезон нигде
не считаются.

**Решение Влада (2026-08-01): зачёт = ОДНО соревнование** (для многодневного — одно событие).
Зимний чемпионат группы «Kids 2025/26» — это конкретный старт, места на нём и есть места за зиму.
Накопительных зачётов из нескольких стартов **нет**.

Это снимает половину сложности: новой сущности «зачёт» не нужно, нужна **разметка соревнования**
(«этот старт — зимний чемпионат группы X») плюс материализованные места клубов. Отсюда же
следует, что футер макета «**N competitions left**» **данных под собой не имеет** — остаётся
только `final` / `in progress` (см. §2.5).

Всё остальное на странице — либо уже есть, либо считается поверх `ResultRecord`.

## 2. Ядро: зачёт = размеченное соревнование

Зачёт — не сущность, а **роль соревнования**: «этот старт — зимний чемпионат группы Kids
сезона 2025/26». Нужны две вещи: разметка (§2.1) и материализованные места клубов (§2.3).

### 2.1 Разметка соревнования: выводится автоматически

**Правило (Влад, 2026-08-01):** у возрастной группы за сезон два чемпионата — **зимний в
бассейне 25м** и **летний в 50м**. Двух зимних быть не может; чемпионат может быть **отменён**
(тогда клетка грида пустая — это нормальное состояние, а не ошибка).

Значит `StandingKind` не надо вводить руками — он **производен от того, что уже в БД**:

```
Competition.IsChampionship = true
  + PoolType = '25m' → winter (❄)
  + PoolType = '50m' → summer (☀)
```

**Проверено на данных 2026-08-01:** 23 соревнования с `IsChampionship`; все 12 в 25м —
январь/февраль, все 11 в 50м — июль/август. Исключений ноль. Правило работает как есть,
бэкфилл не нужен вообще.

Поле в `Competition` всё же заводим — но **только как ручное переопределение** для будущих
исключений (в первую очередь open water, где бассейна нет):

```csharp
/// <summary>Ручное переопределение роли соревнования в клубном зачёте:
/// winter | summer | openwater | none (явно исключить из зачёта).
/// null — обычный случай: роль выводится из IsChampionship + PoolType (25m→winter, 50m→summer).</summary>
[MaxLength(20)] public string? StandingKindOverride { get; set; }
```

Остальное **уже есть у соревнования**:

| Что | Откуда |
|---|---|
| Сезон | `Competition.Date` → сезонный шов 10.1 (1 сен – 31 авг) |
| Зачётная группа | `CategoryCompetition` → `Category` (лестница K/Y/N/B/M — §3) |
| Правило очков | `Competition.PointRuleClubsId` — уже есть |
| Многодневность | `Competition.EventId` + `DayNumber` — уже есть |

**Единственность и пропуски.** Дубль (два зимних чемпионата одной группы за сезон) в реальности
невозможен, поэтому городить защиту не нужно — хватит **чека в дашборде здоровья данных**
(`IDataQualityService`): если дубль всё же появился, значит у соревнования неверно стоит
`IsChampionship` или `PoolType`, и чинить надо там, а не в зачёте.
**Пропуск же — штатный случай** (чемпионат отменили): клетка грида показывает пустое
состояние, а не «#—» и не дырку в вёрстке.

**Многодневное событие.** Зачётная единица — **событие целиком**: если `EventId != null`,
очки и медали суммируются по всем дням, ранг считается один раз.
*Проверено на данных:* все чемпионаты 2025–2026 сгруппированы событиями корректно
(напр. Kids зима 2026 = event 1, дни 57/58/59), одиночным остался только Masters —
у него один день, и это верно.

**Соревнование в нескольких категориях.** `CategoryCompetition` — M:N; в базе таких три:
Хадера-2026 и Лига-3 (Kids **+** Young), Маккабиада-мастерс (Masters **+** `result-maccabiah`).
Первые два дают **два зачёта с одного старта** — по отдельной таблице клубов на каждую
возрастную группу. Это правильно, менять нечего.

⚠ **Но зачёт порождают только категории возрастной лестницы** (`results-kids-team`,
`results-youth-team`, `results-junior-results`, `results-main`, `results-masters`).
Кастомные (`result-maccabiah` и будущие) — это «соревнование само по себе», клубного
зачёта по ним нет, в грид они не попадают.

### 2.2 Что стало ненужным

Сущности `Standing` / `StandingCompetition` из первой редакции **выброшены** — они
существовали только ради накопительных зачётов (вариант Б), которого нет.
Вместе с ними уходит и админка `/Admin/Standings`: разметка — это одна галочка + выпадашка
`❄/☀/🌊` на существующей `/Admin/Competitions/Edit`.

### 2.3 `ClubCompetitionStanding` — материализованные места клубов

Кэш-таблица результата расчёта, не первичные данные. Пересчитывается на существующем шве
`ICompetitionRecalculationService` (импорт, пересчёт очков, смена правила, merge клубов).

```csharp
public class ClubCompetitionStanding
{
    long Id;
    int  CompetitionId;     // зачётная единица: день события НЕ дублируется — строка на событие
    int  ClubId;
    int  Rank;              // 1..N внутри этого старта
    int  Points;            // сумма club_points по правилу соревнования
    int  Gold, Silver, Bronze;
    int  SwimmerCount;      // стартовало
    int  SuccessfulCount;   // доплыло (не DSQ/DNS) — footgun брифа
    int  SwimCount;
    DateTime ComputedAt;
}
```
- Уникальность `(CompetitionId, ClubId)`; индексы `(CompetitionId, Rank)` и `(ClubId)`.
- Для многодневного события `CompetitionId` = **день №1** события (одна строка на событие,
  не на день) — иначе ранг задвоится в timeline и в KPI.
- Таблица полезна **шире страницы клуба**: из неё же дешевеет карточка Top clubs в Overview
  соревнования, которая сейчас считает то же самое на лету по именам.

**Почему материализуем.** При 20+ сезонах карточка Season × Group grid при `Season=All`
поднимает `gridSeasons` × ~7 групп полных таблиц клубов за один запрос страницы. Считать это
по `ResultRecord` в рантайме — заведомо мимо бюджета p95; уроки перф-фаз однозначны
(агрегаты через JOIN по именам — самая дорогая вещь в проекте). Объём мал:
`20 сезонов × 7 групп × 2 × 128 клубов ≈ 36 тыс. строк` плюс обычные старты.

### 2.4 Как карточки читают это

- **3 (grid):** `ClubCompetitionStanding` по `ClubId` → `JOIN Competition WHERE StandingKind IS NOT NULL`,
  группировка по (сезон, kind, категория). Одним запросом.
- **4 (standings):** строки по `CompetitionId` выбранной клетки + окно «1, 2, наш±1».
- **8 (timeline):** те же строки **без** фильтра по `StandingKind`; бейдж `❄/☀ · группа`
  рисуется только там, где `StandingKind` есть.
- **1 (KPI best rank):** `MIN(Rank)` по клубу в scope.

### 2.5 Футер Standings: «N competitions left» убрать

Дизайнер нарисовал его под накопительный зачёт (вариант Б). При «зачёт = один старт»
осталось только два состояния, и оба выводятся из данных без ручного ввода:
- **`final`** — результаты соревнования импортированы;
- **`upcoming`** — соревнование в календаре (`DiscoveredCompetition`), протокола ещё нет.

Так футер и подписываем; счётчик «осталось N стартов» из макета удаляем.

### 2.5 Что даёт эта сущность карточкам

- **3 (grid):** `SELECT Season, Kind, CategoryId, Rank FROM StandingClub JOIN Standing WHERE ClubId=@id` — вся карточка одним запросом.
- **4 (standings):** строки зачёта по `StandingId` + окно «1, 2, наш±1».
  Футер: `PlannedCompetitions - COUNT(StandingCompetition)` → «N competitions left»; `Status='final'` → «final».
- **8 (timeline):** бейдж соревнования = его `Standing` через `StandingCompetition`.
- **1 (KPI best rank):** `MIN(Rank)` по клубу в scope.

## 3. Зачётные группы: маппинг макета на `Category`

Макет: `K 8–11 · Y 11–14 · N נוער · B בוגרים · M Masters · OW3 · OW5`.
Первые пять — **это уже существующая возрастная лестница** (буквы дизайнер взял ивритские,
`N`=נוער, `B`=בוגרים; в БД бейджи латинские `J`/`A`):

| Макет | `Category.Key` | `Badge` в БД | `NameHe` |
|---|---|---|---|
| K 8–11 | `results-kids-team` | K | ילדים |
| Y 11–14 | `results-youth-team` | Y | צעירים |
| N | `results-junior-results` | J | נוער |
| B | `results-main` | A | בוגרים |
| M | `results-masters` | M | מסטרס |

Новой сущности «группа» **не нужно** — `Standing.CategoryId` смотрит на `Category`.
Буква берётся из `Category.Badge`, название — из `Name`, порядок — из `DisplayOrder`
(тот же принцип, что уже применён в плашке соревнования). ⚠ Ключи ротировались 2026-07-31 —
маппинг делать по `Key`, а не по «смыслу названия» (см. `category-ladder-rotation`).

**OW3 / OW5 (open water) данных не имеют вообще:** ни соревнований, ни дистанций, ни признака.
`ResultRecord.Distance` — строка, так что «3km»/«5km» технически влезут, но бассейн
(`Competition.PoolType`) и рекорды на них не определены. Это отдельная работа, не часть страницы
клуба. Модель к ней готова (`Standing.Kind='openwater'` + две категории `ow-3km`/`ow-5km`), но
**наполнять нечем** — вопрос 1 в §6.

## 4. Достройки вне зачёта

### 4.1 Идентичность клуба (блокеры 10.4 / 10.5)

Без изменений относительно плана, повторяю для полноты, потому что это гейт всей страницы:
- `/clubs/{id}` + три зеркала контракта (`routes.ts`, `vite.config.js`, `Program.cs`) + html-точка входа;
- `club_id` в `ResultDto` (агрегаты сейчас клеятся по имени — а имя не уникально);
- **пережить merge:** новое поле `Club.MergedIntoId` (int?, self-FK). Merge не удаляет строку, а
  проставляет ссылку; `/clubs/{старый id}` отдаёт 301 на актуальный. Без этого внешние ссылки
  гниют после каждой чистки дублей (231 → 128).
- **псевдоклуб** (`IsPseudo`) — страницы нет: 404, а не бедный профиль.

### 4.2 Логотип и фото

Сейчас логотип — файл по **имени** клуба; переименование в админке ломает картинку.
Для страницы этого мало (в Hero логотип 96px — заметно). Минимальная правка:

```csharp
// Club
string? LogoUrl;    // явный путь/URL; null → текущий фолбэк «файл по имени» → инициалы
string? PhotoUrl;   // фото 4:3 в Hero; null → блок не рендерится
```
Инициалы остаются штатным видом — это норма, а не пустое состояние.

### 4.3 Тренеры (карточка 7)

Данных нет ни в каком виде. Если карточка нужна — минимальная сущность:

```csharp
public class ClubCoach
{
    int Id; int ClubId;
    string Name; string? NameEn;
    string? Role;        // head | agegroup | masters  (цвета макета завязаны на роль)
    string? PhotoUrl;
    int? SwimmerId;      // если тренер сам есть в справочнике пловцов
    string? Groups;      // какие группы ведёт; CSV категорий или отдельная M:N
    int DisplayOrder;
}
```
Плюс CRUD на `/Admin/Clubs`. Это **ручной справочник** — автоматически заполнить неоткуда,
никакой протокол тренеров не содержит. Оценка: полдня работы + бессрочная ручная поддержка
на 128 клубов. Вопрос 2 в §6.

### 4.4 Ростер, рекорды, top swimmers — без новых сущностей

- Ростер: `Swimmer.ClubId` есть, нужен только API + пагинация. Возрастные пилюли макета
  (`8–11 / 12–14 / 15–16 / 17+`) — считаются из `BirthYear` на дату сезона, **это не `Category`**
  (не путать: у зачётных групп границы свои и они не совпадают).
- Record wall: ось `стиль × дистанция × бассейн × пол` уже реализована для hub-групп (8.3) —
  переиспользовать. Исключать `TimeFail` и `SuspectReason`, эстафеты — отдельно или никак.
  **Переделано 2026-08-01, см. §4.6.**
- Top swimmers: очки пловца считает `PointRuleSwimmers`; ⚠ правил пловцов в БД пока нет —
  High Point вживую считает legacy-путь. Для страницы это значит: очки пловца берём тем же
  способом, что и карточка High Point соревнования, и не изобретаем второй.

### 4.6 Карточки времён: Season best и Record wall (переделано 2026-08-01)

Изначально это была ОДНА карточка «лучшее время клуба по дисциплине». Оказалась
бесполезной: плитку забирал самый быстрый пловец клуба любого возраста — на 50 брасс 25м
у девочек это 23-летняя мастерша (37.26), а лучшая из детей (9 лет, 48.52) не показывалась
вовсе. Разошлись на две карточки с общей формой (`club-record-card.tsx`), но разными данными.

**Season best** — `GET /api/clubs/{id}/season-best?pool=&season=`.
Заплывы пловцов клуба, которые в сезоне **первые ПО СТРАНЕ** в своём слоте
(`стиль × дистанция × бассейн × пол × возрастная ступень`). Лидер считается по ВСЕЙ базе,
и только потом остаются слоты, где первый — наш пловец. Карточка отвечает «наши первые в
Израиле», а не «наше лучшее».

- Ровно ОДИН сезон; глобальный фильтр сезона страницы карточка не слушает и «за всё время»
  не умеет — вне сезона возрастная ступень теряет смысл (решение Влада).
- Ступени как в таблицах федерации: до 18 каждый год отдельно, `adults` 19–24, мастерс
  пятилетками (25-29, 30-34…), `n/a` — год рождения не заполнен (в конец, не выбрасывать).
- ⚠ «Первый в Израиле» = первый **среди импортированного**. Ответ несёт `meets` (сколько
  стартов вошло в расчёт), и UI ОБЯЗАН это показывать: юниорских и взрослых чемпионатов в
  базе может не быть вовсе. На клубе 438 в сезоне 2025/26 — 21 старт, 28 плиток.
- Исключаются эстафеты, `TimeFail`, `SuspectReason` — иначе битый протокол сделал бы клуб
  «первым в стране».

**Record wall** — `GET /api/clubs/{id}/record-wall?pool=`.
Официальные рекорды из таблицы `Records` (нац./возрастные/мастерс/мировые), числящиеся за
клубом. ⚠ У `Record` нет ни `SwimmerId`, ни `ClubId` — только текстовые `HolderName` и
`Club`, поэтому связь с клубом идёт **по названию**: точное совпадение либо «название +
суффикс источника» (в справочнике дописывают площадку: `… אולימפית`, `… לאומית`), плюс
имена склеенных дублей. Префикс, а не подстрока: иначе нетанийский Дольфин утащил бы
нахарийский. Сезона у карточки нет — рекорд живёт, пока его не побили; ссылки на пловца
нет — не по чему.

### 4.7 ⚠ Возраст в сезоне — правило, которое легко сломать

Возраст пловца в сезоне = **сколько ему исполняется в году ОКОНЧАНИЯ сезона**, и он один
на все старты сезона. Сезон 2025/26 считается по 2026 году: декабрьский старт 2025 у
пловца, которому в 2026 исполняется 9, — это «9 лет». Так считает федерация (`cYear`).

Единственный источник правила — `SeasonMath.AgeInSeason(startYear, birthYear)`; `null`,
если `BirthYear` не заполнен (в базе такие есть — иначе получалось «age 2026»).

Считать «год заплыва минус год рождения» **нельзя**: осенние и весенние старты одного
человека разъезжаются по двум ступеням, и один пловец занимает две плитки. Именно этот
баг был в первой версии Season best (исправлено 2026-08-01, правило Влада).

Правило применяется в трёх местах: ступени Season best, возраст и фильтры ростера
(`GetRosterAsync`), подпись «age N» в Top swimmers (`ClubOverviewRepository`).

### 4.5 Один эндпоинт вместо пяти

Дизайнер схлопнул всё в `GET /api/clubs/{id}/overview?season=&group=`. Это правильно для
первой отрисовки (один roundtrip, один ETag), но ростер и record wall — тяжёлые и пагинируемые.
Компромисс:

- `GET /api/clubs/{id}/overview?season=&group=` — Hero + фильтры + grid + standings + timeline
  + top swimmers + **первые N** ростера и рекордов (ровно столько, сколько видно до «Show all»);
- `GET /api/clubs/{id}/roster?…`, `GET /api/clubs/{id}/season-best?pool=`,
  `GET /api/clubs/{id}/record-wall?pool=` — догрузка по «Show all» и переключателю бассейна
  (эндпоинт `/records` переименован в `/season-best` 2026-08-01, см. §4.6)
  и по локальному переключателю 25m/50m.

Кэш + ETag как у остальных публичных эндпоинтов; инвалидация — на том же шве, что
пересчёт `StandingClub`.

## 5. Footguns, которые модель обязана держать

- **Ранги сравнимы, очки — нет.** Grid и timeline подписывают ранг; сумма очков законна только
  внутри одного зачёта (одно правило). В KPI Hero «POINTS» при `Season=All` — сумма по разным
  правилам: либо сноска, либо показывать не сумму, а `best rank`.
- **`SwimmerCount ≠ SuccessfulCount`** — «стартовало» и «доплыло», в `StandingClub` оба.
- **Многодневные соревнования:** зачёт цепляется к `Competition` (день), а timeline должен
  показывать событие целиком — группировать по `Competition.EventId`.
- **Эстафеты:** `RelayMultiplier` (×2 у бугрим) уже в `PointRuleClubs`; ключ клуба для
  эстафетной строки — `relay_team_name`. В `StandingClub.SwimmerCount` эстафету не считать дважды.
- **`EventCategory`** в клубном зачёте сознательно **не** учитывается — не «чинить».
- **RTL:** имена клубов на иврите, UI строго английский.
- **Пустые состояния — норма:** нет логотипа, нет фото, нет официальной группы, нет рекордов,
  клуб без пловцов, пустой сезон («no results in {season}»).

## 6. Решения (Влад, 2026-08-01)

1. **Open water (OW3 / OW5) — заводим пустыми.** `Standing.Kind='openwater'` + две категории
   `ow-3km` / `ow-5km` в лестнице `Category` существуют, данных нет → карточки честно показывают
   «no results». Импорт открытой воды — отдельная будущая задача, модель её уже ждёт.
2. **Тренеры — карточка остаётся, но пустой.** `ClubCoach` **пока не заводим**.
   ☐ **Продумать отдельно:** откуда брать тренеров (ручной справочник на 128 клубов? заявки
   от официальных hub-групп? только у клубов с официальной группой?), кто их поддерживает,
   и нужна ли роль тренера как пользователя системы, а не строка в справочнике.
   До этого карточка рендерится в пустом состоянии, места в вёрстке не теряет.
3. **Фото клуба 4:3 — пока пусто.** `Club.PhotoUrl` не заводим, медиа hub-группы не подтягиваем;
   блок в пустом состоянии. Вернуться, когда будет решение по медиа клуба.
4. **Зачёт = ОДНО соревнование** (для многодневного — одно событие). Накопительных зачётов
   нет. Отсюда: сущности `Standing`/`StandingCompetition` не нужны, админка `/Admin/Standings`
   не нужна, «N competitions left» из макета удаляем. Вся разметка — одна галочка
   `StandingKind` на `/Admin/Competitions/Edit`. См. §2.
5. **Глубина истории — 20+ сезонов и дальше растёт.** Значит:
   - свайп-ряд сезонов в фильтре — обязателен, не «на вырост»;
   - `Season=All` **никогда** не грузит все сезоны: грид отдаёт `gridSeasons` (default 3),
     остальное — по запросу. Иначе overview линейно распухает с каждым годом;
   - `StandingClub` растёт как `сезоны × группы × 2 × клубы` ≈ 20 × 7 × 2 × 128 ≈ 36 тыс. строк —
     мелочь, материализация оправдана тем более.
6. **`Club.MergedIntoId` — мягкое слияние, без 301.** `IClubMergeService` перестаёт удалять
   строку клуба: проставляет `MergedIntoId` и убирает клуб из всех публичных выборок
   (справочник, фильтры, зачёты). Страница `/clubs/{старый id}` просто **отдаёт актуальный
   клуб** (контент клуба-приёмника), без редиректа. Старые id перестают быть «дырой».
