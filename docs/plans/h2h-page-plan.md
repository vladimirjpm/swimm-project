# План — страница H2H: один компонент на таб и на страницу

Сравнение двух пловцов уже работает **табом** страницы пловца (`/swimmers/{id}?tab=h2h&rival={id}`,
макет `!design_handoff/design_handoff_h2h/`, устройство — [athlete-page-plan.md §12](athlete-page-plan.md)).
Этот план — про **отдельную страницу** `/h2h`, где выбираются ОБА пловца, и про то, чтобы
экран при этом остался **одним компонентом**, а не второй копией.

> **СТАТУС 02.09.2026: X1–X6 СДЕЛАНЫ, страница работает вживую.** Ветка `h2h-tab`,
> коммиты `be36e93` (X1) … `445f760` (X5). Тесты 1598/1598, `tsc` и сборка чистые.
> Открытые вопросы — §9: они не блокируют, но решить их стоит до того, как страницу
> кто-то найдёт (её пока нет в меню — только по прямой ссылке).

Решения Влада от 02.09.2026, с которых план начинается:

- адрес — **`/h2h?a=&b=`** (всё в query, как у `/season-best`): пустые слоты тоже адресуемы,
  а пара в пути потребовала бы второго формата адреса для «ещё никто не выбран»;
- слева по умолчанию — **«ME»** (primary favorite залогиненного), **но параметром**: чтобы
  переключить на «два пустых слота» правкой одного значения, а позже — настройкой;
- сезон выбирается **той же каруселью**, что на страницах пловца и клуба.

## 2. Шов: `UI_H2HCompare` — один экран, два вызова

Сборка переезжает в семейство как **`components/mix/h2h/h2h-compare.tsx`**. Компонент не
знает ни про табы, ни про роуты — только про две стороны и данные сравнения.

```tsx
/** Слот стороны: занят пловцом либо пуст. */
type H2HSlot =
  | { kind: 'swimmer'; swimmer: H2HSwimmer; stats?: H2HStats;
      isFavorite?: boolean | null; onToggleFavorite?: () => void;
      /** null — сторону нельзя сменить (таб: левый = хозяин страницы). */
      onClear?: (() => void) | null }
  | { kind: 'empty'; label?: string; onPick: () => void };

interface H2HCompareProps {
  left: H2HSlot;
  right: H2HSlot;
  /** null — сравнения нет: выбран не каждый, либо запрос ещё идёт. */
  compare: SwimmerCompare | null;
  state: { loading: boolean; error: boolean };
  /** Выбор пловца — свой у таба (соперник) и у страницы (любой из двух слотов). */
  picker?: React.ReactNode;
  /** Строку season bests прячем за карьеру: мест среди сверстников там нет. */
  showSeasonBests?: boolean;
}
```

Кто что передаёт:

| | Таб `?tab=h2h` | Страница `/h2h` |
|---|---|---|
| `left` | `swimmer` хозяина страницы, `onClear: null` | выбранный A либо `empty`; сменяем |
| `right` | соперник либо `empty` | выбранный B либо `empty` |
| `picker` | один список (ищем соперника) | тот же список, но пишет в **активный слот** |
| сезон | из карусели страницы пловца | из карусели самой страницы |

Панель таба после переезда — десяток строк: собрать слоты и отдать компоненту. Вся вёрстка,
включая шапку, статы, карточки заплывов и разделитель, живёт в одном месте.

⚠ **`useFavoritesContext` внутрь компонента не тащим.** Сердечко приходит пропсами
(`isFavorite` + `onToggleFavorite`), потому что страница и таб живут в разных провайдерах, а
компонент из `mix/` не должен требовать чужого контекста — правило семейства
`UI_SwimmerIdentity*`, там та же развилка уже решена так.

## 3. Адаптер ширины — container queries, а не медиазапросы

Сегодня `h2h.css` ужимается по **вьюпорту** (`@media (max-width: 900px)`). Для одного
компонента на двух экранах это неверно: в табе он живёт в панели (у которой свои поля и
сайдбар страницы), на `/h2h` — во всю ширину. Один и тот же вьюпорт даёт разную доступную
ширину, и компонент должен смотреть на СВОЙ контейнер.

```css
.h2h-scope { container-type: inline-size; container-name: h2h; }

@container h2h (max-width: 780px) { /* столбик, узкие колонки, дата скрыта */ }
```

- обёртка `.h2h-scope` — внутри самого компонента, чтобы вызывающий не мог забыть её поставить;
- **порог 780px подобран замерами, а не на глаз**: в панели таба контейнер равен 795px при
  окне 900px и 306px при окне 375px, то есть прежняя граница «окно ≤900» соответствовала
  контейнеру ~796. Взято 780 — полный макет на 795px ещё читается (проверено: имена не
  обрезаются, переполнения нет), а на 700 уже нет. Побочный эффект осознан: на окне 900px
  экран теперь показывает полный макет, а раньше ужимался;
- `@media` в файле не осталось вовсе — все правила были про доступную ширину.

Поддержка: Chrome 105+, Safari 16+, Firefox 110+ — совпадает с тем, что уже требует проект
(`color-mix`, `:has`). Фоллбека не делаем: без container queries компонент просто останется в
широком варианте, вёрстка не ломается.

**Явный параметр плотности не заводим.** Соблазн `density="compact|full"` есть, но тогда
вызывающий обязан угадать свою ширину — а он её не знает (панель таба на 1280px шире, чем
страница на 900px). Container queries снимают вопрос целиком; если позже понадобится
принудительный режим (например, печать), он добавится атрибутом `data-h2h-density` поверх.

## 4. Контракт адреса

```
/h2h                         оба слота пусты (либо «ME» слева — см. §5)
/h2h?a=6066                  выбран один
/h2h?a=6066&b=6069           сравнение
/h2h?a=6066&b=6069&season=2025|all
```

Три зеркала контракта правятся вместе (правило `client/CLAUDE.md`):

1. `client/src/utils/routes.ts` — генератор `routes.h2h({ a, b, season })` + разбор
   `parseH2HQuery()` рядом с ним (как `SeasonBestQuery`);
2. `cleanUrlRewrite` в `client/vite.config.js` — `h2h → /h2h.html` (dev);
3. rewrite-middleware в `server/Swimm.API/Program.cs` — та же строка (прод).

Плюс точка входа: `client/h2h.html` + `client/src/pages/h2h-page.tsx`, и `h2h` в
`rollupOptions.input`. Порядок параметров в адресе — `a`, `b`, `season`: пустые не пишем.

**Ссылка с таба на страницу сделана** (02.09.2026): в шапке панели таба справа — пилюля
«Full page →» на `routes.h2h({ a: хозяин, b: соперник, season })`. Пару и сезон уносим с
собой, иначе переход стоил бы повторного выбора: с `?tab=h2h&rival=6069` при сезоне 2025/26
она ведёт на `/h2h?a=6066&b=6069&season=2025`, без соперника — на `/h2h?a=6066&season=2025`,
в режиме ∞ — с `season=all`.

Обратно со страницы на таб не ведём: таб — часть профиля, а страница самостоятельна. Со
страницы есть только ссылка на профиль левого пловца.

## 5. «ME» слева — параметром

```ts
/**
 * Кем занят левый слот на пустой странице: 'me' — primary favorite залогиненного,
 * 'empty' — оба слота пусты. Значение живёт ОДНОЙ константой, чтобы переключение
 * стоило одну правку; когда появится экран настроек — переедет туда, тип не изменится.
 */
export type H2HDefaultLeft = 'me' | 'empty';
export const H2H_DEFAULT_LEFT: H2HDefaultLeft = 'me';
```

Правила:

- `a` в адресе всегда сильнее умолчания: пришли по ссылке — открылось ровно то, что в ней;
- у гостя и у залогиненного без «ME» умолчание молча вырождается в `empty` — заглушки
  «войдите, чтобы сравнивать» тут не место, страница работает всем;
- подстановка «ME» **не пишется в адрес** сразу: пока пользователь не выбрал второго, адрес
  остаётся `/h2h` — иначе ссылка «пустая страница» превращалась бы в чужую личную.

**Сделано в X4** вместе с выбором сторон. Попутно из таба убрана кнопка «Clear» в шапке
панели: сбросить соперника можно крестиком на его карточке — тем же жестом, что на
странице. Два одинаковых действия рядом заставляли бы выбирать между ними на ровном месте.

**ПЕРЕРЕШЕНО 03.09.2026 (Влад): умолчание — `empty`, автоподстановки «ME» НЕТ.** Пловец
появляется в слоте только по явному действию: клик по чипу избранного, поиск или `h2h_a` в
адресе. Причина не вкусовая — см. §8-нон: подстановка спорила с крестиком и делала левый
слот неочищаемым. Константа осталась (переключение стоит одну правку), но при `me`
подстановка теперь ОДНОРАЗОВАЯ (`autoLeftDoneRef`) — иначе баг вернётся вместе с режимом.

## 6. Сезон и карусель

- список сезонов = **объединение** `profile.seasons` обоих пловцов (у соперника бывают
  сезоны, которых нет у первого; пересечение прятало бы данные, которые есть у одного);
- умолчание — витринный сезон (`isDisplayDefault`) из профиля A, как на странице пловца;
  без A — витринный сезон из `useShowcaseSeason` (общий шов, `docs/season-boundary-rule.md`);
- `∞` (карьера) работает так же, как в табе: сравнение по карьерным лучшим, строка
  season bests скрыта;
- сезон пишется в адрес (`season=2025|all`), чтобы ссылка открывала то же самое.

## 8. Что решено заранее (не переоткрывать)

- **Компонент один, вызова два.** Причина не в экономии строк: цифры сравнения (счёт, статы,
  бейджи SB/REC) считаются на сервере, но раскладка «кто слева, кто справа, что победа» —
  на клиенте, и две копии этой раскладки разъедутся на первом же изменении правил.
- **Слот — данные, а не режим.** Компонент не знает слов «таб» и «страница»: он видит
  занятый слот или пустой. Поэтому «левый нельзя менять» выражается через `onClear: null`, а
  не через `variant="tab"`.
- **Ширина решается контейнером, а не пропом** (§3).
- **Сравнение по-прежнему только парное.** Троих и больше не планируем: макет, счёт «3–2»,
  сетка `1fr · центр · 1fr` и правило «cyan = быстрее» держатся на паре.

## 8-тер. Бейджи SB и REC — починка 02.09.2026

Поймано Владом на паре 7424 × 62098 («у этих двоих должен быть и SB, и рекорды»).

**REC не работал у взрослых ВООБЩЕ** — и в H2H, и в личниках страницы пловца. Запрос шёл в
`Category='age'` с ключом-числом, а рекорды взрослых лежат иначе: `masters/{полоса}` и
`open`; `age/{число}` есть только у детей 10–18, а `age/adults` — это эстафеты.

Теперь ступень выбирается **по заплыву**, теми же правилами, что у детектора рекордов
соревнования (`CompetitionRecordsDetector.CandidateKeys`): открытый рекорд страны плюс
`masters/{полоса}` для мастерского старта либо `age/{возраст}` для обычного. Возраст — по оси
`RecordAgeAxis` из настроек, как у детектора: разъедутся правила — бейдж начнёт спорить с
карточкой «New records». Репозиторий получил общий `GetNationalRecordsAsync(регион, пол,
категория, ключ)`, старый метод стал его частным случаем.

⚠ Бейджа может не быть у настоящего рекордсмена, и это НЕ баг: метим по времени, а
рекордный заплыв может быть вне базы. Живой пример — 62098: держит открытый рекорд 21.08,
но лучший его полтинник в наших данных 21.22 (рекорд поставлен до периода импорта).

**Личники (`/personal-bests`) починены тем же швом** (02.09.2026): ступень выбирается по
заплыву, приоритет у возрастной, открытый рекорд — фоллбек. Ответ несёт `nationalRecordScope`
(«age 14», «masters 45-49», «open»), и подпись строки говорит, чем мерили, — «national age
record» у взрослого было бы неправдой. Проверено: 7424 → «masters 45-49» (дельта 0, её же
рекорды), 62098 → «open» (+0.14), 7796 → «age 12», 6066 → дельты нет.

Две ловушки, найденные при этом:

1. **Открытый рекорд — эталон ВЗРОСЛОГО.** Девятилетней он давал «Δ Israel +19.18» до
   взрослого рекорда: детская лестница справочника начинается с 10, и ниже сравнивать не с
   чем. Отсечка — `IsAdultSwim` (мастерский старт либо возраст выше 18).
2. **В `Countries` ДВА Израиля**: «ISR» (id 10, «Israel») и «IL» (id 111), на второй смотрит
   **791 пловец**. Рекорды лежат под «ISR», поэтому этим 791 они не находились вовсе — ни в
   личниках, ни в H2H. В репозитории добавлена защита (`NormalizeRegion`: «IL» → «ISR»), но
   это дыра ДАННЫХ: страны нужно склеить, иначе она всплывёт в любом новом месте, где
   код страны участвует в поиске.
   **ЗАКРЫТО 03.09.2026** (docs/data-integrity.md §14, «Вход закрыт»): дубль был склеен ещё
   02.09, а теперь закрыт и вход — `CountryCodes.Normalize` во всех трёх find-or-create
   (импорт, соревнование, группа), идемпотентная миграция `MergeDuplicateCountryCodes` для
   остальных копий базы и проверка реестра `countries.duplicate`. Разовая чистка тут не
   работала: «IL» уже вычищали миграцией 13.07 — и он вернулся импортом.

**SB в режиме ∞** больше не прячется: места считаются за ВИТРИННЫЙ сезон (как фильтр Season
best страницы пловца), а строка статов подписана «season bests · 2025/26», чтобы цифра не
читалась как «за всё время». Бейдж на строке при этом ставится по `ResultId`: если карьерное
лучшее показано из другого сезона, бейджа нет — иначе он обещал бы первое место времени,
которого в том сезоне не показывали.

## 8-кватер. Рекорды тремя классами (02.09.2026, хендофф `design_handoff_h2h_addrecords`)

Одна цифра «115 рекордов» вводила в заблуждение: справочник ведёт рекорд ОТДЕЛЬНО на каждой
возрастной ступени, и подросток, улучшавший результат с 14 до 18, держит по строке в каждой.
У Горбенко (62115) это 115 строк на 32 дисциплины — против «5» у взрослого рекордсмена,
хотя из его пяти четыре национальные.

Поэтому классы больше не складываются:

| Класс | Бейдж | Цвет |
|---|---|---|
| национальный (`open`) | `REC` | gold |
| возрастная ступень (`age`) | `REC·AGE` | silver |
| мастерская полоса (`masters`) | `REC·M` | silver |

- API отдаёт `records: { national, age, masters }` на сторону и `record: { kind, scope }`
  у каждого времени вместо булева `holdsRecord`;
- на одном времени бейдж ОДИН — старший класс (national > age > masters), перебор ступеней
  идёт по старшинству; SB и рекорд вместе тоже не показываются — рекорд важнее;
- бейдж вынесен в общий `UI_RecordBadge` (`components/mix/record-badge/`): те же три класса
  нужны на стене рекордов, в результатах и на `/season-best`;
- счётчики шапки считаются по СПРАВОЧНИКУ (что пловец держит), а не по бейджам таблицы:
  рекордный заплыв может быть поставлен до периода импорта;
- в узком контейнере три счётчика встают столбиком — в строку они не помещались и
  переносились вразнобой.

Живая проверка: 7424 → `0 REC · 0 REC·AGE · 15 REC·M`, 62098 → `4 REC · 1 REC·AGE · 0 REC·M`
(суммы совпадают с прежними 15 и 5).

### Остальные экраны переведены на тот же бейдж (02.09.2026)

Хендофф требует один компонент везде, и это сделано:

| Экран | Было | Стало |
|---|---|---|
| таблица результатов, имя | «👑 RECORD» | `REC` / `REC·AGE` / `REC·M` — держатель дистанции |

⚠ **Цвета бейджа пришлось сделать парными по теме.** Значения хендоффа — dark-палитра, а

те же оттенки на два шага темнее (`#b17d11` золото, `#64748b` серебро), переключатель —
`data-mode` на `<html>`, общий для всех страниц. Медальные кружки остаются фиксированными:
медаль — физический объект, а бейдж это текст.

**Стена рекордов клуба переведена следом** (02.09.2026): цветная подпись ступени («ISR
record» цветом класса) заменена бейджем плюс областью («NR · ISR»). Своя шкала цветов там
жила ТОЛЬКО на этом экране и спорила с продуктовым правилом — возрастной рекорд красился
cyan, а cyan значит «быстрее/лидер».

**Сокращения у старших классов свои** (решение Влада): национальный — `NR`, мировой — `WR`;
общее «REC» осталось малым рекордам (`REC·AGE`, `REC·M`), которые без уточнения путались с

## 8-квинт. Ссылка «открыть заплыв в протоколе» (02.09.2026)

Ряд H2H (и строка заплыва, и строка соревнования на странице пловца) вёл в **пустую
таблицу**: `/results?competitionId=1559&tab=swims&swimmerId=62115` открывал протокол, где
0 строк и надпись «No results match the current filters».

Причин было две, и обе — старые:

1. **`?swimmerId=` (и `?resultId=`) никто не читал.** Три места собирали адрес строкой,
   параметр доезжал до URL и умирал там — на клиенте не было ни поля фильтра, ни разбора.
   При этом сервер `GET /api/results` умеет `swimmerId` с самого начала.
2. **Дефолтный срез Swims — `freestyle · 50m` + `Position Top 10`.** Пришедшего на 100
   брассом он срезал полностью. Внутренняя навигация (`handleOpenSwim` из Overview/Records)
   про это знала и ставила пресет фильтров, а внешняя ссылка — нет.

Починено так:

- `FilterSelected.swimmer_id` — новый фильтр «заплывы одного пловца». От `swimmer_scope`
  отличается тем, что пловец задан явно, поэтому работает **и гостю**. Матчинг —
  `HelperSwimmer.resultBelongsToSwimmer` (эстафеты по составу ног), в paged-режиме уходит
  на сервер параметром `swimmerId`.
- `results-main-project` читает `?swimmerId=` один раз на маунт: ставит фильтр, снимает
  дефолты (стиль, дистанция, позиция, возраст, пол, клуб, день) и **включает `show_prelims`** —
  диплинк ведут и на предварительный заплыв.
- Срез виден: чип «🏊 <имя> ✕» над таблицей (тот же паттерн, что у скоупа `?filter=`),
  и «Reset Filters» его снимает — иначе кнопка врала бы.
- Адрес собирается **одним генератором** `routes.competitionSwims(competitionId,
  { swimmerId, resultId })` вместо трёх строк вручную; `resultId` пишется как `?swim=` —
  тот ключ, который `results-table` уже читает для скролла и подсветки. Старая форма
  `/results?competitionId=…` продолжает работать (идентичность берётся из `parseRoute`).

Проверено вживую на 62115 (Горбенко, comp 1559): чип с именем, обе строки — финал 01:07.44
и `[PRELIM]` 01:11.09, подсветка строки по `?swim=`.

**Дополнение 03.09.2026 — многодневка.** Строка старта в Season вела на ОДИН ДЕНЬ: в базе
многодневное соревнование это несколько `Competitions` под общим `CompetitionEvent`, а
`meet.competitionId` — первый день. Строка при этом считает заплывы по всему турниру, и
клик по «12 swims» открывал два (Горбенко, чемпионат 23/05–20/07). Теперь `competitionSwims`
принимает `eventId` и при его наличии ведёт на `/results?eventId=`, то есть на весь старт.
Исключение — ссылка на КОНКРЕТНЫЙ заплыв (`resultId`): он лежит в конкретном дне, и адрес
дня точнее.

⚠ Полоса над таблицей (`results-filtered-info`) — это НЕ фильтры: она показывает значение
колонки, когда во всей выборке оно одно (колонка тогда скрывается, а значение уезжает в
полосу). На двух строках одного дня там стояли «EVENT 200 медли · DATE 25 MAY · AGE 23», и
это читалось как выставленный фильтр, хотя в сайдбаре стояло «All».

## 8-секст. Бейдж SB в строках протокола (02.09.2026)

Вопрос Влада: «есть таб рекордов, и протокол сравнивает и пишет, что новый рекорд — почему
нельзя так же с season best?». Можно; мешала только форма API.

**Почему рекорд работал, а SB нет.** Справочник рекордов грузится ЦЕЛИКОМ один раз
(`RecordsHelper.warmUp()` → `GET /api/records`) и лежит в памяти: любая из сотен строк
сверяется с ним локально, чистой функцией. У season best эталон той же формы — «пол ×
возраст в сезоне × стиль × дистанция × бассейн → лучшее время», — но `GET /api/season-best`
отдавал ОДНУ дисциплину за запрос (его писали под панель над таблицей, ей больше и не надо).
Для протокола это означало бы десятки запросов.

**Что сделано.** Второй режим у той же витрины, а не новый механизм:

- `GET /api/season-best/table?season=` — вся сезонная таблица одним ответом
  (`GetSeasonBestTableAsync`). Группировку считает СУБД: 57 тыс. строк сезона 2025/26
  сворачиваются в ~1,1 тыс. ступеней (≈119 КБ), кэш и ETag те же, что у остальных витрин.
  Кроме времени ступень несёт `peers` — число РАЗНЫХ пловцов на ней.
- `SeasonBestTable` на клиенте (`utils/helpers/season-best-table.ts`) — устройство
  `RecordsHelper`: загрузка по сезону, single-flight, синхронная проверка строки. Хук
  `useSeasonBestTable(season)` только прогревает и перерисовывает.
- `UI_SeasonBestBadge` в строке таблицы результатов (все три варианта — mobile/desktop/2xl),
  рядом с бейджем рекорда: одна строка законно носит и «HOLDER·REC·AGE», и «SB».

**Три развилки, которые пришлось решить (они же — места будущих багов):**

1. **Ось возраста.** У рекордов календарная (`recordStepAge`, настройка `RecordAgeAxis`), у SB
   сезонная (`ageInSeason`). Числа разные; перепутать — показать бейдж не тому.
2. **Порог сверстников.** «Первый среди одного» — не достижение: `peers >= 2`, тот же порог,
   что у страницы пловца (`MinPeersForSeasonBest`). Без него одно и то же время было бы SB
   в протоколе и не SB в карточке пловца.
3. **Состав выборки.** Сервер считает эталон без masters, открытой воды, эстафет,
   `TimeFail` и помеченных `SuspectReason`; клиент те же строки пропускает молча — иначе
   сравнивал бы их с эталоном, в который они не входили. Плюс сезон берётся у САМОЙ строки
   (в сборной выдаче нескольких соревнований чужой сезон бейджа не получает).

Свежесть: таблица меняется после каждого импорта, кэш суточный, инвалидация глобальная
(`InvalidateAllAsync`) — то есть после импорта витрина обновляется сама, как и остальные.

Проверено: таблица и панель одной дисциплины совпали ступень в ступень (57 из 57, 0
расхождений); comp 1581 (50м) — бейджи у 24.16 (м, 15 лет) и 26.62 (ж, 14 лет), ровно
эталонные времена; comp 1559 — SB у финала 01:07.44 Горбенко и НЕ у её же prelim 01:11.09.
Тестов на репозиторий добавлено 5 (совпадение с панелью, `peers` по разным пловцам,
раздельные бассейны, отбраковки, сезонная ось); прогон 1611/1611.

## 8-септ. Ссылка на заплыв и класс рекорда в протоколе (02.09.2026)

Два бага одной проверки Влада на паре 7424/62115 (Гостомельская / Горбенко).

**1. Ряд H2H вёл клик не к тому пловцу.** Кликабельной была вся полоса бассейна:
`UI_H2HPoolRow` получал ОДИН `href`, и в нём стояло «у общей пары берём левого». Клик по
правому времени открывал протокол левого пловца. Ссылка переехала на уровень ячейки
(`H2HPoolSide.href`, `<a>` внутри `UI_H2HTimeCell`): у каждого времени она своя, и
кликабельно само время, а не пустая полоса между ними. Строка бассейна ссылок больше не
несёт — иначе получились бы вложенные `<a>`.

**2. Национальный рекорд в протоколе не помечался вовсе.** Тот же баг, что чинили в §8-тер
на странице пловца, но на клиенте: `HelperNormative.findRecord` спрашивал ОДНУ ступень —
возрастную (`age/{возраст}`) либо мастерскую полосу. Взрослые рекорды живут в категории
`open`, поэтому держатель национального рекорда выглядел в протоколе обычным первым
номером: у 00:56.73 Горбенко (100 спина 25м, ISR open, 26/12/2025) не было ни «HOLDER», ни
«★».

Починено зеркалом серверного `RecordStepsOf` — `findRecordSteps`: ступени перебираются от
СТАРШЕГО класса к младшему (national > age > masters), `open` берётся только для взрослого
заплыва (`isMasters || возраст > 18`, константа `TOP_CHILD_STEP_AGE` — зеркало серверной
`TopChildStepAge`; без отсечки девятилетнюю сверяли бы со взрослым рекордом страны). Класс
теперь приходит из поиска (`recordMarkForHolder` / `recordMarkForTime`), а не из догадки
«мастерский источник → masters, иначе age», и вместе с ним — ступень (`scope`), которая
уходит в подсказку бейджа.

Проверено: comp 1626 — у Горбенко «HOLDER · NR» у имени и «★ NR» у времени 00:56.73;
comp 64 (мастерс) — «HOLDER · REC·M» и «★ REC·M» с подсказкой «45-49», как и было;
comp 1581 (дети) — только «HOLDER · REC·AGE — 14», ложных NR нет.

## 8-окт. Имена сторон в адресе: `h2h_a` / `h2h_b` (03.09.2026)

Одна и та же сущность — «второй участник сравнения» — звалась в трёх местах по-разному:
`?b=` на странице `/h2h`, `?rival=` в табе страницы пловца, `rivalId` в запросе к API.
Переименование Rivals → H2H тогда дошло только до `tab=`, параметр остался прежним.

Теперь имя одно на всё h2h — **`h2h_a` / `h2h_b`** (решение Влада):

- страница: `/h2h?h2h_a=7424&h2h_b=62115&season=all`;
- таб: `/swimmers/7424?tab=h2h&h2h_b=62115` — левая сторона там хозяин профиля, поэтому в
  адресе только правая;
- API: `GET /api/swimmers/{id}/compare?h2h_b=62115` — левый в пути, `h2h_a` не нужен.

Имена живут в **одном месте** — `H2H_PARAM` в `routes.ts`; и генератор, и `parseH2HQuery`,
и `writeQuery` обеих страниц, и запрос хука берут их оттуда, а не пишут строкой. Префикс не
украшение: `a`/`b` в общем адресном пространстве витрины ничего не значат, а рядом с
`?tab=h2h&season=` читаются как случайные буквы.

**Прежние имена принимаются на чтение** (`a`/`b`, `rival`, `rivalId`): ссылки уже разосланы,
а редиректов у витрины нет — то же решение, что с легаси `?group=`/`?swimmer=`. При первой
же правке адреса легаси-ключи вычищаются, чтобы адрес не нёс обе пары имён.

Проверено: оба формата открывают экран (14 полос у пары 7424/62115), API отвечает 200 и на
`h2h_b`, и на `rivalId`, 400 — без соперника и на «сам с собой»; выбор соперника в табе
пишет `?tab=h2h&h2h_b=`, ссылка «Full page →» — `?h2h_a=&h2h_b=`, сброс соперника чистит и
легаси-ключ.


## 8-нон. Крестик у левой карточки: два бага в одном месте (03.09.2026)

Жалоба Влада: «не могу ✕ убрать слева пловца». Багов оказалось два, и каждый по отдельности
хоронил кнопку.

**1. Аватар съедал клик.** `.h2h-mini__clear` — `position: absolute` без `z-index`, а
портрет (`.h2h-mini__avatar`) — `position: relative` и стоит в разметке ПОЗЖЕ кнопки. При
равном стеке (обе `auto`) выигрывает тот, кто ниже в дереве, поэтому фото ложилось поверх
крестика: `elementFromPoint` в центре ✕ возвращал аватар, клик всплывал до карточки-ссылки
и открывал ПРОФИЛЬ вместо сброса стороны. У левой карточки крестик стоит во внутреннем
углу — ровно под фото, поэтому там он не работал вообще, а справа (фото у внешнего края)
срабатывал. Лечится одной строкой `z-index: 2`; та же строка добавлена сердечку —
в узком контейнере оно попадает под фото по той же причине.

**2. «ME» возвращался сразу после сброса.** Эффект автоподстановки смотрел на `aId`:
`clear('a')` обнулял слот, эффект видел «пусто и адрес молчит» и ставил primary favorite
обратно — на глаз кнопка выглядела мёртвой даже там, где клик доходил. Поэтому
`H2H_DEFAULT_LEFT` стал `empty` (решение Влада), а сама подстановка — одноразовой:
`autoLeftDoneRef` взводится и при подстановке, и при первом действии человека, чтобы
приехавший позже primary favorite не влез в слот задним числом.

**Размер кнопки.** Символ 12px без подложки давал цель ~10×12 px — на телефоне в неё не
попасть. Стало 28px кругом на десктопе (подложка на hover) и **34px в узком контейнере**
(подложка постоянная: на тач-экране наведения нет, и невидимая цель непонятна). Под кнопки
в узком контейнере отдана верхняя полоса карточки (`padding-top: 42px`): в столбике первым
идёт то текст, то фото, и крупный крестик ложился на имя. Двигать саму кнопку нельзя —
угол это единственная позиция, одинаковая для обеих сторон.

Проверено на 375px и на десктопе: `elementFromPoint` в центре обеих кнопок возвращает саму
кнопку, клик по левой чистит слот и адрес (`?h2h_a=&h2h_b=` → `?h2h_b=`), профиль при этом
не открывается.

**Активный слот подсвечен** (там же, по просьбе Влада). Пикер на странице ОДИН на две
стороны, и то, какую он заполнит, говорила только подпись «choosing the LEFT swimmer» под
слотами — связь приходилось вычитывать из текста. Теперь слот несёт `active`: пустой
получает сплошную акцентную рамку с заливкой и свечением (пунктир у обоих слотов читался
одинаково), занятый — только рамку, потому что там это предупреждение «следующий выбор
заменит стоящего», а не приглашение. Плюс `aria-current`. Флаг живёт в слоте, как и
`onClear`, поэтому таб его просто не передаёт: там пикер всегда ищет соперника.

**Ширина страницы — общая лесенка** (03.09.2026, решение Влада): рама перешла на
`PAGE_CONTAINER` + `content-box-xs` (780px) вместо локального `max-w-[1180px]`, как у ленты
стартового протокола. ⚠ Побочный эффект осознан: 780 это РОВНО порог `@container h2h
(max-width: 780px)`, поэтому на десктопе экран теперь всегда в компактной раскладке —
карточки столбиком, счёт 44px, дата у времени скрыта. Нужен полный макет в той же колонке —
это одна правка порога на `779.98px` (замеры показывали, что полный вариант читается
до 795px).

**Две ступени вместо одной** (03.09.2026): раскладка (столбик, крупный счёт, скрытая дата)
включается на 780, а размеры ПОРТРЕТОВ и иконок стилей — только с 560. Причина в том, что
после перехода на `content-box-xs` в первую ступень попали два разных случая: телефон
(контейнер ~343 при окне 375) и десктопная колонка ровно 780. Картинки ужимались заодно со
всем прочим и на десктопе выглядели марками (замечено Владом). Теперь в колонке 780 портрет
72px и иконка 132×90, на телефоне — 52px и 96×66, как было.

**Счёт в узком варианте удвоен** (22px → 44px, просьба Влада): он был МЕНЬШЕ, чем в
широком макете (30px), хотя «3–2» — главная цифра экрана и на телефоне читается первой.
Центральная колонка расширена 92px → 104px, иначе счёт переносился. Проверено: на 375px
и на 320px переполнения нет, счёт в одну строку, имена сторон не обрезались.

**Порядок фото и подписей в столбике выровнен.** Разметка карточек зеркальная (у левой
текст идёт первым, чтобы фото смотрело в центр шапки) — в ряд это симметрия, а в узком
контейнере превращалось в разнобой: слева фото под подписями, справа над ними. Лечится
`order: -1` у левого аватара внутри `@container`, а не правкой разметки: в широком макете
зеркальность нужна.
