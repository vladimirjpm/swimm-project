# План: один каркас страницы сущности (клуб · пловец · группа)

Каркас `DeepEntityPage` — общий скелет «шапка → табы-папка → панель карточек», на котором
живут страницы клуба, пловца и группы (этапы A–D сделаны 09.09.2026, итог — §11). **База — то, что уже работает у клуба**; группа
получает свой вариант шапки и свой набор табов, не форкая ни одной общей детали.

Дизайн-источник группы: `!design_handoff/design_handoff_group_page_v2/` (вариант 2a) —
он же прямо требует «одна реализация, три потребителя». Разбор различий макета и клубной
страницы — в §2.

> Статус фаз — в [`../ROADMAP.md`](../ROADMAP.md). Этот план раскрывает одну задачу.

| Объём первой итерации | **Только каркас + клуб.** Клуб — живая страница; сперва доказать шов на ней, ничего не сломав. Группа — следующим заходом |
| Шапка группы | **Текущие данные + фото.** Ни расписания, ни посещаемости, ни RSVP пока не делаем — это слоты, включим позже. Фото берём из существующего `cover_image_url` |

| Подложка `.deep-folder` | **Убрать** (хендофф). Тёмной полосы под рядом плиток больше нет; изменение касается клуба и пловца тоже. Подробности — §3.7 |
| Страница пловца | **Подключаем сразу после клуба**, до группы. Три потребителя проверяют шов лучше двух — этап B |
| Тесты React-компонентов | **Пока не заводим.** Обвязки в проекте нет, ради каркаса её не поднимаем; проверяем `tsc`, сборкой и прокликиванием |
| Управление сущностью | **Только в табе `Admin` и только управляющим.** Кнопки управления не рассыпаются по карточкам — §3.8 |

Из решения о наборе табов следует правило, которое держит всю затею: **вариант отличается
набором блоков, а не устройством страницы**. Как только у одного варианта появляется таб,
которого принципиально не может быть у другого, — это повод спросить, а не молча развести
реализации.

## 3. Каркас

### 3.1 Что он делает и чего НЕ делает

**Делает:** обёртку темы, топбар, ширину `main`, тумблер режима, лесенку состояний, слот
шапки, слот «между шапкой и табами», «папку» с табами и панель активного таба, синхронизацию
`?tab=`, раскладку карточек в панели.

**Не делает:** не грузит данные, не знает про сезон, клуб, группу и права, не нормализует DTO,
не решает, какая карточка что значит.

### 3.2 Пропы

```ts
// components/deep/entity-page-types.ts
export type EntityPageStatus = 'loading' | 'ready' | 'notfound' | 'error';

export interface EntityTabSpec {
  id: string;
  icon: string;             // глиф, декоративный (aria-hidden внутри DeepTabs)
  label: string;
  shortLabel?: string;      // мобайл, колонка ~70px
  sub?: string;             // подпись-сводка, ЖИВЫЕ данные (правило хендоффа: не хардкод)
  /** Таб виден, но заперт: рисуем плитку, в панель кладём lockNotice вместо cards. */
  locked?: boolean;
  lockNotice?: React.ReactNode;
  /**
   * Карточки панели. Функция, а не JSX: тело считается только у активного таба.
   * `nav` (добавлен в этапе D) нужен дайджесту: карточка-витрина уводит на «свой» таб
   * через `nav.go(id)` — он же поднимает страницу к верху «папки».
   */
  cards: (nav: EntityTabNav) => EntityCardSpec[];
}

export interface EntityCardSpec {
  id: string;
  /** 'half' — половина ширины от 960px; 'full' (по умолчанию) — во всю. */
  span?: 'half' | 'full';
  render: () => React.ReactNode;
}

export interface DeepEntityPageProps {
  topbarActive: TopbarActivePage;
  status: EntityPageStatus;
  messages?: { loading?: string; notfound?: string; error?: string };
  hero: React.ReactNode;                 // СЛОТ: вариант шапки
  beforeTabs?: React.ReactNode;          // СЛОТ: карусель сезонов, upcoming starts, что угодно
  tabsAriaLabel: string;
  tabs: EntityTabSpec[];                 // порядок = порядок массива
  defaultTabId?: string;                 // по умолчанию tabs[0].id
  onTabChange?: (id: string) => void;    // если странице нужно знать (ленивая загрузка)
}
```

### 3.3 Табы — данные, а не разметка

Набор собирается массивом с отсевом, поэтому «поменять порядок» = переставить элементы,
«убрать таб» = не положить его:

```ts
const tabs = [
  tabSeason,
  tabRecords,
  tabSwimmers,
  tabMedia,
  isGroup && tabTrainings,
  canManage && tabAdmin,
].filter(Boolean) as EntityTabSpec[];
```

`--deep-tabs-count` считается из `tabs.length` внутри `DeepTabs` — при отсеве сходится само.

Право видеть ≠ право читать: таб, который пользователю не положен по членству, **показываем
с замком** (`locked` + `lockNotice`), а не прячем — так требует хендофф. Прячем совсем только
то, чего у сущности не существует в принципе (у виртуального «Моё избранное» нет тренировок).

Если `?tab=` указывает на таб, которого в наборе нет, — молча падаем на первый.

### 3.4 Карточки — тоже данные

Панель рисует **один** grid:

```tsx
<div className="grid grid-cols-1 items-start gap-4 min-[960px]:grid-cols-2">
  {cards.map(c => (
    <div key={c.id} className={c.span === 'half' ? '' : 'min-[960px]:col-span-2'}>
      {c.render()}
    </div>
  ))}
</div>
```

Соседние `half` встают парой сами; `full` разрывает ряд. Это ровно то, что у клуба сейчас
написано руками парами `grid-cols-1 min-[960px]:grid-cols-2` — включая выстраданный порог
**960px, а не lg (1024)**: строке грида нужно ~525px, таблице зачёта ~380px.

`items-start` обязателен — иначе половинки растягиваются до высоты соседа.

Итог для Влада: **порядок карточек = порядок массива, включение = `if`**:

```ts
cards: () => [
  { id: 'record-wall', span: 'half', render: () => <ClubRecordWall clubId={clubId} /> },
  { id: 'season-best', span: 'half', render: () => <ClubRecords clubId={clubId} /> },
  { id: 'best-season', render: () => <ClubSoonCard … /> },
]
```

### 3.5 Шапка — вариант, а не конфиг

Шапок будет много и они непохожи, поэтому каркас в них **не заглядывает**: `hero` это
`ReactNode`. Чтобы варианты не разъезжались, общими делаем оболочку и кирпичики:

- `deep/hero-band.tsx` → `DeepHeroBand` — полоса `--deep-hero-grad`, рамка `--deep-card-border`,
  паддинги, **опциональная правая колонка 380px** (`aside`). Нет `aside` — левая колонка на всю
  ширину (то есть клубная шапка — та же полоса без правой колонки).
- `deep/kpi.tsx` → `DeepKpi`, `DeepBadge` — вынуть из `club-hero.tsx`, где они приватные.
  `DeepKpi` умеет `gold`, `hint`, `title` (нативный тултип оговорки про витринный сезон).

Дальше каждый вариант — свой компонент: `ClubHero` (лого 96, имя HE+EN, бейджи, 5 KPI) и
`GroupHero` (аватар, имя, мета, чипы ссылок, Join/Leave, KPI, фото справа). Третий и
четвёртый варианты просто добавятся рядом; общий у них — `DeepHeroBand` и кирпичики.

### 3.6 Состояния

`status` считает **страница**, не каркас, — потому что правило у клуба выстраданное:
плашка `Loading…` показывается **только когда данных нет вовсе**. При смене сезона данные
остаются на экране и обновляются на месте, иначе плашка вставляется над контентом и страница
прыгает вниз-вверх на каждый клик по фильтру.

```ts
const status = data
  ? 'ready'
  : loading ? 'loading'
  : error === 'not-found' ? 'notfound'
  : error ? 'error' : 'loading';
```

### 3.7 Снятие подложки «папки» (решение: убрать)

Меняется `deep-theme.css`, то есть **все три страницы разом** — клуб, пловец, группа.

1. `.deep-folder { background: var(--deep-tabs-bg) }` → `background: transparent`, скругление
   больше не нужно. Токен `--deep-tabs-bg` **не удалять**: на него завязан `--t-list-head`
   (строка 243) — семья `hp` красит им шапки списков.
2. Заодно снять внутренние отступы корпуса: `.deep-tabs { padding: 12px 14px 0 }` и
   `.deep-tabs-panel { margin: 0 14px 14px }`. Они были нужны, чтобы содержимое сидело
   внутри корпуса; без корпуса панель окажется **на 28px уже шапки** и это сразу видно.
   Мобильные значения (`padding: 8px 8px 0`, `margin: 8px`) — туда же.
3. Стык активной плитки с панелью не трогать: `margin-bottom:-1px` + `z-index:1` — единственное,
   что склеивает язычок с панелью.
4. **Мобайл: язычок возвращается.** Сейчас в `@media (max-width:639px)` он снят намеренно —
   комментарий «в мобайле „папки“ нет: плитки-колонки узкие, язычок на 70px читается как
   артефакт», активную отбивает подчёркивание. Хендофф просит обратное, и это **сознательный
   разворот прежнего решения**: активная плитка получает `--deep-panel-bg`, рамку
   `--deep-panel-border`, без нижней рамки, `margin-bottom:-1px`. Смотреть на настоящем
   390px — если язычок и правда читается артефактом, разворот отменяем и остаёмся на
   подчёркивании (подложка при этом всё равно снята).

### 3.8 Управление — в табе `Admin`

Правило на все варианты: **любое управление сущностью живёт в табе `Admin`** и видно только
управляющим. Кнопки и панели управления не рассыпаются по карточкам и по шапке.

Гейт уже есть и переиспользуется — `manages = isAdmin || myGroups.some(g => g.id === group.id)`
(админ сайта **или** управляющий этой группой). У группы в таб уезжает `PublicationsInbox`
(заявки на публикацию); дальше туда же — правка ростера, ссылок и обложки, когда дойдут руки.
У клуба таба `Admin` пока нет: клубного управления на витрине не существует — появится
вместе с ним, тем же табом и тем же правилом.

Не путать с `locked`: `locked` — «таб есть, но тебе не положено содержимое» (медиа участников,
тренировки). `Admin` тому, кто не управляет группой, не показывается **вовсе** — постороннему
незачем знать, что у группы есть инбокс.

### 3.9 Фото шапки и настройки отображения (решение 09.09.2026)

Отменяет прежнее «фото клуба не рисуем» (01.08.2026): **фото шапки есть у обоих вариантов.**

- Фото **рисуем всегда**, когда блок включён. Нет ссылки — рисуем **заглушку** (пунктирная
  рамка + иконка + подпись), а не схлопываем колонку. Так правая колонка шапки не «прыгает»
  между сущностями, и админу сразу видно, куда класть картинку.
- В табе `Admin` — переключатель **«Показывать фото шапки»**. Он и есть ответ на пустую
  заглушку: не хочешь пустоты — выключил, правая колонка схлопнулась, левая на всю ширину.
- Право править — то же, что у самого таба (§3.8): у группы `manages` (владелец/тренер группы
  **или** админ сайта), у клуба — только админ сайта, владельцев у клуба не существует.
- Настройка **durable и привязана к сущности**. Глобальные настройки (`AdminSettingsService`)
  для этого не годятся: они живут в памяти процесса и сбрасываются при рестарте — ровно та
  причина, по которой в проекте уже заведена таблица `Sys_DebugOptions`.

Что для этого уже есть:

| | Группа | Клуб |
|---|---|---|
| URL картинки | **есть** — `HubGroups.CoverImageUrl`, правится и в `/Admin/HubGroups/Edit`, и самообслуживанием (`PUT /api/me/hub-groups/{id}`, поле `coverImageUrl` уже в `HubGroupInput`) | **нет ничего** |
| Настройки отображения | нет | нет |
| Право править | `manages` — гейт уже написан | только админ сайта |
| Публичное чтение | `HubGroups` в RO-гранте | `Clubs` в RO-гранте |

#### Хранилище — `DisplaySettings jsonb` на сущности (решение 09.09.2026)

`HubGroups.DisplaySettings` и `Clubs.DisplaySettings` — по JSON-колонке на таблицу, каталог
ключей с дефолтами и типами живёт **в коде** (как `DebugOptionKeys`), значения — в колонке.

Почему так: новые настройки добавляются без миграций; приходят одним запросом вместе с
сущностью (ни джойна, ни второго обращения); нового гранта не нужно — `HubGroups` и `Clubs`
уже читает `swimm_ro`, а любая `Sys_`-таблица потребовала бы второго исключения в
`02-grants.sql` после `Sys_RecordIssues`. Прецедент в проекте есть — `HubGroups.Links`
хранится тем же способом. Цена — значение нетипизировано, валидация на аксессоре.

#### Картинка — данные сущности, показ — настройка

| | Хранение картинки | Правится |
|---|---|---|
| Группа | `HubGroups.CoverImageUrl` — **уже есть**, ничего не мигрируем | `/Admin/HubGroups/Edit` и `PUT /api/me/hub-groups/{id}` |
| Клуб | `Clubs.CoverImageUrl` — **добавить** (nullable varchar(1000)) | `/Admin/Clubs/Edit` + таб `Admin` |

Колонка на `Clubs` безопасна: импорт клубы только **создаёт** (`new Club{…}` при промахе
поиска), существующие строки не переписывает — переимпорт картинку не сотрёт. И таблица уже
несёт прикладные поля (`IsPseudo`, `MergedIntoId`), так что это не первое отступление от
«чистого справочника федерации».

#### «Взять фото из медиа» — вторая форма того же указателя

Настройка `hero` держит не только выключатель, но и **откуда брать картинку**:

```jsonc
{ "hero": { "show": true, "mediaId": 123 } }   // взять из медиа-ленты сущности
{ "hero": { "show": true } }                    // взять CoverImageUrl
{ "hero": { "show": false } }                   // блок выключен, колонка схлопнута
```

Резолв на сервере: `mediaId` → URL строки медиа; нет — `CoverImageUrl`; нет — null.
Наружу в DTO уходит **одно поле** `hero_image_url` (+ `show_hero_image`), клиент про формы
не знает вовсе. Медиа удалили или ссылка битая — резолв даёт null и рисуется заглушка,
а не сломанная картинка.

Почему указатель в настройках, а не флаг `IsHero` на строке медиа (как звучало в вопросе):
уникальность «одна шапка на сущность» получается бесплатно (одно поле вместо partial unique
index), медиа-таблицы не трогаем совсем, и правило одинаково для любой будущей сущности.
Действие в UI при этом остаётся тем же — кнопка «Сделать фото шапки» в табе `Media`, просто
пишет она в настройки.

⚠ Для клуба форма `mediaId` пока **недоступна** — клубной медиа-ленты на API не существует
вовсе (поэтому таб Media у клуба и стоит заглушкой). Контракт от этого не меняется: появится
лента — форма включится без правки модели.

#### Порядок работ

Шов (обе формы в модели) закладываем сразу — доделать разбор JSON позже дороже, чем заложить
сейчас. Реализуем по частям: сперва `show` + `CoverImageUrl` + заглушка, затем «выбрать из
медиа» в табе группы.

### 3.10 Медиа: цель публикации — коллектив, а не группа

**Поправка модели (Влад, 09.09.2026).** Клуб и группа — не разные сущности, а **два вида
одного**: коллектив пловцов. Группа = неофициальный клуб, который может завести кто угодно и
в который могут входить пловцы из разных клубов. Отсюда: **логика медиа обязана работать
одинаково у клуба и у группы.** Предыдущее предложение («клуб показывает медиа своей
официальной группы») исходило из неверной посылки — клуб не спутник группы — и снято.

Раньше, чем строить: «медиа группы» — это **не альбом группы**. `Sys_HubGroupMedia` у группы
17 пуст (0 строк); всё, что видно на странице, — публикации пользователей
(`Sys_UserMediaPublications`: 9 `members` + 1 `public`, все `approved`). Значит «так же у
клуба» = дать клубу **публикации**, а не заводить ему галерею.

#### Три оси коллектива — и где у клуба дыры

| Ось | Группа | Клуб |
|---|---|---|
| Ростер пловцов | `HubGroupMembers` (вручную, пловцы из разных клубов) | `Swimmer.ClubId` — **есть**, справочник федерации |
| Аккаунты-участники | `Sys_HubGroupUserMembers` (active / pending) | **нет** |
| Управляющие | `OwnerUserId` + `Sys_HubGroupAdmins` | **нет** — только админ сайта |

⚠ `UserFavorite` умеет `TargetType='club'`, но **членством это не является**: правило
проекта — избранное и «Me» прав не дают. Выводить из него аудиторию `members` нельзя.

Ростер — ось, на которой всё держится, и она у клуба есть даром: «пловец в ростере группы»
и «пловец числится за клубом» — одно и то же правило доступа. Двух других осей нет, и
именно они ограничивают, что заработает сразу.

#### Схема: полиморфная цель

`Sys_UserMediaPublications` перестаёт указывать на группу и начинает указывать на коллектив.
Форма — как у `UserFavorite` в этом же проекте (прецедент): дискриминатор + пара nullable-FK,
а не голая пара `(Type, Id)` — так остаются настоящие внешние ключи и каскадное удаление.

```
TargetType   'group' | 'club'          (NOT NULL)
HubGroupId   int NULL  → HubGroups
ClubId       int NULL  → Clubs
CHECK: ровно одна из двух заполнена и совпадает с TargetType
```

Уникальность `(UserMediaId, HubGroupId)` становится `(UserMediaId, TargetType, TargetId)` —
одна публикация одного медиа в один коллектив.

Что меняется следом: `GetPublishTargetsAsync` отдаёт коллективы (тип + id + имя), а не
группы — к группам добавляется **клуб пловца этого медиа**; `publish-targets`, инбокс
модерации, чтение витрины и сброс кэша идут по цели, а не по `HubGroupId`.

Это касается границ доступа, поэтому по правилу проекта — работа деликатная: менять запросы
видимости и модерации осознанно, с тестами на каждый уровень.

#### Что заработает сразу, а что упирается в дыры

- **`public` у клуба — сразу.** Аудитория «все», членство не нужно, ростер есть.
  Модерация — админ сайта (таб `Admin` у клуба и так появляется в A8).
- **`members` у клуба — нет**, пока у клуба нет аккаунтов-участников. Уровень в селекте для
  клубной цели отключается с подписью, а не показывается неработающим.
- **Модерация тренером клуба — нет**, пока у клуба нет управляющих. Дальше это «claim your
  club»: заявка тренера + одобрение админа сайта, ровно тем же потоком, что уже работает
  для связи группы с клубом (`Sys_HubGroupClubRequests` → `/Admin/HubGroupClubRequests`).

Порядок: (1) полиморфная цель + `public` у клуба + таб `Media` клуба на реальных данных;
(2) управляющие клуба; (3) аккаунты-участники клуба → включается `members`.

Работа отдельная от каркаса и заслуживает своего плана; до шага (1) таб `Media` у клуба
остаётся заглушкой.

## 8. Что нельзя потерять при переезде клуба

Мелочи, выстраданные и объяснённые комментариями в коде — при рефакторинге теряются первыми:

1. `Loading…` только при `loading && !data` — иначе страница прыгает на каждом клике по сезону.
2. Смена сезона **сбрасывает** `standingCompetitionId`: раскрытый зачёт мог принадлежать другому сезону.
3. `SHOW_GROUP_TILES` выключен — карточку `ClubFilters` не рендерим **совсем**, чтобы не осталась пустая рамка.
4. Порог пары «грид + зачёт» — **960px**, не `lg`.
5. `?tab=`: первый таб — **без параметра**, `history.replaceState` (не `push`) — иначе «назад» ходит по табам.
6. `.deep-folder` и `.deep-tabs-panel` — один корпус: активная плитка срастается с панелью через `margin-bottom:-1px` и `z-index`. Между `DeepTabs` и панелью ничего вставлять нельзя.
7. Подписи табов — живые данные; там, где числа нет, стоит слово, а не выдуманная цифра.
8. Имена пловцов и клубов — иврит по умолчанию, английский только фоллбеком.

## 12. Медиа клубу: цель публикации стала коллективом (09.09.2026)

Шаг 1 из §3.10 сделан: клуб — такая же цель публикации, как группа. Тесты **1637/1637**
(шесть новых на клубную цель), сборки клиента и сервера чистые, миграция применена.

### Что изменилось в модели

`Sys_UserMediaPublications` адресует цель парой: `TargetType` (`group` | `club`) + ровно один
из `HubGroupId` / `ClubId`. Форму держит CHECK, уникальность «одна публикация на пару
(медиа, цель)» — **два ЧАСТИЧНЫХ** уникальных индекса, а не один общий: в Postgres NULL'ы в
уникальном индексе считаются различными, и общий индекс уникальность не удержал бы.
Существующие строки бэкфилнуты в `group` прямо в миграции — иначе CHECK упал бы при накатывании.

Наружу это ушло переименованием, а не дублированием: `hub_group_id`/`hub_group_name` стали
`target_type`/`target_id`/`target_name` во всех DTO и на клиенте (7 файлов). Двух источников
правды об одном и том же заводить нельзя.

### Правила клубной цели — и почему они другие

| | Группа | Клуб |
|---|---|---|
| Ростер | `HubGroupMembers`, ведёт человек | `Swimmer.ClubId` — **бесплатно**, из справочника федерации |
| Кто может подать | активный user-член / владелец / админ группы | владелец медиа: членства в клубе как аккаунта не существует |
| Уровень | `members` и `public` | **только `public`** — у `members` нет аудитории |
| Кто решает | владелец / админ группы / site admin | **только site admin** — управляющих у клуба нет до «claim your club» |
| Авто-approve | привилегированному | site admin'у |

Отсюда главное следствие, ради которого всё и делалось: **чтобы предложить видео в клуб,
не нужно заводить ни группу, ни ростер** — клуб появляется в селекте сам, если пловец
числится за ним в справочнике.

### Что сделано на клиенте

Цель ходит **ключом-строкой** `«group:17»` / `«club:438»` (`targetKey` / `parseTargetKey` в
`hooks/useUserMedia.ts`): у `<select>` значение всегда строка, а цель — пара, числом её не
выразить. Уровень `members` для клубной цели гасится и в интерфейсе, а не только на сервере.
Таб `Media` страницы клуба (`club-media.tsx`) вместо заглушки показывает ленту
`GET /api/clubs/{id}/media`.
