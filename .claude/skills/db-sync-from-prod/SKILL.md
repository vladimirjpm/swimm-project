# db-sync-from-prod — локальная копия с прода (Swimm)

После запуска прода **главная база — прод** (решение В17, `docs/plans/azure-deploy-plan.md`
§0-тер-бис, §0-четыре). Локальная — её копия для разработки. Скрипт подтягивает в локальную базу
бизнес-таблицы прода (`server/db/seed-tables.txt`, без персональных данных) и **сливает**, а не
заливает заново: локальные аккаунты, избранное, медиа, группы остаются; пропадает только то, что
держалось за удалённое на проде.

Прод только читается — ролью `swimm_sync`. В прод скрипт не пишет ничего.

## Когда

- Влад просит «обнови локальную базу с прода» / «синхронизируй».
- Локальный API пишет Warning «Локальная база отстаёт от прода…» или в админке жёлтая полоса.
- Перед работой с данными, которая должна стартовать с состояния прода (рискованный
  `--repull`, массовые склейки, чистки — их сначала гоняют на свежей локальной копии, потом
  повторяют в ProdAdmin).

## Шаги

### 1. Проверить, нужно ли
Отставание видно в логе локального API при старте (только если в gitignored-конфиге
разработки задана `ConnectionStrings:ProdVersionConnection`). Нет строки — предложи Владу один раз
запустить `server/db/set-prod-version-connection.ps1` (пароль `swimm_sync` вводит он сам).

### 2. Подготовить
- Docker с `swimm-postgres` запущен (`docker compose -f server/docker-compose.yml up -d`).
- **Ни один локальный API не должен держать Debug-сборку**: скрипт запускает `dotnet run --
  --migrate` и `--seed-personas --reset` (build-lock, см. корневой CLAUDE.md). Погаси свои
  процессы; чужие (порт, который ты не запускал) — спроси Влада.
- Прод-доступ — переменные `PGHOST`, `PGUSER=swimm_sync`, `PGDATABASE=swimm`,
  `PGSSLMODE=require`, `PGPASSWORD`. **Пароль у Влада** — не выдумывай и не ищи по файлам; пусть
  он запустит команду сам или даст переменные в своём терминале. Домашний IP должен быть в
  файрволе Flexible Server.

### 3. Подтвердить с Владом
Синхронизация удаляет локальные бизнес-строки, которых нет на проде (и локальное, что на них
держится). Перед запуском — одно предложение Владу, что произойдёт, и его «да». Затем `--yes`.

### 4. Запустить (Git Bash, из корня репо)
```bash
PGHOST=<сервер>.postgres.database.azure.com PGUSER=swimm_sync PGDATABASE=swimm PGSSLMODE=require \
  PGPASSWORD=... server/db/sync-from-prod.sh --yes
```
Флаги: `--skip-migrate` (миграции уже накатаны), `--skip-personas` (не пересоздавать utest-*),
`--keep-dump` (оставить дамп для разбора).

### 5. Прочитать вывод
- `Миграции прода и локальной базы расходятся` — схема не совпала, ничего не тронуто. Код новее
  прода → сначала `--migrate` на проде (ProdAdmin); старее → `git pull` в master.
- Строки `уходит: <таблица> — N`, `перевешено: …`, `локальное без родителя удалено: …` — что
  поменялось. Большие числа «уходит» — повод остановиться и показать Владу.
- `ERROR` в слиянии — транзакция откатилась целиком, локальная база как была.
- В конце — `Готово: локальная копия = прод vN` и счётчики таблиц.

Кэш запущенного локального API скрипт сбрасывает сам — общим сбросом через канал моста кэша.

## Footguns

- Источник = локальная база (`PGHOST=localhost`, та же БД) — скрипт откажет: «синхронизировать
  базу саму с собой» = удалить всё.
- Новая таблица в `seed-tables.txt` без миграции с триггером версии — упадёт `DataVersionPgTests`;
  гранты `swimm_sync` выдаёт `02-grants.sql` по триггеру, второго списка нет.
- Настройки (`Sys_AdminSettings`) и прочие `Sys_*` с персональными данными не синхронизируются —
  у локальной базы свои.
